# kanpan-api 运维手册

部署、备份与异地容灾见上一级 `README.md` 与本目录的 `OFFSITE.md`。这里只收日常要手动做的几件事。

## 忘了密码：重置成一次性密码

账号只有用户名 + 密码，没有邮箱，所以「忘记密码」由运维在服务器上重置：

```sh
ssh orderflow-vps
systemd-run --quiet --pipe --wait --collect -p DynamicUser=yes \
  -p EnvironmentFile=/etc/kanpan-api/service.env \
  /opt/kanpan-api/target/release/kanpan-api reset-password <用户名>
```

- 标准输出只有一行：新的一次性密码（14 位，不含 0/O/1/l/I 这类易混字符）。把它私下发给本人，让他登录后在「账号」里改掉。
- 同时会做两件事：吊销这个人**所有设备**上的会话（原因记作 `password_change`，和用户自己改密码同一类，旧设备下一次请求就回 401、回到登录页），并清掉该用户名的登录失败锁定。
- 用户名不存在或已停用时，退出码非 0，标准错误输出 `Error: reset-password failed: unknown_username`，库里什么都不改。
- 和 `kanpan-api.service` 同样的环境文件、同样的动态非特权用户：程序开头会拒绝超级用户或 BYPASSRLS 角色，和 `serve` 同一道闸。不用停服务，线上照常。2026-09-23 已在线上实跑过：`qa_export_cli*` 测试账号重置成功；不存在的用户名退出码 1、库里不变。

## 导出一个人的数据

用户自己在 app「账号」页点「导出我的数据」即可（`GET /v1/auth/me/export`，一小时最多十次，单份上限 20 MB，超过回 413 `export_too_large`）。导出内容：用户名与注册时间、同步的自选 / 画线 / 提醒 / 设置、复盘记录与事件、存下的相似案例、朋友名单、往来的画线分享。不含密码哈希、会话与推送令牌，也不含截图等二进制。

## 隐私政策与服务条款

`/privacy`、`/terms` 两张静态页，正文在 `src/legal.rs`，改文案 = 改那里再部署。Caddy 需要把这两个路径转发到 `127.0.0.1:8794`（和 `/v1/auth/*` 同一个上游）。

## 主力订单流：常驻跟踪（2026-09-25 分层版）

serve 进程里常驻跟踪各家挂单簿，按默认门槛判出逐单大单写进 `orderflow_orders`，手机从
`GET /v1/market/orderflow/history` 取。代码在 `src/orderflow_history.rs` 与 `src/orderflow_history/`，
设计与客户端那一半见 `docs/主力订单流-方案-2026-09-24.md`「服务端历史与回填」。

### 跟哪些币（`layers.rs`）

| 层 | 谁 | 多久算一次 | 上限 | 掉榜之后 |
| --- | --- | --- | --- | --- |
| 主币 | BTC ETH SOL | — | 3 | 一直跟 |
| 固定 | AI 产业链 67 只（一个不删，含 SNDK / MU / SKHYNIX / SKHY、INTC、ARM、NVDA）、加密股 MSTR COIN HOOD CRCL BMNR、指数 ETF QQQ SPY TQQQ SQQQ IWM、大宗 XAU XAG XPT XPD CL BZ NATGAS COPPER | 启动时与每 10 分钟对一次合约表 | 表长（85） | 一直跟 |
| 山寨 | 币安 U 本位 COIN 永续 24h 成交额前 40（去掉主币、固定、稳定币） | UTC 0 点与启动时 | 40 | 再跟 24 小时 |
| 热点 | ① 24h 涨跌幅绝对值前 8（成交额 ≥ 5000 万）② 4 小时持仓变化前 8 ③ 24h 成交额前 8 ④ 美股涨跌幅前 6，去重并集 | 每小时 | 30 | 再跟 24 小时 |
| 按需 | 手机打开过的（`/history` 被问到） | 有人要时 | 20 | 24 小时没人要就停 |

- 总数上限 220；满了只从按需与热点里踢最久没人要的，主币与固定永远不踢。按现在的层大小最多 3 + 85 + 40 + 30 + 20 = 178 只，220 是留的余量。
- 名单里币安没有的合约跳过，并在日志里点名一次（2026-09-25 本机实测 85 只全在，没有跳过的）。
- `/etc/kanpan-api/service.env` 里 `KANPAN_ORDERFLOW_LAYERS` 选层：`fixed` / `fixed,alts,hot` / `all` / `none`，缺省全开；主币与按需两层一直开。改完 `systemctl restart kanpan-api`。
- 热点只用币安文档里有的公开接口：`/fapi/v1/ticker/24hr`（不带 symbol，一小时一次，与山寨共用、5 分钟内复用）与 `/futures/data/openInterestHist`（成交额前 150，间隔 300 毫秒）。

### 限速：手机的行情转发永远优先

订单流的连接与 REST 全部自己开，不和 `market_relay` / 网关 stream hub 共用任何一条，额度只拿一小份（`hub.rs`、`snapshots.rs`）：

- **币安 WS**：流名写进 URL（组合流），连上后不发 SUBSCRIBE；一条最多 200 路流；所有币安连接共用一个节拍器，两次新建至少隔 1 秒、5 分钟内最多 60 条（IP 额度 300 的五分之一）；重连退避带 ±50% 抖动；每条连接活到 23 小时 + 0–30 分钟随机就先建一条一样的新连接再交接（簿不重拉快照、不断档）。U 本位深度用 `@depth@500ms`。
- **币安 REST 快照**：U 本位 / 币本位 / 现货三条通道，每条任意 60 秒最多 30 次、两次至少隔 1 秒（IP 权重的四分之一）；429 / 418 按 Retry-After 停（没给就 60 秒 / 5 分钟），打一条 warn；队里按 主币 → 按需 → 固定 → 山寨 → 热点 排先后。
- **OKX**：新建连接至少隔 400 毫秒（≤ 3 条/秒）；订退攒 1 秒成一批、一批最多 20 本（消息远小于 64 KB），每条连接一小时用到 400 次（上限 480）还要发就整条重连；一条连接 50 本。
- **Coinbase**：一本一条连接（level2 的序号按整条连接计，一条多本会互相搅乱断档判定），新建至少隔 250 毫秒。
- **库**：挂着的单每 15 秒刷一次，只写新出现的、名义 / 成交 / 门槛变了 1% 以上的、以及 60 秒没写过的（刷新 `seen_ms`，重启读回时 2 分钟没见的才算失联）；所有币合起来最多同时占 3 条库连接（池子一共 8 条）。

### 资源闸门（`resources.rs`）

进程每 15 秒读 `/proc/self/status` 与 `/proc/self/stat`。RSS > 2.5 GB 或最近一分钟 CPU > 300%（100% = 一个核）算「超」：闸门每分钟看一次，超的那一分钟起停止新增并卸掉热点，下一分钟还超再卸山寨，再下一分钟卸固定；连续 10 分钟不超再一层层加回来。主币、按需与行情转发一概不动。本机 macOS 没有 `/proc`，状态行显示 `RSS ?, CPU ?`，一律当没超。

### 非币门槛标定

T = round125(0.03 × D)，夹在 [5 万, 200 万]，D = 该币各本 U 本位永续簿中间价 ±1% 以内买卖两侧美元之和。

- 簿全部拿到首个快照就标；有簿还没连上（币安新簿攒 5–15 秒成批开连接）或快照还在排队，就接着等，最多 10 分钟；不再有簿在等之后 8 秒（或到 10 分钟），用已就绪的簿标，之后簿都齐了再补标一次。手机是订阅起 8 秒就标——手机只订一只，没有排队；服务端冷启动 U 本位快照要排 7 分钟左右，照搬 8 秒会让 OKX 那一本（流内快照、立刻就绪）单独定门槛。
- 每个 UTC 日重标一次。标定前不评估、不读回挂着的单（读回的单先存着，标完再读回），`/history` 的 `thresholds.usdtPerp` 为 `null`。
- 日志：`Orderflow history: SNDK usdtPerp threshold calibrated to 500000 (±1% depth … USD over 2/2 books)`。

### 看运行状况

serve 缺省 `RUST_LOG=warn`，下面几行是 info，要看就在 `service.env` 里把它设成 `RUST_LOG=warn,kanpan_api::orderflow_history=info`（上线脚本会设）：

- 每分钟 `Orderflow history: tracking N (majors …, on-demand …, fixed …, alts …, hot …), K connections, RSS …, CPU … over the last minute, shedding …`
- 每分钟 `connections per minute: binance-um-depth a/b conns … books … streams … frames; …`（各种连接的条数、簿数、流数、帧数、丢帧数）
- 快照队列每分钟一行（各通道本分钟发出、排队、最久等了多久）。

`journalctl -u kanpan-api | grep -c WARN` 正常应接近 0；`market_meta` 的 `answered with another company's page` 是行情元数据那一侧的旧告警，和订单流无关。

| | 只开固定层 3 分钟 | 全开 7 分钟（写库去重前） | 全开 4 分钟（写库去重后） |
| --- | --- | --- | --- |
| 跟踪 | 88 只（主币 3 + 固定 85） | 154（3 / 85 / 山寨 40 / 热点 26） | 153（3 / 85 / 40 / 25） |
| 订单流连接 | 9 | 53 | 51 |
| CPU（一个 M4 核） | 13.3 秒 / 182 秒 ≈ 7% | 80.8 秒 / 425 秒 ≈ 19% | 24.6 秒 / 242 秒 ≈ 10% |
| RSS | 30–46 MB | 67–157 MB | 44–93 MB |

### 假设（写代码时自己定的）

- 主币与按需不受 `KANPAN_ORDERFLOW_LAYERS` 控制、也不被闸门卸（改版前就是这样）；闸门「超」的时候连按需的新增也拒绝，已在跟的不动。
- 标定等待比手机长（见上）；标定前读回的挂着的单延后到标定之后再读回，避免拿 200 万的旧门槛评估。
- Coinbase 一本一条连接：它的序号按连接计，合用一条就没法按本判断断档。
- XAI 这类最小变动价很小的币，`/history` 里 `step` 显示成 `9.999999999999999e-06`，是既有的浮点写法，手机端按「≈ 本机步长」比对，不影响合并。
- `migrations/0024_orderflow_orders.sql` 的注释还写着「最多 30 天」：迁移文件改一个字校验和就变，`migrate` 会拒绝，所以不改；实际保留期以 `store.rs` 的 3 天为准。
