# kanpan-subagents-use-opus-high

**项目约定**：看盘项目里派子代理（Agent 工具）时，除非用户另有指定，一律用当前最新的 Opus（2026-09-23 为 5.5，不许落到 Opus 5 等旧版）并要求 high 挡位；派活前先用探针核实别名指向；绝不允许开 Fable 子线程

2026-09-17 我在看盘（Kanpan）项目里派了 5 个盘点子代理去清点 AICoin 逆向资源，用的是默认继承模型。
用户随即说：「以后子线程除非指定，否则一律开 opus 最新模型和 high 挡位」。

所以在这个项目里，任何通过 Agent 工具派出去的子代理——盘点、搜索、写代码、审查——默认都要
`model: "opus"`（最新 Opus），并在 prompt 里要求以 high 推理挡位工作（Agent 工具本身没有 effort
参数，能在 prompt 里说明的就说明）。只有用户明确说「这个用 sonnet / haiku 就行」时才降档。
原因是用户宁可多花 token 也要子代理的结论可靠，之前定过「原型定稿后用 Opus 5 子代理写、主窗口验收」，
这次把范围扩大到了所有子线程。

## 不准开 Fable 子线程

2026-09-19 主窗口跑在 Fable 5.1 上，我派了两个 Explore 子代理去摸代码事实。用户看到后立刻说：
「sub 应该开的不是 fable 吧，不准开 fable 子线程」。那两个子代理其实已经是 `model: "opus"`，
但这句话把规矩说得更死了：

- **每一次 Agent 调用都必须显式写 `model: "opus"`**，不能省略让它继承主窗口的模型——
  主窗口是 Fable 时，省略就等于开了 Fable 子线程，这是明令禁止的。
- 无论子代理类型（Explore / Plan / general-purpose / claude）、无论任务多小，都一样。
- 用户在意这一点是因为 Fable 子线程的开销与配额他不想花在子任务上；Opus high 就是子线程的天花板。

## 必须是「当前最新的」Opus，不能是旧版 Opus

2026-09-23 我派子代理接手 Codex 的活时，用户先插话「opus 要使用最新的 5.5，不要使用 5」，
随后把要求说成一般原则：「**我的要求是使用 opus 最新的模型，然后使用 high 挡位**，
避免后续的窗口开 sub 又使用 opus 5」。所以规矩不绑版本号——今天最新是 5.5，以后出了更新的
就用更新的；绝不能落到上一代 Opus 上。

为什么会落到旧版：Agent 工具的 model 只能填别名 `opus`，它解析成哪个版本取决于宿主 CLI 的版本。
2026-09-22 夜里 Remote Control 宿主被钉在旧版 CLI 上，那时的子代理提交署名还是「Claude Opus 5」；
换到 CLI 2.1.280 后实测 `opus` → `claude-opus-5-5`。所以每个窗口第一次派活前都要核实一次：

- 派一个不调工具的探针子代理（`model: "opus"`），让它原样照抄系统提示里自己的模型名与模型 ID。
- 报出来的若不是已知最新的 Opus（例如宿主被钉在旧版 CLI 上），**不要派活**，先解决宿主 CLI 版本
  或别名映射，再派。
- 推理挡位：Agent 工具没有 effort 参数，每个子代理的 prompt 开头都写「请以 high 推理挡位工作」；
  子代理自己再派子代理时也要显式 `model: "opus"`，这条要写进给它的 prompt。
- 子代理提交署名照实写它探针报出的模型名（2026-09-23 为 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`）。
