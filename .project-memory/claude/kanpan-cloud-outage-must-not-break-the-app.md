# kanpan-cloud-outage-must-not-break-the-app

**项目约定**：看盘的账号云端只是同步通道，不是可用性依赖——本地永远留一份带账号标识的完整缓存，服务器宕机照常能用；两份都在时谁新用谁，本地被清才从云端拉

2026-09-19 在讨论「把布局这件事抽成模块」时，用户给了云端与本地这一层的设计要求：

> 「而且云端这块一定要加处理，**假如服务器宕机不能导致不可用**，按理来说**本地也应该缓存一份**，
> 但是**要注意是不是同一个账号**，如果被清理了代码可以**从云端拉配置**，这里面的逻辑要处理好。
> **如果完整哪个快用哪个**。」

所以在看盘里，账号云端的定位是**同步通道，不是可用性依赖**：

- **服务器宕机、断网、登录失败，app 必须照常可用**，并且用的是这个人自己的配置，不是出厂默认值。
  任何「等云端回来才知道该显示什么」的设计都是错的。
- **本地永远留一份完整缓存**，不是只缓存皮肤和深浅那种「够第一帧用」的残片。判据是：
  把网线拔掉冷启动，用户看到的应该和在线时一模一样。
- **这份本地缓存必须带账号标识**。没有标识的本地缓存就是下一个「B 登进来看到 A 的东西」的
  bug 源——项目里已经为这类问题返工过很多次。读之前先确认它属于当前这个账号，不属于就当它不存在。
- **本地被清掉（换设备、重装、清数据）时从云端拉回来**。这是云端真正的职责：跨设备恢复，
  而不是每次启动都当权威。
- **两份都在且都完整时，谁快用谁**——本地那份是立刻就有的，所以正常路径上就用本地先渲染，
  云端回来再对账。对账的规矩要显式写死：谁新谁赢，而且**本地有还没推上去的改动时永远是本地赢**，
  不许被回拉的旧值盖掉。

更一般地：用户要的是**离线优先**。云端是让配置能跨设备跟着人走的手段，不是功能能不能用的前提。
这条和 kanpan-one-feature-one-module 里「登录与未登录不是两个功能」是配套的——正因为本地永远
有完整一份，登录与否才能真的不改变功能的行为。

## 每一次改动都要打标识，否则「改了等于没改」

同一轮里用户把取舍的机制也定死了：

> 「是的体验类当然是**本地优先**，然后**云端自动记录**，下一次使用**假如本地缓存的记录被破坏
> 或者不完整才同步**，但这里一定要注意**标识状态**，比如用户缩小 K 线，改变副图区域大小，
> 指标颜色等等其它体验类操作，那么这是**修改，需要记录一个标识**，避免**云端没同步，下次进来
> 对不上又覆盖回去，相当于没改**。」

所以体验类状态的读写规矩是：

- **正常路径永远读本地**，云端不参与启动时的取值。**只有本地那份缺失、损坏或不完整时**，
  才回落到云端拉一份回来。云端在这里是备份与跨设备恢复，不是每次启动的权威。
- **每一次用户改动都要在本地打一个标识**（脏标记 / 递增版本号 / 修改时间，实现形式不限），
  标明「这一份比云端新，而且还没推上去」。缩放、副图高度、指标颜色、任何体验类操作都算一次改动。
- **带着未同步标识的本地值，永远赢过云端回拉的值。** 推送成功之后才清掉标识。
  少了这个标识，就会出现用户最痛的那个现象：改完还没来得及同步就退出，下次进来云端那份旧的
  和本地对不上，直接把改动覆盖回去——**在用户眼里就是「我明明改了，等于没改」**。
- 写的时候是「先落本地并打标识，再异步推云端」，不是「等云端确认了才算数」。
  网络失败不影响这次改动成立。

## 体验类状态不许放在可被清掉的地方，标识要能说清「为什么没了」

同一轮里用户又补了一条，针对的是「标识到底用来干什么」：

> 「用来判断是**清空了缓存还是什么情况**，一般来说**这种缓存清空不应该出现在可清空范围内**。」

所以看盘的磁盘要分成三层，层与层之间的边界是「能不能被清掉」：

- **真身：跟着人走的体验类状态**（偏好、图表布局、自选与分类、画线、搜索历史）放在
  `Application Support` 一类**不会被系统回收、也不被 app 自己的「清缓存」按钮覆盖**的位置。
  它不是缓存，丢了就真的丢了。
- **哨兵与首帧镜像**放 `UserDefaults`（Library/Preferences）：同样不会被系统腾空间清掉，
  只有卸载 app 才消失。它比真身更「顽固」，所以适合用来记「我来过」。
- **行情缓存**（K 线快照、品种表、报价、开盘价、OI）才放 `Library/Caches`，
  那里系统缺空间可以随时清，清了只是慢一点，不影响正确性。

**光把目录放对还不够，因为「本地这份读不到」有好几种原因，处理方式并不一样。** 标识要能分辨：

1. **首次**——什么痕迹都没有：正常地从云端拉一份回来。
2. **属主不符**——文件在，但记的账号 id 不是当前这个人：当它不存在，绝不能拿来用。
3. **损坏 / 不完整**——解不开或缺字段：回落云端，但**不能顺手清掉脏标记**，
   否则会把还没推上去的改动一起抹掉。
4. **被清空**——真身没了，但哨兵还在（装机 id + 最后写盘时间 + 最后同步到的版本）：
   这一种必须单独认出来，因为它意味着本地**曾经有过比云端新的改动**。
   直接拉云端就是用户最痛的那个现象——「我明明改了，等于没改」。

判断哪一类的依据只能是这个**放在更顽固那一层的哨兵**，不能靠「文件在不在」猜。
反过来说，只要哨兵和真身在同一层，它就会跟真身一起消失，也就分辨不出 1 和 4。

## 「清空」这个动作本身也要划范围：只有可再取的东西才允许被清

用户紧接着把这条收得更死：

> 「体验类**一律不能主动清空缓存，除非删除 app**，必要的数据**不能主动给清空操作**，
> 只有**非必要不影响项目运行的**才可以清空。」

所以看盘里任何「清空 / 重置 / 清缓存」类的动作，无论是系统做的、app 的按钮做的、
还是代码里某条清理逻辑做的，都要先过一道判据：**这份东西没了以后，还能原样拿回来吗？**

- **能重新取回来的**（K 线快照、品种表、报价、开盘价、OI、板块历史）才允许被清。
  清了只是下次慢一点，正确性不受影响。这类东西放 `Library/Caches`，也归「清缓存」按钮管。
- **拿不回来的**（偏好、图表布局、自选与分类、画线、搜索历史，以及任何用户亲手摆出来的状态）
  **不许提供任何主动清空的入口**——不给按钮、不给「重置」、代码里也不许有顺手 `removeItem` 掉
  整个账号目录的清理逻辑。它唯一合法的消失方式是用户卸载 app。
- 推论：**不要为了省事把两类东西放在同一棵目录下再整棵删**。共用目录会让「清一个」变成「清两个」。

现状核实（2026-09-19）：设置里的「清缓存」清的是 `Paths` 指的 series / snapshot /
exchangeInfo / oi 四处，全是可再取的行情数据，不碰账号目录，符合这条规矩；
`MarketCacheTests` 里已经有一条「画线不归清缓存管」的断言守着。
