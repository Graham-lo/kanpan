# kanpan-reproduce-before-naming-the-root-cause

**项目约定**：看盘里报了 bug 之后，先在模拟器/真机上真的复现出来证明机制，再谈根因和修复，不能拿推理出来的假设当结论

2026-09-18 用户报了一个「锁屏解锁或从后台切回来，K 线被挤到上半屏、底下空出一大块，
必须把 app 划掉重开才好」的 bug。我先做的是读代码 + 量他发来的照片，得出一个「底部
安全区被键盘撑大了」的假设，然后试了五种手势都没在模拟器上复现出来。用户接着说
「你看看这个 bug 是否可以复现出来是什么原因」，再补一句「然后从根因修复」。

他要的是**先复现**：在能改的地方临时加一个探针（这次是往 `chartPage` 里塞一个
`TextField`，聚焦它让键盘升起来），亲眼看到画面变成用户照片上那个样子，把机制坐实，
再去谈根因和改法。复现完把探针删掉，只留真正的修复。这比在提交说明里写「疑似是
键盘 inset」要值钱得多——上一次同一个现象就是因为没复现、直接照猜测改，结果那个
提交被另一个窗口判成误诊 revert 掉了。

所以在看盘里遇到「用户报了一个我没亲眼见过的现象」，顺序是：量证据 → 提假设 →
**造一个能稳定触发该机制的最小场景把它演出来** → 再动手修 → 修完在同一个场景里
A/B 验证一遍。不要在只有假设的情况下就提交修复。
