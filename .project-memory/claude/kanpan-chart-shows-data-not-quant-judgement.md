# kanpan-chart-shows-data-not-quant-judgement

**项目约定**：看盘图表上的功能（挂单墙等）是「聚合数据、门槛过滤、实时展示」，不是量化那套判定（质量分、骗单识别、生命周期结局）；把订单流项目的东西搬进看盘时只取过滤与聚合

# 看盘：图表的做法是展示聚合数据，不是量化的判定

2026-09-24 讨论把以前订单流项目（`~/Documents/ChatGPT/项目/send-tradfi` 的「站立墙」，
数据与复盘在 `~/TradeFiData`）的挂单墙搬进看盘时，我先后提了「只画此刻的墙、不留轨迹」和
「沿用站立门槛、六维质量分、测试/守住/击穿/撤单/过期的生命周期、靠近提醒」。用户两次纠正：

1. 「事实上墙是有生命周期的，之前的项目其实功能很完整，现在只取一部分而已。」
2. 「其实不一样，图表只要把相关数据展示上去，聚合起来即可。用户一般想看的是大单，而不是
   简单的订单簿，所以之前那个基础门槛过滤其实是替用户过滤的，过滤的订单才在上面展示聚合，
   不需要分是不是骗单什么的，实时展示即可。**这是图表的做法，那个是量化的做法，有着本质不同**。」

所以在看盘里：

- **图表功能 = 取数 → 聚合 → 门槛过滤 → 实时画出来**。门槛是替用户把「大单」从普通挂单里
  筛出来的手段，筛过就直接展示；数据变了就更新，没了就消失。这就是它的全部生命周期。
- **不带量化判定层**：不做质量分、不判骗单/站立/补单行为、不给测试/守住/击穿/撤单/过期
  这类结局、不做基于 reach 的入场窗口。那些是给「要不要发信号」设计的，图表不发信号。
- **从别的项目搬功能时只取「过滤 + 聚合」那一段**（例如站立墙的 8 bps 桶宽归一、绝对下限、
  局部倍数这几条基础门槛），展示层由看盘自己定；不要把它的信号层、账本、标定一起搬。
- 这条和 kanpan-display-only-needs-no-signal-algorithm（只展示不推送时别搬推送判定算法）
  是同一个原则，这里把它说到了图表功能的层面。
