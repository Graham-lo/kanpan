# kanpan-display-only-needs-no-signal-algorithm

**项目约定**：看盘里把别的项目的功能接进来做「只展示、不推送」时，不要连它为推送设计的判定算法一起搬；展示只要聚合，阈值和间距做成用户可调的设置

2026-09-17 用户问能不能把订单流项目的「主力大额订单流」接进看盘，明确说**只做展示、不做推送**，
直接在图表上标出来。我评估时把旧系统那套「站立墙」算法当成要移植的核心——桶宽按 8bps 派生、
墙质量分 Q、价格上下文 C、14 天冻结分布取 q0.90/q0.97 的准入分位——还建议先补标定。

用户当场纠正：「其实只需要把大单聚合起来就可以了啊，比如说 BTC 我想设置某个数值，并且品种的
间距也可以设置对吧，站立墙和之前的算法解决的是推送这块的吧，现在不需要推送啊」。

他说得对，这是一条方法上的要求：**判定算法是为「什么时候值得打扰用户」服务的。一旦确定只展示、
不推送，那套准入门槛、质量分、标定冻结分布、证据账本就整体不需要了，只剩下「按价格分桶把量聚合
起来画出来」。** 把推送时代的算法整套搬进一个展示功能，等于替用户承担了他没要求的预测承诺，还
把一个几天就能做的东西变成需要重新部署数据链路、重新标定的工程。

配套的第二条：**这类量化参数要做成用户自己能设的值，按品种分别设。** 他点名要的是两个旋钮——
金额阈值（「BTC 我想设置某个数值」）和价格间距（分桶宽度）。我可以给一个自动默认值（比如间距按
8bps 派生、阈值按该品种自身成交分布取分位），但必须让他能直接改成绝对数字，而不是把阈值藏在
算法里当成标定结果。这和「把参数做成滑杆交给用户」是同一个思路在数据维度上的延伸。

以后从别的项目（订单流、复盘等）往看盘搬功能时，先问这一层在原项目里是为什么存在的：如果它
存在的理由是「决定要不要发出去」，而看盘这边不发，就整层删掉，别移植。
