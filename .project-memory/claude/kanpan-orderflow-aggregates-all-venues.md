# kanpan-orderflow-aggregates-all-venues

**项目约定**：看盘「主力订单流」（以及任何盘口类功能）打开一只品种时要把币安、OKX、Coinbase 现货三家的簿聚合到一起算，不是按当前线路/交易所各算各的；用户 2026-09-24 明说「否则没有意义」，原项目也是聚合的

# 看盘：盘口类功能要把三家交易所聚合到一起，不是各算各的

2026-09-24 主力订单流第一版做完后，子代理的实现是「簿跟着当前行情提供者走」：币安线路只看币安簿，
网关线路看 OKX 簿，Coinbase 品种看 Coinbase 簿，三家各自独立出墙。用户看完汇报立刻纠正：

> 「你有没有做成聚合的，就是打开 btc 图表，就聚合币安、okx、coinbase 现货到一起，
> 原项目也是这样而不是单独各个交易所独立搞盘口订单，**否则没有意义**。」

所以在看盘里：

- **打开一只品种，就把它在三家交易所的簿同时订下来、按价格桶合并成一本聚合簿**，门槛和
  展示都在聚合簿上算。币安、OKX 用 USDT 合约，Coinbase 用现货（见 kanpan-multi-exchange-is-in-scope）。
  某家没有这只品种或连不上就少一家，不影响其它两家。
- **「三家都接了」不等于「三家聚合了」**。适配器各写一份只是数据层的事，功能层面用户要的是
  一张图上看到的是全市场的主力挂单。做盘口、大单、成交归因这类功能时，默认就是跨交易所聚合，
  除非用户明说要分家。
- 原项目（send-tradfi 的站立墙）就是这么做的：多交易所簇（cluster）合并再判门槛，
  只有单交易所撑起来的墙才要更高的倍数。把它搬过来时不能把这一层丢掉。
- 用户当时问过「同一个价格里不会同时出现红绿吧」，子代理据此按聚合中间价硬切侧、一桶只留一侧。
  同一天用户看了实现后纠正：「**那假如有人挂单呢，是不是会被过滤掉，买卖挂单都可以挂啊**」。
  所以**不许按中间价裁掉跨侧挂单**：跨交易所有基差时，一家的买墙和另一家的卖墙落在同一价位是
  正常的，原项目 `aggregate_books` 的桶就是按 (side, bucket) 分键、两侧各自成桶各自判门槛。
  同一桶两侧都过门槛时展示上把桶的高度上下分半（买下半、卖上半），不叠色、不混色、也不丢单。
  用户随后登录 CoinAnk 看过后自己说「我之前误会了一个问题，假设现在 btc 是 84000，挂高于 84000 的
  只能是卖单，低于的只能是买单」——单一簿内确实如此，两侧同桶只会出现在跨交易所基差那一两个桶里，
  是罕见边角，不是主流程。结论不变：按原版 (side, bucket) 分键，不加按中间价的裁剪。
  CoinAnk 的主力大额挂单设置也印证了我们的门槛表：BTC 现货 100 万、永续 500 万，
  现货接 Binance/OKX/Coinbase，永续接 Binance/OKX。

## 2026-09-24 晚些的定稿：「聚合」指的是同一张图上叠加所有交易所与产品的大单

改成 CoinAnk 的逐单模型之后（见 kanpan-orderflow-follows-coinank-per-order-model），
「聚合」不再是把各家档位合并成一个桶再判门槛，而是：打开一只品种就同时订下它在
币安 / OKX / Coinbase 的现货、币安 / OKX 的 U 本位永续、币本位永续、交割各本簿，每家每产品各自按
自己的门槛判大单，然后全部叠在同一张图上画。用户要的核心没变：一张图看到全市场的主力挂单，
不是各交易所各看各的。
