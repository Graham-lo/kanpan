# kanpan-one-feature-one-module

**项目约定**：看盘里一个功能要收拢成一个独立模块，不能把它的逻辑散落在图表、宿主页、偏好仓库、账号桥各处

2026-09-19 修「缩放没保存」这个 bug 时，我打算按现有代码的形状去改：在 `ChartView` 加一个
手势结束回调 → 顺着 `ChartHost` 接出去 → 在 `MainScreen` 的闭包里调 `PrefsStore.flushBarSpacing()`
→ 再顺手叫一次 `AppAccountBridge` 的同步，切后台那一刀还留在 `MainScreen` 的 `scenePhase` 里。
也就是说「图表布局怎么记」这件事被拆散在五个文件里，每个地方只拿到一小片。用户看完直接说：
「**把这个功能单独抽出来作为一个模块，不要到处散落**」。

所以在看盘里，一个功能要有**一个自己的模块**，而不是「在每个碰得着它的文件里补一段」：

- **判据是「这件事的规则写在哪里」**。如果我要向别人解释「图表布局是怎么记下来的」，得翻五个
  文件才能讲完，那它就还没成为模块。规则应该集中在一处，外面只负责把事件喂给它、从它那里取值。
- **散落的代价是规则会各自漂移**。同一件事分散在多处时，每处只解决自己眼前那一小块（这里加个
  400ms 节流、那里在切后台补一刀），谁也不为整体负责，于是出现「两个互不知情的后台钩子抢着
  写盘、顺序没人定」这种 bug——那正是这次的根因方向。
- **不要因为「现有代码就是这么摆的」就顺着摆下去**。改 bug 时如果发现要动的点散在四五个文件里，
  这本身就是信号：先把它收成一个模块，再在模块里修，而不是在五个地方各补一刀。

这条和 kanpan-finish-features-completely（功能要做完整）是一对：那条管「功能别缺口」，
这条管「功能别散架」。

## 登录与未登录不是两个功能，是同一个功能的两种存放处

同一轮里用户还补了一条，针对的是我把「本地保存」和「账号同步」当成两条各自为政的路来排查：
「**既然登录和本地有严重冲突，这块需要重点排查，而且本身就算登录或者本地这个布局都是一个
功能，所以放到一起全部处理好，无非是云端还是本地**」。

所以在看盘里：

- **「登录了走同步、没登录走本机」不构成两个功能，也不该是两条代码路径。** 它只是同一个模块
  内部「这一份存哪儿」的一个分支。模块对外的行为、保存时机、读取时机在两种情况下必须一模一样，
  用户登录与否不应该改变功能本身的语义。
- **冲突要在模块里显式定规矩，不能靠时序碰运气。** 本地那一份和云端那一份不一致时谁赢、什么
  时候拉、什么时候推、拉回来的旧值能不能盖掉用户刚做的改动——这些都要在一个地方写死并测到。
  散在两条路上时，就会变成「两个互不知情的钩子抢着写盘」那类 bug。
- 排查这类问题时**两种情况都要复现**：未登录复现不出来不等于没 bug，很可能恰恰说明问题出在
  两条路的接缝上。
