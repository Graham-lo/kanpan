# kanpan-alerts-are-a-standalone-module

**项目约定**：看盘的「提醒」是独立模块（不是画线的属性）；画线提醒 2026-09-23 起是选中栏里一颗「跌到 X 叫我」胶囊，画完不再弹问——那是另一窗口按新需求做的（1e271ee），我这边不主动改提醒这一块

2026-09-20 我作为产品经理给看盘（Hkline / Kanpan）列体验细节时，把「画线到价提醒」设计成
「线的属性：长按那根线打开提醒」。用户同意做这个功能，但把设计改了：

> 「用户画了一个趋势线一个通道什么的，那些点位穿过或者触碰时用户其实是想要提醒的，
> 但是画完最后弹出弹窗让用户确认，是否加入提醒，因为有时候用户只是单纯画线，
> 而且提醒这块后面可以加入更多的提醒方式，所以单独抽出来。」

所以在看盘里，**提醒是一个独立模块**（客户端一个 Alerts 模块、服务端一个 alerts 子系统），
画线到价只是它的第一种提醒方式。数据模型和入口要给价格提醒、复盘到点、以后别的方式留位置，
不能把提醒逻辑写死在画线里。提醒的管理入口在设置里的「提醒」总表。

## 画线提醒的入口已改版（2026-09-23，以最新为准）

另一个窗口按用户的新要求改了画线提醒（提交 1e271ee，PROJECT.md 有记）：

- 选中一条线，选中栏左边就是一颗胶囊「跌到 83,221.7 叫我」，点一下开、再点关；开着时写
  「会叫你 · 还差 x%」。文案统一在 `Kanpan/Kanpan/Alerts/LineAlertPhrase.swift`。
- **画完线不再弹「要不要加提醒」**。上面 09-20 那段「画完弹确认」已经作废。
- 只剩「收下朋友分享的线」时还有一句询问（6 秒）。

同一天我这边的体验整改（C 路）顺手改了提醒总表的文案和那句询问的秒数，用户随即说：
「**画线提醒按照最新的要求来，那是别的窗口改的**」，
紧接着又补一句：「**所以你这边的不要随便修改，因为那是新需求**」。于是：

- 画线提醒 / 提醒总表 / 收线询问这一块归那个窗口的新需求管，我这边（体验审查、整改 lane）
  **不主动改它**——不改秒数、不改文案、不给总表加东西，连「换成和胶囊一致的说法」这种对齐也不做。
  当时的处理是把 ae1e7a4 对提醒的改动整体撤回，而不是改写成新措辞。
- 审查里发现提醒这块有问题，只写进报告交给用户，不派 lane 去改；除非用户明说要我改。
- 动手前先看 main 最新提交与 PROJECT.md，确认某块是不是别的窗口正在按新需求做的东西。
