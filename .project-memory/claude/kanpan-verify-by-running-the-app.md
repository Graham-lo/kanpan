# kanpan-verify-by-running-the-app

**项目约定**：看盘的交互审查/验收要真的把 app 跑起来、以交易员（人）的身份带着真实任务去用，而不是读代码或跑断言；优先真机，其次模拟器

用户要求对看盘（Kanpan）iOS app 做前端交互审查时，明确说「你可以真实用 xcode 模拟器实际体验」，
随后又补了一句「你要体验所有的功能」。也就是说：这个项目里的交互审查、体验评估、验收类任务，
结论必须建立在真的把 app 跑起来、把每个入口都点过一遍的基础上，而不是靠读 SwiftUI/UIKit 源码推断。
覆盖面也要是全量的——所有页面、所有面板、所有手势，而不是挑几个有代表性的看看。

这条很重要，因为只读代码得出的结论在这个项目里被证明会出错：源码上看着能用的按钮，实际跑起来可能被
别的控件压住点不到；源码上看着是「选中」的手势，实际可能新建了一个对象。只有跑起来才能发现这类问题。

**跑在哪里：优先真机。** 用户后来说「我连接了手机，要测试直接真机上测试即可」——他习惯把自己的 iPhone
连在这台 Mac 上（`xcrun devicectl list devices` 能看到），所以不要默认走模拟器，更不要因为模拟器工具链
不通就停下来问。先看有没有已配对的真机，有就直接往真机上装、在真机上验。

实操上，桌面版 Claude Code 里驱动模拟器的原生集成经常不可用（缺 /var/db/xcode_select_link，需要用户
用密码执行 `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`），computer-use 授权也可能被拒。
可行的替代路径是写临时 XCUITest 用例去驱动 app，靠 XCTAttachment 截图和 accessibility 树取证；
这类临时用例是脏文件，审查结束后要从仓库里删掉，不要留下也不要提交。

**体验审查要站在「人」的角度，不是「机器」的角度。** 2026-09-23 用户让我重点审查交互为什么「总感觉不是很顺手」，
我先打算派几个子代理分块读代码找问题，用户当即纠正：「你要以用户的角度去体验这款产品，而不是机器的角度，是人在用」。
所以交互 / 体验类审查的做法是：把自己当成一个做合约波段、短线的交易员，带着真实的任务去用
（盘前扫一遍自选、看到异动赶紧画线挂提醒、切大周期看方向、拿到朋友分享的线……），一步一步点、滑、等，
记下的是人的感受——手指要伸多远、要点几下、有没有等待、找不找得到、结果是不是出乎意料、会不会误触。
读源码、跑断言、数 file:line 只能用来解释「为什么会这样」，不能拿来代替体验本身，也不能当成发现问题的主渠道。

补记（2026-09-18）：我把「顶栏品种名不再弹选择框」只在模拟器上点过一遍就报告做完了，
用户下一句就是「真机怎么还能弹出来」——因为那台 iPhone 上装的是改动之前的包，
本机压根没为真机编过这一版。**所以「验收完成」的前提是新包已经装进真机并在真机上点过，
在模拟器上验过不算数，也不能拿模拟器的截图当交付证据。** 改完 app 侧的代码，
收尾动作是 `make install-release`（它会先重编再装），然后在真机上把受影响的入口走一遍。
