# kanpan-dont-broadcast-to-other-windows

**项目约定**：看盘里做完任务不要再用 ListAgents + SendMessage 去挨个通知其他窗口，那样白烧 token；改完自己 push 完就结束

# 看盘：不要再挨个通知其他窗口

2026-09-21 我清点本机的后台任务时，向用户汇报了 33 个同伴会话、31 个常驻 claude 进程
（约 2 GB 内存）和一批僵住的进程。用户的回复是：

> 「直接全部清理掉，因为目前整轮审查和优化全部完成，相关的全部归档，**后续实现新任务
> 不再到处通知消耗大量 token**。」

这条**推翻了 kanpan-notify-other-windows**（那条说：改动落到共享工作树或线上网关之后，
要主动用 `ListAgents` + `SendMessage` 给其他正在工作的 Claude 窗口发通报）。那套做法是
多窗口并行审查那一阶段的产物：当时确实有好几个窗口同时在同一棵工作树上改代码，互相不
通报就会撞车。审查与优化那一轮在 2026-09-21 收尾归档之后，这个前提没有了，而广播通报的
代价是实打实的——每发一条都要唤醒对方窗口跑一个完整回合。

所以现在看盘里的默认闭环（见 kanpan-dont-ask-just-ship）最后一步变成：

- **改完、测过、push 完、真机包打完，就直接向用户汇报，回合结束。**
- **不要再调 `ListAgents` 去点名同伴窗口，也不要 `SendMessage` 广播提交号和改动文件。**
- 只有用户明确要求「告诉某个窗口某件事」时才发消息，而且是点对点发给他指名的那一个。

同样的道理也适用于我自己派的子代理和后台任务：不要为了「保持同步」而开轮询、发心跳、
或者让窗口空转等待（这一点和 kanpan-no-idle-waiting-for-phone 一脉相承）。
