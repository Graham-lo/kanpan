# kanpan-user-scale-is-tiny

**项目约定**：看盘目前只有 3 位朋友在用、上限约 10 人，做容量与请求量取舍时不必按公开产品的规模来保守

用户在 2026-09-16 说明，看盘（Kanpan）当前的实际使用者只有 3 位朋友，预期上限不超过
10 人。

这条会影响性能与架构上的取舍：凡是「多发几个请求换更低延迟」这类方案，成本按 10 个
用户估算即可，不要按公开发行的 App 去做保守的容量假设。例如让直连与 VPS 网关并行竞速
（对冲请求）会使网关请求量上升，在这个规模下完全不构成负担，因此不必为了省网关流量而
放弃明显的体验收益。

需要注意的是，这条**不**推翻另一条约束：看盘的两台 VPS 行情网关仍然是线上服务，验证
时只能做轻量只读探测，不要压测、也不要改动它们。两者的区别在于，前者说的是 App 正常
运行时的请求量无需过分克制，后者说的是不要把网关当测试靶子。

## 补充（2026-09-17）：服务端资源也按「最大化利用」来放

做性能优化那一轮，用户在授权我接手 VPS 后又补了一句「性能随便用，因为就 10 个人以下使用这个产品，
最大化利用」。所以网关与个人 API 的 systemd 配额（CPUQuota、MemoryMax、TasksMax）、每 IP 限流、
并发槽位、缓存大小这些参数，都不必按公开服务的保守默认来定，而是按「整台机器就是给这十个人用」
来放宽；只需保留防止单个异常客户端把机器打死的兜底上限，不需要为陌生流量预留余量。
