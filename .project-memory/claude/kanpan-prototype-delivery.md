# kanpan-prototype-delivery

**项目约定**：看盘的原型做完要覆盖全部状态，并且一律部署到 VPS 的 /ui/ 目录让用户在浏览器里看

在看盘（Kanpan）项目里做 UI 原型时，用户反复强调过两件事，每次都要照做，不用再问。

**原型要覆盖各个场景，不能只画顺利状态。** 用户的原话是「重点覆盖到各个场景」。所以一套原型
除了默认画面，还要把冷启动、断网重连、同步失败、搜索中、搜不到、空自选、空复盘、未登录、
撤销提示这些真实状态一并画出来。他看原型是为了判断产品在各种情况下长什么样，只给主流程的
几屏对他没用。

**做完的原型一律部署到 VPS 上。** 用户前后说过「帮我放到 vps 上方便查看」「做好放 vps」
「做好把原型放到 vps 上」「还是部署到 vps」。他在手机或别的机器上用浏览器看，不方便开本地
文件。落地方式是往 `orderflow-vps:/var/www/kanpan/ui/` 里加静态 HTML，然后把新原型作为第一张
卡片加进同目录的 `index.html`，文件属主改成 `caddy:caddy`、权限 644。这是纯追加的静态目录，
不要改 Caddyfile，也不要碰网关路由。公开地址是 `https://<VPS 主机>/ui/`，
部署完要用公网 HTTPS 验证一次再回报。

**2026-09-17 补充：原型要「定板后可以直接施工」，交互要看得出参考了用户习惯研究。** 我交出「青瓷」
整套原型后，用户连问两句：「交互体验是否有参考用户习惯」「原型的设计上要体现出来，我定板后可以直接
施工」。这意味着看盘的原型有两条额外验收标准：

- 每一屏、每个交互决定都要能对应到桌面 / `docs/` 里 GPT 那份用户习惯研究（`产品体验设计-2026-09-16.md`）
  的具体条目，并且要**写在原型页面里**（每节的说明或单独一节「交互依据」），不能只在我脑子里或只写在
  另一份审计文档里。用户是在原型页面上定板的，依据不在页面上等于没有。
- 原型本身要达到施工图的完备度：尺寸（字号 / 行高 / 圆角 / 间距 / 热区）、全部状态、动效与触感参数、
  颜色 token 全在页面上，实现方（现在是 Opus 5 子代理，不是 Codex）拿到原型 + 实施说明就能开工，
  不需要再回来问设计意图。
- 用户随后又补了一条（2026-09-17）：「功能怎么重排，布局怎么放，什么功能应该放主页面，哪些可以放到二级页面，
  重要的常用的功能不要点来点去才能用到，是否要设置各个页面的返回按钮等各种体验细节，你都要囊括到，这关系到
  后面的施工。」所以看盘原型里必须有一张「功能分层表」（每个功能 · 使用频次 · 从首页几步到达 · 放在哪一层 ·
  为什么）和一张「导航与返回规则表」（每类页面怎么进、怎么退、左上右上放什么、Dock 何时保留），再加手势 /
  默认值 / 键盘 / 撤销 / 触感 / 热区这类体验细节清单。这些都是施工项，不是可选的补充说明。
