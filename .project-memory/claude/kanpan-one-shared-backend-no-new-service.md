# kanpan-one-shared-backend-no-new-service

**项目约定**：看盘 iOS 与网页版共用同一个后端 kanpan-api，网页版需要的服务端能力一律加进它并把能通用的抽成共用层；不许为网页版另起一个 Rust 服务或另一个网关；用户 2026-09-29 明说

# 看盘：后端只有一个 kanpan-api，网页版不另起服务

2026-09-29 网页版账号 / 订单流 / 多图布局这一批正在收尾时，用户插话：

> 「**后端还是共用一个，能通用的都抽出来，不要再写一个 rust 或者网关**」

所以这是长期规矩：

- **iOS 端与网页版共用同一个后端**，就是 `Backend/kanpan-api`（Rust）。网页版要的接口、
  同步字段、订单流历史、复盘运算，全都加到这个服务里，与手机端走同一套路由、同一套鉴权、
  同一份数据库。
- **能通用的抽成共用层**：两端都要的逻辑（账号与会话、同步字段白名单、订单流聚合口径、
  热力 / 历史查询的分页与缓存、复盘的回合拼接）不要在「手机路由」和「网页路由」各写一份，
  抽到公共模块让两边调用；只有展示层的差异才允许分叉。
- **不许另起服务**：不写第二个 Rust 服务、不加第二个网关、不为网页版单独开进程或端口。
  之前的规矩 kanpan-backend-rust 说「后端一律 Rust、要加功能去 kanpan-api 写」，
  这条把它说得更死：不只是语言要 Rust，而且**就那一个进程**。
- 原因：用户不想维护两套服务端；两端共用一份数据与口径，同步与账号才不会出现两边对不上的情况
  （参见 kanpan-finish-features-completely 里两端清单对账的教训）。
