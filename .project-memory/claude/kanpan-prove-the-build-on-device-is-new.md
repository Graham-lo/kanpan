# kanpan-prove-the-build-on-device-is-new

**项目约定**：看盘真机验证时，如果设备上的行为和刚改的代码对不上，先证明装上去的是新包，不要急着回头怀疑代码

2026-09-18 排查「K 线和自选都不跳」时，我把默认推送域名从测试网改成
`dstream.binance.me`，`make install-release` 装上真机，日志里却仍然打印
`WS有效首帧 stream.binancefuture.com`。我先去怀疑代码——查了 `PrefsCodec` 的老配置
迁移、查了 `PersonalSyncCodec.keepDeviceFields` 会不会用账号同步把域名盖回去，
两条都没问题，白花了一轮。真正的原因是仓库 `Makefile` 里 `install-release:` 当时
**没有任何前置依赖**，它只负责把上一次编出来的包装到手机上，改完代码直接装等于装旧包。

这条已经在 `Makefile` 里修掉了（`install-release: device-release`，增量编译没改动时
只要十几秒，不值得为省这点时间冒装错包的风险），但教训是通用的：

**真机上观察到的行为与刚改的代码矛盾时，第一步是证明设备上跑的是新二进制，而不是
去推测代码为什么没生效。** 最快的证法是把改动里那个字符串常量直接从包里捞出来，
例如 `strings <装出来的 .app>/<可执行文件> | grep stream.binance`——它要么打印新域名，
要么打印旧域名，一行就能定案，比读几百行源码找解释快得多。确认是旧包之后再重编、
重装、重跑，才开始分析行为。

同理，任何「装一下」的 make 目标都必须依赖它对应的编译目标。一个不重编的安装目标
迟早会让人对着旧包调试，而这种坑排查成本极高，因为所有证据看起来都自洽。
