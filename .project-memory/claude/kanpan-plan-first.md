# 看盘：先给方案，别急着产出交付物

**这条只管「从零起头的新功能 / 新视觉方向」。** 2026-09-18 用户下了一条更强的长期指令
（见置顶的 `kanpan-dont-ask-just-ship`）：修 bug、审查整改、以及他已经说清楚要什么的活儿，
一路做到 push 为止，不要停下来问。下面这段讲的是剩下的那一类。

在这一类事情上，用户要的第一样东西是**方案**——把事情讲清楚：要做什么、数据放哪儿、
边界在哪儿。原型和真正的代码，都要等他看过方案、点头之后才开始。

这条是用户的直接纠正。做账号系统那一轮，我按老习惯一口气交了原型加一份两万多字的
实施说明，他的回话是「你不必写提示词，你先把方案搞出来」「不要改代码先给方案」。
问题不在于那份说明写得好不好，而在于方案还没被确认之前，任何下游交付物都可能整篇作废，
写了也是浪费两边的时间。

所以顺序是：方案 → 他确认（常常会推翻一部分）→ 再谈原型和实现。他没说「开始写」之前，
不要自作主张往 `docs/` 和 `prototype/` 里加东西，更不要动 Swift 代码。

方案确认之后接的是 `kanpan-who-writes-the-code` 那条流水线：原型定稿 → 我派 Opus 5 子代理
实现 → 我验收 → 装真机 → push。用户已经选定方案或直接下令实现时不要再回头问。

## 2026-09-28 补充：做减法（收设置项、撤功能）也要先列清单

我按用户「尽量减少设置」的原则盘出一份要收掉的设置清单并准备直接派人改时，用户说：
「你认为还有哪些设置可以做成自动化或者减少设置量，**你可以先罗列出来，但是不要先直接改代码**」。
所以「先给方案等确认」的范围除了新功能、新视觉方向，还包括**收敛设置面、退役开关、撤掉
用户可见的能力**这类减法——拿走的东西用户看得见、可能正用着，要先把清单摆出来让他勾，
他点头了再改；修 bug、整改、他已说清的活仍按 kanpan-dont-ask-just-ship 一路做到 push。
