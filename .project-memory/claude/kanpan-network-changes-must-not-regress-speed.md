# kanpan-network-changes-must-not-regress-speed

**项目约定**：看盘的网络/行情线路层已经做过一轮速度优化，之后任何改动（含抽包重构）都不能让连接与首屏变慢，改完要拿实测数据证明没倒退

2026-09-17 我在把看盘的行情网络层（线路选择、REST 传输、网关竞速、RoutedMarketFeed）
抽成独立模块并修启动竞态时，用户特意叮嘱：「因为之前优化过网络速度，现在改了容易有问题，
你改完之后性能不能倒退，不能因为代码的问题导致连接访问变慢。」

这条要求是长期有效的，不只针对那一次重构：

- 之前那轮性能优化（提交 `3e0b8dc`，缓存/网络/图表/账号同步全链路）里网络这块的成果——
  直连币安不绕网关、网关双节点竞速、Retry-After 冷却、首屏用缓存先画再拉——是**基线**，
  后面动网络代码时不能把这些顺手改没或改弱。
- 只做结构性搬动（抽包、改名、拆文件）时，网络行为要**原样保留**：同样的请求路径、同样的
  并发/竞速策略、同样的超时与冷却参数，不额外串行化、不加多余的一跳。
- 修 bug 也要以「不变慢」为前提：例如修「被取消的请求误记网关冷却」是让连接更快恢复，
  这种可以做；但不能为了保险加人为的等待、轮询或重复拉取。
- 改完要用真机上受影响的 UI 用例或启动首屏计时拿到**实测数字**，和改前对比后再报告，
  不能只说「逻辑没变」。若实测确实变慢，要先查原因修掉，而不是把变慢当作可接受代价。

2026-09-18 用户在让我动手优化 VPS 行情网关（Python）之前又加了一句「改完要实测一下有没有提升」，
所以这条规矩是双向的：**不只是改动不能变慢，声称是优化的改动必须拿改前／改后的实测数字证明确实变快了。**
做法是先写一个可重复跑的基准脚本、在改动前跑一遍留下基线，改完在同一台机器同样条件下再跑一遍对比，
而不是改完凭道理说「这样应该更快」。没有量到提升的那一项要如实说，不能混在总体数字里蒙过去。
