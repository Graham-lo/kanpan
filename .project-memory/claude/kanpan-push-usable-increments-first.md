# kanpan-push-usable-increments-first

**项目约定**：看盘里能用的功能增量要先推上 main，不等整个功能做完、报告写齐或部署完成；用户 2026-09-22 明说「功能能用的先优先 push，不需要等待完整功能实现」

2026-09-22 四条 Codex 线程并行时，对比 K 线线程把阶段一的提交在本地反复 rebase 攒了一个多小时没推，
提醒铃声线程把已经全绿的阶段三提交压着等部署证据补齐再推。用户看到后说：
「**功能能用的先优先 push，不需要等待完整功能实现**」。

所以在看盘里，交付节奏是：

- **能用就推。** 一个阶段（或阶段里的一段）只要构建和受影响的测试全绿、app 不坏，就立刻 rebase 并
  ff 推到 main，不等这条线程把整个功能做完。
- **报告、截图、性能证据、部署记录都可以后补一个提交**，不能成为压着代码不推的理由。
  「先推代码，再补报告」是正确顺序；「攒到报告齐了一起推」是错的。
- 这条同样适用于我给 Codex 写的交接书与 AGENTS 规则：阶段划分要小到「每一段推上去都能用」，
  验收也按推上来的增量做，不必等全功能。
- 原因是用户要尽早在手机上看到能用的东西，而且几条线程并行时，谁压着不推谁就让别人反复 rebase。
  它和 kanpan-finish-features-completely 不冲突：功能最终必须做完整，但中途的可用增量不许扣着。
