# kanpan-gateway-is-production

**项目约定**：看盘的两台 VPS 行情网关是线上服务，默认只做轻量只读探测、不压测；用户明确授权时可以接手改服务端，但要备份、先动备用节点、改完只读验证

看盘（kanpan）项目在两台 VPS 上跑着公开行情网关（主节点 `<VPS 主机>`，
备用节点 `<VPS 主机>:8443`，源码在 `Backend/kanpan-gateway`）。用户明确要求
测试网络兜底、选路这类问题时**不要把网关搞坏**：这两台是真实在用的线上服务，不是实验环境。

所以验证时的做法是：只发少量只读请求（单条 WS 连接拿首帧、`/chart-gateway/health`、
`/chart-gateway/stream-health`、一次 OI range 查询），不做并发压测、不批量建连、不改服务端配置、
不重启 systemd 服务、不动 Caddy 路由。需要「制造故障」来验证兜底时，改本机或客户端这一侧
（绑网卡绕过代理、把 App 里的自定义域名指向不通的地址），不要去改网关本身。

同样地，为了做测试而改动本机环境（例如在 Mac 的 Surge 里关掉某台设备的「使用 Surge 作为网关」、
改路由规则、改 App 的自定义域名）属于临时手段：用户要求测完必须把这些设置恢复原样，
不要把「为了复现直连而制造的故障状态」留在他日常使用的机器上。做这类改动前先记下原始状态，
测完立刻改回去并向用户说明已恢复。

## 补充（2026-09-17）：用户授权时可以改 VPS

做性能审查那一轮，用户看到报告里有一批优化落在网关 / 个人 API 侧（限流配额、gzip、上游连接复用、
数据库索引等），明确说「如果 VPS 需要使用你可以接手」。也就是说「不改服务端」不是绝对禁令，
而是默认姿态：**没有授权时只读探测；用户点名授权后可以直接改并部署**。接手时仍要按线上服务对待：
改前备份原配置与服务文件，先在备用节点部署并用只读探测验证（health / stream-health / 一次
klines / 一次 OI range），再上主节点；不做并发压测；每一步在报告里写清改了什么、怎么回滚。
