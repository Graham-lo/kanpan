# kanpan-who-writes-the-code

**项目约定**：看盘（Kanpan）的实现由 Claude 这边完成（主窗口把控设计与验收，Opus 子代理写代码）；2026-09-23 起不再默认交给 Codex，只有用户明说时才交

早期看盘这个项目的分工是「Claude 出原型和实施 prompt，实际代码由 Codex 写」，
仓库根目录的 `CLAUDE.md` 里那段 Scorebook 交接说明也是这么写的。这条已经过时了。

用户在 2026-09-17 明确纠正过一次：「不是 codex 在实现，目前是 opus 另一个窗口在实现，
并且大部分任务都完成了」。也就是说，看盘的实现是用户自己另开的一个 Opus 会话在推进，
和本会话共用同一个工作区。

由此有两件事要做：

**不要再默认「代码归 Codex」。** 用户让我实现的时候就直接实现，不要以分工为由停下来
只出方案；反过来，也不要假定没人在动这份代码。

**同一个仓库可能同时有另一个窗口在写。** 开工前先看一眼工作区最近被改过什么，免得两个
会话互相覆盖；具体看哪几处见 `kanpan-sync-other-window-state-first`。用户提到另一个窗口
正在做同一件事时，直接避开那批文件（按 `kanpan-dont-ask-just-ship` 不要停下来问），
不要把自己那份改动继续往同一棵工作树上堆。

**2026-09-17 之后的固定流程：原型定稿 → 我派 Opus 5 实现 → 我验收 → 装真机 → push。**
用户在自选页原型选定「琉璃」后说的是「交 opus 来实现这个自选页面，你来验收即可」，紧接着补了
「实现使用 opus 5 high 即可，测试通过后把安装包安装到我手机并 push 到远程」。也就是说，
这不是让我等他另一个窗口去做，而是让我在本会话里用 Agent 工具起一个 Opus 5 子代理写代码，
自己只负责写实施说明、验收（真机跑起来看）、把包装到连在 Mac 上的 iPhone、再 commit 并
push 到 origin/main。以后原型被选定之后，默认就按这条流水线走，不要停下来问「谁来实现」。

**2026-09-17 傍晚再确认一次分工。** 交互定板原型交付后，用户说「这些交互设计都交给 opus 5
high 来实现，你负责具体的验收和矫正，注意实现要在最新的代码上」。所以流水线不变：我出实施
说明、派 Opus 5（high）子代理写代码、我验收并纠错。「最新的代码上」是硬要求——开工前先
`git fetch` 并核对工作树与 origin/main 的最新提交，不要在旧快照或另一个窗口尚未合并的
状态上改；验收也要针对最新构建。

**2026-09-18 再定死一次，范围扩到「所有代码」。** 做板块强弱那一轮，两个 Opus 子代理在写
甲版与服务端时，我在汇报里说了后续手机端 乙.3/乙.4 我自己接着写。用户随即插话：
「你只负责验收矫正设计」「代码交给 opus 5 high」。所以分工不再限于「原型定稿后的实现」：
在这个项目里，**任何要落到仓库里的代码——新功能、后续阶段、验收发现的修补——都派
Opus 5（high）子代理去写**，主窗口做的是设计决策、写实施说明、验收（跑受影响用例、
真机看）、发现问题后给子代理下矫正指令、commit / push / 装真机 / 通报其他窗口。
验收时发现的小问题也走 SendMessage 让原子代理改，而不是自己顺手用 Edit 改掉。

**2026-09-20 主窗口是项目经理，核对也可以派出去。** 第四轮审查整改我派了四个 Opus 子代理
分线写代码后就只等通知。用户随即说：「你自己也要核对并补充，因为你可以访问 vps 运行模拟器，
但是核对这些事你可以交给 opus。你自己负责项目经理的角色把控重要总关口，负责设计验收」。
所以主窗口的角色是**项目经理**，不是被动等子代理交活：

- **核对与补充是主窗口的责任，但具体核对活可以再派 Opus。** 例如：报告条目是否被四条线
  完整覆盖、子代理的改动是否真的对上报告原文、两端契约是否一致、漏掉的项要补派——
  这些「审计」也派 Opus（high）子代理去做，主窗口拿结论。
- **只有主窗口能碰的通道由主窗口自己用**：VPS（部署、只读探测）、模拟器 / 真机跑起来
  看现象。这是主窗口「核对」里不可外包的那部分。
- **主窗口把控的总关口**：派工前的设计与拆分、子代理交活后的验收（复现现象消失）、
  提交 / 推送 / 部署 / 装真机、通报其他窗口。每一道关口都要主窗口亲自过，不能只看
  子代理的自述汇报就放行。
