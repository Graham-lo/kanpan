# kanpan-prototype-reuses-implemented-ui

**项目约定**：看盘的皮肤、底栏、徽章等视觉已在 app 里定型，交互原型默认照抄真机视觉；只有用户点名要某一页「极致好看」时才对那一页做整体视觉重设计

2026-09-17 我交完交互审查文档后，用户让我直接出完整原型，并且明确说「ui 你不必自己设计了，
目前的 ui 都已经实现好了」。也就是说看盘（Kanpan）的视觉层（青苔／陶土／经典三套皮肤、深浅色、
底栏、卡片、徽章、字号）已经在 iOS app 里落地并被用户认可，从这一轮起它是既成事实，不再是
原型要回答的问题。

因此以后给看盘做原型时：

- 视觉照抄 app 现状：颜色 token、字号、圆角、底栏样式直接复用已实现的那套（可以从
  桌面上 `看盘原型-陶土青苔-2026-09-17.html` 的 CSS 和真机截图取），不要再提出新的配色、
  新的排版风格，也不要为了「好看」改动已定型的组件。
- 原型的价值全部放在交互与状态上：功能重排、导航与返回、各页面的全部状态、反馈与撤销、
  手势与默认值。审查里发现的问题要能在原型上看到「改成什么样」。
- 用户同时把之前审查文档里留给他的开放决策交回给我（「你按照最好的方案你来决断即可」），
  所以这类原型里遇到二选一的交互决定，我直接选并在页面上写明理由，不再回头问。

同一天稍后用户又把范围收得更窄：「其实你要做的是交互设计相关的问题，其他你一概不需要管」。
所以在看盘项目里我的角色就是交互设计师：原型和文档只回答「怎么交互、有哪些状态、怎么导航
和返回、反馈与撤销」，不要再附带色板 / 字阶 / 图标规格板这类视觉规格，也不要顺手评论
工程实现、后端或性能——那些不归我管，写进交付物只会稀释重点。

**2026-09-17 晚间的边界修正：这条不是「永远不再设计视觉」。** 同一天用户又拿自选分类页说
「要极致好看」，让我出五套方案、选定「琉璃」并交 Opus 实现，最后评价「自选那个很好」。所以规则是：

- 交互原型（导航、状态、手势）默认照抄 app 已实现的视觉，不顺手改色板、字阶、组件。
- 用户点名某一页要「更好看 / 极致好看」时，那一页可以整体重做材质、版式、装饰（光斑、玻璃、
  印章、迷你走势图都是被接受的），但仍只在青苔 / 陶土 / 经典这三套既有皮肤里做，尺寸按「克制」那条取。
- 图表底座与指标仍然不动。
