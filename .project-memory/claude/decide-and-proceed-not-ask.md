# 自己拿最好的方案往下做，别把选择题甩回来

在看盘项目里，我把 M3 验收的三处分歧整理成「要你拍板」的清单丢给用户
（一屏根数达不到任务书写的 2000、亚像素影线有 1/255 的舍入差、三层结构让最新价的
叠放顺序变了）。用户的回复是：**「数量按照实际情况来即可，不要那么死板，其余的使用
最好的方案解决」**。

这里面有两条要一直记住的：

**一、规格里的数字是目标不是教条。** 任务书写「一屏 ≈ 2000 根」，实测在该机型上只能到
860 根，原因是别处定死的常数。正确做法是把实测值如实写进证据，说明为什么是这个数，
然后继续往下走；不是为了凑那个数字去改常数，也不是停下来等用户裁决。

**二、能自己判断的分歧就自己判断。** 用户要的是我给出并执行最好的方案，把判断依据和
做了什么写清楚，而不是把 A/B/C 摆回他面前。只有真正非他不可的事（需要密码、需要他的
账号身份、需要他本人在真机上体验判定）才交出去。

这条和 `prefer-doing-over-handing-commands.md` 是一回事的两面：那条讲的是别把命令甩
给用户，这条讲的是别把决定甩给用户。
