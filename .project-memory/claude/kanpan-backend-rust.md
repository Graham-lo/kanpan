# kanpan-backend-rust

**项目约定**：看盘的后端一律用 Rust 写；服务端要加功能或提速时，重写到 Rust 的 kanpan-api，不要继续在 Python 网关里补

# 看盘的后端：Rust，而且只为体验服务

**语言是 Rust。** 凡是给看盘设计服务端（账号、同步、复盘判定）的方案，默认技术栈就是 Rust，
不要照着 `Backend/kanpan-gateway` 的 Python 往下推——那套只是早期的行情转发，不代表后端选型。

**服务端要加功能或提速时，直接用 Rust 重写，不要在 Python 网关上打补丁。** 2026-09-18 我查出
持仓量历史慢是因为 `Backend/kanpan-gateway/server.py` 的归档回填按「每 4 天一批」串行下载，
提了「把并发提到 16 并加 keep-alive」的改法，用户的回话是「直接使用 rust 实现，这样更快」。
也就是说，遇到 Python 网关里性能不行的那一块，正确的动作是把它搬进 Rust 的
`Backend/kanpan-api`（axum + tokio + reqwest，已经在主节点上跑着，端口 8794），
再改 Caddy 路由把那条路径指过去，而不是继续优化 Python 那份。

**但已经在跑的那套 Python 行情网关是个例外，可以就地优化。** 2026-09-18 用户问「网关用 Rust
或 C++ 会不会更快」，我实测后回答瓶颈不在解释器（一次请求里 Python 自己只占几毫秒，其余全是等上游），
他的回话是「我想代码层面性能更快，有没有更好的方案」「直接一起全做啊」——也就是说，`Backend/kanpan-gateway`
里已经上线的行情转发，只要拿实测证明慢在结构性等待（TTL 到期重取、上游 WS 冷启动、重复分页下载）而不是
语言，就在原地改 Python，不必为了提速把它搬进 Rust。上面那条「搬进 kanpan-api」针对的是新功能和
归档/账号/同步这类本来就该长在 Rust 那侧的东西。

**定位是「提升体验」，不是产品的地基。** 用户的原话是「后端这边只是为了提升体验，比如记录 K 线
图表指标的大小布局等，复盘的一些数据等」。也就是说后端存在的理由，是换一台设备之后还能回到
原来那套图——指标参数、副图高度、配色、自选、画线、复盘记录。它不是权威数据源（复盘判定是唯一
的例外，因为客户端不能自己宣布自己判对了）。

由此推出的几条设计约束，做方案时默认成立：

- 不登录必须能用全部看图功能，登录只是多了跨设备这件事。
- 同步失败、令牌过期、服务端下线，都不许打断用户，更不许拦住启动。
- 因为不追求强一致，同步存储可以简单：以 jsonb 为主，末次写入胜出加墓碑就够，不必为每个偏好
  字段在 SQL 里建模，也不必上复杂的冲突解决。
