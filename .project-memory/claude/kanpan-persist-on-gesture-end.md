# kanpan-persist-on-gesture-end

**项目约定**：看盘里连续手势（缩放、拖分隔线等）改出来的值，手指一离开屏幕就必须立刻落盘并同步，不许靠定时器节流兜底

2026-09-19 用户报「进 BTC 缩小后立马退后台冷启动，回来不是缩小后的样子」。当时根间距
（缩放）的落盘是这么写的：手势每变一次记在内存，另起一个 400ms 的定时器延后写盘，
外加切后台时 `flushBarSpacing()` 补一刀。我还在排查，用户直接给了结论：
「**用户手离开的瞬间就应该做同步做持久保存啊**」。

所以在看盘里，连续手势产生的值（双指缩放的根间距、拖分隔线的副图高度，以及以后任何
「按住不放会一直变」的东西）：

- **手指抬起（手势 `.ended` / `.cancelled`）那一刻就落盘并同步**，把它当成一个离散动作的
  终点来处理。这是主路径。
- **定时器节流只能是手势进行当中的降频手段，不能充当保存时机**。指望「400ms 后自然会写」
  或者「切后台时补一刀」，就会出现用户手一松、马上杀 app，改动没了的情况——而用户的心智
  是「我松手了，这事就算数了」。
- 切后台时的 flush 仍可保留作最后一道保险，但它是保险，不是设计。

更一般地：用户判断「这次修改算不算数」的时刻是**他手离开屏幕的那一刻**，不是我们内部
某个定时器到点的那一刻。任何落盘时机的设计都要对齐这个时刻。

用户当场还补了两句，一起构成「布局怎么记」的完整规则：

- 「**自动记录布局**」——这件事不只针对缩放那一个值：**图表的整个布局（缩放、副图高度、
  副图顺序、开着哪些指标）都由 app 自己记下来**，不需要用户做任何保存动作，也不要给他
  「保存布局 / 恢复布局」之类的按钮。他摆成什么样，下次来就是什么样。
- 「**而且布局要同步到所有品种的任意周期**」——布局是**全局的一份**，不按品种分、也不按
  周期分。在 BTC 的 1h 上缩小，换到 ETH 的 5m 也是那个疏密。理由还是那条判据：
  疏密是他看盘的习惯，不是某个品种或某根周期自己的属性。所以它进 `Prefs` 随账号同步，
  换台设备登同一个账号也得是这个布局。
