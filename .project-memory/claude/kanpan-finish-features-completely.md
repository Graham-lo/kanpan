# kanpan-finish-features-completely

**项目约定**：看盘改交互时功能要做完整——合并入口不能把功能弄丢，发现残留问题直接修不要停下来问

用户在看盘（Kanpan）项目里两次因为同一件事纠正我：一次是我把底栏的「自选」入口合并掉之后
他发现进不去自选页（「你怎么把自选的入口弄没了」），一次是我改完底栏后报告说
`bottom.style` / `bottom.landscape` 相关的测试套件已经失效、问他要不要顺手对齐，
他回的是「你要把功能搞完整才行啊」，紧接着又补了一句「有问题直接修复」。

所以在这个项目里有两条并行的要求：

**整合入口时功能不能丢。** 精简底栏、合并面板、收敛重复入口都是被鼓励的，但每砍掉一个
按钮都要先确认那个功能还有别的路能走到。K 线风格就是正面例子——底栏的「风格」格子没了，
但风格选择仍然活在「图表」面板里的 `CandleStylePicker`，功能没断；自选是反面例子——
入口没了之后那张分类页就真的进不去了。改完一定要从用户视角把被影响的功能各走一遍。

**发现问题直接修，不要停下来请示。** 包括不是我引入的存量问题（比如我动手之前就已经红了的
测试套件、指向已删除 id 的用例）。只要它挡在「功能完整」前面，就一并修掉再报告结果，
而不是列出来问「要不要我顺手改」。

## 「完整」包括服务端那一半

2026-09-19 重做体验类状态的云端/本地这一层时，我给出的方案写着「协议不动、服务端不动，
只在客户端补脏标记」。用户回了一句：「**要做就做完整的服务**」。

所以在看盘里，「功能做完整」不只是横向的（入口别丢、残留问题一并修），还是**纵向的**：

- **一个跨端功能要端到端做完**：iOS 客户端、`Backend/kanpan-api`（Rust）、以及两边之间的
  协议与字段白名单，都是同一个功能的组成部分。只改客户端那一半不算做完。
- **两端各有一份清单时，必须对账**。这次就是活例子：客户端的同步字段白名单
  （`Prefs.syncedFieldNames`）比服务端 `src/sync.rs` 的 `valid_field` 多出十九个字段，
  而服务端对含未知字段的操作是**整条拒绝**，于是那条操作永远推不上去、还把队列堵死。
  两份清单分别看都「没错」，只有放在一起比才看得出来。
- **所以设计跨端改动时，先把两端的约束都读一遍再下结论**，不要默认「服务端已经支持」。

这条是 kanpan-backend-rust（后端一律 Rust、要加功能就去 kanpan-api 写）的补充：
那条说「改哪儿」，这条说「什么时候必须去改」。
