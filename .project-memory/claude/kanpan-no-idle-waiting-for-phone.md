# kanpan-no-idle-waiting-for-phone

**项目约定**：看盘里不许开空等的后台轮询——真机锁着就跳过装机、活干完就结束回合；不要阻塞在 until grep 日志标记上，也不要用 tail -F 这类不会自己结束的 Monitor 盯测试，收尾前必须停掉自己起的所有后台任务

2026-09-20 我把 VWAP 三把画线工具做完、推上远程之后，按闭环去装 Release 真机包，
`devicectl` 报「device was still locked」。我开了一个后台循环每 30 秒重试一次、等了
二十多分钟，还再开了第二轮。用户回来先说「不用等 iphone 了，目前手机不在身边没法解锁，
暂时跳过就行」，紧接着又说「**把相关等待手机解锁的全部清除，另外已经完成的窗口不准
消耗 token 空等待**」。

同一天晚上他又在手机上看到一个后台任务跑了 4 小时还在 Running，问「这个是什么运行这么久」
「会不会消耗了很多 token，没结果直接终止，**这明显不正常**」。查下来是我派的实现子代理
自己留下的：它把 UI 测试重试脚本扔到后台写日志，然后自己阻塞在
`until grep -qE "DONE-OK|DONE-TESTFAIL|DONE-GAVEUP" <log>; do sleep 15; done`；
那个脚本在第一次尝试就因为别的窗口的编译错误死了，DONE 标记永远不会写出来，于是子代理
从 19:18 一直挂到 23:17，直到我 kill 掉那个 shell 才收尾。

所以在看盘里：

- **手机锁着或不在身边就一次报错、直接跳过装机**。在最终汇报里写清「包已打好在哪、
  没装上、下次解锁后装」即可，不要开轮询 / 重试循环去等它解锁。用户不一定在电脑旁，
  手机也未必在他身边，这种等待多半是白等。
- **活干完就结束回合**。不要用后台任务、ScheduleWakeup、Monitor 让一个已经完成任务的
  窗口继续活着「等某个外部条件」。有事用户会再开口。
- **绝不要阻塞在「轮询别的进程写出的哨兵标记」上**。这种等待的失败模式是静默的：生产者
  一死，等待方就永远等下去，看起来和「还在跑」一模一样。要等某个后台命令，就用会自己
  退出的那种等待，并且判据里必须覆盖失败路径，不能只认成功标记。
- 空等的直接 token 开销其实接近零（阻塞的 shell 不调模型），但用户在意的是**它看起来
  像没结果就被终止、像出了故障**。所以即使不烧钱也不许留。

这条是 kanpan-dont-ask-just-ship 里「闭环的最后一步是真机包」的补充：那条说要装机，
这条说装不上的时候怎么收——跳过并说明，而不是等。

## 2026-09-29：等「exit=」标记的循环空转了九个小时

用户看到会话里挂着两个后台任务，问「怎么还有两个后台任务一直在运行」。查下来是 09-28 第二阶段
那一轮起的两个 `until grep -q "^exit=" …; do sleep 15/20; done`：等的标记是自己想当然写的，
被等的脚本实际只打 `rc=`（或者根本不打），于是两个循环一直空转到第二天才被发现。

所以起任何「等某件事结束」的后台命令时：

- **优先直接 `run_in_background` 跑那条命令本身**，它结束时自然会通知，用不着再起一个循环去等它。
- 真要写等待循环，**必须带上限**（例如最多等 N 分钟就退出并打印「超时」），并且匹配的标记
  要先 grep 被等脚本的源码确认它真的会打。
- **派出去的子代理收工后、以及自己收尾前，都要 `ps` 一眼有没有残留的 `until` / `sleep` 循环**，
  有就杀掉（父进程是会话本身，看门狗的 zombie-gc 不会清它们）。

## 2026-10-02：第三次——`tail -F` 的 Monitor 测试跑完了还挂着

跑 iOS UI 测试时，我除了用 `run_in_background` 跑测试脚本本身，又另起了一个 Monitor
（`tail -F <log> | grep …`）去看逐条结果。测试 262 秒就跑完了、提交也推了，但 `tail -F` 永远不会
自己退出，那个 Monitor 一直以「iOS UI test results…」的名字挂在后台。用户问
「**怎么后台有个测试一直在跑，经常出现这种问题**」——「经常」说明他已经烦了好几次。
同一次还查出一个 9 天前留下、父进程已死的 `tail -f cb7.log`。

所以：

- **已经 `run_in_background` 跑了命令，就不要再叠一个 Monitor 去盯它的日志**——那条命令结束时
  自己会通知，结果收尾时再 grep 日志即可。
- 非要用 Monitor 盯一个有终点的任务，命令必须在终点自己退出（循环里检测被盯进程已退出就 `break`），
  不许用 `tail -f/-F` 这类永不结束的源。
- **回合结束前必做一步**：把自己起的 Monitor / 后台任务全部停掉（TaskStop，或按 pid kill），
  再 `ps` 一眼确认没有 `tail -f`、`until`、`sleep` 残留。看起来像「测试还在跑」的东西，
  用户就会当成故障。
