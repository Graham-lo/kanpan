# kanpan-look-up-how-others-solved-it-first

**项目约定**：看盘里碰到已经有成熟行业做法的机制（同步、冲突解决、缓存分层等），先联网查主流方案怎么做再设计，不要凭空自创一套

2026-09-19 设计「体验类状态云端/本地」这一层时，我自己推了一套「哨兵 + 脏标记」的结构，
用户连着点了两次：先是「**很多 app 都是这么做的**」（指缓存分层与「只清可再取的数据」），
接着是「**本身同步就要有标识啊，你可以联网查主流云端和本地怎么做的**」。

所以在看盘里，凡是碰到**已经被业界解决过很多遍的通用机制**——数据同步、冲突解决与合并、
离线优先、缓存分层与淘汰、增量拉取、幂等重试这一类——正确的顺序是：

1. **先联网查主流实现怎么做**（CloudKit / Firestore / Dropbox / Realm / CRDT 那些公开的设计，
   以及它们各自的同步元数据长什么样：修订号、变更令牌、版本向量、tombstone、ETag 之类）。
2. **再挑一套对得上看盘规模的**，说明为什么选它、放弃了什么。
3. **最后才动手设计**。

不要拿自己现推的方案直接开工——用户的判断是「这类问题已经有标准答案了，你去看一眼比自己想强」。
这条和 kanpan-references-are-for-absorbing-not-cloning 是配套的：**查是为了吸收成熟做法的骨架，
不是整套照搬**；查完仍然要按看盘自己的规模（几个人在用、iOS 原生、离线优先）裁剪。

反过来也成立：如果我给出的方案里出现了「业界通行但我没提」的部件（比如同步必须带版本标识），
那说明我跳过了第 1 步。
