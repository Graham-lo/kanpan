# kanpan-parallel-codex-threads-per-feature

**项目约定**：看盘里独立的功能可以并行做，但不许每个功能挂一条自己的长命分支——所有改动小步直接进 main；用户 2026-09-23 明说「别搞得每个功能都是独自的分支」，推翻了 09-22「一功能一 worktree + 分支」的做法

2026-09-22 用户说「可以分开并行的功能单独开 codex 进程即可」，我据此给每个功能开了一个 worktree
和一条分支（`multi-exchange`、`compare-kline`、`alert-sound`、`indicator-set`……），约定按阶段 ff 合回 main。
结果到 09-23 凌晨一盘点：`indicator-set`（用户定稿的画线砍到 12 把、指标换新）、多交易所阶段 1、
对比 K 线阶段 1 全都挂在各自分支上没进 main，别的线程照着 main 上的旧交接书差点去做已经作废的
枢轴点和净流入；多交易所阶段 1 的后端甚至从没合入的分支部署上线、又被别的部署覆盖。
用户看到后先说「你先把代码合进去，还有哪些分支代码没有合并」，接着说：
「**别搞得每个功能都是独自的分支**」。

所以现在的规矩是：

- **并行仍然可以**（用户宁可多开几路也不要排队），但并行的单位是「一路实现者」，不是「一条分支」。
- **没有长命的功能分支。** 每一路做完一小段、构建与受影响测试全绿，就 rebase 到 `origin/main`
  直接推 main；分支/worktree 只作编译隔离用的临时工作区，推完即弃，不在上面攒提交。
- 我接手或开工前先查一遍 `git for-each-ref` 里有没有「有提交但不在 main」的分支；有就先合进 main，
  合完删分支、收 worktree，再派新活。
- 交接书、验收报告都以 main 为准；一份决定（比如某项作废）如果只写在某条分支的文档里，
  等于别人看不见。
- 永不 force-push main；只提交自己动过的文件。

同日（09-22）用户把此前不做清单里的三项翻成要做：多交易所 / Coinbase 现货、对比 K 线、提醒铃声。
「不做清单只有用户能推翻」这条规则没变。
