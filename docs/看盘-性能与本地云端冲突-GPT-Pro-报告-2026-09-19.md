## 第一章：性能

### [阻断] A1：冷缓存的元数据请求等待全市场串行刷新，查询一个品种也不能提前返回

位置：Backend/kanpan-api/src/market_meta.rs:49–55；498–543；568–656；market_meta.rs 中的 meta() 请求入口。

机制：supply_table() 在已有旧缓存时能够立即返回，并把刷新放到请求之外；但缓存完全为空时，直接 await refresh_supply()。refresh_supply() 依次请求币种来源、CoinGecko 分页、合约分类，再等待 refresh_equities() 逐个抓完股票页面，最后才 store(Market)。股票循环每个合约还有固定的 LISTING_GAP = 200ms，单页失败时另有重试。请求里的 symbols 过滤发生在完整表取得之后。

启动预热并没有消除这个等待窗口：spawn_refresh() 自己刷新，冷请求也自己刷新；冷分支没有复用预热中的同一项任务。即使只有一个用户，也可能和启动任务重复抓取全表。

触发场景：服务端刚重启、进程缓存尚未建立；手机对目标品种也没有可用的元数据缓存。用户打开 BTC 或一只股票的详情，价格可能已经通过直连行情出现，但市值等元数据持续空白或请求超时。仅以 50 个待处理股票合约作为示例，循环固定间隔就有 10 秒，尚未计算所有网络等待及 CoinGecko 分页间隔。50 是说明机制的输入，不是对线上当前合约数量的断言。

证据：缓存只保存在进程的 RwLock<Option<(Instant, Arc<T>)>>；冷分支同步等待完整刷新；股票逐个 await 后 sleep(LISTING_GAP)；全部完成才发布缓存。这是代码可以推导的请求等待，实际生产耗时未测量。现有解析器测试不能覆盖"启动任务进行中时第一个请求到达"的调度问题。

建议：保留当前连接复用、上游节流和旧缓存立即返回机制；让启动、冷请求、过期刷新共享一个进行中的刷新任务。为完整、已验证的 Market 增加小型持久化快照，启动先装入上一份可用结果，再更新。不要为了提前返回而把尚未分类的股票当成同名币种。元数据仍与直连 K 线启动并行，不新增任何"等元数据再连 WS"的前置条件。

用本地假上游测试"预热中请求到达""仅查一个品种""某股票页面超时"，记录 meta_request → cache_hit/cold_wait → first_response。无需线上压测。

### [重要] A2：每次个人改动都在主线程等待整份同步存档重写，离线积压会放大手势结束时的停顿

位置：Kanpan/Kanpan/Account/AppAccountBridge.swift:302–331；KanpanAccount/Sources/KanpanAccount/SyncStore.swift:64–117；Kanpan/Kanpan/Main/AppLifecycle.swift:107–120；KanpanAccount/Tests/KanpanAccountTests/PerfBenchmarkTests.swift:36–79。

机制：capture() 虽然先把编码和写盘交给 ArchiveWriter，随后却立即调用 sync.flushNow()；flushNow() 最终执行共享串行队列的 queue.sync {}。调用方处在 MainActor，所以用户这次修改必须等前面所有排队写入完成。写入内容是整个 SyncArchive，包括已下载对象、本地对象和待发操作，而不是本次修改的几个字段。

离线期间连续产生 n 条操作，每次都把更长的操作数组重新编码、写盘；仅累计队列部分就形成约 1 + 2 + … + n 的重复处理量。这个结论不依赖用户数量。它也说明代码注释里的"几百字节小 JSON"不能作为所有使用阶段的规模假设。

触发场景：用户离线或关闭自动同步，累积大量设置、画线修改；之后继续编辑并松手，或切到后台触发 .data → .sync 排空。可见停顿发生在主线程等待持久化的位置，而不必发生在图表绘制函数里。

证据：主线程阻塞位置和整档重写机制静态确定；是否已超过帧预算、具体多少毫秒，属于未验证推测。现有 testSyncStoreCapture30() 在循环 capture() 后就结束计时，没有把 flush()／flushNow() 包进测量，因此主要量到排队和内存工作，不能代表 App 真实等待路径。

建议：不要撤销 45aac37 加回来的耐久性保证，也不要简单改回"延迟几百毫秒再写"。优先与 B2 的修复统一：把小型、可恢复的个人修改事务／操作日志先可靠提交，完整快照随后按序归并。保留 .data 先于 .sync 的顺序，不把网络请求放进持久化临界区。

验证使用 Time Profiler + File Activity／System Trace，分别给 capture、编码、写入、drain 加 signpost；用临时目录测试不同存档和积压规模，记录主线程等待的 p50、p95、最大值。基准结束前必须真正排空写队列，并把"入队耗时"和"耐久提交耗时"分开报告。

### [重要] A3：近期 OI 归档的临时 404 被无限期记进内存，稍后发布的数据仍不会重新获取

位置：Backend/kanpan-api/src/oi_archive.rs:44–47；377–430；434–462。

机制：代码正确地区分了"刚结束的一天尚未发布"与"历史上确实没有数据"：只有超过 SETTLED 才写永久的 .none 文件。但是同一 404 分支在这个条件之外，无条件执行 remember(stem, Day::Absent)。内存 Memory 没有时间戳或 TTL，cached() 命中后立即返回 Absent。

因此，"不把近期缺失持久化"并没有解决进程内的负缓存问题。该缺失只有在 FIFO 容量淘汰或进程结束后才可能重新查上游；不是过了发布等待期就自动恢复。

触发场景：昨天刚结束、归档还没上传时，用户打开跨日的 OI 图，服务端收到 404。过一段时间上游已经发布该文件，用户再看同一段或手机重新请求，仍得到同一天的空缺；这一期间内存项未被淘汰。

证据：SETTLED 只包住 mark_absent()，没有包住随后的内存 remember()；Memory 仅存 Day，读取时不做时间判断。这是缓存正确性缺陷，实际缺口持续时间未在生产测量，不能写成"必然永远缺失"。

建议：近期缺失使用短期负缓存及到期重试，或在确认稳定之前不进入永久形态的 Absent；已稳定的历史缺失仍保留现有负缓存，正缓存、预热、16 路请求并发都不必撤销。只重查近期缺失日，不重新拉完整年份，因此不会让已有图表首屏或连接建立变慢。

增加本地假时钟／假上游测试：首次返回 404，时间推进且上游改为 200，确认不依赖服务重启、内存挤出或用户清缓存也能补齐。

### [重要] A4：只剩一根 K 线时，增量更新跳过第 0 根，MA 状态会与全量结果不同

位置：KanpanCore/Sources/KanpanCore/Indicator/IndicatorEngine.swift:68–83；KanpanCore/Sources/KanpanCore/Indicator/IncrementalLines.swift:24–46；KanpanCore/Tests/KanpanCoreTests/IndicatorIncrementalTests.swift:8–118；KanpanChart/Sources/KanpanChart/ChartRenderer.swift:56–72。

机制：updateTail() 把起点固定下限设成 max(1, …)。当序列只有一根时起点是 1。SMA 的 sum[0] 已经是有限值，canTail(from: 1) 返回真，但 recompute() 的 1..<1 是空区间，于是这根 K 线的新收盘没有进入累计和。

这不仅是当前值没变。后续追加时，累计和继续从旧的 sum[0] 接算，错误可以延续到均线开始出值之后。渲染器对同前缀末根更新、单根追加都会选择增量路径，因此不是一个完全没有调用方的内部接口问题。

触发场景：新上市或历史极短的品种只有一根 K 线；用户的 MA 参数包含 1，末根收盘由 100 变成 110，MA 仍显示 100。更常规的 MA(5) 场景是：先把唯一一根从 100 改为 110，再追加四根收盘 100 的 K 线；错误累计和得到 100，全量应为 102。后续 REST 全量替换可能修正它，但不能把那次重新加载作为正确性保证。

证据：隔离 Swift 样本实际得到：MA(1) 增量 100／全量 110；按短序列尾部调用序列追加至五根后，MA(5) 增量 100／全量 102。该样本提取了 SMALine，没有运行完整 App 或完整指标测试套件。

现有短序列测试虽然包含 n=1，但使用默认参数，只修改一次就结束；多条输出此时仍是 NaN，未继续追加到首次有效输出。随机长期测试又从数百根开始，因此挡不住这个暖机边界。

建议：显式处理可变化的第 0 根：当首根仍是末根时，从 0 正确重建受影响的种子，或对此极短状态走全量。不要改变 AICoin 的公式、浮点运算顺序或改成近似均线。新增"单根修改 → 连续追加到指标首次出值"测试，覆盖 MA(1)、MA(5) 以及 ATR 首根输入等相同边界；不能只比较全 NaN 的阶段。

### [建议] A5：指标的公开结果与增量状态共享整列数组，尾部算术不等于尾部内存成本

位置：KanpanCore/Sources/KanpanCore/Indicator/IndicatorEngine.swift:68–83；119–190；KanpanCore/Sources/KanpanCore/Indicator/IncrementalLines.swift:9–46。

机制：引擎同时持有 states 与 values，State.result 把内部 out 数组放进公开结果。更新又通过 for (id, var st) in states 取得值副本，修改状态中的数组，再覆盖 states[id] 与 values[id]。旧结果仍持有数组存储时，Swift 写时复制需要分离整列，不是只复制被改的尾巴。

因此应区分两个复杂度：递推算术可能只处理末尾 K 根；数组所有权和结果快照仍可能带来随历史长度 N 增长的复制与分配。不能仅凭尾部循环短，就宣称整个 updateTail() 的成本与 N 无关。

触发场景：长历史、多条指标线、连续行情更新。用户看到的表现若有问题，应是更新时分配量／主线程负担增加，而不是缓存键字符串突然成为首要瓶颈。

证据：输出数组的共享路径由代码可见；优化构建下具体发生多少次复制、是否影响帧预算，属于未验证推测。本次没有把它评成阻断。cacheKey 操作的是有限的指标名与参数，而不是扫描历史 K 线；在现有合帧机制下，没有证据把字符串拼接排在这个问题之前。

建议：先用 Allocations + Time Profiler 对固定参数、不同历史长度做 Release 对比，观察 memcpy、数组存储分离和分配字节数，而不是只看算术循环。证实后再调整结果所有权：减少同一批输出在可变状态与公开快照中的重复持有，按发布批次建立只读结果。不要通过不安全共享可变数组破坏 Sendable 或值语义，也不要为省内存砍历史缓存。

### [建议] A6：十字线移动仍会重建几何缓存并写回主屏状态，分层绘制没有隔离掉全部高频工作

位置：KanpanChart/Sources/KanpanChart/ChartView+Gesture.swift:407–423；KanpanChart/Sources/KanpanChart/ChartRenderer.swift:27–43；79–114；KanpanChart/Sources/KanpanChart/ChartRenderer+Layers.swift:35–45；Kanpan/Kanpan/Main/MainScreen.swift:126–139；809–848 的 ChartHost 十字线回调接线处。

机制：十字线每次移动会赋值 ChartView.state 并回调 onCrosshairChanged。ChartRenderer.recalc() 对任何 state 变化都新建 GeometryCache，所以虽然指标输入没有变化、不需要重新算指标，布局、价格范围、隐藏输出掩码等缓存仍失效。开启隐藏指标输出时，下一次访问还会重新构造整列 NaN 掩码。

与此同时，十字线回调写入 MainScreen 自己的 @State crosshair，不是只更新独立的十字线读数子视图。它把高频交互重新带回了主屏 SwiftUI 的更新范围。这里必须区分"body 重新求值"和"所有像素重画"：代码证明的是前者的失效入口，不足以证明后者。

触发场景：用户持续拖动十字线，尤其有多副图、隐藏输出时，指标不变却重复准备几何；主屏也持续收到交互状态变化。

证据：新建缓存与回调赋值路径静态确定；是否已造成可见掉帧属于未验证推测。仅凭 MainScreen 有一千多行不能证明它慢，因此只列建议，不以文件长度定罪。

建议：按数据／布局相关输入的版本保留可复用几何缓存；十字线、倒计时等不影响几何的变化不要清空整只缓存。保留旧状态副本的隔离，不能简单复用一只可变缓存而造成串状态。把十字线读数下沉到只由价格行／读数容器观察的交互模型，主屏保留导航和布局状态即可。

使用 Time Profiler、Animation Hitches，并给十字线回调、主屏 body、computeLayout、priceRange、blankLine 加计数／signpost；量清一次手势触发多少次工作后再改。无须改绘图口径、图层视觉或网络节奏。

## 第二章：本地／云端冲突

### [阻断] B1：离线删除后撤销会组成必败批次，409 恢复逻辑又先重发旧批次，整个账号队列无法前进

位置：KanpanAccount/Sources/KanpanAccount/SyncStore.swift:137–153；179–193；Kanpan/Kanpan/Account/AppAccountBridge.swift:383–510；Backend/kanpan-api/src/sync.rs:84–91；123–169；KanpanAccount/Tests/KanpanAccountTests/StorageTests.swift:44–66。

机制：删除与恢复具有版本依赖，但客户端直接从队列取前 100 条一起发送。操作创建时的 baseRevision 来自当时的云端对象；离线删除尚未收到 ACK 时，随后的恢复仍使用删除之前的 revision。

服务端在一个数据库事务里逐条合并。删除会推进 revision，恢复却要求 base_revision == object.revision，所以同批恢复失败，整批回滚。客户端只在 catch 中设 needsBootstrap = true；下一轮 .full 仍先执行推送循环，之后才 bootstrap。相同 409 因而一再发生，永远到不了用来修复它的拉取阶段。

触发场景：设备 A、B 已同步一条画线，云端 revision=4、generation=0。A 离线删除该线，随后撤销；B 不做修改。A 重连后发送：

| 同批操作 | 创建时 base／generation | 服务端逐条结果 |
|---|---:|---|
| 删除 | 4／0 | 暂时得到 revision=5、deleted=true |
| 恢复 | 4／0 | 要求 base=5，返回 `resync_required` |

事务回滚到 revision=4。A 重试同一批仍失败；后续对设置、自选的修改也堵在后面，B 收不到。另一类触发是 A 离线期间 B 删除并恢复同一对象、推进 generation，A 带旧 generation 重连；恢复闭环相同。

证据：版本条件、批次选取、事务边界与推送先于拉取的顺序共同构成确定性失败路径。隔离状态模型重放得到相同 409／回滚，但没有代替实际 axum 集成测试。

现有 offlineDeleteThenUndoRetainsExplicitRestoreAfterRestart() 先单独 ACK 删除，再检查恢复的 base 被推进。真实批量发送在两者之间没有这个 ACK，测试恰好绕过了失败条件。

建议：批次编排识别删除／恢复／代次变化的依赖边，让依赖操作等待相应前置结果；互不依赖的对象和补丁继续批量发送，不要把全部同步退回逐条跨洋请求。遇到 resync_required 进入明确恢复状态：先取得对象、generation 及必要回执，再保留并重放本地意图。对结果不明的已发送操作，不得直接改原 ID 的载荷；确认被拒后，需要重建载荷的操作使用新 ID，并保留原始意图记录。

新增离线删除＋撤销同批、删除＋恢复＋继续编辑、B 跨 generation 修改三个本地集成用例。恢复不能靠清空队列、退出账号或用户重置。

### [阻断] B2：画线先写入正式文件、同步操作后写入另一文件，崩溃窗口后的启动对账只保护设置

位置：Kanpan/Kanpan/Drawing/DrawingController.swift:125–153；Kanpan/Kanpan/Account/AppAccountBridge.swift:230–259；302–331；KanpanAccount/Sources/KanpanAccount/SyncStore.swift:64–95；194–212。

机制：画线控制器先保存 draws.json，然后通过 onArchiveChange 让桥接层生成、保存同步操作。这是两个文件的两次提交。flushNow() 缩小了第二次提交之后的风险，却不能让两次提交变成原子事务。

进程如果在 draws.json 已提交、sync-v1.json 尚未持久化新操作之间结束，重启会读到"新画线文件＋旧同步档"。prepare() 只为 archive.local 中缺失的对象填初值；已经存在的旧画线对象保持旧值。随后那段脏标识／ChartLayoutReconcile 对账只处理 settings，没有给既存画线补出操作。拉取时又因为没有待发操作，云端旧对象进入 local，最终由 applyPending() 覆盖正式画线文件。

触发场景：A、B 已同步趋势线 L。A 移动 L 的端点，新的几何已写进 A 的 draws.json；在同步档提交之前 App 被杀。B 没改线，仍持有原几何。A 重启并同步后，新端点回到旧位置；新几何并非没有落盘，而是落盘后被恢复流程覆盖了。

证据：保存回调的先后顺序、两个独立文件，以及启动时"只对 settings 做既存对象差异对账"均由代码可见。本次未对 App 实施故障注入，但上述明确中断点能够推导状态结果。现有存储测试多数先 flush() 再重开，只证明完整落盘后的可读性，不能证明两文件之间被杀的恢复正确性。

另一个相关事实是：ArchiveWriter 保存错误供下一次 transaction() 提取，flushNow() 本身并不返回最新写入错误。因此"排空完成"也不能直接等同于"最后一份已成功保存"。

建议：建立账号目录内的可恢复个人修改事务：正式值变化和相应待发意图必须在同一提交记录中出现，再从该记录生成／更新各快照。也可以使用系统 SQLite 的本地事务，但不需要新服务或重型依赖。崩溃后按提交记录向前恢复，不回滚成云端旧值。

过渡修复至少给画线增加启动差异对账，明确区分本地未提交修改、服务端 tombstone 和显式 restore；不能把所有磁盘旧对象无条件重新上传。用临时目录在每次文件提交边界注入中断，并补"最后一次写入失败后立即 flush／重启"的错误可见性测试。

### [阻断] B3：清空标注文字是合法本地操作，却被服务端拒绝，隔离流程随后把旧文字覆盖回来

位置：KanpanCore/Sources/KanpanCore/Drawing/Drawing.swift:193–275；Kanpan/Kanpan/Account/PersonalSyncCodec.swift:84–108；KanpanAccount/Sources/KanpanAccount/SyncStore.swift:137–172；Backend/kanpan-api/src/sync_validation.rs:35–40；99–105；Kanpan/Kanpan/Account/AppAccountBridge.swift:435–453；520–551。

机制：Drawing 允许空文字，但编码时省略空 text。SyncStore.stage() 发现先前存在的键被省略，便发出 text: null，表示删除该字段。服务端 null 白名单却只有 color、groupId 及若干嵌套字段，不包含 drawings.text，因此整个操作被判为 400。

隔离并非只停止重试：quarantine() 删除操作后，在同对象没有其他待发操作时，把 archive.local[key] 退回 archive.objects[key]。设置还有 SettingsStamp 可保住脏字段，画线没有同样的保护；applyPending() 将旧云端文字重新写回。

触发场景：A、B 都看到同一条标注"顶背离"。A 把文字全部删掉并结束编辑；B 不做修改。A 上传的是 text:null，被拒绝并隔离；下一次允许应用时，A 的"顶背离"重新出现，B 也始终保留旧文字。同一被拒操作里别的合法画线修改也可能一并回退。

证据：这是客户端编码、差分、服务端校验和隔离应用之间的完整链路，不是抽象"未来协议不兼容"。同一字段另有已核验的合法输入不一致：客户端上限是 60 个 Swift Character，服务端上限是 240 个 UTF-8 字节。隔离 Swift 样本中，11 个家庭组合 emoji 是 11 个 Character、275 字节，足以触发拒绝。服务端"240 字节覆盖任意 60 字符"的注释对组合字符不成立。

已有文字测试覆盖短中文和超长 ASCII，没有覆盖"非空→空"、组合字符和"拒绝→隔离→再次应用"的终态。

建议：明确空文字的线协议：可以总编码空字符串，或接受 text:null 并在接收端解释为空；统一字符／字节限制，并兼容已经保存的合法内容。更关键的是，拒绝记录要与用户原始意图一起持久化，不能用"从活动发送队列隔离"代替"用户撤销修改"。让坏操作不堵其他对象，同时保留待修复状态；服务端修复后能重新生成有效操作，无需用户再输入一次。

### [重要] B4：applyPending() 会留下半应用状态，并在真正成功之前清掉重试标志、记录同步时间

位置：Kanpan/Kanpan/Account/AppAccountBridge.swift:488–502；515–581；Kanpan/Kanpan/Drawing/DrawingController.swift:145–153；PrefsStore.applySynced() 与 PersonalFileStorage 的非抛错写入接口。

机制：进入 applyPending() 就把 pendingApply 设为 false，接着先应用设置，再解码画线偏好和画线，之后执行可抛错的 drawings.applySynced()，最后才重建分组、自选。后半段解码或保存失败，已经生效的前半段没有回滚。pendingApply 又不再为真，关闭面板触发的 resumeApply() 不会替这次失败补跑。

此外，lastSync 在调用 applyPending() 前就已经写入同步档；完成下载与完成可见状态提交没有被分别记账。设置存储有另一个需要纳入事务的边界：某些写入以存储对象的 error 状态报错，而不是通过此函数的 throws 统一传播。

触发场景：A 修改设置、画线、自选并上传。B 拉到响应，先应用新设置；保存新 draws.json 时出现可注入的磁盘写入错误，函数提前退出。B 看到新设置，但仍是旧画线、旧自选；关闭面板也不会由 resumeApply() 自动补齐。这里不需要假设云端发来故意损坏的数据，正常文件写入失败就足够。

证据：应用顺序、抛错位置、提前清标志和提前更新 lastSync 均由代码确定。本次未执行完整 UI 故障注入。已有空 styles 解码测试只能封住 76e658d 那个具体入口，不能证明其后所有步骤不会失败。

建议：分成"准备候选状态→耐久提交→发布可见状态"三阶段。先在不修改各 store 的情况下完成所有解码、校验和引用关系检查；再使用 B2 的账号级事务／提交代次提交；最后在 MainActor 上发布同一代次的状态，提交期间禁止跨模型回调观察中间态。失败保留待应用记录，下载完成时间与本地应用完成时间分开。

单纯加 do/catch、换应用顺序或包一层 SwiftUI withTransaction 都不构成文件事务。测试应对每个解码／写入点注入失败，核对内存、磁盘、待应用状态和用户看到的代次只能全旧或全新。

### [重要] B5：ACK 把旧的未发送操作抬到新云端 revision，冲突结果会因是否跨过 100 条批次边界而改变

位置：KanpanAccount/Sources/KanpanAccount/SyncStore.swift:179–193；Backend/kanpan-api/src/sync.rs:95–110；Kanpan/Kanpan/Account/AppAccountBridge.swift:417–432；KanpanAccount/Tests/KanpanAccountTests/StorageTests.swift:24–43。

机制：acknowledge() 对同对象的所有未发送操作，直接把 baseRevision／generation 推进到 ACK 返回对象的版本。这个对象可能包含设备 B 的并发修改，而 A 创建后续离线操作时根本没有见过该版本。

服务端又把 op.base_revision >= old.revision 当成因果先后，短路跳过时间戳比较。于是"传输上晚发"被误当成"用户已观察新版本后再次修改"。

触发场景：A 离线连续改同一设置，例如取值均在合法范围内的 barSpacing；这些操作都早于 B。B 后来把该字段改为 B 值，云端字段 stamp 的 revision 为 1。A 重连时：

| A 的积压 | 发送与 ACK 路径 | 结果 |
|---|---|---|
| 100 条 | 全部在第一批，都是旧 base；时间戳小于 B | B 值胜出 |
| 101 条 | 前 100 条同上；第 101 条尚未发送，被 ACK 改为新 base | 第 101 条通过因果短路，把更旧的 A 值写回 |

B 没有因为 A 多积压一条就改变自己操作的时间或因果关系，最终赢家却变了。

证据：操作创建时间戳没有改变，改变的是 ACK 回写的 base。按实际比较条件建立的隔离状态模型得到：100 条时保留 B，101 条时变为 A 第 101 条。这是条件级重放，不是声称已经运行完整 Rust／Swift 联调。现有"未确认请求保持身份"测试检查了未发送操作推进 base 的行为，但没有放入 B 的并发字段修改。

建议：区分"这条操作依赖我前一条本地操作"和"用户实际基于哪个云端字段版本作决定"。只推进真实依赖需要的元信息，不把 ACK 里附带的全部远端状态变成后续旧操作的观察上下文。可以保留字段级基线或显式本地操作依赖；若产品要采用"本地离线意图总优先"，也必须明确、一致地实现，不能让 100／101 决定语义。

增加不同分批方式下最终状态一致的测试：1／99／100／101 条、不同无关字段交错、B 的并发更新、删除／恢复。这个修复应与 B1 的依赖编排一起设计。

### [重要] B6：合并后补推脏设置的调用必然被 applying 挡掉

位置：Kanpan/Kanpan/Account/AppAccountBridge.swift:302–304；329–331；520–535。

机制：applyPending() 先执行 applying = true，并通过 defer 在函数退出时复原。它在这个保护区内发现 prefs.stamp.isDirty 后调用 captureSettings()；后者最终进入 capture()，第一道 guard 就要求 !applying。因此这条"合并后反向推本地"的路径不会生成任何操作，和旁边注释承诺的行为相反。

触发场景：A 的某个设置保留脏标记，但已没有活动待发操作，例如此前操作被隔离或字段被旧服务端丢弃。服务端随后已能接受该字段，A 拉取并合并时保住了本地新值，却没有生成补推操作。B 继续看到旧值；A 不再主动编辑或重新触发别的捕获，就不会因为这次合并自动补齐。

证据：调用链里的布尔条件互相矛盾，静态即可确定；不需要 profile 或时序猜测。只测试 SettingsStamp 清脏／保脏不等于测试桥接层确实补出了待发操作。

建议：完成成功的本地应用、离开 applying 保护区后，再针对仍有效的脏字段捕获差异，且检查账号 epoch 未改变。与 B3 的拒绝记录配合，不能把永久不支持的字段做成马上重复提交的忙循环。补一个"脏设置＋空操作队列→bootstrap→无需用户再次操作即可产生有效待发项"的桥接测试。

### [重要] B7：routePolicy 被同步，但同一字段归类判据明确要求本机网络属性留在本机

位置：Kanpan/Kanpan/Settings/Model/PrefsFieldPlan.swift:7–20；59–93；Kanpan/Kanpan/Account/PersonalSyncCodec.swift:43–72；Backend/kanpan-api/src/sync.rs:42–54。

机制：字段计划把行情域名、线路开关定义为这台设备的网络属性，apiHost、streamHost、smartMarketRoute 也确实是 deviceOnly。但当前真正的直连／网关选择 routePolicy 却是 .synced，被编码上传、被服务端接受，并在本地干净时由云端覆盖；keepDeviceFields() 不会保留它。

这不是"应该增加自动线路切换"的建议，恰好相反：按现有归类判据，另一台设备不应替这台设备改网络选择。

触发场景：A 在自己的网络环境里选择网关并同步。B 原本选择直连，而且该字段已干净；B 同步后，存储的 routePolicy 变为网关，即使 B 没有操作线路选择。这一偏好覆盖由同步代码可证明；具体何时重建活动连接还取决于线路镜像／通知调用方，本条不把未实测的切线耗时算进严重度。

证据：表内存在直接的语义矛盾，且字段完整经过上传白名单与接收合并，不是未使用的旧键。现有穷举测试只能证明每个字段有分类，不能证明分类符合上方的产品判据。

建议：按本次委托给定判据，将 routePolicy 作为本机选择保存和保留。迁移原样保住这台设备当前选择，不重置成默认、不清除旧个人档案；停止新客户端对此字段的跨设备覆盖，服务端可继续识别它以兼容旧客户端。保留直连／网关两档、出厂默认直连和手动选择；该调整不增加连接等待，反而避免跨设备偏好覆盖诱发的非必要变更。

增加"A=网关、B=直连，各自同步后仍保持本机选择"的双档案测试。若将来另立明确的产品规则要求账号同步线路选择，需要同时改掉字段判据，而不是靠一行分类偷偷决定。

### [建议] B8：两端白名单测试仍在比较手抄副本，不能阻止下一次跨语言契约漂移

位置：Kanpan/Settings/Tests/KanpanSettingsTests/PrefsFieldPlanTests.swift:1–180；Backend/kanpan-api/src/sync.rs:34–81；sync.rs 测试 the_allowlist_is_what_ios_sends；Backend/kanpan-api/src/sync_validation.rs:1–39；Kanpan/Kanpan/Account/PersonalSyncCodec.swift:13–40。

机制：Swift 测试里有一份代表 Rust 的字符串集合，Rust 测试里也有一份代表 iOS 的集合。它们不直接读取另一端实际导出的字段／枚举。开发者只更新同一语言的实现和测试副本，另一端保持旧版，两边都可能绿。

此外，名字相等也不能约束 null、数值范围、组合字符长度、嵌套层级、空字典展开、对象依赖字段等行为。B3 是当前就存在的反例：text 名字两边都有，合法值／删除值却不一致。

触发场景：开发者新增指标或设置字段，更新 Swift 分类与对应 Swift 测试，忘记 Rust 校验器；A 保存的新偏好被丢弃或隔离，B 收不到。反方向只更新 Rust 接受范围，也可能让 B 的旧解码器无法接收。

证据：本次比对没有发现新的顶层 SETTINGS_FIELDS 漏项；问题是防回归机制仍非真实跨端检查，不是把 a161bb0 修过的 19 项再报告一次。反射穷举有价值，能挡"Swift 存储字段忘记归类"，但挡不住另一端忘记更新。

建议：继续以 PrefsFieldPlan／SymbolFieldPlan 为归类真源，由实际 Swift 类型与 IndicatorID、画线工具类型导出机器可读契约和测试样本，不再增加第三份手工清单。Rust CI 消费该产物，校验实际 allowlist／枚举／规则；Rust 合并后的真实 JSON 再交回 Swift 解码，测试往返。

样本至少包含默认值、最大合法值、非空→空、六个字典缺键、嵌套 tombstone、文字组合字符，以及删除／恢复依赖。生成产物可在 CI 检查是否与提交内容一致。跨语言不一致主要应由这种 CI 契约测试阻断；不能声称两个独立编译器会自动发现远端字符串差异。旧版本兼容用明确样本保留，不靠扩大范围后猜解码器能否接受。

## 对指定六个问题的直接回答

1. applyPending() 怎样做到要么全成、要么全不成？

不能只调换设置／画线／自选的应用顺序。需要先完整构造候选 PreparedPersonalState，再提交账号级持久化事务，最后发布一个可见代次。所有会抛错或通过 error 属性报错的步骤都应位于发布之前。失败留下待应用记录；成功后才推进"本地已应用"的 revision／时间。B2 的用户编辑事务与 B4 的远端应用事务应共享同一耐久边界，避免新加一套互不协调的写盘队列。

2. 两端字段、指标、嵌套路径现在是否一致？

当前顶层字段没有重新出现那 19 个缺项；服务端保留 styleID 是兼容旧档，不应误删。五类设置字典和第六类 styles 需要分开看：

| 拍平字段 | 路径形态 | 接收／清脏结论 |
|---|---|---|
| `params` | `params/MA` | 设置合并以完整本地编码为底；清脏映回 `params` |
| `hiddenOutputs` | `hiddenOutputs/MA` | 同上，映回自己的顶层字段 |
| `subHeights` | `subHeights/VOL` | 同上 |
| `subHeightOverrides` | `subHeightOverrides/VOL` | 同上 |
| `indicatorColors` | `indicatorColors/MA/0` | 三段路径的根仍是 `indicatorColors`，不是用末段去找本地字段 |
| `styles` | `styles/trend` | 属于 `drawingPreferences`，不是 SettingsStamp 的设置路径；当前 `DrawingPreferences` 自定义解码已给缺失字典默认值 |

对这六项，本次没有找到新的"空字典缺键必然抛错"反例。PersonalSyncCodec.apply() 先编码完整本地 Prefs，再覆盖实际收到的键；不能把网络缺键直接等同于合成 Codable 缺键。嵌套删除还应保留 tombstone 和明确的空容器语义，不能把字段缺失一概解释为用户清空。真正仍需修的是 B3 的值契约、B6 的补推入口和 B8 的跨端验证。依据：Kanpan/Kanpan/Account/PersonalSyncCodec.swift:13–56、Kanpan/Kanpan/Settings/Model/SettingsStamp.swift:109–153、222–293、KanpanCore/Sources/KanpanCore/Drawing/Drawing.swift:275–352。

3. 四元组、时钟与 base_revision 分别意味着什么？

| 情况 | 当前实际规则 | 审查判断 |
|---|---|---|
| 设备时钟回拨，操作确实基于当前字段版本 | `base_revision >= old.revision` 直接接受，不比较时间戳 | 因果上在后的修改不应只因时钟小而输，这个短路本身有合理用途 |
| 离线设备回拨，仍拿旧 base，与另一设备并发 | 时间戳较小的操作可能输；代码只限制未来上界，没有补足过去的时钟 | 可能丢掉用户以为更晚的意图，但不能单凭"LWW 有输家"就判 merge 错；应明确冲突反馈及时间语义 |
| 两设备同一毫秒 | 依次比较 logical、device UUID 字符串、operation UUID 字符串 | 可以确定性收敛，不代表现实世界的真实先后 |
| 重装后 logical 归零 | logical 只是时间戳之后的排序项；新设备身份／重新 bootstrap 的版本上下文同样重要 | 没有证据证明计数器归零本身导致所有修改永久失效；它也不是完整的混合逻辑时钟 |
| 设备时间过于超前 | 写入 stamp 的 timestamp 被限制为 `now + 300000ms` | 将未来优势限制在约五分钟，但不等于已解决时钟漂移 |
| 未观察 B 更新的离线操作，被 ACK 人工推进 base | 绕过正常时间比较 | **这是已发现的真实语义缺陷 B5**，不能用"确定性 LWW"掩盖 |

还有一个语义边界：响应中的 droppedFields 表示未知字段被丢弃，不表示 LWW 竞争中所有字段都取了客户端值。服务端接受一条操作并返回当前对象，并不承诺该操作每个字段都赢。建议记录明确的 accepted／superseded／rejected 原因，区分正常冲突与协议拒绝；不能把全部 ACK 一律解释成"用户修改原样落云"。依据：Backend/kanpan-api/src/sync.rs:84–112、KanpanAccount/Sources/KanpanAccount/SyncStore.swift:137–153、179–202。

4. 长时间离线和重连是否可靠？

普通旧 base 的 patch 会按字段 stamp 竞争，不能简单描述为整份覆盖；已发送但结果不明的请求保留 ID／载荷也是正确方向。但删除、恢复、generation 变化和批次 ACK 的依赖处理不完整，分别对应 B1、B5。当前 needsBootstrap 只是一个意向标志，不是一套能够越过失败队列的恢复状态机。

5. 档案切换是否会把 A 数据带进 B？归类还有什么问题？

已读正常路径中，目标账号先准备自己的目录，切换时更新 epoch／taskID、取消旧同步任务，并把设置、自选、画线、搜索和复盘存储一起换过去。没有找到足够证据报告"普通切 A→B 必然串号"；也不把访客认领机制本身当成串号。这个结论不覆盖所有可能的 keychain／文件故障组合。

字段归类按以下维度复核：图表、外观、指标、页面排序／展开／分类、板块选择、工具和复盘偏好属于手工习惯；自动 recents、viewScores、scoredAt 属于设备派生统计；legacySelectedGroup 已是迁移壳，其有效值进入 favoritesGroup。这些地方没有再次报告已修复的 8f6f883。仍存在的具体反例是 routePolicy，见 B7。 搜索历史当前按账号分开存放，不等于已经通过这五类 sync collection 跨设备同步，不应把这两个概念混淆。依据：Kanpan/Kanpan/Account/AppAccountBridge.swift:149–288、Kanpan/Kanpan/Symbols/SymbolFieldPlan.swift:33–60、Kanpan/Kanpan/Account/AccountFeature.swift:97–121、Kanpan/Kanpan/Settings/Model/PrefsFieldPlan.swift:59–116。

6. 写到一半被杀，存档会不会损坏或回退？

原子文件替换能避免把半截 JSON 当成完整目标文件，串行队列也能保持同一路径的写入顺序。这两点值得保留。但它们不自动提供多文件事务，也不保证在系统杀进程前一定收到 willTerminate，更不能把无错误返回的队列排空视为写入成功确认。

所以应分开回答：单文件半截内容不是本次最有证据的风险；多个完整文件停在不同代次、然后启动时回退用户数据，才是 B2 的关键。 设置已有启动对账，不能因此假定画线也被保护；B4 则是相同边界在远端应用方向的表现。

## 我认为最该先做的三件事

第一件：先打通删除／恢复的依赖编排和 409 恢复路径，同时固定冲突的因果语义

先修 B1，再把 B5 放在同一套状态机里验证。 B1 的触发只需要一个用户离线删除再撤销，不需要极端规模或罕见故障，而且会连带堵住整个账号的新操作。继续只加 needsBootstrap、扩大白名单或无限重试都没有用。验收条件应是同批删除／撤销可恢复，跨 generation 不丢本地意图，并且最终状态不随 100／101 条分批改变。

第二件：建立一次可恢复的个人状态提交，统一解决丢改动、半应用和主线程整档等待

把 B2、B4 和 A2 当成一个问题修。 当前为了防杀进程而同步排空整档，花了等待成本，却仍没有跨文件原子性。把用户值、待发意图、已应用代次纳入一个小型耐久事务，才能同时减少回退窗口和重复整档等待；仅把写盘挪到另一个队列，不是解法。设置、画线等文件继续留在 Application Support 的账号目录，缓存边界不变。

第三件：让拒绝操作真正"不堵队列但不丢意图"，并用真实跨端样本守住契约

先修 B3 的空文字／组合字符，并修 B6 的不可达补推；随后建立 B8 的跨端往返测试。 这是当前存在的合法用户操作，不是未来扩展假设。坏载荷可以退出活动重试队列，但用户已经做出的修改必须留下可恢复记录。把这条终态不变量放进测试，比再写一份"另一端字段清单"更能防住第十八、十九个同族 bug。

性能侧的 A1、正确性边界 A3／A4 可以作为独立的小修并行处理；不要在上述三个同步问题尚未封住时，先把工程精力投入缓存键字符串、换绘图库或调整已优化的连接建立流程。
