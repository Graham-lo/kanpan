# A．图表交互、视口与画线

## A.1 问题清单

### A-01 · P1 · 文字标注看得见，却没有对应的文字命中区域

**现象：**“我点在自己写的那句话上，选不中；只能去找当初落笔的那个小点。”

**机制：**`DrawGeometry.swift:70–103` 的 `hit` 只检查手柄、线段、填充多边形，完全不检查 `labels`。同文件 `.note` 分支只生成一个文字标签，默认手柄仍在原锚点。`ChartView+Drawing.swift:372–385` 直接调用这个命中结果，没有补充文字包围盒。于是长文本主体虽然画出来了，离锚点超过命中半径的部分并不可选。`Drawing.swift:309–325` 的通用 hitDraw 也不能弥补这一点。

**触发条件／最短复现：**放一个文字标注，写至少十个汉字；取消选中；点击距锚点超过 22pt、但确实位于文字内部的位置。应当选中文字，现代码没有对应命中体。

**确信度：确认。** 不需要把所有标签工具都推断为相同故障；这里用只有标签的 `.note` 已足以成立。

**建议：**文字排版输出同时提供真实可见文字区域，命中与绘制共用该区域。只扩大锚点半径解决不了长文本。

### A-02 · P1 · 选中大图形后，图形内部的其他线被整个选中体压住

**现象：**“我选了一个矩形，再点框里面另一条线，总还是选中这个框。”

**机制：**`ChartView+Drawing.swift:375–379` 注释说“选中手柄优先”，但实际调用的是整个 `g.hit(..., handleRadius: 22)`。`DrawGeometry.swift:80–101` 除手柄外还会命中线身、整个填充多边形。只要选中矩形／通道的填充体命中，就提前返回，根本没有机会遍历其他图形。问题不只是 22pt 偏大，而是**把手柄优先扩大成了整个图形优先**。

**触发条件／最短复现：**画一个大矩形，在内部画一条趋势线；选中矩形后点击内部趋势线中段。另一个最小例是选中图形手柄距离相邻线的目标点 15pt。

**确信度：确认。** 15pt 的两条普通平行线并非必然无法选择，见 A.4；大填充体优先才是确定的问题。

**建议：**先比较真正的手柄候选；非手柄命中回到统一的可见层级／距离仲裁。不要对选中物的全部填充体直接提前返回。

### A-03 · P1 · 捏合先抬一指、再抬另一指，会额外触发一次点击

**现象：**“我只是放大了一下，松手却多出一根十字线。”

**机制：**`ChartView+Gesture.swift:210–232`：捏合剩下一指时 `reset()` 把 `moved` 清为 0，并切成 `.pan`。若剩余手指没再移动就抬起，`245–254` 的轻点条件成立，进入 `handleTap`。此前 beginPinch 已清掉十字线，所以这一下一般会新建十字线，甚至触发只在新建时执行的 `onTapped`。

**触发条件／最短复现：**双指放大→抬左指→右指原地抬起；不要求明显时间间隔，只要 UIKit 分两次送结束事件。

**确信度：确认。** 两指恰好在同一次结束事件里全部抬起不触发；这也是普通 pinch UI 用例不稳定复现的原因。

**建议：**保留“本轮来自捏合”的消歧标记，剩余指可以继续拖，但原地抬起不能再解释为单击。不要破坏当前以剩余手指现位置接续的正确基准。

### A-04 · P1 · 回弹途中点停，再原地抬手，弹性空白可能永久停住

**现象：**“我拖到边缘松手，回弹时点了一下，图就歪在那个位置不回去了。”

**机制：**`ChartView+Gesture.swift:87–99` 任何按下都停止 `animation`；`settleView:551–560` 的回弹中间帧可以在硬约束之外。随后轻点、长按等结束分支 `245–270` 提前返回，没有 settle。`finishTouches:189–195` 确实会发出交互结束通知，但它不是视野约束收尾，不能替代 settle。

**触发条件／最短复现：**在左右边界拉出弹性空白→松手启动回弹→回弹未完成时点住→不移动抬手。把“回弹”换成正常 fling 不足以复现，因为 fling 每帧都经过 clamp。

**确信度：确认。** 具体残留像素数依赖停止时刻；明显空白才按当前严重度处理，不把不可见误差升级。

**建议：**最后一指离开时统一确保视野约束完成；轻点、轴点击和长按完成只能跳过业务分支，不能跳过几何收尾。

### A-05 · P2 · 切周期保住了根宽，却把正在看的历史右缘送回最新

**现象：**“我正在看前几天的走势，切到四小时，突然回到了今天。”

**机制：**`ChartHost.swift:223–248` 的 `.switchInterval` 调用 `ViewMath.switchInterval` 时传 `anchorRight: nil`；`Clamp.swift:65–71` 的默认锚点是新序列最新端。根宽来自现有／用户偏好，不等于历史时间锚点也被保留。

**触发条件／最短复现：**1h 图拖到明确不含末根的历史位置，记录右缘时间与根宽→切 4h。相同画布宽度和根宽下可见根数大体不变，时间跨度约变为四倍，但右缘改成新序列末根加半根；不会留在原历史日期。

**确信度：确认（行为）。** 按本委托“操作后保住刚看到的位置”应修；不把它描述成“切周期根宽一定丢失”。默认 rightInset=0 下稳定存在的未来留白本来就不成立，不能拿尚未回弹的空白当持久视口设计。

**建议：**区分正在跟随最新与历史浏览：前者对齐新末根，后者传入原历史时间锚点，并在新序列边界内钳制。根宽仍按人的偏好走。

### A-06 · P2 · 两指保持距离一起平移，图可能完全不动

**现象：**“我两根手指一起挪图，图不跟；先捏开一点才跟。”

**机制：**`ChartView+Gesture.swift:332–359` 在 `pinchActive` 之前只用两指距离变化 `abs(d - pinchD0) > 2 * panSlopPt` 激活。中点的移动量不参与激活条件，因此纯平移在入口即被 return。`362–370` 的平均绝对偏差对两指等价于两轴间距的组合，不能替代平移识别。

**触发条件／最短复现：**在历史窗口放两指，保持相互距离，整体横移 50pt。最新对齐模式还有额外的右缘锁定，测试此问题应先离开最新位置。

**确信度：确认。** 若产品只承诺双指缩放，可降为行为限制；委托明确问到双指缩放／平移，当前实现并没有完成两者独立识别。

**建议：**把中点位移和指距变化作为独立输入，平移不应以先发生缩放为前置条件；保留缩放死区，避免把噪声当缩放。

### A-07 · P2 · 与本品种无关的云端画线变化，也会清掉本图撤销历史

**现象：**“我回来想撤销刚才的一条线，撤销已经没了，但这张图的线根本没变。”

**机制：**`DrawingController.swift:157–166` 按整份同步档案是否变化决定发布当前桶；发布走 `ChartView+Drawing.swift:168–184` 的 `setDrawings`，清空撤销栈和会话状态。宿主 `MainScreen.swift:1319` 的同步门挡住 active 绘画，故完整的可达路径是**退出画线→延迟同步落地→整批换入当前桶**，不是正在画一半被云同步直接打断。

**触发条件／最短复现：**BTC 图画一条线并结束绘画；另一设备只改 ETH 的画线；本机应用同步；再次进 BTC 工作台检查撤销。

**确信度：确认。** 正在落笔时打断的更强结论已排除。

**建议：**只有当前桶内容确实改变时才整体换入；整批外部替换与本地交互编辑使用不同的撤销政策。不要让无关桶更新触碰当前图的编辑会话。

### A-08 · P2 · 行情推动纵轴时，画线拖动可能按旧坐标落地

**现象：**“我手指拖着端点没松开，价格一跳，端点就不在手指下面了。”

**机制：**`ChartView+Drawing.swift:660–662` 使用按下时存入的 `drag.axes`，遮蔽实时 axes 参数；绘图却可使用新行情导致的新自动价格区间。固定快照能防累计误差，但只有显示映射也冻结／重基准时才能保证跟手。

**触发条件／最短复现：**自动纵轴下拖端点，手指保持原屏幕位置；期间注入足以扩大主图价格范围的新高／新低，再继续移动 1pt。比较端点的绘制像素与手指像素。

**确信度：疑似。** 是否出现明显偏差取决于行情更新能否在当前绘画模式中推动映射；需要 UIKit 宿主注入行情验证。第二根手指加入会取消画线拖动并交给图表手势，不是“同时缩放同一条线”的竞态。

**建议：**一场拖动期间冻结实际显示映射，或者映射改变时按当前屏幕位置重建拖动基准。不要只改成逐帧相加。

### A-09 · P3 · 两次不连续的轴点击可能被拼成双击

**现象：**“我中间还点过图，再点价格轴却翻转了。”

**机制：**`GestureState.reset:58–67` 保留 `lastAxisTap`；`handleAxisTap:469–485` 只检查与上次轴点击相隔是否小于 300ms，没有检查中间是否出现其他手势，也没有空间邻近条件。

**触发条件／最短复现：**先开启允许主轴翻转；一次轴点击→一次图内点击→再次轴点击，首尾小于 300ms。

**确信度：确认（状态路径）。** 默认关闭主轴翻转，触发窗口也小，因此不列高危；正常相邻两次轴点击必须保留跨 reset 时间，这个字段不能简单每次清空。

**建议：**只在相容的轴轻点序列中继承双击候选；其他模式、切图、取消应终止该候选。

## A.2 手势转移表

V＝时间视野，C＝十字线，Y＝价格变换。“交互结束通知”与“settle”是两件事。

| 触发／模式转移 | 进入／退出清理 | V / C / Y 结果 | settle |
|---|---|---|---|
| 空数据按下 → 交给 super | 不进入图表状态机 | 不创建十字线 | 不适用 |
| 任意动画 → 第一指按下 | 停 animation；reset；保存按下点、V、Y、range | 按当前中间帧起手 | 此时不做 |
| 第一指落 A 徽章 → autoFit | 新一轮快照 | V 不动；抬手在按钮内才 reset Y | 结束早退，不做 |
| 第一指落主价格轴 → axisPrice | 新一轮快照 | 超 slop 后第一帧建立轴缩放锚，后续改 Y；V 不变 | 轻点不做；拖动走末尾收尾 |
| 第一指落副图轴 → subAxis | 新一轮快照 | 小移动抬手可翻相应副图；不缩主 Y | 轻点早退 |
| 第一指落时间轴 → parentScroll | 新一轮快照 | 图自身不拖；实际父滚动还取决于手势路由 | 最后一指走收尾 |
| 第一指落交点 44pt 方框 → crosshair | 不清 C；记录起点 | C 跟第一指；V 不变 | 拖动结束会收尾；轻点走 toggle |
| 第一指落图区 → pan | 记录快照；无 C 才安排长按 | 未过 slop 不动 | 轻点早退 |
| pan 首次过 slop，横向为主 → 锁横拖 | directionChosen=true；清 C | 从 startView 算横移；Y 保持 | 结束 fling 或 settle |
| 已锁横拖 → 后续改为竖拖 | 不重新选方向 | 仍是横拖，不改主 Y | 同上；这是防抖选择，不单列缺陷 |
| pan 首次过 slop，竖向明显、手动主轴 → verticalPan | 锁方向 | V 不动，Y 平移，使用起始 range | 最后一指收尾 |
| 同上但自动主轴／非主区 → parentScroll | 锁方向 | 图自身不改 Y | 最后一指收尾；父路由须宿主测 |
| pan 长按到时 → crosshair | longPressActivated=true；磁吸触觉索引重置 | 在起始按下点创建 C | 完成长按后早退，存在 A-04 同类收尾缺口 |
| pan／axis／vertical／parent → 加第二指 → pinch | 清 C、取消长按、清 axisScaleAnchor；记录双指基准 | 可继续缩放；不继承旧轴锚 | 不做，手还在 |
| crosshair → 加第二指 | beginPinch 守卫拒绝转换 | 仍由第一指拖 C；不是双指缩放 | 最终按实际 mode 收尾；需用例固定产品预期 |
| pinch 距离未过门槛，仅中点变化 | pinchActive 仍 false | V 不动，见 A-06 | 不做 |
| pinch 激活 → move | 更新 d0/mid0，改 V | 历史窗口可缩放＋中点平移；最新对齐有右缘锁 | 不做 |
| pinch 多指 → 抬后仍 ≥2 指 | 重建双指基准 | 从现 V 接续，无轴锚 | 不做 |
| pinch → 只剩一指 → pan | reset 清 moved；重新存现点、V、Y | 能无跳变续拖，但继承点击资格错误，见 A-03 | 不做 |
| pinch → 同一事件全抬 | reset | C 已清；Y 留现值 | 做 |
| pan／crosshair → 小位移全抬 | 保存结束数据后 reset，再 handleTap | 切换 C；新建 C 才 onTapped | 不做 |
| subAxis → 小位移全抬 | reset | 允许时翻指定副图 | 不做 |
| axisPrice → 小位移全抬 | reset，保留 lastAxisTap | 单击 reset Y；双击且允许时翻主 Y | 不做 |
| pan → 拖后全抬且无 C | reset，保留采样得到的速度 | 合法 V 启动 fling；越界直接回弹 | startFling 决定 |
| 其他拖动 → 全抬 | 清 axisScaleAnchor；结束 C 收盘吸附 | 现有 V/Y 留下，V 归约束 | 做 |
| 任意 → cancelled | 清 touches、reset、停动画、清轴锚 | 不制造点击；C 按已有选择收尾策略处理 | 做 |
| 最后一指离开 | finishTouches 外层通知 | `onInteractionEnded` 会执行，早退也不漏 | 通知本身不负责归位 |

**reset 留存字段的结论：**`startView` 在第一指和捏合降一指时重写，不是凭这个字段就能推出串手势。`lastMagnetIndex` 只用于触觉，不能造成画线吸错根。`askedHistory` 在 needsMoreHistory 变 false 时释放；失败后始终留在左边界、或换序列仍处于需历史区的重试行为要另测，不能把“数据长出来了就一定清标记”当作已有保证。`wasAtZoomLimit` 留存主要影响下一次是否震动，属于低严重度。

# B．复盘端到端

## B.1 问题清单

### B-01 · P1 · 一根有效观察收盘都没有，也会被正式判错

**现象：**“我设了四小时后看结果，还没得到一根符合规则的收盘 K 线，系统已经把我记成判错了。”

**机制：**`review_worker.rs:62–90` 的收盘路径计算 `begin = ceil(submitted/checkpoint)`、`end = floor(min(now, expires))`。当 `end <= begin` 且已经到期，直接创建 `unrealized`，理由是“观察期内没有达到目标的完整收盘”，没有取数，也没有调用领域库检查缺失证据。对照 `core/domain/native_review.rs:34–88`：同样在没有 `seen` 的情况下，领域库返回 `needs_verification`。worker 把“没有符合口径的观察样本”和“有完整证据证明没达到目标”合并了。

**触发条件／最短复现：**以 UTC 为例，4h 图在 09:15 提交，13:15 到期；正在形成的 08:00–12:00 根按规则排除；下一根 12:00–16:00 尚未完成。begin=end=12:00，worker 到期分支直接判错。只要 index 任务成功且保存／提交差在 60 秒内，这条还会成为 eligible，并进入输赢分母。此例不依赖 451 或数据库异常。

**确信度：确认。** 这是本轮优先级最高的问题；不是把所有“到期没达标”都判为错误，只针对**没有有效观察证据**的分支。

**建议：**裁定只保留一个权威的证据完整性规则；零有效观察不能由 worker 快捷分支生成输赢。可按已有领域政策保留“待核实”，或者在冻结规则前禁止不可观察的窗口，但不能偷偷延长用户已提交的期限。

### B-02 · P1 · 一次永久冲突会堵住整个复盘上传队列

**现象：**“一条备注同步冲突以后，后面新记的那些也都传不上去了，重试也没有用。”

**机制：**`ReviewFeature.swift:229–292` 每次只处理 queue.first。第一次发送前重写 expectedRevision 并把 attempted 记成 true；发生 409 后退出整个循环，但保留这个操作及固定 body。下一次同步因为 attempted=true，不再重基准，也没有获取最新记录、隔离失败项或继续处理其他记录的路径。队首永久 400／不受支持的提交也有同样阻塞效应。HTTP 幂等重试需要固定请求体，**不能靠随意修改同一个幂等键的 body 修复**。

**触发条件／最短复现：**手机离线以 revision 1 编写反思；平板提交到 revision 2；手机尝试发送旧 revision，得到 409；手机再创建一条不同 ID 的记录，触发同步。第二条一直排在不可恢复的第一条后面。

**确信度：确认。** 服务端 CAS 本身正确；这里是复盘客户端队列的恢复政策缺失，不重审此前通用 SyncStore 冲突机制。

**建议：**区分暂时不可达与确定的业务冲突／非法请求；保留冲突的本地内容，读取权威版本后生成**新操作／新幂等键**，或者把此记录隔离为“冲突”，允许无关记录继续同步。不能无条件最后写入获胜。

### B-03 · P1 · 服务器列表加载过后，本地新记录可从列表里消失

**现象：**“刚刚保存成功的一笔，断网后打开复盘本却找不到。”

**机制：**`ReviewFeature.swift:90–99` 的 bookRecords 在 `isConnected && historyLoaded` 时，只遍历 `history.map`。它能用本地待上传版本替换**服务端页中已有 ID**，但不会把服务端页里没有的本地新 ID 补进来。`isConnected` 仅表示 client 存在，不代表网络此刻可达；`loadHistory:208–227` 失败也不会清掉 historyLoaded。因此这是渲染集合漏并集，不是本地存档被删除。

**触发条件／最短复现：**登录并成功加载一次复盘列表→断网→新建并保存一条复盘→再看当前列表。该 ID 在本地 archive 和 queue 中，却不在 bookRecords 中。

**确信度：确认。** 冷启动尚未成功加载历史时走 records，不是同一条故障路径。

**建议：**分页服务端记录与本地新增／待上传记录按 ID 做受过滤条件约束的并集；已在服务端页中的 ID 用本地待提交版本覆盖。分页不能把本地还没有服务端游标的记录隐藏。

### B-04 · P1 · 跨品种回放会沿用当前品种的小数位和 tickSize

**现象：**“我从比特币页面打开一个低价币的旧复盘，价格轴和画线数字变成 0.0 了。”

**机制：**`ReviewChartBridge.swift:101–145` 用传入的 live ChartState 做 base，只替换回放 series。构造新 SymbolInfo 时，`pricePrecision` 仍取 `base.decimals`，`tickSize` 也按它推导；没有根据回放品种解析真实精度。`DrawAxes.decimals` 和画线标签又沿用 ChartState.decimals。真实行情数值未必损坏，但回屏价格会按错误精度显示。

**触发条件／最短复现：**当前图为小数位很少的品种，打开价格需要更多小数位的另一品种复盘；例如用一位小数的 live 状态打开价格 0.00001234 的回放 fixture。比较坐标轴、十字线、画线标签与目标品种精度。

**确信度：确认。** 不重审第四轮目录元数据；这是回放桥没有使用目标品种元数据的独立接入缺陷。

**建议：**回放状态按记录的 venue／market／symbol 解析精度，不从当前 live 图借用；历史行情与历史绘图上下文分别建模，避免沿用无关品种的显示元信息。

### B-05 · P1 · 回放每推进一次，用户的缩放和历史位置就被重设

**现象：**“回放里我放大看细节，一播放下一根又缩回去了。”

**机制：**`ReviewChartBridge.swift:217–226` 的 updateReplay 每次都写 `ViewWindow(to: lastTime + step * 6, span: step * 80)`，随后直接 `chart.state = base`。这不是首次打开时的默认值，而是每次步进／播放都会执行，绕过 ChartViewport 对人的体验偏好和当前视野的仲裁。

**触发条件／最短复现：**进入回放→手动调整到明显不是 80 根的视野→前进一步或播放一拍。立即观察 span、根宽和右缘。

**确信度：确认。** 保存 drawingSnapshot 并非丢失：同函数会在回放已知时刻到达 draft.created 后恢复快照，这是避免未来标注提前进入历史的有效防护；问题在每拍重设 V。

**建议：**80 根只作无个人／会话视野时的首次兜底；推进时保留根宽和用户历史锚点，仅在用户仍跟随播放头时移动右缘。

### B-06 · P2 · 客户端允许的复盘范围比服务器宽，合法操作可能生成必败请求

**现象：**“这个品种明明能看图，也能写复盘，保存后却怎么都传不上去。”

**机制：**`ReviewModels.swift:61–96` 的客户端校验没有完整复刻服务器支持范围；`core/domain/native_review.rs:5–29` 要求 usd_m、USDT 后缀、ASCII 代码、3…1500 根、时间跨度严格对应根数，另有规则／正文／快照长度上限。USDC 图的名称处理正确，不等于其复盘创建被服务器支持。客户端目前能把这种请求入队；它再触发 B-02 的队首阻塞。

**触发条件／最短复现：**用 venue=binance、market=usd_m、symbol=BTCUSDC 的合法已收盘区间，客户端 validation 通过并入队；服务端报 invalid_chart_range。超过 1500 根、超长度备注等也应以契约 fixture 验证，不必假设每条都能由当前 UI 直接造出。

**确信度：确认（客户端与服务端契约不一致）；特定品种在 UI 目录中的可达性以实际当前目录为准。**

**建议：**在用户保存前自动采用后端真实支持集合；不支持的品种不生成永远失败的上传操作。服务端必须保留校验，不能为了“能上传”放松证据完整性。

### B-07 · P2 · “战绩”使用绝对价格和绝对到期时间分组，几乎每笔都可能成为独立的 0%／100%

**现象：**“我已经记了很多笔，战绩却是一排同名项目，有的 0%、有的 100%，看不出自己到底怎样。”

**机制：**`review.rs:142–160` 的 signature 包含 reference、target、invalidation、**绝对 expires** 等；即便方向、品种、确认方式与观察时长一样，只要另一时刻提交使 expires 不同，就是不同组。标题却只包含品种、形成方式和收盘／触价，不能区分这些 signature。领域库本来给了样本不足等状态，但 `NativeStatsResponse` 只接 groups，未使用 proof 的判定状态。

**触发条件／最短复现：**两条同品种、同方向、同形成方式、同相对目标与时长的独立记录，expires 不同；一赢一输。得到两个标题相同的 n=1 组，而不是一个 n=2 的可比策略组。

**确信度：确认。** **不是算术分母算错。** 每个 exact-rule 小组的率数学上正确；问题是它不回答长期可比判断的胜率问题，且展示隐藏了分组差异。不能为凑样本随意混合不同规则。

**建议：**把冻结的单笔规则身份与可比统计规则身份分开；可比性依据确认策略、相对阈值和观察时长等，而不是绝对到期时间。没有足够可比样本时沿用领域的“样本不足”决策，不给单样本百分比冒充有效统计结论，也不增加一行工程解释。

### B-08 · P3 · 回放位置超过 500 条后，淘汰不是“最久没看”的那条

**现象：**“我刚回看过的记录，下次打开进度却重置了。”

**机制：**`ReviewStore.swift:185` 附近按 UUID 排序裁到 500，而不是按最后访问／更新时间。UUID 字典序与用户最近是否看过无关，因此刚写入的进度也可能被淘汰。

**触发条件／最短复现：**预置 500 个回放位置，写入一个在 UUID 排序淘汰侧的新 ID；读回这个新 ID。

**确信度：确认。** 当前只有几名用户，达到 500 条回放后才触发，优先级低。

**建议：**进度条目保存最近使用时间，按最近使用淘汰；本地容量上限不需要增加。

## B.3 裁定时间线

### 例：用户在图上判断“未来四小时达到目标 X”

以下展示时间使用 UTC；台湾／中国大陆界面显示时整体加八小时。存储／比较都是 epoch 毫秒，**不要把 UTC+8 再加进时间戳本身**。观察 K 线的开盘锚定规则则是另一个问题。

| 步骤 | 时钟／时间 | 行情来源 | 失败分支 | 用户看到什么 |
|---|---|---|---|---|
| 圈选已收盘区间 | 客户端ReviewClock；图表closeTime | 当时图上的实际MarketSource；桥去掉未收盘尾根 | 根不足／年线不支持→不开始捕获 | 原图＋已有中文提示，不产生判定 |
| 编辑草稿两分钟 | 客户端created最初是圈选时刻；expires是绝对毫秒 | 草稿冻结区间／设置／画线快照 | 本地校验失败不入队 | 草稿仍在 |
| 按保存09:15 | **created重写为客户端此刻**；expires不偷偷延长 | 保存已有区间，不把“后来截图”替代原区间 | archive事务失败返回false | 不应宣称保存成功 |
| 请求到服务器 | **submitted=服务器Utc::now** | 尚未做裁定证据取数 | auth／参数校验失败→不创建；网络断开留队列 | 本地记录等答案；失败可成为待办 |
| 创建episode | submitted起120小时 | 无 | SQL失败事务回滚 | 不是120小时后才裁定；episode是样本归组窗口 |

| 未终结重试 | 通常收盘30秒、触价5秒；落后checkpoint快追2秒 | 同源续取 | 451识别分支86400秒；普通错误60秒 | 状态仍是一个词，不需要加工程计时字段 |

# C．界面状态、皮肤、Release、上架与测试有效性

## C.1 问题清单

### C-01 · P2 · 板块一次临时没有统计数据，就会永久退掉当前钻入层级

**现象：**“我正在某个板块里面，数据空了一下，就被退回上一层了。”

**机制：**`SectorPage.swift:337–352` 的 listLayer 在当前 snapshot.stats 找不到 id 时直接放置 `Color.clear.onAppear { pop() }`。这里没有区分“板块被永久移除”和“这次快照暂时没有该板块报价”。宿主持有 route 只能防止页面重建重置，防不住子页主动 pop 这个持久路由。

**触发条件／最短复现：**保持 route.last=.list(id)，向页面注入一次不含 id 的临时快照；触发 onAppear；随后恢复含 id 的快照。路由已经被 removeLast，不会自动回到该板块。

**确信度：确认（给定数据形状下）。** 未证明每次普通切页都会遇到这类空快照，因此不扩大成“板块切页必丢层级”。

**建议：**只在目录确认该板块不再存在时退栈；行情暂缺应保留路由及原上下文。不要把数据加载状态当用户导航动作。

### C-02 · P2 · Release 仍可被启动环境切到测试存储／测试启动路径

**现象：**“同一个 Release 包用测试启动方式运行，自选和账号行为跟平时不一样；这样的绿不能证明正式启动也对。”

**机制：**`SymbolPrefs.swift:413–415` 的 deviceStorage 仍不受 DEBUG 保护；`MarketRoutePolicy.swift:37–43` 切测试 defaults；`Paths.swift:38–43` 改缓存根；`MainScreen.swift:1266–1273` 可绕过正常账号接线。这些与已经 DEBUG 化的 AccountFeature Keychain／URL、LaunchMirror.defaults 不一致，Release 注入环境后可能是“部分测试、部分正式”的混合状态。

**触发条件／最短复现：**在可设置启动环境的签名／测试运行环境下启动 Release，设置 KANPAN_TEST_PROFILE=1，必要时加有效 KANPAN_PERSISTENCE_PROFILE，再与无环境启动比较实际存储实现、目录、账号接线。普通其他 iOS app 不能因此给已安装 App Store app 远程注入环境。

**确信度：确认（编译可达与分支能力）。** 不是远程账号接管漏洞，也不声称普通 MDM 配置能任意修改 ProcessInfo.environment。

**建议：**会替换存储或跳过产品初始化的钩子统一收进开发专用编译边界；同时给 Release 验收使用独立安装沙盒／测试包身份，不再依赖这些产品二进制内的测试分支隔离真实档案。只删隔离代码却仍让 UI 测试跑用户真沙盒也不安全。

### C-03 · P2 · 隐私清单遗漏实际上传的设备级标识

**现象：**“隐私申报说没有设备标识，但账号系统实际保存了这台安装的设备 UUID。”

**机制：**`PrivacyInfo.xcprivacy:146–218` 的收集数据只列 UserID、OtherUserContent、OtherDataTypes；注释以 `UIDevice.current.model` 不是标识为理由不申报 DeviceID。但 `AccountFeature.swift:19、61–64` 创建并恢复的是 AccountDevice，账号请求发送的 device 不只有 name；`0001_accounts.sql` 的 sessions 还存 device_id。设备名称是 iPhone／iPad，不会让另一个被存储的 UUID 失去“设备级 ID”性质。Apple 的 Device ID 定义不仅包含广告 ID，也包括其他 device-level ID〔Apple-2〕。

**触发条件／最短复现：**正常注册／登录一次，检查请求 device.id 与对应数据库会话 device_id；与清单类型比较即可，不需收集真实用户隐私。

**确信度：确认（仓库清单与数据流不一致）。** App Store Connect 实际填写内容未读取，不能声称已发生拒审，也不能把它错误写成 required-reason API 缺项的自动 ITMS-91053。

**建议：**按实际用途声明设备级标识用于账号功能、与用户关联、非追踪，并与 App Store Connect 隐私标签核对。不要改成不准确的“所有设备名都是设备 ID”。

### C-04 · P2 · iPad 复盘宽度用例可以没进入目标界面就通过

**现象：**“测试说复盘页在 iPad 上没破，但它其实只看到了未登录页。”

**机制：**`IPadLayoutUITests.swift` 的复盘用例把宽度断言放在 `if segment.exists` 内；缺少分段控件时并不失败。默认测试启动档案没有真实登录客户端，恰好可能不展示有待办／历史／战绩分段的复盘本，因此目标断言整块不执行也可绿。

**触发条件／最短复现：**宽屏 iPad 测试窗口，保持未登录，打开复盘入口，确保目标分段控件不存在；检查用例是否仍通过。

**确信度：确认。** 宽屏前置 XCTSkipUnless 本身是设备范围声明；真正的假绿来自目标控件不存在时的 if 分支。

**建议：**登录门与已登录复盘本分别测试；后一条必须先强制断言目标页面已进入，再检查560pt列宽。不能用控件不存在跳过核心断言。

### C-05 · P2 · 默认“全测”目标没有选中账号与复盘，Release 修复又移除部分行为测试

**现象：**“make test 全绿，但账号／复盘改坏了它也不会发现。”

**机制：**`Makefile:188–197` 默认 test 不含 KanpanAccount、KanpanReview 或 UI；strict 只含四个包。`8733e3f` 四个测试文件的 #if DEBUG 使部分测试在 Release 不再存在，不是改成 Release 可运行的同等测试。`Kanpan.xcscheme` 的 TestAction 仍是 Debug，现有入口不能证明 Release 行为。

**触发条件／最短复现：**故意破坏只被 Account／Review 测试覆盖的功能后只执行默认 make test；或者比较 Debug 与 Release 的实际测试标识集合，确认被条件编译消失的测试。

**确信度：确认（入口及编译选择）。** 不能进一步声称“第三轮从未人工回归过”；提交作者明确写有单独验证记录，只是默认目标没有持续包含它。

**建议：**让被称为全测的本地入口包含账号、复盘及明确的 Release 测试配置；行为测试尽量用白名单内 URL 配合自有 URLProtocol／transport 截获，而非依赖 Release 已删除的任意主机能力。DEBUG-only 测试名单必须单独列出，不并入 Release 通过数。

### C-06 · P2 · 设置页账号入口同时驱动两处 presenter

**现象：**“从设置点账号，有时弹层被抢走、关闭不同步，或再次点才出现。”

**机制：**`MainScreen.swift:394` 附近根 sheet 绑定 account.presented（仅排除 review.bookOpen），`SettingsPanel.swift:100–102` 自己也绑定同一个 presented。设置页 asPage 嵌在根里时两者同在树上。复盘本的第三个 presenter 则已通过根部 !review.bookOpen 门隔离，不能把三个都说成无条件同时弹。

**触发条件／最短复现：**进入设置整页→打开账号→拖动关闭→立刻再次打开；并测设置其他sheet在场时进入账号。

**确信度：疑似（竞争结构确认，SwiftUI实际选择及用户症状需运行）。** 多个 .sheet 修饰符不是静态语法错误，不能武断说一定“静默丢第二个”。

**建议：**同一上下文由一个 presenter 持有账号呈现权；设置整页交给根，真正作为上层sheet的设置上下文才自行呈现。保留复盘book的既有层级隔离。

### C-07 · P2 · 指标非法中间输入可能在失焦钳制前先被保存

**现象：**“我在参数框输入一个数直接点保存，保存的不是最后显示出来的那个数。”

**机制：**`IndicatorPanel.swift:234–435` 的 ParamField 持有字符串；合法值即时更新draft，非法／越界字符串等到失焦 commit 才钳制。保存按钮先执行 draft.save 再 dismiss，没有明确先结束焦点并提交当前字符串。SwiftUI 的按钮动作与 onChange 焦点回调次序决定是否保存了此前合法中间值。

**触发条件／最短复现：**选择上限小于999的参数，从空串输入999，保持焦点直接点保存；比较最终显示、持久化值与规定的钳制结果。另测输入空串直接保存。

**确信度：疑似。** 已确认输入／保存有两条提交时机；需模拟器验证实际事件先后，不能凭读码断言某一特定中间值必然落盘。

**建议：**保存动作显式完成当前输入的规范化后再一次性写draft；失焦继续作为辅助，不承担唯一收尾职责。

### C-08 · P3 · 自选页滚动位置尚未得到跨页持有／恢复的证据

**现象：**“自选滚到下面，去设置再回来又回到了上面。”

**机制：**`MainScreen.swift:433–475` 拆掉非当前页面；`FavoritesView.swift:1–145` 的分类和编辑会话有宿主／Prefs来源，但本次未找到已验证的滚动锚点保存与重入恢复链。不能由分类保住推出滚动也保住。

**触发条件／最短复现：**一个超过两屏的分类，停在中部指定symbol，切设置再回自选，比较该symbol在可视区的位置。

**确信度：疑似。** 此项没有完成整个 FavoritesView 滚动实现的穷尽核读，也没有运行，因此**不作为已确认丢失**；保留在验收缺口而非强制修复清单。

**建议：**先跑同symbol锚点测试；确实丢失才把会话滚动锚点放到长寿命的用户体验状态中。不要因此保存不可恢复的绝对屏幕像素。

### 生产账号 UI 测试的实际风险

已核读的 `AccountPreferenceSyncUITests.swift` 使用带随机UUID后缀的测试用户名，记录创建列表并在teardown尝试删除。因此它**不会仅因为“都是手机”就踢掉普通用户手机**：每类一台限制仍以同一个user为范围。测试自己的两台同类设备互踢可以是有意验收；不能把它推成所有生产用户受影响。

风险在于：进程被强杀、网络失败、teardown失败会残留测试账号；其他账号测试是否都遵守相同隔离，本次没有全量核读确认。隔离方法不是把注册／登录改成假实现，而是继续打真实接口，但使用每次运行独有的测试账号前缀／运行ID、独立测试安装沙盒，并依据运行ID做可重复清理；清理绝不按宽泛用户名模式触及正常用户。不存在真实个人账号凭据时，不可拿个人账号验证互踢。

## D.1 问题清单

### D-01 · P3 · 带数据升级时，普通建索引与 ALTER TABLE 会占用表锁

**现象：**“升级服务那一会儿，保存或同步可能等一下；锁竞争严重时请求会失败。”

**机制：**`0002_mail_recipient.sql:1–2`、`0005_challenge_retry.sql:1–3`、`0006_public_history_ann.sql:2–9`、`0007_hot_path_indexes.sql:6–21`、`0010_device_kind.sql:4–14` 含普通 `CREATE INDEX`／`ALTER TABLE`，并不是无锁迁移。建立索引需要扫描已有数据，具体等待时间取决于库大小和当时事务，不能从DDL推导秒数。

**触发条件／最短复现：**在有数据的测试库维持一个涉及目标表的长事务，同时运行对应迁移；另一个连接提交写操作，观察等待和超时。空库执行通常不能暴露这一点。

**确信度：确认其锁需求；实际用户可见影响未实测。** 对只有3～10人的系统，这不是当前发布阻断，不需要为此引入大型在线迁移体系。

**建议：**升级时短暂停写并确保没有遗留长事务；先在代表性小库验证迁移及回滚／恢复流程。不要把“CREATE INDEX成功”记成“在线无阻塞”。

**未新增其他已确认的数据层阻断项。** 新个人表的RLS漏配、一天退避霸占API连接池、group绕过revision等候选在已读路径中不成立；下面分别说明依据。数据库实跑、查询计划和全后端错误出口穷尽检查仍未完成。

## D.3 连接池与 worker 退避

| 问题 | 结论与依据 |
|---|---|
| 复盘HTTP、同步、账号是否共用池 | 同一个serve进程里的路由共享AppState.pool；不能把各路由当独立池。见 `src/lib.rs` 的AppState及路由组合 |
| review worker是否和API进程共享同一个内存池 | **不是必然，也不是当前命令结构的默认结论。** `src/main.rs` 将worker作为独立运行模式；另起worker进程会构造自己的AppState／连接池。即使DATABASE_URL相同，也不是同一个进程内池 |

## D.5 内部错误文本是否回到客户端

在已核读的复盘／搜索公共错误转换中，`src/error.rs` 的 `ApiError` 保存状态码与静态错误码；sqlx错误转换成统一的服务不可用错误，而不是把sqlx.to_string()塞进JSON。`review.rs`、`review_worker.rs`、`review_market.rs` 的这些路径也使用固定错误码。`ScorebookClient.swift:58–63` 的独立URLSession分支还会丢弃非2xx响应正文。

**结论：已读路径未确认存在sqlx错误串／内部文件路径直接返回客户端的漏洞；不能扩张成“全后端所有出口已经逐一排除”。** 本次没有完成全仓所有IntoResponse、直接Json、stream错误项及非复盘路由的穷尽枚举。尤其不能把“客户端某一个实现隐藏正文”当作服务器无需约束错误输出的理由。

应补一条路由层测试：以测试数据库制造语法／约束／连接失败，以及无法解析的JSON，分别调用复盘创建／列表／搜索状态接口；断言响应只有规定中文产品映射或固定错误码，不含SQL、表名、连接串、绝对路径、原始请求正文。错误的完整原因留在测试断言上下文，而不进入产品屏幕。
