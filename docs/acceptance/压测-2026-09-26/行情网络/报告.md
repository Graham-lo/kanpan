# 行情与网络层压测审查报告（2026-09-26）

范围：`KanpanNetwork`（HTTP / WS、币安 / OKX / Coinbase、限流器、线路策略、网关竞速）、`KanpanData` 的行情部分（MarketFeed / FeedComposer、深度流与主力订单流、补缺、回放、多品种快照）、以及它们直接用到的 `KanpanCore` 序列与聚合。

## 加压方式与约束

- 全部在本机进程内完成：包内假传输（`NetworkFakes`）、自写的「滴水」URLProtocol、假 WS 会话、虚拟时钟（`ManualPacer` / 注入 `now`）、伪随机录制流（SplitMix64，固定种子）。
- **没有对线上 VPS 网关或任何交易所生产接口发起加压请求**；币安生产接口一次都没碰。
- 编译与测试一律经 `make network-test` / `make data-test` / `make core-test`（走 `scripts/machine-guard.sh` 排队），同一时刻只有一个编译，没开模拟器。
- 回归测试全部是结构性断言（连接次数、请求次数、整条重建次数、merge 触及的根数、状态机结局），不靠墙上时间阈值。

## 已看过不改

- **限流器 200 并发抢额度（M5）**：200 个并发 acquire 共 791 次睡眠（每个约 4 次），最差一个比到达顺序晚 17 位。不预留额度是有意设计——预留后被取消的请求要回收额度，而且严格 FIFO 会让普通请求排在「等 5 分钟合约数据配额」的请求后面。保持现状。
- **单页严格解码（L4）**：K 线整页有一行解不出就整页判错，是为了不把一个静默的洞写进缓存；行与行独立的列表已经用 `LenientList`，Coinbase 也已经 `compactMap`。保持现状。
- **Coinbase 时钟偏差与 `end`（L1）**：本机时钟快于服务端时，最后一页可能少几根。要确认 Coinbase 对未来 `end` 的处理必须打生产接口（本轮禁止）；iOS 自动对时下偏差在 1 秒以内，影响是「偏差 / 步长」根的小洞、不会形成循环，下一轮对表补上。
- **`FeedComposer.pending` 无上限（M6）**：修完 #12 后它的长度受补缺时长约束，最坏估算约 1 MB。
- **币安直连与网关共用一个限流器**：直连路线挨 418 时网关路线也跟着停，这是现有设计（同一个账号 IP 权重的保守处理），线路仍是直连 / 网关两档、不自动切换。
- **OrderFlowFeed 服务端历史的退避只在成功加载后清零**：符合预期。
- **VenueBook 缓冲 `removeFirst`**：5000 条时每次约 400 KB 内存搬移，10 Hz 下只在 REST 长时间不可用时出现，可接受。
- **WS 多品种推送（#5）**：消费方已按品种过滤，不串品种。
- **快照落盘（#6）**：1500 根约 1 ms / 72 KB，不必优化。
- **WS 解帧热路径**：0.13 µs/帧（对照 0.087 µs），不是瓶颈。
- **深度簿最优价重扫（F）**：1k / 10k / 40k 档分别 6 / 54 / 218 µs（调试包），且只在最优档被删时才重扫。
- **Coinbase 覆盖范围漂移（G）**：单连接内价格漂移 ≥ 9% 才会出现覆盖外空白，表现与其他家超出覆盖范围一致。
- **WS 最大消息 8 MB（I）**：快照估计 2–4 MB，余量足够。
