# 后端压测审查报告（kanpan-api，2026-09-26）

范围：`Backend/kanpan-api`（Rust）。全部压测在本机做：`ops/test.py` 起的隔离库（Docker Compose 的 Postgres，55432）、进程内夹具与 mock 上游。**没有对任何线上 VPS 发过一个请求**，也没连交易所。重活一律经 `scripts/machine-guard.sh run` 排队、同一时刻只有一个 cargo。

内存一律用 macOS 的 `footprint`（在独立子进程里量，`ps` 的 RSS 在 macOS 上不可信）。「修前 / 修后」都是同一条压测用例在修复提交前后各跑一遍的实测数；每条修复都带回归用例，并确认过把修复去掉时用例会红。

## 一、结论

- 共发现并修掉 **18 个**问题：10 个在账号 / 连接池 / 复盘 / 导出 / 分享 / 提醒 / 行情元数据 / worker，8 个在主力订单流。其中 9 个是能把 serve（`MemoryMax=1G`）顶到被杀或把整站连接池攥满的「高」。
- 回归：全量 `ops/test.py` **528 通过、0 失败、2 忽略**（压测前基线 480 通过），33 个测试二进制，193 秒。
- `cargo clippy --all-targets`：lib 10 条、lib test 15 条，与压测前基线逐文件一致，没有新增。
- 不需要迁移。serve 与 worker 两个二进制都要重新部署（见第五节）。

## 二、发现与修复

严重度：**高** = 线上能被一次普通操作或几个并发打到进程被杀 / 整站卡死；**中** = 局部功能长时间不可用或数据断档；**低** = 浪费资源、放大故障。

## 四、已看过不改

| 项 | 为什么不改 |
|---|---|
| 同步：一批里有一条毒丸就整批 400 | 与客户端的隔离机制兼容（客户端把被拒的那条隔离出去，其余照推）；已补回归用例 |
| 同步：对已删除对象的补丁多记一条 `sync_changes` | 只多一条变更记录，无害 |
| 同步：未来时间戳 | 服务端夹到当前时间，多设备收敛，已测 |
| Webhook 按域名解析后的内网地址（DNS SSRF） | 既定决定，文档里有记录 |
| 分享发信时自动互加好友 | 产品设计，不是负载问题；收件箱的负载问题已在 #6 修掉 |
| worker 收到 SIGTERM 不排空在途任务 | 租约与 `lease_id` 围栏保证不会重复落库，代价只是那一条最多晚 120 秒被别人重接 |
| 币安封禁截止时间只在单个进程里有效（serve 与 worker 共用出口 IP） | 另一个进程下一次出站自己就会收到 429/418 并按住，至多多出一个请求；为这一个请求把闸门搬进库里不划算 |
| 评估器每帧 O(用户) 刷新、品种集合一变整体重连 | 10 人规模下实测无害（上限约 10 人） |
| 提醒效果队列串行、满 1024 丢弃 | 现有规模下触发不了；队满之前 Webhook 已有在途 / 积压上限（#3） |
| 复盘统计、修订历史、好友列表不分页 | 数据量按人计、增长很慢，10 人规模下无害 |
| 行情中继每个 IP 可占 16 条、全局 64 条 | 内存有界，单帧发送 10 秒超时；账号规模下占不满 |
| 复盘 worker 租约丢失时 attempts 只涨 | 只有连续 5 次部署都恰好打断同一条任务才会放弃，概率极低 |
| 压测后内存不回落到起点 | macOS 分配器缓存，稳定后不再涨，不是泄漏 |
| 图片下载闸门不覆盖慢客户端的发送阶段 | 答复在闸门里组装好、放闸后才发；一份至多约 7 MB（5 MiB 图），同一把令牌同时最多 3 个请求（#2），慢客户端占不出量级 |
| 收件箱：客户端每次刷新只拉一页 | 服务端页变小后要多拉几次，是客户端的事（`ShareInbox.swift`），不在本轮范围 |
| 请求隔离按登录令牌而不是按账号 | 一个账号同时在线最多每类设备一台，按令牌已足够 |
| 订单流：OKX 每小时订退 400 次用完整条重连 | 订退每秒攒一批只算 1 次；#16 之后重同步已退避 |
| 订单流：Coinbase 断档整条重连 | Coinbase 一本簿一条连接，整条重连就是只重连这一本 |
| 订单流：异步线程上的重计算 | debug 下 6 本 × 2 万档一次约 63 ms、每 500 ms 一次，release 为个位数毫秒 |
| 订单流：每只币写库积压上限 5 万行、若干不限长的控制通道 | 行按单去重、控制通道都是低频消息；整体内存由 RSS 资源闸门兜底 |

## 五、部署与迁移

- **没有新迁移。**
- **serve 与 worker 两个二进制都要重新部署**：
  - serve 涉及：账号、请求隔离、复盘图片、导出、分享、行情元数据、订单流。
  - worker 涉及：复盘 / 找相似、提醒 Webhook。
- serve 的库连接数由 8 条变成最多 14 条（订单流单开 6 条、按需建立）。线上 Postgres 是 pgvector pg17 镜像默认的 `max_connections=100`，加上 worker 8 条、metrics 与导入，合计约 30 条，余量够；容器内存上限 512 MB，多出的 6 条后端连接只占几十 MB。
- 订单流历史接口的答复改成边读边写：JSON 内容不变，顶层字段顺序不同；超过 2 个并发只是排队。
- 资源闸门日志里「clear for N minutes」的 N 现在会在 10–120 之间变化。
