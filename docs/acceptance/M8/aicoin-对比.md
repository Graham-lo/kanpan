# AiCoin 桌面版 ⇄ 看盘：图表细节逐项实测对比

> 目的：用户要求「仔细对比各种细节，k 线的大小粗细，放大的移动轨迹，k 线屏幕的大小，
> 上下间距等各种设置」。这份文档把 **AiCoin 桌面版的像素实测值** 和 **本项目的常数出处**
> 摆在一起，每行给一个结论：一致 / 有差 / 已改。
>
> AiCoin 侧数据来源：`screencapture -l <windowid>` 抓的 **1920×975 原生截图**
> （`scratchpad/aicoin.png`），显示器是 **1x**，所以截图里 1 像素 = 1 pt，可以和我们的 pt
> 直接比。逐像素统计脚本：`scratchpad/bmp.py`（自写的纯 Python BMP 解码，这台机器上
> 没有 PIL / Quartz / ImageMagick）、`scratchpad/geom.py`、`scratchpad/wick.py`。
> 样本：主图区 x∈[390,1800]、y∈[160,566]，共识别出 **198 根**完整蜡烛。
>
> 本项目侧数据来源：`scratchpad/ours-geometry.md`（九节，逐条带 `文件:行号`）。
> 下文凡写「出处」的都指仓库根目录的相对路径。

## 0. 一句话结论

三处**真差异**，按影响从大到小：

| # | 差异 | 影响 | 状态 |
|---|---|---|---|
| 1 | **价格轴没有「自动 / 手动」两档**——我们的手动缩放是贴合结果上的相对量，横向一平移就跑 | 用户报的「缩放 K 线会自动上下跳」的后半截 | **本次已改** |
| 2 | **影线被兑淡**（`wickTint`），AiCoin 影线与实体**同色满饱和** | 用户报的「颜色都好像变淡了，特别是影线」 | **本次已改**，见 §6.1① |
| 3 | **影线在 3x 上只有 0.667pt**（AiCoin 恒 1.0pt），而且挤到 3 像素一格时影线自己把缝占满 | 用户报的「影线好像挤在一起」 | **本次已改**，见 §6.1②③ |

其余（布局比例、网格步长、刻度候选表、字号、缩放锚点语义、回弹曲线）基本对得上，
差的是数值口味不是做法，逐项列在下面。

## 2. 蜡烛：大小、粗细、间距

### 2.1 AiCoin 实测（198 根样本的众数分布）

| 量 | 分布 | 均值 |
|---|---|---|
| **实体宽** | 4px ×123，5px ×56，3px ×14，6px ×5 | **≈ 4.3 px** |
| **步距（根间距）** | 6px ×132，7px ×50，5px ×3 | **≈ 6.27 px** |
| **间隙（相邻实体之间）** | 2px ×148，3px ×24，1px ×14 | **≈ 2.0 px** |
| **影线宽** | **1px ×127**（其余读数是「顶端就是实体」的根，不算） | **恒为 1 px** |
| 实体高 | 10 分位 2px，中位 4px，最大 258px | 十字星保底 ≈ 2px |
| 一屏根数 | 198 根完整 + 边缘残根 ≈ **226 根**（1420/6.27） | |

派生比例：**实体 / 步距 = 4.3 / 6.27 = 0.686**；**间隙 / 步距 = 2.0 / 6.27 = 0.32**。

步距 6 和 7 交替（132 : 50 ≈ 2.6 : 1）说明 AiCoin 也是**整数像素量化 + 累计误差摊到相邻根**，
和我们 `snap(x) = round(x*scale)/scale` 是同一路数。

### 2.2 本项目

实体宽不是绝对值，是 `spacing × bodyR × scale` 取整（出处 `CandleWidths.swift:79–94`）：

```
wick  = max(1, round(max(0.5, style.wick)))     # 整数设备像素，与 scale 无关
raw   = spacing * style.bodyR * scale
cell  = floor(spacing * scale)
cap   = max(wick, cell - 1)                     # ← 留缝：相邻两根至少 1 个设备像素
body  = (raw < 2) ? wick : max(1, round(raw))
body  = min(body, cap)
body  = evenUp(raw, body, wick)
```

十一款风格的 `bodyR`（出处 `CandleStyle.swift:70–124`）：

| 风格 | 墩(默认) | 砖 | 描 | 纸 | 密 | 阔 | 靛 | 辉 | 针 | 芯 | 骨 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| bodyR | **0.86** | 0.96 | 0.68 | 0.64 | 0.62 | 0.58 | 0.55 | **0.70** | 0.42 | 0.40 | 0.34 |
| wick(设备px) | 1.8→**2** | 0.5→1 | 0.9→1 | 0.8→1 | 0.5→1 | 1.0→1 | 0.5→1 | 1.2→**1** | 2.0→2 | 1.0→1 | 0.5→1 |
| wickTint | **0.7** | 0.45 | 0.85 | 1 | 1 | 1 | 1 | **0.6** | 0.9 | 1 | 1 |

### 2.3 逐项对照（统一折算成 **pt**，我们按 3x 屏）

| 量 | AiCoin | 我们「墩」默认 spacing 9.2pt | 我们「辉」默认 spacing 7.2pt | 判定 |
|---|---|---|---|---|
| 步距 | 6.27 pt | 9.20 pt | 7.20 pt | 我们的默认视野更疏（一屏 36 根 vs AiCoin 226 根，但那是窗口宽度差，不是口味差） |
| 实体宽 | 4.3 pt | **8.00 pt**（24 设备px） | 5.00 pt（15 设备px） | |
| **实体 / 步距** | **0.686** | **0.87** | **0.694** | **「辉」正好等于 AiCoin；默认的「墩」明显更胖** |
| 间隙 | **2.0 pt** | 1.20 pt | 2.20 pt | 同上 |
| **影线宽（物理）** | **1.0 pt**（1 设备px @1x） | **0.667 pt**（2 设备px @3x） | **0.333 pt**（1 设备px @3x） | **我们的影线物理上更细**：3x 屏上 1 个设备像素只有 0.33pt，AiCoin 是它的 3 倍 |
| **影线颜色** | **与实体完全同色**，实测 `#CF3E3E` / `#26A380`，`tol=26` 下 260+231 个样本无一偏离 | `mix(bg, 涨跌色, 0.7)` → 明显偏背景 | `mix(bg, 涨跌色, 0.6)` → 更淡 | **有差**，直接对应用户说的「颜色都好像变淡了，特别是影线」 |
| 实体最小高 | ≈ 2 px | `max(wickW, minBody/scale)`，墩 `minBody=2`→0.667pt | 辉 `minBody=2`→0.667pt | 一致（都是「十字星至少看得见一条」） |

关键推论：

- **`wickPixels` 忽略 `scale`**（出处 `CandleWidths.swift:63–65`，参数被 `_ = scale` 丢掉），
  所以屏幕越精细影线的**物理宽度越细**——2x 上是 3x 上的 1.5 倍。这和「看起来糊」
  的方向完全一致：iPhone 15/16 都是 3x，影线只有 1/3 pt。
- **`wickTint` 只在实体细到 `bodyW*scale <= 2` 时才被强制拉满**（`ChartRenderer.swift:273`）。
  缩小到中等密度（实体 3–6 设备px）时 tint 仍然生效，影线就是淡的。

> 以上两条是**测量当时**的状态，本次已经改掉，改法和影响见 §6.1①②。改后墩在 3x 上的
> 影线是 **1.0 pt**，和 AiCoin 那一列对齐；辉是 0.667 pt。

### 2.4 留缝：为什么缩小后会「挤在一起」

| | AiCoin | 我们 |
|---|---|---|
| 留缝规则 | 间隙 ≈ 0.32 × 步距，**按比例留**，实测恒在 1–3 px | `cap = cell - 1`，即**恒留 1 个设备像素** |
| 3x 手机上的物理缝宽 | — | **0.333 pt** |
| 密集时的表现 | 缝始终看得见 | 缝只有 1/3 pt，视网膜上几乎并成一片 |

「墩」的 `cap` 在 spacing < 3.34pt（3x）时开始生效（出处 `ours-geometry.md` §1.4），
也就是**一屏超过 100 根**之后，实体就被 `cell-1` 截住、缝被压到 1 个设备像素。这正是用户
截图里「缩小后挤在一起」的那个区间。

> 复查之后这一条的锅分成两半，见 §6.1③ 和 §6.2④：
>
> - **真正的漏洞**是 `cell - 1` 这条上限**只管实体、不管影线**。再挤一点（一格 3 个像素）
>   就会退化成只画影线，而影线用的是风格量化值——墩在 3x 上 3 个像素，一格 3 个像素，
>   缝是 **0**。已经改成影线也受 `cell - 1` 约束。
> - **按比例留缝**（`cap = cell - round(cell * 0.15)`）**没有采纳**：真正顶到上限的只有
>   「砖」，它的一句话就是「实体几乎满格 · 彼此只留一线缝」；其余风格的缝是 `bodyR`
>   直接决定的，改上限等于绕过风格表重新设计每一款。

## 3. 放大 / 缩小的运动轨迹

### 3.1 价格轴：两档语义（本次最重要的一条）

**AiCoin 桌面版实测**，价格轴右下角有「对数 / % / 自动」三个钮：

| 状态 | 行为 | 实测证据 |
|---|---|---|
| 「自动」**开**（默认） | 每次平移/缩放都按可见窗口**重新贴合**价格轴 | 一次横拖，轴从 `1349.58…1262.36` 变成 `1344.15…1262.51` |
| 竖拖价格轴 → 切成**手动** | 刻度变成**绝对钉死**的区间，此后横向平移/缩放**一个像素都不动** | 跨度 81.6 → 102.8 之后连拖两次，七个标签 `1354.74 / 1339.55 / 1324.53 / 1309.68 / 1294.99 / 1280.47 / 1266.11` **逐字节相同** |
| 复位 | 图区右上角出现一个复位钮 | 手机版的形态见 §7（当时写的「圈着的 R」是**错的**，已订正） |

**我们改动前**：`PriceTransform.zoom` / `shift` 是**贴合结果上的相对倍率**，而
`KanpanCore.priceRange(...)` 每帧都按可见 K 线重算贴合——所以「手动调好的价格刻度」
横向拖一下就会跟着极值进出而漂移。**我们根本没有真正的手动档。**

**本次改动**（全部在本次 commit 内）：

| 改动 | 出处 |
|---|---|
| `PriceTransform.pinned: (lo, hi)?` —— 非 nil 即绝对钉死，`zoom`/`shift` 一并失效 | `PriceScale.swift` |
| `priceRange(...)` 在钉住时**短路返回**，一根 K 线都不扫；`base` 照旧跟着视野走 | `PriceScale.swift` |
| `PriceAnchor.pin(range:factor:keeping:at:pane:mode:)` —— 解析解，不再二分 | `PriceAnchor.swift` |
| `PriceAnchor.pan(range:dy:pane:mode:)` —— 手动档下的整段平移 | 同上 |
| 竖拖价格轴改成写 `pinned`；单指拖图的竖向分量在钉住时也走 `pan` | `ChartView+Gesture.swift` |
| 捏合冻结在钉住时**不参与**（`freeze` 解出的是 `pinned == nil` 的变换，会把钉子拔掉） | 同上 |
| 复位钮：`Layout.autoFitButton` / `hitsAutoFit` + `ChartRenderer.drawAutoFitButton` + `ChartView.resetPriceScale()`（240ms 三次缓出，插值的是**钉子本身**，所以缓动过程中也不会边动边重新贴合）。**造型与位置后来按安卓包实测订正过，见 §7** | `Layout.swift` / `ChartRenderer.swift` / `ChartView+Gesture.swift` |

为什么 `pin` 能解析求解：区间一旦是绝对的，`yOf` 在正向空间里就是线性的，于是
`u = (pane.y + pane.h - y) / pane.h；newSpan = span / factor；newA = f(p) - u × newSpan`。
从前非得二分 60 步，只是因为 `zoom`/`shift` 得穿过那层每帧重算的贴合。

百分比档同样精确：`base` 在 `u = (p-lo)/(hi-lo)` 里会约掉，所以在价格空间里钉 lo/hi
对百分比档也是逐比特稳定的——这条有测试（`PricePinTests.钉住不影响 base 跟着视野走`）。

## 6. 落地情况

### 6.1 已改（本次一并实现，基线已重录）

**① 影线不再一律兑淡 —— 改的是生效区间，不是风格表**

AiCoin 的做法是根本不兑（§2.3：491 个影线样本与实体完全同色）。我们的 `wickTint`
（墩 0.7 / 砖 0.45 / 辉 0.6）本来是给「大实体配粗影线」准备的，让影线往背景退半步、
实体才压得住；可蜡烛一捏小，这份退让就只剩「影线看不见」。

风格表是定版规格不动，改的是 `ChartRenderer.drawCandles` 里兑淡的**生效区间**：

```
旧： tint = bodyW*scale <= 2 ? 1 : style.wickTint          // 一个硬台阶
新： fade = clamp((bodyW*scale - 2) / 6, 0, 1)
     tint = wickTint + (1 - wickTint) * (1 - fade)         // 8 像素以上照兑，8→2 线性收回
```

旧阈值太低（一屏一百多根时实体还有 3~6 个像素，照兑不误），而且跨过去的那一帧颜色
会跳一下。默认根间距下 11 款的实体都在 8 个设备像素以上，`tint` 就是风格表原值，
一张基线都不动；真正变的是捏小之后——以及 2x 上的「针」（默认实体只有 6 个像素，
兑淡从 0.900 收到 0.933）。

**② 影线物理宽度跟屏幕倍率走（`wickPixels`）**

`wickPixels` 从前把 `scale` 参数 `_ = scale` 丢掉，于是风格表的 `wick` 被当成
「所有倍率下都是这么多个设备像素」——屏幕越精细影线越细。风格表是照 2x 屏调出来的，
所以按 2x 口径换算：

```
旧： max(1, round(max(0.5, wick)))
新： max(1, round(max(0.5, wick) * scale / 2))
```

| 风格 | wick | 2x 旧→新 px | 3x 旧→新 px | 3x 旧→新 pt |
| --- | --- | --- | --- | --- |
| 墩 | 1.8 | 2→2 | 2→**3** | 0.667→**1.000** |
| 针 | 2.0 | 2→2 | 2→**3** | 0.667→**1.000** |
| 辉 | 1.2 | 1→1 | 1→**2** | 0.333→**0.667** |
| 阔 | 1.0 | 1→1 | 1→**2** | 0.333→**0.667** |
| 芯 | 1.0 | 1→1 | 1→**2** | 0.333→**0.667** |
| 描 0.9 / 纸 0.8 / 靛 · 砖 · 骨 · 密 0.5 | | 1→1 | 1→1 | 0.333→0.333 |

墩因此落到 **1.0pt**，正好是 AiCoin 实测的 1 个设备像素 @1x（§2.3）。iPhone 15/16/17
全是 3x，从前那 0.667pt 比 AiCoin 细三分之一——这是实机反馈「影线模糊」的另一半。

后四款（0.5~0.9）要的就是发丝影线，量化后仍是 1 个设备像素，没动。

**③ 影线也要让出那条缝（`candlePixels`）**

②把影线加粗之后暴露了一个旧漏洞：`cell - 1` 的留缝上限**只管实体**，影线直接用风格
量化值。捏小到一格只剩 3 个像素时，墩在 3x 上的 3 像素影线自己就把一格占满了，缝是
**0**，一排影线糊成一堵墙——正是「影线挤在一起」那句话的字面意思。改成

```swift
let wick = min(wickPixels(style: style, scale: ratio), max(1, cell - 1))
```

`KanpanCore` 的「实体之间至少 1 像素缝」那条测试也跟着从「只在非 `thin` 时要求实体让缝」
扩成「`thin` 时轮到影线让缝」，一格只有 1 个像素时除外（那是密度上限，谁也让不出来）。

**这三条动了哪些证据**

- A3.11 的 176 张像素基线：**64 张变了**（5 款 × 2 主题 × 6 台 3x 机型 ＝ 60 张，
  加上 2x 的「针」4 张），已用 `make evidence` 重录。变的都是影线那几列。
- A3.2 的 77 个数里 `wickW` 变成**有意分歧**，不再进 ±1 设备像素的比对：原型算的是
  `style.wick / dpr`（墩在 3x 上 0.6pt），我们算的是固定物理宽度（1.0pt），差 1.2 个
  设备像素。分歧逐条记进 `A3.2-geometry.json` 的 `knownDivergences`，其余 66 个数
  照旧 ±1。这一条符合任务书「原型即规格，冲突时以原型为准并说明」的例外口径：
  原型这里的口径本身跨倍率不自洽，说明写在 `CandleWidths.wickPixels` 的文档注释里。

### 6.2 不改，以及为什么

**④ 留缝按比例（`cap = cell - round(cell * 0.15)`）——不改**

真正会顶到 `cell - 1` 这条上限的只有「砖」（`bodyR = 0.96`，一句话就是「实体几乎满格 ·
彼此只留一线缝」）。其余风格的缝是 `bodyR` 直接决定的，不是被上限截出来的：墩默认档
缝占 4/27 ＝ 14.8%，辉 5/21 ＝ 23.8%。把上限改成按比例，等于绕过风格表去改每一款的
体宽比——那是重新设计，不是对齐。捏小之后的糊成一片已经由 6.1③ 解决。

**⑤ 副图之间留 9px 空隙——我们本来就有，而且更宽**

`ChartRenderer+Sub.swift` 画副图时用的是 `Pane(indicator:, y: pane.y + 15, h: pane.h - 19)`，
也就是上留 15pt、下留 4pt，比 AiCoin 的 9px（＝9pt，显示器 1x）还分得开。原先这一条
是测 AiCoin 时只看了面板分隔线、没去查我们自己的 inset，属于记错了。

**⑥ 默认风格「墩」的 `bodyR = 0.86` 比 AiCoin 的 0.686 胖——不改**

「墩」这一款就是为「胖」设计的（`one: "实体九成 · 圆头粗影线"`）。想要 AiCoin 那个比例，
现成的「辉」正好是 0.70。这是口味差异，不是谁做得更好。

## 7. 订正：复位钮是「A」不是「R」，弱徽章不是描边钮

写 §5 那一节时我手上只有 AiCoin **桌面版**的截图，桌面版价格轴右下角是「对数 / % / 自动」
三个钮。手机版长什么样我没有证据，却写成了「官方自己收成一个圈着的 R」并照着实现了——
那是推断，不是实测。

后来另一个会话把 AICoin 安卓包反编译出来，拿到了这颗钮的原始定义
（`docs/AICoin-安卓包-UI规格提取.md` §3 / §23.3 / §23.4），三处都对不上：

| | 我们改动前 | AICoin 安卓包实测 | 本次 |
|---|---|---|---|
| 字面 | 「R」 | `android:text="A"`（Auto） | 改成「A」 |
| 造型 | 描边圆圈，`dim` 色 | 圆角 2dp 的实底小方块，灰字浅底 | 改成圆角 2pt 弱徽章：底 `crossBg`、字 `dim` |
| 字重 | — | `D.t()` 挂载时强制 `Typeface.DEFAULT` + `setFakeBoldText(false)`，**明确非粗体** | 常规字重（本来就是） |
| 内边距 | — | 上下 2dp / 左右 6dp，12sp | 上下 2pt / 左右 6pt，10pt（跟着我们自家轴字号，比例照它） |
| 位置 | 价格轴底部、**时间轴上面**那一格 | 贴**主图区底边**，和「展开右侧面板」图标共用基线 | 改成贴主图区底边 |

位置这条对我们比对它更要紧：AICoin 的主图底边和时间轴之间只隔着副图，而我们默认挂
**MACD + RSI 两个副图**，时间轴离主图的价格刻度隔着大半屏——一个管价格轴的钮摆在那儿，
用户根本不会把它和刚拖过的价格刻度联系起来。贴主图底边之后它正好落在价格轴最后一个
刻度标签底下。

**没照抄的一条**：AICoin 是 `layout_gravity="end"` + `marginEnd 18dp`。它的价格轴画在
图表 View 内部，浮层得靠 `marginEnd` 躲开；我们的价格轴本来就是独立一列，所以跟着这一列
里另外两个方块（最新价胶囊、倒计时）一样从 `plotW + 2` 起算——自家对齐比模仿它的
gravity 重要。

**颜色**：AICoin 用的是一组专门的中性色 `ui_kline_scale_auto_bg_color`（日 `#f3f5f7` /
夜 `#303442`）。我们不新增颜色常数，借十字线读数那一对 `crossBg` / `crossInk`，理由和
倒计时那格一样——它是浮在图上的一小块开关，跟行情无关，不该跟着涨跌色走，语义对得上。

**显隐语义本来就对**：AICoin 的 `setOnMainYAxisScaleStateChanged` + `getIsMainYAxisScaled`
决定徽章显隐，点一下 `chart.z()` 恢复自动后立刻消失——**不是常驻按钮**。我们的
`PriceTransform.isManual` 是同一套语义，这条不用改。

**不动像素基线**：徽章只在 `price.isManual` 时才画，A3.11 的 176 张取证帧全是自动档，
一张都没动。

## 8. 安卓包第二批：落笔对齐、影线口径、副图量柱

对照源换成了 AICoin 安卓包的反编译结果，规格整理在
`docs/AICoin-安卓包-UI规格提取.md`（§3 蜡烛几何 / §23.3 复位徽章）。这一批一共五条，
**改了一条，四条记录不改的理由**。

### 8.1 改了：副图量柱漏掉了「留缝」上限

安卓包里量柱和蜡烛实体同宽——实体 = 节距 × 2/3，两边各留 节距/6，**恒有缝**。
回头查我们自己的代码，`subVol` 取的是 `candleWidths`（原型对账口径），
不是主图在 37b8825 之后改用的 `candlePixels`（渲染口径）。两者差的正是
「相邻两根至少留 1 个设备像素缝」这条上限。

算一笔账（墩，根间距 1.2pt，3x）：

| | 旧（`candleWidths`） | 新（`candlePixels`） |
|---|---|---|
| 影线像素 | 2（只看 dpr） | 2（风格量化后再让缝） |
| 实体像素 | `round(3.096)=3` → `evenUp` 配偶数顶到 **4** | 先被 `cap=2` 压住 → **2** |
| 一格宽 `floor(1.2×3)` | 3 | 3 |
| 缝 | **−1（相邻两根重叠）** | **1** |

也就是说捏小之后量柱不是「挤在一起」而是真的**互相压住**，和用户实机反馈的
那堵墙是同一个病根，只是主图修了、副图漏了。MACD 柱本来就自带 `cell − 1` 上限
没这个病，但它的「目标是实体宽的一半」也跟着换成实画宽度，两个副图口径统一。

代价：A3.11 的 176 张基线动了 **32 张**，全落在四款紧凑风格上
（砖 / 针 / 纸 / 密 × 8 机型 × 明暗里各自受影响的那些）。默认视野下改动是
「量柱宽度从对账口径换成实画口径」，多数差 1 个设备像素；重叠只在捏小之后才出现，
取证帧拍不到。已重录，`make chart-test` 66/10 全绿。

### 8.2 不改：落笔对齐——这条反过来印证了我们的分歧是对的

安卓包里**一个对齐动作都没有**：没有 `+0.5`，没有按 density 取整，全是裸 float。
它之所以不糊，是因为蜡烛（`C2723k`）、网格（`J`）、十字线（`F0`）三个文件里
**一次 `setAntiAlias` 都没调**——抗锯齿是关的。

这是二选一不是三选一：**路线 A** 关 AA + 两个方向都不 snap；**路线 B** 开 AA + snap。
我们走的是 B，而且 `drawCandles` 的注释里早就写了「和原型的分歧：x 和 y 两个方向
都对齐到设备像素（原型只对齐 x）」。在 B 路线下双向 snap 比只 snap x 更自洽，
所以这条**不改**，只是把它从「我们自己的取舍」升级成「有外部佐证的取舍」。
真正要避免的是「开着 AA 又不 snap」，那才是糊的来源，我们没犯。

### 8.3 不改：影线宽与节距无关

安卓包的影线是固定 `strokeWidth = 2.0f` 裸像素，**不随缩放变**。我们的
`wickPixels(style:scale:)` 同样只看风格表和屏幕倍率，不看根间距——两边口径一致。
唯一的附加约束是 `candlePixels` 里那句 `min(wickPixels(...), max(1, cell − 1))`，
只在捏到极小时才生效，是我们为「留缝」多加的保险，安卓包没有对应物但不冲突。

### 8.4 不改：涨跌蜡烛的 ±1 不对称

安卓包给涨蜡烛画的是 `drawRect(左, 上, 右 − 1, 下)`，跌蜡烛不减这个 1，于是
涨的比跌的窄 1 个像素。这看着像是历史遗留而不是设计——同一份规格的提取方也建议
「要么两边都做要么都不做，别复制这个不对称」。我们的 `cell − 1` 上限是对称施加的，
**照旧**。

### 8.5 不改：网格只有横线

安卓包的网格层只画横线，没有竖线。我们的竖向网格挂在用户可选的
`.none / .tick / .both` 三档上，默认也不是 `.both`——这是个功能位而不是缺陷，
把它删掉等于砍掉一个已验收的设置项。**不改**。

### 8.6 已经一致：十字线竖线钉在 bar 中心

安卓包的十字线竖线是 `(i + 0.5) × 节距 − scrollX`，钉在第 i 根的中心，不跟手指
像素走（那个 `+0.5` 是「第 i 根的中心」的语义，不是半像素对齐）。我们
`ChartRenderer.swift:127-128` 的 `state.magnet ? nil : cross.t` 正是同一套：
磁吸开着（默认）就取 `x(b.time(at: i))` 也就是 bar 中心，关掉才停在手指上。
**本来就一致，不用动。**
