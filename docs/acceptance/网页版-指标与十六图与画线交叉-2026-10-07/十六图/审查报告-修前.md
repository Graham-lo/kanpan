## 问题清单（按严重度）

### P0-1　自选品种多时，网关第 3 条连接被拒，全页判「断线」，16 格全部不再跟推送，而且永远恢复不了
- **复现**
  1. 默认网关线路，自选面板打开「加密 300」，十六图，开不开订单流都一样。
  2. 等 8 秒：`__stream()` 显示 `conns [64,64]`、state `closed`。
  3. 再等 30 秒，16 格的最新价全部没动。
- **对照**：自选只有 20 只时，连接是 `[34]`，state `open`，16 格都在跟推送。
- **证据**
  - 截图：`C15-大自选下十六图实时全停.png`。每格红标「30 秒内最新价没动」，每格底栏小红点。
  - 前两条连接这 30 秒其实一直在收帧（931 帧、535 帧）。BTC 1h 的 kline 就在第 1 条上，数据在来，是被丢掉了。
  - 挂机 3 分钟那段（c13 里的 C15）同样是 0/16 格变过价。
- **根因**（客户端为主，网关为辅）
  1. `src/market/stream.ts:46`：网关上限 `TOTAL.gateway = 160`。`effective()`（:140–145）把格子流、自选报价一起截到 160，所以要开 3 条连接（64+64+32）。
     - 第 3 条（32 只自选报价）被网关拒掉：1008 或握手 429。
     - 网关的同一 IP 合计上限是 160（`Backend/kanpan-gateway/stream_hub.py:210`）。同一出口 IP 下的其他标签页、手机网页版、iOS 走网关都在吃这 160。
  2. `stream.ts:300–306` 的 `fail()` 一条连接失败就设 `failed = true`，`paint()`（:162–168）随即把**全局** `S.wsState` 置成 `'closed'`。
     - `failed` 只有等「所有连接都收到过帧」才清（:202、:251、:278）。
     - 而 `apply()` 每次退避后又按 160 规划出第 3 条，它又被拒。所以 `failed` 永远是 true。
  3. `src/pages/chart.ts:1224–1227` 的 `updateStale()` 在 `wsState==='closed'` 5 秒后 `setStale(true)`。
     - :1304 的 kline 推送处理 `if (... st.stale) return`，**所有格子的推送一律丢弃**。
     - 结果：前两条连接上 128 路数据照常进来，图却全冻住，底栏小红点亮着。
  4. 叠加 `assignStreams`（stream.ts:78–95）不看优先级：
     - 16→1→16 之后，15 格的 kline 成了「孤儿」，被分到新开的第 3 条上。
     - 而那几条报价占着前两条不动，于是优先级最高的格子流反而落在最容易被拒的连接上。
- **建议修法**
  1. 单条连接失败不等于全局断线。`wsState` 应该按「核心流（各格 kline/ticker、当前格 mark/trade）所在连接」来判；自选报价那条断了只把那几只报价置灰。
  2. 被拒（1008、429）的流计入 `rejected`，或者把 `TOTAL` 动态收缩到已成功连接数 × 64，不要无限重开同一条注定被拒的连接。
  3. `assignStreams` 带优先级：核心流永远落在第 1 条、最早建立的连接上；超额时先挤掉自选报价。
  4. 网关和客户端的上限对齐：要么网关同 IP 上限大于 160，要么客户端 `TOTAL.gateway` 小于同 IP 余量，比如读 1008 的回执后自适应。
  5. 回归用例：自选 300 + 十六图挂 1 分钟，16 格都要变过价。

### P1-1　K 线没缓存、每格都拉 1500 根：反复切 1↔16（或者 16 格连扫品种）会把额度打穿，被排队的格子长时间空白、没有提示
- **复现**：十六图 → 一图 → 十六图，每轮间隔约 1 秒，来回 20 轮（b10）。
- **证据**
  - 每轮 1→16 都重拉 15 格 × `limit=1500`（权重 10/格）。20 轮共 213 个 K 线请求，约合权重 2130，额度只有 800/分（`src/market/limit.ts`，GATEWAY_SHARE 2/3）。
  - 第 5–7、12–14、19–20 轮，最多 15 格空白超过 16 秒：背景空着，`.cell-empty` 隐藏，没有「排队中」或「限流」字样。截图：`B10-限流排队时的空格.png`。
  - 堆从 3.47 涨到 7.55 MB，悬着 15 个 timeout。这是限流排队里没带 alive 的请求在睡（`admit` 睡 `min(w, alive?1000:5000)`，limit.ts:293）。65 秒后回落到 4.2 MB、0 个。
- **根因**
  - `src/market/rest.ts:156` `klines()` 默认 1500 根，没有任何会话内缓存。刚关掉的格子再开回来要重新取。
  - `src/pages/chart.ts:262–300` `loadCell` 只在取数完成或失败后才调 `showCellEmpty`。在 limiter 里排队期间什么都不显示。
- **建议**
  1. 加一层会话内 K 线缓存，键为品种 + 周期，LRU 约 32 份。回切直接出图，只补尾巴（跟 `resyncTail` 同一路）。
  2. 多格布局里非当前格首屏先取 300–500 根（权重 2）；往左拖时再补，按现有 `loadMore` 路径走。
  3. `loadCell` 进 limiter 排队时显示轻提示，比如「排队取数…」或骨架；被限流时已有文案，排队也要有。
  4. 见 P2-3：排队请求要可撤销。

### P2-1　十六图在 2560×1440 及以下永远不画副图；2560×1440 的十二图只因为宽度差一点就被降级
- **证据**（`A7`、`A8`，截图 `A8-*-十六图.png`）

| 视口 | 十六图格子 | 档位 | 十二图格子 | 档位 | 九图格子 | 档位 |
|---|---|---|---|---|---|---|
| 1920×1080 | 368×214 | 只主图 | 368×296 | 只主图 | 492×296 | 主图+量 |
| 2560×1440 | 528×304 | 主图+量，**副图 0（配了 3 个）** | 528×412 | 主图+量（只因 w<640） | 705×412 | 全，副图 3 |
| 3440×1440 | 748×304 | 主图+量（h<400） | 748×412 | 全 | 999×412 | 全 |
| 125% 缩放 | 400×232 | 只主图 | 400×320 | 只主图 | 535×320 | 主图+量 |

- **根因**
  - `src/chart/panes.ts:68–69` `degradeFor`：`w < 640 || h < 400` 就收掉所有副图。
  - CSS 的紧凑档是 `c-narrow w<640 / c-tiny w<420 / c-short h<360`（`src/styles/app.css:894–898`）。两套门槛不一致：2560 的十二图 CSS 不算短，JS 却按窄降级。
- **建议**
  - 副图改成按剩余高度逐个保留，不再全有全无。主图至少 160 px，每个副图至少 56 px，放得下几个画几个。
  - 宽度门槛降到约 480。
  - JS 与 CSS 用同一组常量。

### P2-2　九图、十二图在「全」档时图例占画布高 24–29%
- **证据**：2560×1440 九图图例 120 px（29%）；3440×1440 九图、十二图都是 100 px（24%）（A8）。十六图的紧凑档只有 7%，反而更清爽。
- **根因**：全档图例每个指标一行，ma、ema、boll、vol 加 3 个副图的标题全堆在主图左上（`src/styles/app.css` legend 509–522 段）。
- **建议**：格子高 < 500 时，图例把主图指标并成一行，超出部分用「…」折叠；或者鼠标悬停才展开。

### P2-3　排队请求不可撤销：被关掉的格子的持仓量请求、限流重试还在排队、还在发
- **证据**：B10 里悬着的 15 个 timeout，每个睡 5 秒一轮；关掉的格子的 `openInterestHist` 请求照常发出。
- **根因**
  - `src/market/rest.ts:169–173` `attachOI` 调 `j()` 时没传 alive。`pages/chart.ts` 在 settle 时检查了 `dead`，但入队以后就不再检查。
  - 持仓量副图没开、或格子被降级不画副图时也照样取。
  - `pages/chart.ts:288` 限流后的 `setTimeout` 重取只比对 token，不看 `cell.chart.dead`。
- **建议**
  - `attachOI` 接受 alive，并且只在该格真的显示持仓量副图时才取。
  - 限流重试同时判断 `!cell.chart.dead`。

### P3-1　底栏区间按钮（1天 / 5天…）点在非当前格上：改了那一格的周期，却不把它设为当前格，也不管「周期跨图同步」
- **复现**：十六图，当前格是 BTC，点 XAU 格底栏的「1天」。XAU 从 1d 变成 1m，但工具栏、高亮仍在 BTC 上。打开周期同步后，其他格也不跟着变。
- **根因**：`src/pages/chart.ts:228` 的底栏点击直接调 `applyRange`（:353–362），没有先 `setActive(cell.idx)`，也不走 linkIv 分支（同一处的 `save` 按钮倒是先 `setActive` 了）。
- **建议**：`applyRange` 前先 `setActive`；改周期统一走与工具栏周期相同的入口，自然带上 linkIv。
- 截图：`A2-十六图-当前格高亮.png`（高亮仍在原格）。

### P3-2　没有「单格放大」
- 双击格子没有反应；右键菜单 7 项（创建提醒、画水平线、记一笔、复制价格、重置视图、对数坐标、隐藏画线）里也没有放大。⇧F 是整页全屏（`pages/chart.ts:1126`）。
- 多图看盘的标准动作是「放大一格看细节 → 再缩回」。TradingView 是 Alt+Enter 或格子角上的最大化按钮。
- **建议**
  - 格子底栏或右键菜单加「放大这一格」，双击格子标题区也可以。
  - 放大时临时按一图渲染，不改布局存档；Esc 或再按一次还原。
- 截图：`A6-十六图-右键菜单.png`。

### P3-3　撤销栈是全局的，跨品种
- **复现**：两格（BTC、ETH）。在 BTC 格画一条线，点 ETH 格，按 ⌘Z，撤掉的是 BTC 格那条线，只有一句「已撤销」toast，用户看不到被撤的是什么。
- **根因**：`src/pages/chart.ts:395` 全局只有一组 `undoStack` 和 `redoStack`。
- **建议**：按品种分栈（画线本来就按品种存）；或者撤的不是当前格品种时，先把那一格闪一下。

### P3-4　常态下每秒约 10–16 次布局
- 一图（自选面板开着）就有约 10 次/秒，十六图挂机 3 分钟是 2898 次（16 次/秒），样式重算 4534 次。
- 来源之一：`pages/chart.ts:1324–1329` 每秒给所有格子底栏的 `.clock` 写 `textContent`，十六图就是 16 次写入；另一个来源是自选报价刷新。
- 每次代价很小，没有长任务，属于优化项。
- **建议**：时钟只留一个，比如放在顶栏；或者给 `.clock` 设 `contain: strict` 和固定宽度。

### P3-5　测量与环境说明（不是应用的问题）
- 用 Playwright 的 locator 点菜单时，它会持有已脱离文档的菜单节点，每开一次菜单约留 180 个节点。脚本改成在页内 `.click()` 以后，节点数平稳在 1201。`overlay.ts` 的 `closeMenu` 没有泄漏。
- 无头 Chrome 的帧间隔 p50 33–50 ms、p95 约 67 ms，一图和十六图一样，是无头模式的节拍，不是应用造成的。所以性能对比用布局、样式重算、长任务、CPU，不用帧时。

### C15 挂机 3 分钟（十六图 + 订单流 + 自选 300）
- CPU 15.7–17.2%（机器负载 4.4–9.6）。
- 布局 2898 次、样式重算 4534 次。
- 长任务：第二轮 0 个；第一轮负载 9.6 时 17 个，最长 217 ms。
- interval 稳定在 6 个；rAF 约 41 次/秒。
- WS 消息约 4–6 万条，主要是订单流。
