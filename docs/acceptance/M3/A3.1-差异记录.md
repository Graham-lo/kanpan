# A3.1 / A3.6 原型并排对照 —— 差异记录

对照物：定版原型 `prototype/看盘原型.html`（§12.1 唯一对照物）。
被测物：`KanpanChart` 离屏渲染出的 app 基线（`docs/acceptance/M3/M3-*.png`）。

取证方式：Python 标准库静态服务器伺服 `prototype/`，浏览器加载真实原型 JS，接管
`devicePixelRatio` 后按 8 个机型的设备 pt 尺寸渲染，由页面 JS 把 canvas
`toDataURL('image/png')` POST 回服务器落盘（**没有用浏览器截图工具**）。
逐像素比对与并排合成同样在页面内用 `OffscreenCanvas` + `getImageData` 完成，
`createImageBitmap(blob,{colorSpaceConversion:'none'})` 关掉色彩管理。
解码可信度自检：同一张 app png 解码两次逐字节比对，差异 0。

**本文只记录差异，不修改任何一侧。** 原型与 app 源码在本轮全程只读。

| 项 | 结论 |

## 二、⚠️ 疑似真实 bug（唯一一处，单列）

### `M3-ipad-light-needle-06.png` / `M3-ipad-dark-needle-06.png` —— 主图 17 根蜡烛整体偏 1 个设备像素

**现象**：iPad mini（744×1133 @2x）+ `needle` 风格下，主图里有 **17 根**蜡烛的实体
在 app 与原型之间整体错开 1 个设备像素。以其中一根为例：

- app 实体覆盖设备像素 `[1262 .. 1268]`
- 原型实体覆盖设备像素 `[1263 .. 1269]`
- 宽度同为 7 px，**形状完全一致，只是整体右移 1 px**

**量化**：主图区 `mainPlot` 的 `r64`（差值 > 64 的像素占比）
= 0.000400（light，约 1037 px）/ 0.000370（dark，约 959 px），
`maxChannelDelta` = 230 / 218。
这两张是全部 183 对里 **mainPlot `r64` 唯一超过 1e-4 的**——
其余 181 对的 mainPlot `r64` 平均只有 0.000026，最大 0.00011。

**根因（已定位，不是逻辑 bug）**：两侧把 `x(t)` 的分母算成了不同的浮点数。

`KanpanCore/Sources/KanpanCore/Geometry/ViewWindow.swift`：

```swift
public struct ViewWindow {
  public var to: Double
  public var span: Double                 // ← 存的是 span
  public init(from: Double, to: Double) { self.to = to; self.span = to - from }
  public var from: Double { get { to - span } set { span = to - newValue } }
  public func x(_ t: Double, plotW: Double) -> Double { (t - from) / span * plotW }
}                                                    //          ↑ 除以存储的 span
```

原型 `prototype/src/chart.js` 对应写法：

```js
((t - this.view.from) / (this.view.to - this.view.from)) * L.plotW
//                        ↑ 每次用 to - from 重新算
```

实测数值（就是上面那根蜡烛）：

```
span            = 318461538.4615385      （app：构造时一次算出并存起来）
to - from       = 318461538.4614258      （原型：每次重算，from 本身是 to - span 反推的）
差              = -1.127e-4 ms
xApp            = 632.9999999999186   → raw = 1262.4999999998372 → snap → 1262
xProto          = 633.0000000001426   → raw = 1262.5000000002851 → round → 1263
```

即 `raw` 正好落在 `.5` 上，`(x * scale).rounded()` 的进位方向被 1e-13 量级的
浮点尾差掰反。ipad@2x + needle 这个组合下，恰好有 17 根蜡烛的 `raw` 同时命中 `N.5`，
所以差异集中爆发；其他 `dpr=3` 的机型 `raw` 很少正好落在 `.5`，因此看不到。

**判断**：
- **不是渲染逻辑错误**。两侧都满足 A3.10（`x * scale` 为整数、无半像素模糊）。
- 是 `ViewWindow` 存 `(to, span)` 并除以 `span`，而原型存 `{from, to}` 并除以
  `(to - from)`，IEEE754 结合律导致的尾差。
- **风险**：数学上 app 与原型的 `x(t)` 不是同一个表达式，任何 `raw` 命中 `.5`
  的场景都可能出现 ±1 设备像素抖动。这一条**建议提给 owner 决策**
  （例如让 `ViewWindow` 也存 `from` 并按 `to - from` 求分母，或在 `snap()` 里
  统一加一个确定性的 epsilon），**本轮按约定没有改任何一侧代码**。
- 影响面：肉眼几乎不可见（1 个设备像素 = ipad@2x 上 0.5 pt），但它是本轮
  **唯一一处「图形几何真的不一致」**的差异，其余全是光栅化差异。

热力图证据：`sbs/DIFF-ipad-light-needle-06.png`（红色 = 差值 > 64）。

## 三、其余差异：按成因分类

183 对全部计算了逐像素差异，并按 5 个版面分区二次定位。结论很干净：

| 分区 | 平均 `r`（差 > 0 占比） | 平均 `r64`（硬差占比） | 结论 |
|---|---|---|---|
| `legendMain` 主图图例行 | 0.16718 | **0.124545** | 字体光栅化 |
| `priceAxis` 右侧价格轴 | 0.06597 | **0.037860** | 字体光栅化 |
| `timeAxis` 底部时间轴 | 0.04516 | **0.025003** | 字体光栅化 |
| `subPanes` 副图整体 | 0.06234 | 0.024340 | 见下方拆分 |
| `mainPlot` 主图绘图区 | 0.01128 | **0.000026** | 仅抗锯齿 |

把 `subPanes` 再拆成图例条与绘图区（`A3.1-subpane-diff.json`，183 行）：

| 子分区 | `r` 中位数 | `r64` 中位数 | 结论 |
|---|---|---|---|
| `subLegend` 副图图例文字行 | 0.15018 | **0.11153** | 字体光栅化 |
| `subPlot` 副图绘图区 | 0.03365 | **0.00015** | 仅抗锯齿 |

**读法**：凡是画文字的地方，硬差（`r64`）占到 10%–12%；凡是画图形的地方，
硬差是 0.002%–0.03%（万分之几到百万分之几）。
→ **全部「肉眼可辨」的差异都来自文字，不来自图形。**

### 3.1 字体渲染差异（`legendMain` / `priceAxis` / `timeAxis` / `subLegend`）

- **差在哪**：所有文字的字形边缘与字重。app 侧是 CoreText 光栅化
  `ui-monospace`（SF Mono）到 CGBitmapContext；原型侧是浏览器
  （Skia/CoreGraphics 混合路径）光栅化同一 CSS 字体栈
  `10px ui-monospace, SFMono-Regular, Menlo, monospace`。
- **差多少**：文字行内 `r64` 10%–16%，`maxChannelDelta` 达 253（黑底上白字的
  某个亚像素位置一侧画了、另一侧没画）。但文字**位置、内容、行高、基线完全一致**
  ——差异像素全部贴着字形轮廓，没有整体位移。
- **归类**：**字体渲染差异**。两套光栅化引擎的 hinting / gamma / 亚像素策略不同，
  不可能逐像素相同，也不构成规格偏离。
- 证据：`sbs/DIFF-pro-light-stout-01.png` 中，图例行与价格轴整条被标红，
  而蜡烛区几乎全白。

### 3.2 抗锯齿差异（`mainPlot` / `subPlot`）

- **差在哪**：蜡烛实体与影线的边缘、MA/MACD 折线的斜边、网格线端点。
- **差多少**：`mainPlot` 平均 `r` 1.13%，其中 99.8% 落在差值 ≤ 32 的区间；
  `r64` 平均 0.000026。`subPlot` 同理（`r` 中位数 3.37%，`r64` 中位数 0.00015）。
- **归类**：**抗锯齿差异**。两边都在同一设备像素栅格上 `snap()` 过，
  差的是边缘那一条 alpha 覆盖率的量化方式。

### 3.3 个别 `maxChannelDelta` 偏高但像素数极少的（已逐一核过，可忽略）

| 图 | 主图 `maxDelta` | 差 > 64 的像素数 | 说明 |
|---|---|---|---|
| `M3-mini-dark-dense-11.png` | 233 | **约 20 px** | `dense` 风格 spacing 最小，个别蜡烛边缘 alpha 量化翻转 |
| `M3-mini-light-dense-11.png` | 209 | 约 41 px | 同上 |
| `M3-std-dark-dense-11.png` | 233 | 约 23 px | 同上 |
| `M3-std-light-dense-11.png` | 209 | 约 45 px | 同上 |
| `M3-se-light-stout-01.png` | 101 | 约 63 px | 同上 |

这些都是**几十个像素级别**的孤立点，与 §二 的 1000 px 量级（17 根蜡烛整体位移）
不是一个量级，归类为抗锯齿。

## 五、结论

1. **A3.1 / A3.6「肉眼无差别」成立**。图形几何在 181/183 对上完全一致
   （主图硬差占比 2.6e-5），差异集中在文字光栅化，属两套渲染引擎的固有差异。
2. **唯一一处需要 owner 决策的是 §二 的 `ipad × needle` 1 设备像素偏移**，
   根因是 `ViewWindow` 除以存储的 `span`、原型除以重算的 `(to - from)`，
   IEEE754 尾差把落在 `.5` 上的 17 根蜡烛的舍入方向掰反。**本轮未修改任何一侧。**
3. 无其他疑似 bug。
