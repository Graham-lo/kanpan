# A3.12 [I] 静止时 DisplayLink 暂停，CPU 占用 < 1%

方法：Instruments Time Profiler，30 秒。证据类型按任务书 §12.1 的 ④（`.trace` / 导出 csv）。

结论：**通过**。静止 30 秒内 `CADisplayLink` 全程 `isPaused == true` 且 `timestamp` 一动不动；
同一段时间里 Time Profiler 对取证 app 进程只采到 **15 次**（每次 1 ms），折算 CPU 占用 **0.049%**，
`ps` 侧 CPU 时间增量 **0.03 秒 / 30.876 秒 = 0.097%**。阈值是 1%，两条线都差着一个多数量级。

那 15 次采样一帧都不属于图表：全部落在 FrontBoard 从进程外推来的一次 scene 设置变更上
（栈根是 `FBSWorkspaceScenesClient _queue_updateScene:withSettings:diff:`），跟 `ChartView`、
`CADisplayLink` 无关。在模拟器完全没有其他 app 活动的那一轮（下表 run 4），
Time Profiler 对本进程的采样数是 **0**，CPU 占用 **0.000%**。

## 2. 为什么要单独做一个取证 app

仓库里现有的 `Kanpan` app target 还是 M0 的占位壳，只链 `KanpanCore`、只显示一个启动配色页，
**里面根本没有 `ChartView`**，拿它测不出 A3.12。M3 的图表是 SwiftPM package，包本身跑不起来。
所以新开了一个只有一个 `ChartView`、别的什么都不做的最小取证宿主：

```

└── KanpanEvidenceHost/
    ├── HostApp.swift                      # 纯 UIKit 入口，无 SwiftUI、无定时器、无网络
    ├── HostFixture.swift                  # 按 EvidenceSupport.swift 的口径读定版快照
```

`KanpanChart/Sources/` 下**一个既有文件都没改**，`App/`（`Kanpan/`）、`KanpanData/`、

回溯到仓库根目录去读那一份（模拟器进程能直接读宿主机路径）。

## 3. DisplayLink 真的停了（A3.12 前半句）

### 3.1 代码侧：直接读 `ChartView` 里那个 link

`ChartView.link` 是 `private`，产品代码不该为了取证开口子。所以取证宿主用
`Mirror(reflecting: chart)` 把这个存储属性读出来（Swift 的 Mirror 能看到 private 存储属性），
**没有给 `KanpanChart` 加任何新接口**。

用 `--probe` 启动时，宿主挂一个 1 Hz 观察定时器打点，完整日志见 `A3.12-displaylink.log`，摘要：

```
  1.050  settled     paused    2940251.376415      ← 画完一屏就自己停了
     —   poke        setNeedsRedraw(.all)
  2.100  poked       RUNNING   2940251.376415      ← 戳一下，link 确实能被唤醒
  3.150  repaused    paused    2940253.450000      ← 刷完又停，timestamp 往前走了
     —   window      静止 30 秒开始（不碰屏幕）
  5.158 … 35.159     paused    2940253.450000      ← 31 次采样，全是 paused，
                                                      timestamp 一个值都没变过
== 结论 ==
静止窗口采样 31 次（1 Hz，30 秒）
其中 isPaused == false（link 在跑）：0 次
其中 没有 link 对象：0 次
窗口内出现过的 link.timestamp 取值：1 个 → 2940253.450000
```

中间那次 `poke` 是故意的：它证明观察点能看见「link 在跑」这个状态，不是探针本身瞎了。
`CADisplayLink.timestamp` 只有回调真的触发时才会往前走，所以 30 秒里 timestamp 只有一个取值，
比单看 `isPaused` 更硬。

### 3.2 系统侧：Time Profiler 的栈里没有图表

跑过的四轮有效采样（见下表），对 `KanpanEvidenceHost` 的采样数分别是 1 / 29 / 0 / 15，
**逐条把栈全部翻过一遍：`KanpanChart`、`ChartView`、`CADisplayLink` 的栈帧一共出现 0 次。**

模拟器上完全没有其他 app 活动的那一轮（run 4），30.839 秒里采样数是 **0**——
连 trace 的 TOC 进程列表里都没有这个进程，一次都没在 CPU 上被抓到。

有采到东西的那几轮，栈根都能指认出来是进程外的刺激：留档的 run 5 里那 15 次采样挤在
第 24.9–25.9 秒，完整调用栈是

```
-[BSAction(UIActionType) UIActionType]
-[UIScene _actionsWithSubstitutionsForTransitionActions:forFBSScene:fromTransitionContext:]
-[UIScene scene:didUpdateWithDiff:transitionContext:completion:]
-[UIApplicationSceneClientAgent scene:handleEvent:withCompletion:]
-[FBSScene updater:didUpdateSettings:withDiff:transitionContext:completion:]
-[FBSWorkspaceScenesClient _queue_updateScene:withSettings:diff:transitionContext:completion:]
...
-[UIApplication _run] / UIApplicationMain / AppDelegate.$main()
```

——FrontBoard 从进程外推过来一次 scene 设置变更，app 的 runloop 被动处理了 15 ms，
跟绘制、跟 DisplayLink 一点关系都没有。run 1 那唯一一次是 `_dispatch_cache_cleanup`，同理。

## 4. CPU 占用的数（A3.12 后半句）

两条互相独立的算法：

**a) Instruments 侧。** Time Profiler 每条采样的 `weight` 是 1.00 ms（trace 里 `<weight fmt="1.00 ms">`），
所以 `CPU% = 采样数 × 1 ms ÷ 墙钟时长`。导出命令：

```
xcrun xctrace export --input A3.12.trace \
  --xpath '/trace-toc/run[@number="1"]/data/table[@schema="time-profile"]'
```

按进程归并后的采样数在 `A3.12-samples.csv`（留档那一轮共 682 个进程，第一行就是被测进程）。

**b) `ps` 侧。** 在 30 秒窗口的正前和正后各取一次 `ps -o time= -p <pid>`，做差。

跑了五轮，一轮作废，四轮有效（`A3.12-cpu.csv` 是同一张表的机读版）：

| run | 时长 | 本进程采样数 | CPU%（Time Profiler） | `ps` CPU 增量 | CPU%（ps） | 图表栈帧 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 30.758 s | 1 | 0.003% | 0.00 s | < 0.033% | 0 | 同机有别的会话在跑 `make chart-test` |
| 2 | 30.800 s | 29 | 0.094% | 0.03 s | 0.097% | 0 | 同一台模拟器上有别的进程在装/起 app |
| 3 | — | — | — | — | — | — | 作废：模拟器被别的会话连 app 一起关掉了 |
| 4 | 30.839 s | 0 | **0.000%** | 0.00 s | < 0.032% | 0 | 模拟器最干净的一轮 |
| **5** | **30.876 s** | **15** | **0.049%** | **0.03 s** | **0.097%** | **0** | **留档这一轮，`Tools/a3.12-cpu.sh` 跑出** |

**留档取值 run 5：静止 30 秒，CPU 占用 0.049%（Instruments）/ 0.097%（`ps`），阈值 1%，通过。**

留档的是 run 5 而不是数字最好看的 run 4，是因为 run 5 的 trace / csv / 截图全部由仓库里那份
`Tools/a3.12-cpu.sh` 一条命令跑出来，别人重跑能对得上；run 4 是手工分步做的，没留档。
run 5 那 0.049% 的来路在 3.2 节写清楚了，是 FrontBoard 推来的一次 scene 设置变更，不是绘制。
把这个外部干扰摘干净（run 4），数字就是 0.000%。

`ps` 那一列的 0.03 秒要打个折扣看：`ps` 的 TIME 只有 10 ms 分辨率，0.03 秒本身带着
±0.01 秒的量化误差，它和 Instruments 的 15 ms 之间那点差距落在分辨率里，没有意义。

## 5. 踩到的坑，如实记

- **`xctrace` 对模拟器进程 attach 不了。**
  `xcrun xctrace record --template 'Time Profiler' --device <sim-udid> --attach <pid> --time-limit 5s`
  会打出 `Attaching to: A3.12 (85616). Time limit: 5.0 s` 然后**永远卡住**——5 秒的限时等了 5 分钟
  还在跑，产物只有一个 52K 的 `Trace1.run/RunIssues.storedata`，最后只能 `kill -9`。
  换 `--launch` 一样卡。不带 `--device` 直接在宿主机 attach 则是 `Cannot find process for provided pid`
  （宿主机看不到模拟器进程号），`--attach KanpanEvidenceHost` 是 `Cannot find process matching name`。
  `Activity Monitor` 模板在模拟器上直接报 `Activity monitoring service not available on this device`。
- **绕法：在宿主机上 `--all-processes` 录。** 模拟器进程是宿主机上的真实进程，`--all-processes`
  能把它们一起采到（trace 里能解析出 iOS 26.5 simruntime 的 dylib，进程列表里有 SpringBoard、
  backboardd、MobileCal 等模拟器进程，说明模拟器侧确实在被采样），然后按 pid 归并即可。
  代价是 trace 很大（76 MB）、stderr 会刷一堆无害的 `Timeline modification failed -- dylibs overlap by ...`。
- **`.trace` 不入库。** 仓库 `.gitignore` 第 13 行是 `docs/acceptance/**/*.trace`，
  所以 `docs/acceptance/M3/instruments/A3.12.trace` 在磁盘上有、但 git 不收。
  没有擅自改 `.gitignore`。入库的是导出的 csv（`A3.12-cpu.csv`、`A3.12-samples.csv`）、
  探针日志和截图，数都能从 csv 复算出来。
- **中途 app 被别的会话连模拟器一起关掉过一次**（run 3 作废，`ps` 读到空）。
  重新 boot、重装、重跑，才有 run 4 / run 5。同一台模拟器被多个会话共用时，
  别人一次 `simctl install` 就会给所有前台 scene 推设置变更，把本进程的 CPU 抬到几十毫秒。
  要拿最干净的数，测的时候别让别人碰这台模拟器。
- **`A3.12-samples.csv` 里别的进程数字很难看**（宿主机上还有别的活儿在跑，
  有进程能吃掉将近一整个核）。那是 `--all-processes` 的副产物，只用来证明这份 trace
  确实在采样、确实覆盖到了模拟器侧；A3.12 只看 `KanpanEvidenceHost` 那一行。
