### 13:21:13 那一轮两路同时 503：根因与修复

- **现象**：第一轮币安、OKX 两路同时 503 `market unavailable`。币安在这条路上本该是 451，说明请求根本没走到币安的应答，是更早一步就失败了。
- **日志**：网关 journal（`4.9/gateway-journal-2050-2122.txt`）只记了 503，看不到原因。
  - `server.py` 把 `Unavailable/HTTPError/OSError/…` 一起吞掉，原样回 503。
  - 往前翻，上一次行情 REST 请求在 20:23:21，**中间空了约 58 分钟**。
- **机制（本机复现，`4.9/gateway-stale-pool-repro.py`）**：
  - `market_rest.Upstream` 给每个交易所主机留最多 8 条保活连接。`fetch` 只在复用连接失败时重试一次，而重试又从池里拿下一条。
  - 交易所按自己的时钟关掉空闲连接，一段安静之后池里的连接是一起死的。
  - 池里有两条以上死连接时，两次都拿到死连接，抛 `upstream unreachable`，结果是交易所好好的，手机却拿到 503。
  - 复现脚本输出：`Unavailable: upstream unreachable | cause: ConnectionResetError(54, 'Connection reset by peer')`。
- **为什么空闲 10 分钟没复现**：10 分钟短于交易所关闭空闲连接的时限，池里的连接还活着。58 分钟的那次，两家的池都已经死了。
- **修复（提交 1b53091）**：
  - 一条复用连接失败就清空整池，重试必走新连接。新增回归用例 `UpstreamPoolTests`，旧代码上红（`ConnectionResetError` → `Unavailable`），新代码上绿。网关单测 64 条全过。
  - 503 的原因写进 stderr，也就进了 journal，以后能分清是死池、冷却还是限速。
- **部署状态：没有部署。** 往主节点备份并 rsync 这一步被本机自动模式分类器拦了，已打包成桌面脚本 `~/Desktop/kanpan-P4-网关保活修复部署.sh`。脚本会：
  1. 拿部署锁；
  2. 从 origin/main 取文件；
  3. 备份到 `/opt/kanpan-gateway/backup-<时间>/`；
  4. 语法校验后替换，只重启 kanpan-gateway；
  5. 只读验证 health、OKX 100 根、币安 451；
  6. 验证不过就自动回滚。
  备用节点这次没有动。

#### B2. 测试账号隔离

**用户名：** 各用例都是「前缀 + UUID 去掉横线后的前 12 位十六进制」，也就是 48 位随机，彼此碰撞可以忽略。后端用户名不分大小写（accounts.rs:81），所以没转小写的前缀也不会出问题。

- **密码：** 大多数用例用固定的 "Testpass2026"，ShareFlow、AccountExport、Compare 用随机密码。
- **每个用例一个账号：** 都成立。XCTest 每个测试方法新建一个实例，ShareFlow 在 setUp 里为每个方法造两个。例外是设置了环境变量 `SHARE_QA_USERS` 时，ShareFlow 改用一组固定账号（:19-20）：多轮、多个方法、并发运行都共用这组账号。它的 HTTP 会话 kind 是 desktop（:225-227），并发运行时同一类别的会话会互相顶掉。
- **会话共享：**
  - AccountExport 和 ShareFlow 的 HTTP 会话用 desktop 类别，不会顶掉 app 里的手机会话。
  - 各用例 tearDown 里的 forceDelete 登录不带 kind，服务端按手机算，会把 app 的会话顶掉。这发生在收尾阶段，没有害处。
  - AccountSessionReplaced 故意用同一类别，就是要测被顶掉。
- **启动环境隔离：**
  - 钥匙串服务名是 `kanpan.account.test.<PERSISTENCE_PROFILE 或 "normal">`（AccountFeature.swift:66-70）。
  - 本地文件放在 `kanpan/accounts/tests/<uuid>`，前提是 profile 必须是合法 UUID（AppAccountBridge.swift:69-71）。
  - 这两条都只在 DEBUG 构建里生效。
  - 各账号用例都给了新的 UUID profile：
    - AccountExport:28、PrefSync:53、FavoritesGroupSync:30-31、ShareFlow:43
    - ReviewInteraction:24、IPadSignedIn:118-120、Compare:15、ChartLayout:18,:25
- **隔离缺口：**
  1. 基类 KanpanUICase（UITestSupport.swift:119-124）只设 `KANPAN_TEST_PROFILE=1`，不设 profile。继承它但没覆写 profile 的用例（KeyboardUsability、IPadLayoutUITests 的访客用例 :84 等）会：
     - 共用钥匙串服务 `kanpan.account.test.normal`；
     - 让本地文件落回**非测试的** `kanpan/accounts` 根目录，和开发者手动运行 app 的数据是同一处。
     眼下没有用例在这个共享档案里登录成功，但只要那里残留一个会话，访客登录门用例就会误判。
  2. Info.plist:41-42 把线上地址写死了。所以不设 `KANPAN_ACCOUNT_API_URL` 的用例连的也是线上后端，而所有 UI 账号测试本来就跑在**共享的线上后端** `https://kanpan.107-174-172-10.sslip.io`，没有隔离的测试后端。
  3. 每个 profile 留下的钥匙串条目和 `tests/<uuid>` 目录没有任何用例清理，会在模拟器里越积越多。走 HTTP forceDelete 的收尾不会清 app 的钥匙串。
