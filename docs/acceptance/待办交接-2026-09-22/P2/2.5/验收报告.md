## 时序怎么摆的（不靠 sleep）

- **BT-06**：新增假件 `GateSocket` / `GateSocketBench`（`KanpanNetwork/Sources/KanpanNetworkTestSupport/NetworkFakes.swift`）。
  - `receive()` 挂在不理会取消的 continuation 上，只有真的有人调 `cancel()` 才回来。
  - `holdCancel(on: 1)` 把 1 号 socket 的 `cancel()` 扣在一道 Gate 上。这样 `networkChanged` 就停在 `await ws.stop()` 里（「关旧连接要等一次真往返」）。
  - 测试等到闸前真有人报到，再依次插入 stop / 第二次 online / 进后台 + `ManualPacer` 拨 25 秒闹钟 / 回前台，最后开闸。
  - 连接数按 `bench.live()` 数，即从没被 cancel 过的 socket。
- **BT-08**：消费者任务取消后，等 `for await` 循环真的退出。随后断言：socket 没被 cancel、连接数没变（owner 还在管）。owner `stop()` 之后才断言 socket 被 cancel。
- **BT-10**：两条候选都是 `GateSocket`（聋）。
  - 选路超时由 `ManualPacer` 推进。
  - 父任务取消用 `task.cancel()`。
  - 首帧静默、传输静默由 FastPacer / ManualPacer 推进。
  - 断言的是每条 socket 的 `cancelCalls ≥ 1` 且挂着的收帧已经带错返回；`connect` / `stop` 自己能返回。
- **BT-13**：全部是同步用例，直接调 `AppLifecycle.shared.phaseChanged`，中间没有 `await`，别的用例插不进来。钩子故意先登记 `.sync`、后登记 `.data`，以此证明先后由档位决定、不由登记顺序决定。`sync` 钩子执行时记下「data 已经跑完几个」，必须是全部。
- **BT-14**：
  1. 用 `store.afterArchiveWritten { blocked.signal(); release.wait() }` 把写盘队列真堵住。
  2. 堵着时排进 v1 存档写和一笔正式文件写（伴随写）。
  3. `.data` 钩子产出 v2。`.sync` 钩子先发 `leaving` 信号，再调 `flushNow()`。
  4. 另一条线程等到 `leaving` 信号才放行队列。
  - 断言：离场能返回（自锁就永远挂在这里）；放行发生在主线程已经挂到排空上之后；伴随写执行时盘上已经是 v2；两版只真写一次；重开存档读到的是 v2。
- **BT-20**：
  - 把 `MainScreen` 里 `didBoot` 那道闸收成 `BootOnce` 修饰符 + `BootLatch`，测试直接用 `MainScreen` 实际用的那只修饰符。
  - 纯闸用例由两种先后、重入各覆盖一遍。
  - 真 SwiftUI 用例：挂进 `UIWindow` + `UIHostingController`，用 `latch.onAttempt` 这个 continuation 等到「第二个入口也到了」。10 秒兜底只在入口根本不来时才会走到，走到本身就算失败。
  - 假的行情 / 报价簿 / 账号加 Counter，数 boot 实际跑了几次。
- **BT-21**：
  1. `SyncGateProtocol`（URLProtocol）把 `/v1/sync/operations` 扣在 `ResponseGate` 上，请求一到就往 AsyncStream 报一声。
  2. 等 A 的推送真挂上之后，同一个 `AccountClient` `accept(B)`，B 用另一个临时目录建存档、记自己的一条操作。
  3. 开闸：A 的回执到达。
  - 两道门各测一遍：调用方拿到的是 `CancellationError`（客户端换代）；把 A 的回执原样递给 B 的 `acknowledge`，B 的存档在内存里和盘上一个字节都不动。同一份回执对 A 仍然有效。
- **BT-22**：
  - 假钥匙串 `HeldVault` 可以把「下一次写」扣住。
  - 先让 A 的一次后台令牌轮换（`client.accept`）卡在 `vault.write` 里。这时 `AccountClient` 这个 actor 被占着，restore 和退出 / 登录的 actor 调用都只能排在它后面。
  - 主 actor 上依次启动 `restore()` 和 `logout()`（或 `accept(B)`），用一格空的主 actor 任务把它们都送到各自第一个 `await`（主 actor FIFO），再放开钥匙串。
  - 旧代码下 restore 读到 A、回来照样装 A，这个结果是确定性的（修复前日志见下）。

另有两处「证明没有多拨」的负向窗口，都是在确定性断言之后补的一道：`FeedConvergenceTests.noNewConnection` 等 0.3 s，`DeafSocketTests.stopCancelsDeafSocket` 等 50 ms。时序本身不靠它们摆。

## 修掉的产品 bug

1. **BT-06：`MarketFeed.networkChanged` 迟到重连**（`KanpanData/Sources/KanpanData/Feed/MarketFeed.swift`）
   - 问题：`await ws.stop()` 之后只看了 `networkGeneration`。所以：
     - owner 已经 `stop()` 了，迟到的切换还会再拨一条没人管的孤儿连接（06a）；
     - 在后台里被迟到的切换拨号（06d / 06e）；
     - 回前台已经重连之后又起第二条（06f）；
     - 迟到的 `suspendWS` 还会把新连接刚报的「在线」盖成「离线」（06f）。
   - 修法：新增 `stopped` 标志（`stop()` 置位，`switchTo` / `start` 清掉）。重连前还要求 `lifecycleEpoch` 未变、`wantsForeground`、`!stopped`。`suspendWS` 收尾时如果 `wsGeneration` 已被换掉，就不再报离线。
   - 修复前 06a/d/e/f 共 10 处断言红，见 `logs/data-bt06-before-fix.log`。
2. **BT-21：`SyncStore.acknowledge` 不认 operationId**（`KanpanAccount/Sources/KanpanAccount/SyncStore.swift`）
   - 问题：A 的回执一旦递到 B 的存档，A 的画线就进了 B 的 `objects` / `local`，下次同步会当成 B 的推上去。
   - 修法：只认本存档 `operations` 里的那几条。一条都不是自己的，就整份回执不动存档（连 `offset` 都不抬）。
   - 修复前 7 处断言红，见 `logs/account-bt21-before-fix.log`。
3. **BT-22：`AccountFeature.restore` 迟到装回旧 owner**（`Kanpan/Kanpan/Account/AccountFeature.swift`）
   - 问题：restore 要跨两次 actor 往返，期间用户退出或登上 B，restore 回来照样 `onPrepareAccount(A)`。结果是刚退出的人又被登回来，B 被 A 的档案盖掉。
   - 修法：新增 `generation`，`accept` / `logout` 各抬一次，restore 两次 `await` 后号对不上就作废。
   - 修复前日志：退出用例事件序列是 `prepare:guest, apply:guest, prepare:alice, apply:alice`，`user` 仍是 alice；登录用例 `user` 被盖回 alice。见 `logs/main-bt20-bt22-mutation.log`。
4. **BT-20：启动闸移出 `MainScreen`**（`Kanpan/Kanpan/Main/BootOnce.swift` 新增，`MainScreen.swift` 改用 `.modifier(BootOnce(boot: boot))`）
   - 行为不变（原来 `didBoot` 这道闸是对的），但它埋在 app 工程里，无从测量。收成独立件后可以在 KanpanMain 里真挂视图测量。
   - 顺带让 `MainScreen` 那条修饰符链少套一层（iOS 27 栈深那件事）。
   - 变异检验：删掉 `guard !fired` 后三条全红，见同一份 mutation 日志。
   - BT-10 的变异检验在 KanpanNetwork 那一侧做过三处（probe 的 onCancel 置空、超时分支删 `socket.cancel`、首帧静默删 `cancel`），每一处对应用例都红，见 `logs/mutations.txt`。

## 判断

- **BT-21 的「桥上 epoch 守卫」**：`AppAccountBridge` 在 app 工程里，不进任何测试包。所以 BT-21 量的是它下面的两道门：`AccountClient` 换代丢弃，和这一轮补上的 `SyncStore.acknowledge` 自守。存档自守之后，就算桥漏了，也串不了户。
- **BT-22 的 `AccountFeature`**：以符号链接接进 KanpanMain，新增的 `init(client:)` 只给测试用；`accept(_:)` 从 `private` 放宽到 internal，因为用例要从这里摆「登录先完成」。
- **BT-13 / BT-14 共用 `AppLifecycle.shared`**：用例全是同步的，和同包里 BT-17 的同步用例在主 actor 上不会交错。
