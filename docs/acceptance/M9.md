## 1. 怎么跑

```

cd Kanpan/Diagnostics && xcodebuild test -scheme KanpanDiagnostics \
  -destination 'platform=iOS Simulator,name=iPhone 16 Pro'   # 51 条 / 9 套件（含帧探针）
```

本轮实测：mac 47/47 全过（0.018s）；iOS 模拟器 51/51 全过（2.59s）；`make core-test`
180/180 全过；`make build` BUILD SUCCEEDED。零警告（mac 和 iOS 两边都用
`-warnings-as-errors -strict-concurrency=complete` 单独过了一遍）。

`Kanpan/Kanpan/Diagnostics/` 这个目录不需要改 `project.pbxproj`——app target 用的是
`PBXFileSystemSynchronizedRootGroup`，丢进去的文件自动进编译。

在 mac 上整个文件被 `#if os(iOS)` 编掉，`swift test` 连编都不编它。所以帧探针那 4 条

「DisplayLink 真的回调了吗、两个 runloop 观察者真的夹住了一帧吗」，是这条链上最容易

## 2. 这一摞东西是什么

| 文件 | 干什么 |
|---|---|
| `MeasurementText.swift` | 把 MetricKit 的 `"500 ms"` / `"12 kB"` 解析成数。这是全链上唯一会因为系统改文案而碎掉的地方 |
| `PayloadDigest.swift` | JSON → 摘要（启动分位、挂起、写盘、崩溃/挂起/CPU/启动四类事件） |
| `DiagnosticsStore.swift` | 落盘、淘汰、导出。原文一个字节不丢，摘要另存一份 |
| `DiagnosticsCenter.swift` | `MXMetricManager` 订阅 + 补收历史 payload；`simulateReceive` 是注入假 payload 的口子 |
| `FrameStats.swift` | 帧样本 → hitch 占比 / 丢帧数 / 绘制耗时分位 / 三条预算判定 |
| `FrameProbe.swift` | 采集端：`CADisplayLink` 取帧节奏，一对 `CFRunLoopObserver` 夹主线程忙时 |
| `FrameReportStore.swift` | 帧报告落盘与汇总 |

**帧探针为什么不去改 `ChartView`。** 最直接的做法是在 `onFrame()` / `drawPlot` 前后打
时间戳，但那要动 M3 已经封版的绘制层（176 张逐像素基线压着）。这里改用完全不侵入的
办法：主 runloop 一轮的形状是 `afterWaiting`（醒）→ 各种回调 → CoreAnimation 的
commit observer（order 2000000）→ `beforeWaiting`（睡）。在醒的那一端挂 order `Int.min`
的观察者、睡的那一端挂 order `Int.max` 的，一减就盖住了这一帧主线程上的全部工作，
**包括 CA commit**——而三层重绘真正发生的地方就在 commit 里。

**单测揪出来的一个真 bug**：`record(label:seconds:)` 原来写的是

mac 上编不到这段，是 iOS 模拟器那 4 条冒烟测试撞出来的。

## 5. 我自己定下来的几处

**① 「hitch 时长占比」按 Instruments 的口径算，不另造一个。**
任务书 P9.2 写「hitch 时长占比 < 1%」，Instruments 的原生指标叫 hitch time ratio，
单位是 ms/s。1% 就是 **10 ms/s**。`FrameStats.hitchRatio` 算的是同一个量
（超时总毫秒 ÷ 采集总毫秒），所以两边的数可以直接对着看，不用换算。

**② 「掉帧」的判据是每帧各自的预期间隔 × 1.5，不是全局中位数。**
低电量模式、系统降频、后台回来，都会让 120Hz 中途变 60Hz。用全局中位数当基准，
降频后每一帧都会被算成掉帧，占比冲到 50%，报告说「掉帧一半」而其实一帧没掉
（`refreshRateChangeMidRun` 就是钉这个的）。所以每帧都取 `targetTimestamp - timestamp`
作为当下的预期间隔。1.5 倍这个系数是为了容忍 DisplayLink 本身 ±20% 的抖动——
按「超一点点就算」去判，一台没问题的 120Hz 机器能报出 4% 的占比。

**③ P9.3 的「三层合计」，进程内量的是上界，不是精确值。**
runloop 观察者夹住的是这一帧主线程上发生的**一切**：手势处理 + 指标增量 + 三层
`draw(in:)` + CA commit。它一定 ≥ 真正的三层绘制耗时。这个方向是安全的：**上界
< 3ms 就说明绘制一定 < 3ms，判过不会放水**；反过来超了才需要 Time Profiler 归因。
GPU 那一侧完全看不到（在渲染服务进程里），只能靠 Instruments。

**④ 「没收到」一律报 `nil`，绝不报「过」。**
P9.7 的原话是「MetricKit 崩溃报告为空」。刚装上、一份 payload 都没收到时，
报「为空 = 过」是在说谎——所以 `crashFree`、`Verdict.allPassed` 都是 `Bool?`，
没数据就是 `nil`，脚本打出来是「判不了」。同理 `MeasurementText` 解析失败返回 nil
而不是 0，`FrameQuantiles.of([])` 返回 nil 而不是全零。

**⑤ 存储单位跟 MetricKit 走 1000 进制。**
`MXUnitStorage` 的 `kB` 是 1000 字节。任务书 §11 的「磁盘 K 线痕迹 ≤ 60 KB」如果用
`du -k` 量就是 1024 进制，两个数差 2.4%。诊断链里一律按 MetricKit 的 1000 进制报，
证据表上写 `kB`；`du` 那条另算，不混。

**⑥ 诊断自己占的盘：64 份 / 512KB 封顶，超了从最旧删，最新那份永远留着。**
这是诊断数据，不是行情数据，所以不吃 §11 那条 60KB 的预算；但也不能无限涨。
512KB 是按「MetricKit 一天最多一份、一份典型 5–30KB、留够两周还有余量」定的。
「最新那份永远留着」是硬规矩：否则一份超大的崩溃报告一进来就会被清理逻辑自己吃掉。

**⑦ 取证产物放 `docs/acceptance/M9/`，`.trace` 不入库。**
和 M3 的 `docs/acceptance/M3/` 同一个约定。`.gitignore` 里已有的
`docs/acceptance/**/*.trace` 正好盖住 `trace-perf.sh` 的输出——trace 动辄几百 MB，
导出的 XML 和汇总 JSON 入库就够了。

**⑧ 不引任何崩溃 SDK。**
任务书「零第三方依赖」是硬约束，所以没有 Crashlytics/Sentry 那种进程内捕获信号的
兜底。代价要说清楚：MetricKit 给的 `callStackTree` 是**未符号化**的地址，要配
`.dSYM` 才看得出函数名；而且**最快也要等到下一次启动**才拿得到。换来的是零依赖、
零网络外传、崩溃数据全在用户自己手机的沙盒里。这个取舍我按任务书的约束定了。

## 7. 你要验的

第 3 节那张表每次 `swift test` / `xcodebuild test` 全跑，不需要你逐条点。
到手机上真正要你做的是第 4 节那 8 行——其中 P9.2 / P9.3 两行，`Tools/trace-perf.sh`
