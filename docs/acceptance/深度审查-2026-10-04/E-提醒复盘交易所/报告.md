**E-1 [P1] 画在已经走完那段行情上的回撤 / 矩形提醒永远不响，胶囊却照出、提醒一直挂「生效中」**
- 文件：`KanpanCore/Sources/KanpanCore/Alerts/AlertGeometry.swift`（rectangle、fibonacci 两个分支，以及新增的 `canAlert`）、`Alert.swift`（`AlertLine.isSpent` / `Alert.isSpent`）、`Kanpan/Kanpan/Alerts/LineAlert.swift`（`phrase`）、`AlertStore.swift`（`add`）、`AlertPrompt.swift`（`offerBatch`）、`AlertRecordRow.swift`（`spentNote`）、`Backend/kanpan-api/src/alerts.rs`、`contract/alert-cases.json`、`KanpanChart/Sources/KanpanChart/ChartView+Drawing.swift`（`bells`）。
- 根因：两锚点区间之外 `price(at:)` 一律返回 nil。矩形上下沿、回撤各级只在 [t0, t1] 内有效，价格回到 0.618 时那一截早就过去了。胶囊只看「能不能摊出线」，不看「此刻还有没有线价」。服务端用同一份几何，同样永远不响。
- 修法（按已定取舍）：
  - 矩形上下沿、回撤每一级视为水平价位，`extendRight: true`，从左锚点起一直往右延。
  - 趋势线 / 箭头线不替它延，只有线本身开了延长才延。
  - 新增 `AlertGeometry.canAlert(_:at:)`：线段已走完且没开延长的，胶囊不出、存档不建、收朋友的线也不问。走完之前就已经开着的那条照出胶囊，方便人点掉。
  - E-1 之前建的、已经走完的旧提醒，在总表里写「线段已走完」，不再假装生效中。
  - 服务端几何与契约夹具同步改。`AlertTests.swift` 原来把「区间外 == nil」当正确行为断言，这次一并改对。
  - 铃铛配套：提醒线右延之后铃铛仍挂在画出来的右锚点上，不飘到图区右边的空白里。
- 回归用例：

**E-2 [P2] 跨分钟一跳穿线漏判（约 1/60 的穿越不响）**
- 文件：`Kanpan/Kanpan/Alerts/AlertEngine.swift`（`observe` 换桶处）。
- 根因：新桶的高低价只用这一分钟第一口价初始化。上一口价与这一口价之间那一段不属于任何桶，线落在缝里就漏掉。
- 修法：换桶且间隔不超过 `staleBuckets` 时，新桶 `high = max(price, 上一桶收盘)`、`low = min(price, 上一桶收盘)`。断流超过阈值时不补，避免误响。

### 诊断（`fdcec19f`）

**E-9 [P3] 诊断存储按字节先进先出混删，每日指标把崩溃报告挤掉**
- 文件：`Kanpan/Kanpan/Diagnostics/DiagnosticsStore.swift`（`Limits.diagnosticRecords / diagnosticBytes`、`pruneLocked`）。
- 根因：指标与崩溃 / 卡死诊断共用一条队列、一份 512 KB 字节预算。每天一份 20–60 KB 的指标，十来天就填满，最值钱的崩溃报告被当作「最旧」先删。
- 修法：
  - 诊断占条数与字节各 3/4 的配额。
  - 超限时先删最旧的指标；诊断自己超出配额、或已经没有指标可删时，才删最旧的诊断。
  - 最新那一条永远不删。
- 回归用例：`DiagnosticsStoreTests`「每天一份的大指标挤不掉崩溃报告：先删指标」「诊断自己超了配额才删诊断，最新那条永远留着」。

**诊断-F1（自查，即待核实二）帧探针：record 倒计时里手动停掉又开新一轮，旧倒计时到点会把新那轮提前掐掉、存盘**
- 文件：`Kanpan/Kanpan/Diagnostics/FrameProbe.swift`。
- 修法：

  - `record` 记下自己开的那一场；倒计时醒来后，场次号不一致就直接 `completion(nil)`，不动新的那一轮。
- 回归用例：`FrameProbeSmokeTests`「record 倒计时里手动停掉又开新一轮：到点不掐新的那轮」。

### 交易所账户（`d89baa24`）

**R1 [P1] 品种名带中文时签名串与发出的串不一致，整次拉单永远失败，界面报「Key 或 Secret 不对」**
- 文件：`Kanpan/Kanpan/Exchange/Binance/BinanceRequestSigner.swift`（允许字符集）、`BinanceFuturesAccount.swift`（发送端）。
- 根因：`CharacterSet.alphanumerics` 含 CJK，中文原样进了被签名的串；`URL(string:)` 又会把非 ASCII 自动转义，于是币安回 -1022。
- 修法：
  - 只放行 ASCII 字母数字与 `-_.~`。
  - 发送端用 `URLComponents.percentEncodedQuery` 原样放入签好名的串，并加守卫：发出去的 query 必须等于签名的串，不等就不发。
- 回归用例：`ExchangeAuditRegressionTests` 三条「R1 非 ASCII 代号先按 UTF-8 百分号转义再签名」「R1 只放行 RFC 3986 非保留字符」「R1 账户请求里的中文代号：线上的查询串是转义过的，签名覆盖的正是它」。
- **只有单测、未真机验。**

**R2 [P1] 首次回溯期间又成交，凭空生出孤儿仓，之后这个品种这个方向的回合全被吞掉**

- 回归用例：`ExchangeAuditRegressionTests`「R2/R6 先对时、再拿持仓快照……」「R2 仓位变动时间早于交易所此刻」；`BinanceFuturesAccountTests.pagesAreStitched` 按新顺序重写。

## 五、续：待核实五与 R13 桥层（`a5505117`）

### 待核实五：后台刷新拉起 app 时，回合当轮就上传

**现象**：后台刷新（BGAppRefresh）在没有界面时拉起 app，拉到的新回合要等下次回前台才上传。这次复核发现还有更重的一半：已登录用户的回合档记在 `u-…` 名下时，后台那一轮连拉都不拉。

**根因**（两半）：
1. ReviewFeature、AccountFeature、AppAccountBridge 都是 `MainScreen` 里视图的 `@State`。没有界面就没人建它们，桥的 `weak var review` 是 nil，所以没有上传通道。只把 ReviewFeature 提到 app 级没用：它要的账号会话 client 也在 MainScreen 里。
2. `AccountFiles.currentProfile` 只在账号桥的提交点（`AccountFiles.activate`）赋值，后台拉起时是空串。`ExchangeRoundsOwnership.view(rounds, owner: "u-…", profile: "")` 判为 hidden，于是 `ownerMismatch` 为真，`pullNow` 在 `guard !ownerMismatch`（`ExchangeReviewBridge.swift:237`）就回去了。

**修法**：在桥层，不动 MainScreen。
- 新增 `Kanpan/Kanpan/ReviewIntegration/ExchangeReviewUplink.swift`。`resolve()` 不靠任何视图，按账号根目录与钥匙串会话问出两件事：
  - 此刻是谁：已登录给 `u-…`；会话读不出时给 `lastOwner`；否则给访客档案。
  - 上传通道：只有已登录才有。它用该账号目录下同一份 `trades-v1.json` 开 `TradeReviewStore`，客户端用 `AccountFeature().client` 并钉住 owner，走 `TradeSync.upload`。上传是幂等的（批次键、uploaded 标记都落盘），回前台后 ReviewFeature 再 synchronize 也不会重传。
- `ExchangeReviewBridge.backgroundPull()`：
  - review 在时照旧：先拉，再 `review.trades.synchronize()`。
  - review 为 nil 时：先 `resolve()`，`currentProfile` 为空时用它的 profile 判属主，再拉，最后把属于此人、可见的回合交给 uplink 上传。
  - 属主不符、没接入、没登录时不上传。
- 装配口可注入：`currentProfile` 与 `headlessUplink` 两个闭包，正式装配仍走 `convenience init()`。

### R13 桥层用例与它暴露的 `removeAll` 漏洞

桥层单测能写：`ExchangeReviewBridge` 的指定构造器接收 `ExchangeCredentialStore`，store 接受可注入的 `ExchangeKeychainIO`，给它一个假 Keychain（`MemoryKeychain`，新加 `allowDeletes(_:)`）即可。原先「它用真 Keychain、没法测」的判断不对。

写桥层用例时发现 `d89baa24` 里 `removeAll` 的毛病：它两项都试着删，Key 删不掉时元数据照删。桥这一刻显示「已接入」，但下次启动读状态是 nil，显示未接入，Key 却还留在钥匙串里，用户也没法再点断开。现在改成先删 Key、删不掉就抛错，元数据原样留着；Key 删掉了、元数据没删掉时照实抛错，再移除一次就收干净。规则是「元数据在 = Key 可能还在」。

用例：
- 存储层（`ExchangeAuditRegressionTests`，替换原「R14 断开时 Key 删不掉：另一项照删」）：
  - `removeAllKeepsStatusWhenKeyDeleteFails`
  - `removeAllRetriesAfterStatusDeleteFails`
- 桥层（`ExchangeBridgeBackgroundTests`，suite「审查 E · 桥层移除交易所 Key（R13）」）：
  - `keyDeleteFailureKeepsConnected`：重开桥仍是已接入，可以再断开。
  - `statusDeleteFailureThenRetry`
  - `cleanDisconnect`
