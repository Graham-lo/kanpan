## 偏差与说明

按开工提示词「原型即规格，两者冲突以原型为准并说明」的要求，这里把和任务书字面不一致的地方列全：

1. **`KanpanData` 是独立的 SwiftPM 包**，不在 `KanpanCore` 里。任务书 §3 只说分层，没规定包边界；
   拆开是为了让 `KanpanCore` 保持零依赖、能在纯 CLT 下跑（A0.4）。

2. **WS 的录制和线上验证走的是期货测试网 `fstream.binancefuture.com`**。
   你这台机器的代理把 `fstream.binance.com` / `stream.binance.com` 的 TLS 握手掐了
   （`curl` 退出码 35 / `NSURLError -1200`），`fapi.binance.com` 和 `data.binance.vision` 正常。
   报文格式两边完全一样，回放 fixture 与单测不受影响；真正的生产 WS 要等换网络环境再验一次。

3. **A2.9 线上那次切 20 次建立了 2 条连接**（[`logs/M2-switch.log`](logs/M2-switch.log)），
   不是 1 条。原因是测试网在密集 SUBSCRIBE/UNSUBSCRIBE 下会直接把 socket 关掉
   （`NSPOSIXErrorDomain Code=57`）。对照实验：同一条连接空跑 72 秒不切流，一次都没断；
   录制那 31 分钟也没断。所以是测试网对控制帧的容忍度问题，不是客户端行为问题。
   即便如此还是按币安「每条连接入站 10 条/秒」的限制把 `WSClient` 改成了
   **控制帧一条一条发、每条间隔 250ms（4 条/秒），睡醒只看「现在想订哪套」**——
   手指一路划过 14 个周期时，中间那些一闪而过的周期会被合并掉，不再一次发 28 条。
   判定 A2.9 的 [A] 证据是单测「连续切 20 次：连接 id 不变，走 SUBSCRIBE / UNSUBSCRIBE」。

4. **归档站每日 metrics CSV 的行序不固定**：近几天的文件是乱序的，早几天的是升序。
   解析器一律自己排序，单测「归档站有的文件本身是乱序的：解析器必须自己排」把这条钉住了。

5. 冷启动时 `fill` 和 WS `connected` 都会补缺，热启动（快照打底）那一下会重复请求一次
   `startTime=末根`。已在 `MarketFeed` 加 `filling` 标志去掉，A2.5 的日志是修完之后跑的。

## A2.14 怎么跑的

```bash
cd KanpanData && swift build -c release --product kanpan-feed
.build/release/kanpan-feed BTCUSDT 1m --minutes 30 --cache-root /tmp/kanpan-a214/cache
```

- 不设 `KANPAN_STREAM`，走的是 app 自己选的生产推送域名（日志里是 `dstream.binance.me`）。
  原来这里写的 `fstream.binancefuture.com` 是合约**测试网**，推的不是生产盘，已删掉。
- `--cache-root` 让快照落在单独的目录，不和别的窗口共用临时目录。
- 看三件事：末根每秒跳；每到整分钟追加一根新的；跑完不崩。统计口径见上表那一行。

## 备注

- 取证命令行 `kanpan-feed` 的子命令：`info / history / snapshot / oi / switch / churn / record`，
  加 `-v` 打每一条 HTTP 请求。REST 与 WS 默认都走 app 自己的生产线路；`KANPAN_STREAM`
  只用来临时换一个**生产**推送域名，绝不能指到 `*.binancefuture.com`（那是合约测试网，
  2026-09-23 从本文件删掉了这个例子）。`--cache-root <目录>` 把快照放到单独的目录。
- K 线**不落盘**这条是硬约束：沙盒里只有 `last.kbar`（≤ 60 KB）、`exchangeInfo.json`
  和 OI 日切片，A2.12 的 `find` 清单可以逐个核对。
