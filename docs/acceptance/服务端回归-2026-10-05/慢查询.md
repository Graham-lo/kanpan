## 2. 根因

### A. REC：每 30 s 重走一遍刚删掉的死索引项

`heat::bases()`、`flow::bases()` 用递归的「`min(base) WHERE base > 上一个`」从 `orderflow_heat` / `orderflow_flow` 的主键里跳出全部 base（285 个）。
每一跳都落在下一个 base 的键区间**最前端**——那正是每小时清理（`purge`，删掉最老的那一段）刚删掉的地方。
被删的行在索引里还是项，`min()` 要逐条回表确认不可见才能往后走；有快照 / xmin 挂着的时候这些项标不了 LP_DEAD，
于是汇总器每 30 s 调一次就重走一遍「285 个 base × 每个 base 清理掉的上千条」，一次 6–18 s，成片出现，直到 vacuum 收掉。
清理过后没有快照挡着时同一条语句只要 68 ms（修前 EXPLAIN：`CTE Scan on b … actual time=0.066..67.668 rows=285`），所以它是「平时快、一清理就成片慢」。

而这份 base 清单本来就有：`orderflow_bases`（435 行的小表，跟踪器每分钟 `alive()` 一次），`store` 读订单早就用它。

### B. ORD：第二支把这只 base 三天的单全翻一遍

`range_sql` 取窗口内结束的单（第一支 `end_ms BETWEEN from AND to`）和「窗口结束时还挂着、之后才结束」的单（第二支 `end_ms > to AND first_seen_ms <= to`）。
第二支只能走 `orderflow_orders_first_seen (base, first_seen_ms)`：`first_seen_ms <= to` 在 to = 此刻时等于这只 base 的全部单，全部回表再按 `end_ms > to` 滤掉。

## 3. 改了什么（`4cab6bef`）

1. **REC**：删掉 `heat.rs` / `flow.rs` 里的递归 `bases()`，汇总器、启动续跑、两处清理一律读 `store::bases()` = `SELECT base FROM orderflow_bases`。
   - `store::alive()` 改成 upsert：`start()` 写失败（只告警）的 base 也会在下一分钟被登记，清单不会漏。
   - `heat::resume()` 只在某一层汇总一段都没有时才按 base 取 `min(bucket_ms)`（`unnest` + `LATERAL`，每个 base 一次索引探测），平时一条都不跑。
2. **ORD**：迁移 0044 `CREATE INDEX CONCURRENTLY orderflow_orders_end_first_seen ON orderflow_orders(base, end_ms, first_seen_ms)`，两支都走它：
   第二支变成「`end_ms > to` 的区间扫描 + 索引内判 `first_seen_ms <= to`」，不再回表滤。
   0045 / 0046 `DROP INDEX CONCURRENTLY` 删掉被它覆盖的 `orderflow_orders_end`、`orderflow_orders_first_seen`（写入少维护一个索引）。
   三份迁移都是 `-- no-transaction` 单语句，`migrations_after_0010_are_lock_free` 守着。查询本身没改一个字，返回内容不变。
3. **没做**：没加缓存、没改存储结构、没动 ROLL30。
