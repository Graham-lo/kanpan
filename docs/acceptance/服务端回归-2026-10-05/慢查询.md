## 2. 根因

### A. REC：每 30 s 重走一遍刚删掉的死索引项

`heat::bases()`、`flow::bases()` 用递归的「`min(base) WHERE base > 上一个`」从 `orderflow_heat` / `orderflow_flow` 的主键里跳出全部 base（285 个）。
每一跳都落在下一个 base 的键区间**最前端**——那正是每小时清理（`purge`，删掉最老的那一段）刚删掉的地方。
被删的行在索引里还是项，`min()` 要逐条回表确认不可见才能往后走；有快照 / xmin 挂着的时候这些项标不了 LP_DEAD，
于是汇总器每 30 s 调一次就重走一遍「285 个 base × 每个 base 清理掉的上千条」，一次 6–18 s，成片出现，直到 vacuum 收掉。
清理过后没有快照挡着时同一条语句只要 68 ms（修前 EXPLAIN：`CTE Scan on b … actual time=0.066..67.668 rows=285`），所以它是「平时快、一清理就成片慢」。

而这份 base 清单本来就有：`orderflow_bases`（435 行的小表，跟踪器每分钟 `alive()` 一次），`store` 读订单早就用它。

### B. ORD：第二支把这只 base 三天的单全翻一遍

`range_sql` 取窗口内结束的单（第一支 `end_ms BETWEEN from AND to`）和「窗口结束时还挂着、之后才结束」的单（第二支 `end_ms > to AND first_seen_ms <= to`）。
第二支只能走 `orderflow_orders_first_seen (base, first_seen_ms)`：`first_seen_ms <= to` 在 to = 此刻时等于这只 base 的全部单，全部回表再按 `end_ms > to` 滤掉。

## 3. 改了什么（`4cab6bef`）

1. **REC**：删掉 `heat.rs` / `flow.rs` 里的递归 `bases()`，汇总器、启动续跑、两处清理一律读 `store::bases()` = `SELECT base FROM orderflow_bases`。
   - `store::alive()` 改成 upsert：`start()` 写失败（只告警）的 base 也会在下一分钟被登记，清单不会漏。
   - `heat::resume()` 只在某一层汇总一段都没有时才按 base 取 `min(bucket_ms)`（`unnest` + `LATERAL`，每个 base 一次索引探测），平时一条都不跑。
2. **ORD**：迁移 0044 `CREATE INDEX CONCURRENTLY orderflow_orders_end_first_seen ON orderflow_orders(base, end_ms, first_seen_ms)`，两支都走它：
   第二支变成「`end_ms > to` 的区间扫描 + 索引内判 `first_seen_ms <= to`」，不再回表滤。
   0045 / 0046 `DROP INDEX CONCURRENTLY` 删掉被它覆盖的 `orderflow_orders_end`、`orderflow_orders_first_seen`（写入少维护一个索引）。
   三份迁移都是 `-- no-transaction` 单语句，`migrations_after_0010_are_lock_free` 守着。查询本身没改一个字，返回内容不变。
3. **没做**：没加缓存、没改存储结构、没动 ROLL30。

### 8.1 热力清理 `DELETE FROM orderflow_heat WHERE ctid=ANY(ARRAY(SELECT …))`（36 条，1.0–2.3 s）

- **根因**：每小时一次、逐只 base 跑 `base=$1 AND bucket_ms<cutoff LIMIT n` 的无下界删除。`bucket_ms<cutoff` 没有下界，每批都要从这只 base 索引的最左边走起，
  一路踩过前几次清理留下、还没被 vacuum 收走的死索引项（位图扫描不设 LP_DEAD 提示，所以同样的死项每小时都重走一遍，直到 autovacuum 来）。
  一小时攒下来一只热门 base 有几万行要删，每批都是「先踩一大片死项、再删一批」，于是清理窗口里成片 1–2 s。
- **修法**（不是加缓存，也不是调批大小）：
  - 清理改成**每分钟删刚过保留期的那一分钟**：`DELETE FROM orderflow_heat WHERE base=ANY($1) AND bucket_ms>=$2 AND bucket_ms<$3`，`[a,b)` 是一分钟的片，有上下界，
    索引范围只覆盖这一分钟，不碰更老的死项。
  - 进度存进新表 `orderflow_purged`（迁移 0047，`target='heat'`、`before_ms`），重启接着删；进度只进不退。
  - 进度缺失或落后超过保留期时，退回原来的逐 base 有界批删兜底（`delete_before`）。
  - 表超体积的那道闸也改成按片推进（每次推 6 小时，内部仍是一分钟一片）。
  - 三档汇总表（rollup）也按「每档宽度 × 60 段」一片、从上次进度往后删，不再无下界。
  - 每小时只打一条汇总日志：`Orderflow heat: purge deleted N; table … bytes`。
- **autovacuum**（迁移 0050）：
  - `orderflow_heat` 设 `autovacuum_vacuum_scale_factor=0.05`（2266 万行的表，缺省 0.2 要攒 450 万死元组才清）；
  - `orderflow_orders` 设 `autovacuum_vacuum_insert_scale_factor=0.01`（让只插入的表常做 vacuum，可见性图跟得上，仅索引扫描才不用回表）；
  - `market_features` 设 `autovacuum_vacuum_insert_scale_factor=0.02`。
- **线上实测**：
  - 一分钟一片约 5.6K 行，同条件 SELECT 180–344 ms（修前每条 1.0–2.3 s）。
  - 部署后 05:52 起每分钟清一次，2 分钟内追平：`orderflow_purged` 落后「此刻 − 3 天」只有 25–28 s，即不到一片。
  - 21:56 UTC（部署后 4 分钟）`orderflow_heat` 已按新阈值自动 vacuum 一次，死元组 3.4 万 / 活 2266 万。

### 8.2 订单流历史读 `SELECT * FROM (SELECT base,venue_id,…`（11 条，1.1–3.5 s）

- **根因**：
  - 一只 base 的行在 heap 里是按写入时刻散开的（几百只 base 交错写）。`(base,end_ms,first_seen_ms)` 索引找得很快，但每一行都要回表，冷读时一行一页。
    修前 ETH 24 h 3.07 s、LTC 冷 3.47 s。
  - 其余时间花在排序上：内外两次排序在缺省 4 MB `work_mem` 下溢出成外部归并（3–5 MB 临时文件）。
- **修法**：
  - 迁移 0048 `CREATE INDEX CONCURRENTLY orderflow_orders_end_covering ON orderflow_orders(base,end_ms,first_seen_ms) INCLUDE (venue_id,exchange,product,side,bucket,price,status,initial_notional,notional,filled_notional,threshold,vanished_notional,step,seen_ms)`，
    让结束的两支都走仅索引扫描（Index Only Scan），线上 294 MB。
  - 0049 `DROP INDEX CONCURRENTLY` 被它覆盖的旧 `orderflow_orders_end_first_seen`。
  - 0050 的 insert vacuum 阈值让可见性图跟得上（否则仅索引扫描仍会回表）。
  - `store::range_each` 包进一个事务、`SET LOCAL work_mem='16MB'`（`468e7055`）：排序全在内存里做完（quicksort，最大 8.4 MB）。
    读历史同时最多 `HISTORY_READS`=2 条，内存上界几十 MB；热力汇总已有同样的做法（64 MB）。
  - 测试 `three_days_of_orders_read_without_walking_the_whole_base`：VACUUM 后 EXPLAIN，要求两支都是 `Index Only Scan using orderflow_orders_end_covering`、滤掉 0 行、回表次数 < 返回行的 5%。

### 8.3 `market_features` 分块计数 `SELECT symbol,div(start_at,$1)…`（10 条，1.2–1.5 s，每小时 :44）

- **根因**：
  - 每小时、每次清理之后都把全部品种按每档重数一遍，一条语句扫所有品种一年的窗口。
  - 其实计数在启动后由 `credit()` 随写随记，一直是准的；清理删的是深度以外的窗口，而计数只数深度以内的，两者不相交，删完不需要重数。
- **修法**：
  - 只在启动时和每次重排名单后（6 小时一次）数，清理不再触发重数（代码里写了不相交的证明）。
  - 每条语句只数 8 只（`CENSUS_SYMBOLS`），用 `start_at/$1` 整数除代替 `div()::bigint`，并带 `start_at>=since` 下界走 `(symbol,start_at)` 前缀。
  - 新测试 `census_in_batches_counts_exactly_what_was_written`：11 只 × 2000 根 1h，分批计数与写入时记的逐只逐块一致，深度以外的窗口、名单以外的品种不计。
- **线上**：8 只一条，1h 68–75 ms、15m 37.5 ms、4h 26.9 ms（修前单条 1.2–1.5 s）。05:52 与 06:00 两次启动的计数都没有进 slow statement。
