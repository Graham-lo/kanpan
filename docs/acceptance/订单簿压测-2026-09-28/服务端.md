# 主力订单流 · 服务端审查与压测（2026-09-28）

范围：`Backend/kanpan-api` 的 `orderflow_history`（book / model / hub / feeds / snapshots / store / layers）、历史接口、`/v1/market/depth`。
线上只做了只读操作（EXPLAIN 在只读事务里、压测有界），没有部署、没有改库里的数据。

## 结论先说

1. **失联尖峰的根因找到并修了（bug 1）。** 每次部署重启，非币（美股 / 贵金属等）那一侧有 1,200–1,400 条挂单在读回时被误判失联，一两分钟后又在同一档当新单出现。原因是延后读回时，「缺席超过 2 分钟」是按标定那一刻算的，而标定要排币安快照，要等几分钟。现在改成按读库那一刻算。
2. **日常失联的七成是 ±10% 扫描线上的抖动（bug 2），已修。** 一面没动过的墙，因为价格来回摆、反复进出 10% 线，被切成几十截「失联」。现在挂着的单要出了 15% 才判失联；10%–15% 之间直接查那一个桶，照常判还在、撤了还是成交。
3. **历史接口慢，瓶颈在库的读取和跨洋传输，不在服务进程。**
   - 服务端热态首字节：ETH 24h 约 0.55 s，ETH 3d 1.1–1.7 s。
   - 远端 5 并发时 ETH 3d 最长 29 s，主要是 `HISTORY_READS=2` 排队，加上跨洋把 5 × 2.9 MB 传回来。
   - 方案见「设计问题」第 1 条。
4. **`/v1/market/depth` 正常。** 20 次全 200，一秒缓存与并发合并在线上确实生效；最近 24 h 上游告警 0 条。
5. `cargo test --lib`：462 过、0 挂，包括新加的 4 条回归。带库的 `ops/test.py --lib`：462 过、0 挂。订单流带库加 `--ignored` 压测：101 过。

## 二、bug

### 已修 1：非币延后读回按标定时刻判「缺席」，每次部署一千多条假失联

**位置：** `src/orderflow_history.rs`
- `Calibration.restored`（:393）
- `calibrate` 里的 `self.model.restore(rows,read_at)`（:572）
- `track` 里存读库时刻（:731）

**机制：**
- 非币要等门槛标定完才读回库里挂着的单。标定要等币安的快照排队，重启时整批簿一起排；2026-09-27 15:27–15:32 um 队列压了 103 本，最长等 237 s。
- 原来 `model.restore(rows, now)` 用的是**标定那一刻**。可库里的 `seen_ms` 本来就可能落后 75 s（`LIVE_REWRITE_MS` 60 s 加 15 s 刷写），再加上停机几十秒，`now - seen_ms ≥ STALE_MS(120 s)` 几乎必然成立，于是全部当场判失联。

**证据：** 09-27 四次部署重启（每次部署重启两次），日志里读回的数字：

| 重启（UTC） | 币：读回 / 当场失联 | 非币：读回 / 当场失联 |
|---|---|---|
| 07:23 | 1888 / 38 | 2072 / **1411** |
| 15:26 | 1673 / 8 | 2052 / **1416** |
| 18:10 | 1247 / 7 | 1997 / **1215** |
| 21:49 | 68 / 7 | 1783 / **1389** |

- 例子：DRAM 68/68、CRCL 89/89、NATGAS 82/82、AVGO 45/45。
- 这些尖峰里的失联单，74–89% 在 25 分钟内于同一档复现（07:23 1018/1551、15:25 1144/1433、18:10 994/1222、21:49 1158/1356）。它们的中位寿命 149–387 分钟，复现发生在重启后 60–180 s，也就是标定完、新候选确认的那一刻。

**影响：** 历史图上长寿命的美股 / 金银墙每部署一次就断成「失联 + 新单」两截；一天两三次部署就是几千条假失联。父窗口看到的「当天失联 1.73 万」里，尖峰那部分主要是它。

**修法：**
- 延后的行连同读库时刻一起存，标定后 `restore(rows, read_at)`。
- 读库时还在 2 分钟以内的接着跟；读库时就已经缺席 2 分钟的，照旧按最后一次看到的时刻失联。

**回归：** `deferred_restore_judges_absence_at_read_time_not_calibration_time`。读库后 237 s 才标定：落后 75 s 的单接着跟；落后 130 s 的按 `seen_ms` 失联。

### 已修 2：挂着的单在 ±10% 扫描线上来回进出，被切成几十截失联

**位置：**
- `src/orderflow_history/model.rs`：`EXIT_RADIUS_BPS`（:23）、`evaluate` 里的活单循环（:356 起）
- `src/orderflow_history/book.rs`：`LocalBook::for_each_between`、`VenueBook::bucket`（:419 起）

**机制：**
- 原来 `evaluate` 只合计中间价 ±10% 以内的桶；挂着的单一旦出了 10% 立刻判失联，回到 10% 以内又当新单确认。
- 进和出是同一条线，没有滞回，价格小幅摆动就来回切。

**证据：**
- 今天（UTC 前 13.5 小时）结束 78.3 万条，其中失联 10,381。失联里 **72% 在 1 分钟内于同一档复现**（币 4946/6693，非币 2566/3682）。
- 按交易所：币安合约 4809、币安现货 3507、Coinbase 1344、OKX 现货 187、OKX 合约 99。中位寿命约 0.2 分钟。
- 失联按 10 s 窗口成批（≥5 条）的只有 33 组 / 8129，所以不是连接事件。
- 典型例子：XRP 现货 1.63 那面约 40 万的卖墙，名义一直没变。10:11 UTC 的高点 1.4831 使它正好在 +9.9%；12:11 的 1.66 离低点 +10.0%。它每隔几秒到几分钟被切一次。

**修法：**
- 新单仍只在 10% 以内起。
- 已挂着的单：桶的远端出了 10%（整桶在外，或骑在线上、扫描只合计到一部分）时，直接按价位区间查这一个桶（BTreeMap range，不扫整侧），照常判「还在 / 撤了 / 成交了 / 看不见」。
- 出了 15% 才按最后一次真看到的时刻失联。15% 在 ±20% 的留存带以内，那一档的量本地一直有。

**回归：**
- `a_wall_at_the_scan_edge_stays_one_order_while_price_swings`：20 拍来回跨线，仍是最早那一条。
- `a_wall_beyond_the_exit_radius_ends_lost_at_its_last_sight`
- `a_wall_pulled_between_the_scan_and_exit_radius_is_cancelled`：10%–15% 之间撤掉判已撤销；在 10% 外重新挂出不当新单。
- 旧用例 `an_order_the_price_ran_away_from_is_lost_not_cancelled` 的价格从 67,000 改到 71,000：原来的 −10.5% 现在落在滞回带里，按设计会接着跟。

**预期效果：** 日常失联减掉大头，上限约七成，每天约 1.3 万条。上线后可以用同一条 SQL（失联且 1 分钟内同档复现）复核。

### 未修（范围外）

- **手机端 `KanpanCore/Sources/KanpanCore/OrderFlow/OrderFlowModel.swift:480-500` 有同一条边，而且更糟。** 手机没有「出了范围」这一分支：单走出 10% 后 `map[key]` 为空、价位又是已知的，就直接走撤单确认，判成**已撤销**（服务端原来至少是失联）。建议照搬这次的 15% 滞回加单桶直查。

## 三、设计问题与方案

1. **历史接口的时延：堆页读取为主，排队与传输为次。**
   - 数字见上文：库内 ETH 3d 读 2 万堆页，1.7–2.5 s；gzip 0.2–0.6 s；信号量 2 让 5 并发排三波；答复整块攒好才发，首字节等于查询加序列化。
   - 方案按性价比排：
     1. **客户端增量取：** 带 `from=上次拿到的最后时刻`。已经结束的单不会再变，重复拉三天是浪费。ETH 3d 2.9 MB 可以降到几十 KB。需要手机端配合。
     2. **同窗口单飞加短缓存：** 同一 (base, from 取整到分钟, to 取整到分钟) 合并成一次查询，压缩后的答复缓存 30–60 s。5 个人同时开 ETH 就只查一次。改在 `orderflow_history.rs`，不动协议。
     3. **库的内存：** `shared_buffers` 128 MB 太小（VPS 有 4.6 GB 页缓存可用）。容器上限 512 MB → 1.5 GB，`shared_buffers` → 512 MB，热点 base 的页就能常驻。属于运维改动，不在本次范围。
     4. **按 base 聚簇：** 按 `list(base)` 或 `hash(base)` 分区，或按天分区后在分区内按 base 排序，一只 base 的行不再散在整张表里。改动大，等体量上去再做。
     5. `SET LOCAL work_mem='32MB'` 能去掉落盘排序，但实测总时长不降，**不值得单独做**。
   - 边读边发（流式答复）能把首字节提前，但总时长不变，而且答复内存已经有界（20 万行 +108 MB），优先级低。

2. **重启后远处的长寿命墙被 `UNKNOWN_MS` 判失联，而且认不回来。**
   - 币这一侧每次重启额外有 130–290 条失联，远超读回当场判掉的 7–38 条。
   - 它们的中位寿命 2–17 小时，30 分钟内同档复现的只有 30–45%。
   - 机制：
     - 币安 um / cm 快照最多 1000 档，BTC 这类只盖盘口 0.3% 左右。
     - 快照覆盖以外、重启后没有增量推到的价位是「不知道」，等满 600 s 就按最后一次看到失联（`model.rs` 的 `!book.knows` 分支）。
     - 本地簿里没有这一档，那面墙就算还挂着也不会被当新单认回来，要等它被动过才重新出现。
   - bug 1 修掉以后，非币这一侧也会走同一条路。
   - 方案：
     - (a) 币安现货快照改用 `limit=5000`（权重 250）。spot 车道要从每分钟 30 本降到约 20 本，才不超过 6000/分钟的权重。
     - (b) 部署不要重启两次（见第 3 条），并缩短停机，让「不知道」的窗口少发生。
     - (c) 合约没有更深的 REST 快照。只能接受，或者对读回的单在「不知道」时把等待延长到 30 分钟。代价是真撤掉的单在历史上多挂一会儿，需要权衡后再定。

3. **每次部署服务重启两次，间隔约 10 s**（09-27 07:23:08/07:23:20、15:26:26/15:26:36、18:10:45 两次、21:49:27 两次）。
   - 快照队列要排两遍，也让 bug 1 和设计第 2 条的窗口翻倍。
   - 部署脚本不在本次范围，建议查部署流程里重复的 restart。

4. **`seen_ms` 在库里最多落后约 75 s**（`LIVE_REWRITE_MS` 60 s + `FLUSH` 15 s），而 `STALE_MS` 是 120 s，停机只剩约 45 s 余量。
   - 币这一侧仍按启动时刻判缺席：停机超过 45 s，没动过的单就会在读回时失联。
   - 方案：收到 SIGTERM 时把所有活单的 `seen_ms` 刷一遍库（一条批量 UPDATE），或者让读回的阈值等于 `STALE_MS + LIVE_REWRITE_MS + FLUSH`。

5. **`orderflow_orders_first_seen` 索引几乎不用。**
   - 129 MB，idx_scan 120 次；三路 UNION 全走 `_end`，写库冲突走主键。
   - 它在每次非 HOT 更新（结束一条单）时都要维护。
   - 删之前要把 `purge` 与 `continuous_since` 的执行计划再核一遍；迁移不在本次范围。

6. **写入量主要来自短命撤单。**
   - 今天撤单 77 万条：中位寿命 22.5 s，33% 不到 10 s，68% 不到 60 s；每天约 92 万行、约 400 MB。
   - 与手机模型（照 CoinAnk 逐单）语义一致，不是 bug。
   - 三天留存约 1.2 GB，离 20 GB 闸门很远，暂不用动。如果以后要省，可以在历史里不落寿命 < 10 s 的单，但得先和手机的展示对齐。

7. **OKX `books` 频道只有 400 档，却按全簿处理**（`feeds.rs:209/241` 的 `requested:usize::MAX` → extent None）。一面墙掉出前 400 档时，会被当成「已知且没了」判撤单。
   - BTC / ETH 400 档大约覆盖 ±1–3%，10% 以内的远墙会受影响。
   - 方案：OKX 快照记 `requested=400`，让覆盖范围以外按「不知道」处理。
   - 线上 OKX 的失联与撤单数都小（今天失联 286），先列出不改。

8. **热点层换人时，被换掉的 base 上的活单按失联结束**（`model.stop`）。今天有 56 次停跟，影响有限，符合「不再跟就不知道后来」的语义。

## 第二轮（2026-09-28 晚）：历史接口、簿覆盖、停机不丢

提交：`561998e2`（簿覆盖）、`254cf8d7`（历史接口 minLifeMs + 单飞缓存、停机交接、install.py / README）。只动了 `Backend/kanpan-api`；未 push、未部署。

### 1. 历史接口 `minLifeMs`

- `GET /v1/market/orderflow/history?base=&from=&to=&minLifeMs=`，可选，0 到 86 400 000（一天）；负数、超出、不是整数一律 400 `invalid_query`。
- 只滤**已结束**的单：三路 UNION 里「区间内结束」「区间后结束」两路在 SQL WHERE 里加 `end_ms-first_seen_ms>=$5`；挂着的一路不加，照回。
- EXPLAIN（带 minLifeMs=60000）三路仍是 `orderflow_orders_end`：挂着的一路 Index Scan（`end_ms IS NULL`），区间内结束的一路 Index Scan、寿命条件只是一行 Filter，区间后结束的一路 Bitmap Index Scan。计时用例里断言「`orderflow_orders_end` 出现三次、没有 Seq Scan」。注意本机测试库用的是非属主角色，`ANALYZE` 不生效，行数估计是缺省值；线上第一轮带真实统计的 EXPLAIN 本来就三路走这条索引，新条件不改索引条件。
- 照 ETH 24h 的形状，minLifeMs=60000 把 gzip 后的答复从 1.23 MB 降到 0.49 MB。

### 2. 同窗口单飞 + 60 秒缓存

- 键：（base，from 所在分钟，to 所在分钟，minLifeMs，是否 gzip）。读的区间放宽到整分钟（from 取整到分钟开头、to 到分钟末尾），同一分钟里来的请求拿同一份答复，是各自要的区间的超集（客户端按单合并，多几条无妨）。
- 并发同键：`tokio::sync::OnceCell` 单飞，只读一次库，其余的等它。读库失败或第一个请求被取消（客户端断开）不进缓存，等着的接着自己读。
- 缓存的是压好的体和头（Content-Type、Content-Length、`Content-Encoding: gzip`、`Vary: accept-encoding`、`Cache-Control: no-cache`），60 秒（从答好那一刻算），最多 64 份、32 MB，按最久没用的踢；单份超过 32 MB 的照回但不留。`HISTORY_READS` 信号量 2 保留（只管真读库）。
- 压缩改在接口里做（tower-http 的压缩层去掉，否则缓存不了压好的体）：flate2（zlib-rs 后端），级别 6 与原来相同，前面垫 64 KB 缓冲。第一版没垫缓冲，serde_json 每个记号一次 `write` 直接进 deflate，ETH 24h 首次要 0.8 s；垫了之后压缩只占零头。
- 新鲜度：`to` 缺省是此刻，每过一分钟就是新键，所以最坏晚一分钟看到最新的挂单变化；手机每分钟增量拉一次，自己的实时簿本来就补着最新的。

**计时**（本机 M4，release，`ops/test.py` 的隔离库，照线上 ETH 24h 的形状摆 30 887 行、六个产品、约 1% 挂着；`ops/test.py --lib --release -- orderflow_history::tests::eth_day --ignored --nocapture`）：

| 光读库（热） | 60 ms | — |

### 3. 簿覆盖（`561998e2`）

- `book::Levels` 记快照的覆盖区间（最远一档）：全簿增量（币安、Coinbase）不外扩、逐价记推过的档；窗口增量（OKX `books` 400 档）推来更远的正量档就外扩，推成 0 的不外扩。
- 簿就绪、只是那一档在覆盖区间以外的挂着的单：不判撤单、不判失联、不记消失名义，`seen` 照走，等增量推到它（或覆盖外扩到它）再照常判，价格走出 15% 退出半径才失联。簿断线在等快照那段仍按 `UNKNOWN_MS`。
- 币安现货快照 1000 → 5000 档（权重 250，现货通道每分钟 20 次 = 5000 / 6000）；合约仍 1000 档。200 本现货簿重启时同时要，最后一本约 9 分 20 秒拿到。

### 4. 停机不丢

**顺序**：supervisor 收到 SIGTERM → 停机信号同时交给两边——axum `with_graceful_shutdown`（不接新连接、等进行中的请求答完）和 `orderflow_history::shutdown()`，两者**并行**，都结束进程才退出：

1. 置全局 `CLOSING`，各品种的跟踪循环退出，不再评估；
2. 各品种写完手里已结束的行，把新出现 / 移动过的挂着的行交给自己的写库任务，交上全部挂着的单的（主键，此刻）——最多等 2 秒；
3. 一条 `UPDATE orderflow_orders o SET seen_ms=v.seen_ms FROM unnest(…) v WHERE 主键相等 AND o.end_ms IS NULL AND o.seen_ms<v.seen_ms`；
4. 等各品种的写库任务排空。整段上限 10 秒，到点照常退出。

挂着的单停机时**不结束**，下次启动 `restore` 读回时 `seen_ms` 是停机那一刻，不会因为「两分钟没见」判失联。upsert 对挂着的行 `seen_ms` 取 `GREATEST`，在途的旧批次写不倒回去。

**journalctl**：`journalctl -u kanpan-api -n 50 | grep 'Orderflow history: shutdown'`

```
Orderflow history: shutdown kept <N> live orders on <B> bases (seen_ms refreshed on <R> rows), all writers drained in <T> ms
```

`R` 略小于 `N` 正常（刚出现、还没落盘的行由写库任务自己带着新 seen 写入）；`refreshed on failed rows` = UPDATE 没在时限内做完；warn 级的 `… trackers still writing after 10000 ms` = 有品种没排空。

**仍会丢的情形**（照实列出）：

- 非币在标定前延后读回的行，停机时还没交回跟踪器，`seen_ms` 不会被刷新；两次重启挨得近（第二次时这批行已超过 `STALE_MS`）仍会失联——所以部署只重启一次（install.py 自己 try-restart，不要再 restart）。
- 进程因后台任务挂掉而退出时，supervisor 只给 10 秒排空再 `exit(1)`，收尾可能来不及，退回原来的读回判定。
- systemd 缺省 `TimeoutStopSec` 90 秒，远大于 10 秒，不需要改单元。

### 线上要手工做的（主窗口）

1. **部署**：同步源码 → `cargo build --release` → `ops/install.py`，**到此为止**。install.py 末尾已经 `systemctl try-restart kanpan-api kanpan-worker`，不要再 restart 第二次（每重启一次订单流停一次、非币重新排标定）。部署后看上面那行停机日志（在旧进程退出时打出，新代码要到**下一次**重启才会打；这次部署的旧进程还是老代码）。
2. **数据库容器内存**（install.py 不动已有容器；三步，改一次即可）：

   ```bash
   docker update --memory 1536m --memory-swap 1536m kanpan-postgres
   docker exec kanpan-postgres psql -U kanpan_admin -d kanpan -c "ALTER SYSTEM SET shared_buffers = '512MB'"
   docker restart kanpan-postgres
   docker inspect -f '{{.HostConfig.Memory}}' kanpan-postgres                     # 1610612736
   docker exec kanpan-postgres psql -U kanpan_admin -d kanpan -Atc "SHOW shared_buffers"   # 512MB
   ```

   - `docker update` 在线生效，不停库；`shared_buffers` 只在启动时读，**必须重启一次 Postgres 容器**。
   - 预计库停 3–10 秒（快速关机 + 启动）。期间 serve / worker 的请求报库错误，连接池自己重连，不用重启 kanpan-api；订单流写库批次下一轮重试。
   - 先 update 再 restart（顺序反了可能被 OOM）；挑人少的时候，不要和部署挨着做。
   - VPS 7.9 GB，serve 单元上限 1 GB，Postgres 1.5 GB 之后仍有余量。
