# 订单簿 / 主力订单流 · 数据层审查与压测（2026-09-28）

范围：`KanpanCore/OrderFlow`（LocalBook、VenueBook、OrderFlowModel、历史合并、日志）、`KanpanNetwork/OrderFlow`（DepthStream、三家适配器）、`KanpanData/OrderFlow`（OrderFlowFeed）。图表 / App 展示另有一份报告，不在本文。

## 结论

- **性能不是问题**：13 本 BTC 簿每 100 ms 各一条 200–500 档增量，簿更新一帧 0.12 ms（release）；13 本 × 2000 档、1500 条挂着时每 500 ms 评估一次 2.9 ms；满额 2 万条时评估 3.1 ms、合并服务端 2065 条 6–10 ms、落盘 5000 条 17 ms。真正的热点是**每帧 JSON 解码**（币安 500 档一帧 0.26 ms，是簿更新的约 27 倍），13 本合计约占一个核的 3%，仍然很轻。
- **正确性**：四种序列规则（币安现货 U/u、币安合约 U/u/pu、OKX seqId/prevSeqId、Coinbase sequence_num）在注入丢包、对调、重复、整段重放、快照迟到 / 过旧的情况下，**就绪时逐档对真值 2276 次，0 次静默错数**：断档只会表现为「不就绪、重拉」，不会表现为「就绪但数是错的」。历史合并逐条核对不丢不重、重复并同一页幂等；连切 20 只无泄漏；坏日志不崩、会被新的一份盖掉。
- **发现 1 个能复现的 bug，已修**：DepthStream 在「刚连上、还没登记连接」那一次 actor 跳转里被 stop / 重开，会漏掉一条 socket（保活一直发）、同一条流同时活两条连接，并把新一轮的连接号与保活改坏，导致新连接上的重订请求被忽略。
- 设计问题 8 条（见下），都不影响正确性，只记录不改。

线程归属：解码在 **DepthStream actor**（每条连接一个）；簿更新、评估、历史合并、日志编码与写盘、读日志都在 **OrderFlowFeed actor**；两者都不在主线程。帧经 `AsyncStream(bufferingNewest(8))` 交给界面；DepthStream 到 Feed 的事件缓冲是 512 条，满了就整条重拨并照常退避。Feed 上单次最长的占用是写日志的约 17 ms，远填不满 512 条的缓冲。

## bug（已修 / 未修）

### 已修 1：DepthStream 连上那一跳里被 stop / 重开 → 漏一条连接、新一轮的重订被忽略

- **位置**：`KanpanNetwork/Sources/KanpanNetwork/OrderFlow/DepthStream.swift:159–178`（`loop()` 连上之后），以及同一文件里两处 `backoff.settle` 与 `pump` 的 `lastFrameMs`。
- **现象**：原来先 `connectedAt = await pacer.nowMs()` 再 `socket = s`。在这次 actor 跳转里 `stop()` 或新的 `start()` 插进来做 teardown，那时 `socket` 还是空的，掐不到这条连接；旧一轮醒来照样登记 socket、`connection += 1`、起保活，再撞上取消直接 return。结果是：
  1. 这条 socket 没人 cancel，保活一直在发；
  2. 重开的情况下同一条流同时活两条连接；
  3. 旧一轮把新一轮的保活任务换掉、把连接号加了 1，于是 Feed 拿新一轮的连接号调 `reconnect(connection:)` 被当成过期请求忽略，这条连接上的簿断档后重建不了。
  另外，被取消的旧一轮醒来还会改共享的退避档位和最后收帧时刻。
- **复现**：`StressDepthStreamTests.swift` 里的 `DepthStreamConnectRaceTests` 两条用例（`GatedClock` 把连上后那次 `nowMs()` 挂住，在这一刻 stop / 再 start）。修之前 8 处断言失败：socket 未 cancel、保活仍在发、活连接 2 条、新一轮保活停发、reconnect 没触发第 3 次连接。
- **用户影响**：快速切品种、或者 Feed 在连接刚建好的瞬间停掉再开时，会残留一条一直在发保活的 WebSocket（白耗流量和电量）；更糟的是新连接上某本簿断档后不会再重订，那一家交易所的主力订单流就一直停着，直到下一次断线。这个窗口只有一次 actor 跳转那么长，但切品种频繁时真会撞上。
- **修法**：过了取消检查就立刻登记 `socket`，中间不再有 `await`。之后的 `await pacer.nowMs()` 醒来先查取消，再写 `connectedAt` / `lastFrameMs`。两处 `backoff.settle` 和 `pump` 里的时刻同样改成「先问钟、查取消、再写」。
- **状态**：已修。回归用例修后全绿，`make network-test` 222 条全过。

### 未修

无。其余嫌疑项都用压测证明没有问题（见「其他」）。

## 设计问题（只记录，不改）

1. **日志一条坏了整份作废**（`KanpanCore/Sources/KanpanCore/OrderFlow/OrderFlowModel.swift:215`，`JSONDecoder` 整体失败即返回 nil）。压测里改坏第 17 条的状态，5000 条全部读成 nil。影响是最多丢这只品种本机 24 小时的记录：币有服务端历史可以补回来，非币就没了。可改成按行宽容解码，跳过坏行。
2. **落盘在 Feed actor 上同步做、间隔 60 秒**（`KanpanData/Sources/KanpanData/OrderFlow/OrderFlowFeed.swift:74` 的 `saveEveryMs = 60_000`，`save()` 在 :718）。5000 条编码加写盘约 17 ms，期间这只品种的簿更新和评估都要排队；这点量级无害。app 被杀时最多丢 60 秒的结束状态（任务描述里写的 15 秒和代码不一致，以代码为准）。
3. **解码是整条链上最贵的一环**：`DepthWire.object`（`DepthFeedAdapter.swift:133`）逐帧走 `JSONSerialization`。币安 500 档 0.26 ms，是簿更新的约 27 倍。Coinbase 整本快照 3 万档要 47 ms（debug 下 98 ms），每条连接一次，都在 DepthStream actor 上，不阻塞 Feed。现在的量用不着优化；以后品种多了，可以对 `b` / `a` 数组做流式解析。
4. **交叉簿直接整本清空重拉**（`LocalBook.swift:484` → `failSequence` 在 :328）。这样做是正确的（交叉说明本地簿已不可信），代价是一次 REST 快照或重订。压测没有观察到频繁交叉。
5. **币安现货 REST 快照只有 1000 档**：BTC 按 0.01 的最小价位算，只覆盖现价约 ±0.17%。覆盖范围以外的价位只有被增量碰到过才算「知道」（`LocalBook` 的 coverage 与 `knows`），所以 10% 扫描半径内远处早就挂着的墙，要等它变动一次才会出现。这是交易所接口的限制，合约与 OKX、Coinbase 不受影响。
6. **合并服务端历史时，本机挂着的同一条单换 id**（`OrderFlowModel.swift:761–764` 的 `adopt` 把 `firstSeenMs` 改成服务端的，而 id 是 `venue|side|bucket|firstSeenMs`）。数据上正确（不重复，由压测断言保证），但界面上若有按 id 记住的状态（点开的详情卡、高亮），会在合并那一拍失去目标。请图表侧确认。
7. **每帧都带整个 orders 数组**（`OrderFlowModel.swift:544`，满额 2 万条）。数据层靠写时复制，几乎不花钱（`sameContent` < 1 µs），但成本转移到了渲染侧的筛选上，需要图表侧按可视窗口裁剪。
8. **等快照时的缓冲满了用 `removeFirst`**（`VenueBook.swift:77`，上限 5000 条），满了以后每条是 O(n)。只发生在一直等不到快照的极端情况，实测可以忽略。

## 其他（嫌疑项已排除）

- **迟到快照**：原有 `OrderFlowLateSnapshotTests` 覆盖三种情况：就绪后到的快照被忽略、断档后快照仍能起簿、落后的增量不会每条都重建。本次乱序性质测试又让 REST 快照随机迟到 0–3 条、取自最多旧 3 步的时刻，四种规则都能正确重建。两者加起来已经够。
- **120 秒失联**：原有 `testDisconnectedVenueFreezesThenExpires` 已覆盖（失联冻结、到 `staleMs` 判「失联结束」）。日志读回时按存盘时刻处理，也有用例。
- **会不会两条连接同时活着、回调会不会乱序**：修复后同一个 DepthStream 同一时刻最多一条活连接（用例断言 `live() == 1`）。所有事件经同一个 AsyncStream 按顺序发出。拉 REST 快照的任务在断线或换连接时被取消，`OrderFlowFeed.applied` 先查取消才用这份快照（`OrderFlowFeed.swift` 约 :497），旧连接的快照不会塞给新连接的簿。
- **泄漏**：连切 20 只，每只停完订阅对象都释放，40 条连接全关（`OrderFlowFeedTests`「压测 · 连切 20 只」）。
- **坏日志**：空文件、截断、随机字节、非对象、版本不对、步长为 0、一条状态坏了，7 种都读成 nil、不崩。Feed 读到坏文件照常起订、照常出墙，停的时候用新的一份盖掉（`OrderFlowFeedTests`「压测 · 日志文件坏了」）。
- **满额裁剪**：一拍从 2.2 万条挤到九成（1.8 万），挤完 id 不重复；服务端刚给的最近 2 小时的单一条没被挤掉。
- **簿内存**：600 帧后档数有界（`retainBps` 2000 bps 裁远处），13 本常驻内存增长不到 0.5 MB。
