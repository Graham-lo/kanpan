# 多交易所接入指南（现行规格）

> 2026-09-23 起生效。看盘接一家新交易所（或同一家的另一个市场）时，照这份清单改；
> 清单之外的文件一个都不该动。改到了清单之外，说明抽象漏了，先补抽象再接。
> 守卫：`Tools/check-venue-isolation.sh`（挂在 `make app-logic-test` 里）。

## 1. 三个正交概念

| 概念 | 在哪 | 说什么 |
| --- | --- | --- |
| 品种身份 `InstrumentID` | `KanpanCore/Sources/KanpanCore/Model/InstrumentID.swift` | `venue/market/symbol`，键 `key` 形如 `binance/usd_m/BTCUSDT`、`coinbase/spot/BTC-USD`。自选、画线、提醒、复盘、K 线缓存、账号同步全按这个键。裸符号（旧数据）一律归默认交易所。`display` 把代号里的 `-` 显示成 `/`。 |
| 行情提供者 `MarketProvider` | `KanpanNetwork/Sources/KanpanNetwork/Provider/` | 品种表、K 线、24h 行情、推送、历史翻页。上层只认协议 + `ProviderCapabilities` 能力位，从不问「这是哪家」。 |
| 线路 Route | `MarketRoutePolicy`（直连 / 网关）+ `RouteResolver` | 一个全局开关，对所有交易所生效，无自动切换。每家提供者自己决定两条线路各连哪台主机。 |

## 2. 客户端：新建一个目录 + 注册表一行

> 2026-10-08 起（用户定）：**一家交易所一个目录、一个限流器、一套报文解码**。行情提供者与订单流适配器只是它上面
> 两个薄的使用面，不许各写一份域名、路径或解码。通用件都在 `KanpanNetwork/Sources/KanpanNetwork/Provider/`，
> 不认识任何一家。Coinbase 是迁上去的样板，照它写。

1. **新建** `KanpanNetwork/Sources/KanpanNetwork/<交易所>/`，五个文件各管一件事：
   - `<X>Venue.swift`：**这一家的唯一事实来源**——`id`、`market`、`displayName`、`shortName`（品种展示用的缩写，见第 7 节）、
     `quote`、直连域名、`VenueEndpoints.Spec`（直连 REST 主机与前缀、直连推送地址、网关推送是共享 hub
     `.hub`（`/v1/market/stream?source=<id>`）还是中继 `.relay`（`/v1/market/ws/<id>`）；网关 REST 一律是
     `/v1/market/raw/<path>?source=<id>` 原样透传）、`limiter`（一把 `VenueRateLimiter` 的 static 实例，
     **按官方文档的口径**设：按 IP 还是按接口、按次数还是按权重，行情、订单流快照、小组件补价、探测全经它）、
     代号互译（键 ↔ 交易所原生写法）、周期互译、推送控制帧间隔。
   - `<X>DTO.swift`：这一家**全部**的报文解码——品种表 → `SymbolInfo`、K 线 → `Bar`、24h 行情 → `Ticker`、
     费率 / 持仓量、推送帧（行情 / K 线 / 逐笔 / 标记价）→ `StreamPayload`、订单流的盘口 / 逐笔帧 → `BookSnapshot` / `BookDelta` /
     成交。单位、字符串数值、时间、顺序都在这里翻平；出了这个目录谁都不认识它的格式。`SymbolInfo.underlyingType`
     按币安口径填（全是币就填 `COIN`），徽章与分类都认它。
   - `<X>Provider.swift`：实现 `MarketProvider`，请求走 `VenueREST`（GET / POST JSON，主机按顺序试、5xx 换台、4xx 直接报、
     429 按 Retry-After 罚本家限流器），并给出 `static let capabilities`（能力位如实填，见第 2 条）。
   - `<X>Wire.swift`：实现 `VenueWire`（订阅帧怎么拼、一帧放几个订阅、保活发什么、一帧怎么解成 payloads /
     confirmed / error / rejected），交给通用的 `VenueStream`（连接、退避、分层看门狗、订阅同步、拒订记账）。
     要两条连接的（OKX 的 public / business 端点）由 Provider 把两条 `VenueStream` 合成一个 `MarketStream`。
   - `<X>OrderFlow.swift` + `<X>…Adapter.swift`（第 2b 节）：从 `<X>Venue` 取地址与保活参数，用 `<X>DTO` 解帧。
2. **能力位**（`ProviderCapabilities`）如实填写，界面据此自动降级，不写任何 `if venue == …`：
   - `nativeIntervals` + `aggregatedFrom`：14 档周期里原生没有的由上层聚（源周期必须是原生档）。
   - `liveKlineIntervals`：有原生 K 线推送的档；其余档用逐笔拼末根 + 定时 REST 对表。
   - `hasMarkPrice` / `hasFunding` / `openInterestSource` / `hasDerivativeMetrics` / `hasOpenInterestHistory`：没有就 false / nil，
     顶栏六格对应格写「—」；持仓量与衍生统计都没有时，外部指标副图直接不画、不报错。
   - `quoteAssets`、`maxKlines`、`initialKlines`（首屏一发 300 根，深度交给后台加深）、`hasBulkTickers`。
   - `hasOrderFlow`：没有盘口（算出来的指数）填 false，主力订单流不起、图上不挂、不转圈。
   - `hasSessionChange`：帧里的涨跌已按交易日算好（对上一交易日收盘）填 true，客户端照用，不再拿 UTC 0 点开盘价重算。
   - `hasVolume`：K 线没有成交量（算出来的指数）填 false，成交量（连均量）、量差副图与均价线不画，十字线读数不写「量」。
   - 同一家在两条线路上能力可以不同（币安网关档没有盘口与逐笔方向），用 `capabilities(viaGateway:)` 之类按线路给；
     **没有「替身」**：`upstream` 恒等于 `venue`，`isSubstitute` 恒为 false，`snapshotNamespace` 恒为 nil。
3. **注册**：`KanpanNetwork/Sources/KanpanNetwork/Provider/VenueRegistry.swift` 里新建一个
   `VenueDescriptor`，加进 `all`。这一行决定：
   - `displayName`：全名（搜索分区的组头、设置、日志）；`hasFavoriteCategory == true` 时它也是自选页上那一类的名字
     （第一次加这家的品种时在「美股」之后开这一类，这家的品种固定进这一类）。
   - `shortName`：品种展示里带的交易所缩写（列表行名字前的灰小字「币安 DOGE / USDT」、顶栏角标「币安 USDT 永续」、
     桌面快捷方式撞名时的前缀）。空串 = 不带（美元指数）。
   - `joinsSectors`：板块页只收分类表所属那一家，其它家填 false。
   - `defaultSymbol`、提供者工厂（`make`）。
   - `all` 里的第一家是默认交易所（裸符号旧数据归它）；顺序就是自选分类条、搜索分区同档时的先后。
4. **隔离脚本**：把新目录加进 `Tools/check-venue-isolation.sh` 的 `VENUE_DIRS`，
   并把该交易所的名字 / 域名加进 `PATTERN`。
5. **复盘**（要支持复盘才做）：`KanpanReview/Sources/ReviewDomain/ReviewContract.swift`
   的 `supportedMarkets` 与品种形状判断，要和服务端 `sync_validation.rs` / `review_market.rs` 同一口径。
6. **测试**：`KanpanNetwork/Tests/KanpanNetworkTests/<X>*Tests.swift`——解码（按官方文档或实录的帧）、代号与周期互译、
   Provider 走假传输时两条线路的 URL、限流器共用、Wire 的订阅帧与拒订。`VenueFrameworkTests` 里有一个假交易所的示范。

自动跟上、**不用改**的：品种表缓存（`SymbolCatalog` 按交易所各一份，非默认交易所落在
`sources/<venue>/` 子树）、K 线快照（文件名按品种键，天然分开）、多家推送合流（`MergedMarketStream`）、报价簿、
搜索（按交易所分区、代号去分隔符再比）、自选分类、深链（`hkline://drawing/<venue>/<market>/<symbol>/<id>`）、
账号同步编码、顶栏角标（市场为 `spot` 写「现货」，`index` 写「指数」，其余写「永续」，前面带 `shortName` 与计价币）。

### 数据口径（用户 2026-10-08 定）

- **按品种所属交易所给、不混源**：K 线、最新价 / 24h 行情、标记价、资金费率、持仓量（及其历史）、衍生统计、盘口五档。
- **仍然五家聚合、与品种所属交易所无关**：主力订单流（大单挂单、逐笔大单、爆仓、足迹 / 热力）。`OrderFlowCatalog.books(base:)`
  按图上品种的 base 币（`OrderFlowBase.normalize`：`1000PEPE` → `PEPE` × 1000，`kPEPE` → `PEPE` × 1000）去服务端品种表找各家的簿。
- 市值 / 总供应量按 base 币查，和交易所无关；板块页只收币安。

## 2b. 客户端：接进主力订单流（盘口 + 逐笔 + 大单与爆仓）

> 2026-10-08 起主力订单流只查交易所注册表；`OrderFlow/` 里的通用代码不认识任何一家（隔离脚本不再整目录放行它）。
> 现有五家，清单顺序即合并顺序：`VenueRegistry.orderFlow = [.binance, .okx, .coinbase, .bybit, .hyperliquid]`。

1. **适配器**放在那一家的目录：`KanpanNetwork/Sources/KanpanNetwork/<交易所>/<X>…Adapter.swift`，实现 `DepthFeedAdapter`
   （`streamURLs`、`connect`、`decode`、可选 `keepAlive` / `resubscribeMessages(venueID:)` / `fetchSnapshot`）。
   `decode` 只产 `VenueMessage`：`.snapshot(BookSnapshot)`、`.delta(BookDelta)`、`.trade`；回执、pong、心跳帧回空。
   成交的 `hit` 一律按「主动方吃哪一侧」：主动买 = `.ask`。
2. **注册表条目** `<交易所>/<X>OrderFlow.swift`：`extension OrderFlowExchange { static let x = OrderFlowExchange(…) }`，
   一条说清楚：
   - `key`（与品种表 `exchange` 列、簿 id 第一段同一个）、`displayName`（图例、弹层副标题、爆仓最大一笔的来源）；
   - `sequenceModel`：按产品 / 面值口径回 `DepthSequenceModel`——`rangeOverlap`（币安 U 本位）、`previousFinalOverlap` /
     `previousFinalExact`（币安现货 / 币本位、OKX）、`strictIncrementing`（Bybit：`u` 严格 +1）、`snapshotOnly`
     （每帧整本、没有序号，Hyperliquid）。没有「信任上游、不校验」这一档；
   - `snapshotInBand`：快照随流下发填 true；要另拉 REST 快照（币安）填 false，模型在连上时回 `.fetchSnapshot`；
   - `maxBooksPerConnection`：按中继 / 上游的订阅配额取（Bybit 12、Hyperliquid 8）；
   - `liquidationCode`：服务端 `/liq`「哪家」列的编号（0 币安 / 1 OKX / 2 Bybit），没有强平推送填 nil；
     同时在 `KanpanCore/…/OrderFlow/BigTradeDigest.swift` 的 `LiquidationRow.Exchange` 加同号一项；
   - `fallback`：服务端品种表没收这只时保底订哪几本（Bybit `<BASE>USDT`；Hyperliquid `<BASE>`，价格乘回图上缩放）；
   - `makeAdapters`：把这一家的一批簿分到连接上（`OrderFlowExchange.chunks`）；只能走中继却没有 kanpan-api 主机就回空。
3. **加进** `VenueRegistry.orderFlow`。`OrderFlowCatalog.venue(…)` / `catalog.adapters(_:)`、`OrderFlowBase.exchanges`
   （代号 → 显示名）、大单流（`BigTradeFlow`，五家合并按门槛 ÷ 50 记）、「大单与爆仓」弹层的现货 / 合约分账、价位梯、
   每根柱都自动跟上，**不用改**。
4. **测试**（`KanpanNetwork/Tests`）：用真实录下的帧写解码用例（快照、增量、成交方向、回执 / pong 忽略、跳号只重订那一本）；
   把这家加进 `StressFiveVenueStreamTests`（深度流 × 模型 × 大单流）与 KanpanCore `OrderFlowStressFiveVenueTests`。
5. 隔离脚本 `VENUE_DIRS` 加这家的目录、`PATTERN` 加名字 / 域名（第 2 节第 4 条）。

| | Bybit | Hyperliquid |
| --- | --- | --- |
| 线路 | 一律经 kanpan-api 中继 `/v1/market/ws/bybit?category=spot\|linear\|inverse` | 一律经 `/v1/market/ws/hyperliquid` |
| 订阅 | `orderbook.1000.<代号>` + `publicTrade.<代号>`；一条消息 ≤ 10 个 args，一条连接 ≤ 12 本 | `l2Book`（`nSigFigs` 4，每侧 20 档）+ `trades`；一条连接 ≤ 8 本；`subscriptionResponse` 忽略 |
| 序号 | `strictIncrementing`；`u == 1` 的 snapshot 整本重来；接不上只退订再订那一本 | `snapshotOnly`（每帧整本） |
| 心跳 | 每 20 秒 `{"op":"ping"}` | 每 30 秒 `{"method":"ping"}`，静默看门狗 60 秒 |
| 成交方向 | `S = Buy` 吃卖盘 | `side = B` 吃卖盘 |
| 爆仓 | `/liq` 编号 2 | 无 |

## 2c. 网页版（电脑 `Web/src` + 手机网页 `Web/src/m`）接进主力订单流

## 3. 服务端 `Backend/kanpan-api`

> 2026-10-08 起：**一家一个目录、一个出站节拍、一处注册**。`src/venues/mod.rs` 的 `trait Venue` + `venues()` 是唯一清单，
> 分发、校验、白名单、命名全问它；`src/venues/outbound.rs` 是共用件（`Pacer`、`Upstream`、带节拍的 GET / POST、短缓存合流）。

1. **新建** `src/venues/<id>/`：
   - `mod.rs`：`SOURCE`、主机、**唯一的出站节拍 `PACER`**（按官方口径设：按 IP 的次数、按接口的车道 `Lane`、或按权重的格数；
     透传、补缺 K 线、订单流品种表、持仓量 / 费率、`market_meta` / `listing_watch` 顺手拉的表全部经它）、透传白名单
     （路径 + 查询键 + 值长度，短 TTL 缓存 + 同键合流）、`candles(symbol, step, start, end)`（1 分钟必须支持，提醒补缺用）、
     持仓量 / 费率（有的才有）、`impl Venue`（`source` / `market` / `market_key` / `symbol_ok` / `short_name` / `display` /
     `webhook_name` / `meta_symbol` / `raw` / `raw_post` / `stream` / `candles` / `open_interest` / `funding` / `oi_history` / `alert_feed`）。
   - `relay.rs`：`/v1/market/ws/<id>` 中继的上行白名单（传输、名额、超时在 `market_relay`）。要共享一条上游的（Hyperliquid）
     用 hub，中继挂在 hub 上。
   - `orderflow.rs`（第 3b 节）：主力订单流的品种表，出站经本家 `PACER`。
   - `alerts.rs`：实现 `alerts::KlineFeed`（连上并订好一批品种的 1 分钟 K 线或逐笔、解帧、保活、补缺默认问本家 `candles`），
     通用循环 `alerts::run_feed` 负责重连、补缺、判定、自选波动；`main.rs` 按注册表每家起一条任务。
2. **注册**：在 `venues()` 的数组里加这一家。`raw` / `stream` / `funding` / `open-interest` / `open-interest/history` 的分发、
   `sync_validation::identity` 的 `(venue, market)` 与代号形状、提醒的 `market` 白名单、搜索的复盘白名单（`Venue::review`）、
   深链 / 通知标题 / Webhook 的品种名、`/v1/market/meta` 的代号折算全部自动跟上。路由挂在 `/v1/market/` 下——`/market/*`
   在 Caddy 上整段归 Python 网关，不许占。
3. **复盘**（要支持才做）：`Venue::review` 回 true，并在 `review_market.rs` / `review_worker.rs` 按 `(venue, market)` 加取 K 线与逐笔的分支。
4. **不混源**：任何一家的数据缺了就是缺了，不拿别家顶。条件提醒（`conditions.rs`）仍只判币安。
5. **契约**：`contract/instruments.json` 的 `venues` 清单两端对账（Rust `instruments.rs`、Swift `InstrumentContractTests`）。
6. 部署：先推上 `origin/main`，从干净的 `origin/main` 检出 → 加部署锁 → 备份 → rsync 到
   `/opt/kanpan-api` → `cargo build --release` → `python3 ops/install.py` →
   `systemctl restart kanpan-api kanpan-worker` → 只读验证（下面第 4 节）。不改 Caddy、不动 Python 行情网关
   （它只转币安：`/market/stream` 共享 hub 与 `/market/v1/*?source=binance`）。

### 3b. 服务端：接进主力订单流（常驻跟踪 / 大单分钟历史 / 热力 / 墙条件 / 爆仓）

服务端常驻跟踪的簿与逐笔都在 `src/orderflow_history/`，一家交易所要接的只有下面几处，分钟历史、热力、墙条件、
`/history` 的显示名都按 `tracked_venues` 自然带上，**不用改**：

1. **品种表**：`src/venues/<id>/orderflow.rs` 出 `KEY` 与合约表（`orderflow_instruments` 收行），簿 id 是 `<key>:<product>:<代号>`。
2. **序号模型**（`src/orderflow_history.rs` 的 `info()`，同第 2b 节口径）：交易所 → 显示名、`Sequence`、快照是否在推送里（in-band）、
   是否滑动窗口（深度只给前 N 档、跌出窗口的档位不推删除）。`has_feed` 加上这家的 `KEY`，`tracked_venues` 才会收它。
   - Bybit：`StrictIncrementing`（`u` 严格 +1；`u`==1 是交易所重推快照，整本重置）、in-band、滑动；
   - Hyperliquid：`SnapshotOnly`（每帧整本、没有序号，`last` 取帧里的 `time`）、in-band、滑动。
3. **连接种类**（`feeds.rs` 的 `Kind`）：URL、每连接容量、订阅请求、解码。
   - Bybit 三类各一种（`bybit-spot` / `bybit-linear` / `bybit-inverse`）：`wss://stream.bybit.com/v5/public/{category}`，
     连不上与 `stream.bytick.com` 交替；订 `orderbook.1000.{代号}` + `publicTrade.{代号}`，一条请求最多 10 个 args，
     每连接 50 本；20 秒发 `{"op":"ping"}`；`S`=Buy 是主动买（吃卖盘）；断档只重订簿话题；`success:false` 回执打 warn。
   - Hyperliquid 一种：不自己开连接，挂进 `venues/hyperliquid/hub` 的共用连接（`Class::Tracking`，与给手机转发的共用一条上游）；
     订 `l2Book`（`nSigFigs` 4、每边 20 档）+ `trades`；`side`=B 是主动买；订上后第一帧成交是回放，整帧丢掉，
     之后早于订阅时刻的成交也丢掉。
4. **节流**（`hub.rs` 的 `pace`）：一家一组。Bybit 两次建连至少隔 250 毫秒、5 分钟最多 100 条；Hyperliquid 走共用 hub 自己的节流。
5. **爆仓**（`liq.rs` 的 `Source`）：有全市场强平推送的才接，`/liq`「哪家」列编号 0 币安 / 1 OKX / 2 Bybit。
   - Bybit 只有 linear 与 inverse 两路（现货没有强平）：`allLiquidation.{代号}` 只能按代号订，订的是此刻跟踪的 base 在 Bybit 的合约，
     每 30 秒随映射对一次差；`S`=Buy 是**多头被平**（被平仓位的方向，与币安 / OKX 记平仓单方向相反）；名义 U 本位 p × v、币本位 v × 1 美元。
   - Hyperliquid 爆仓无公开数据源：公开推送只有不带强平标记的 `trades` 和按地址订的 `userFills` / `userEvents`，不接。
   - Coinbase 只接现货，没有强平。
6. **测试**：解码用线上实录帧（`feeds.rs` / `liq.rs` 测试里的原样帧）；`btc_is_tracked_on_all_five_exchanges` 断言 BTC 五家都在跟踪表里。
   上线后看 journal 里每分钟一行 `connections per minute: … bybit-linear n/n conns … hyperliquid 1/1 conns …` 与
   每小时一行 `Orderflow liq: … bybit-linear … seen`，再 `curl /v1/market/orderflow/history?base=BTC` 看 `exchange` 有没有这家。
