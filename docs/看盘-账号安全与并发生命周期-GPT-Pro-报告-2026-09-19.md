## 阅读结论

本轮没有确认"B 凭自己的账号经现有云端接口读取或修改 A 的自选、画线、复盘正文"的完整漏洞路径。已读取的个人正文查询走 RLS 事务，账号表的裸池查询另有身份范围约束。这不是对所有部署状态的安全认证：没有连接生产数据库核验实际角色、策略和迁移执行状态。

真正应先处理的，是 退出登录与档案准备绑在一起、合法 refresh 重试超过 60 秒被误判重用、全员共用登录 IP 额度，以及线路启动与前后台恢复中的代际/任务收尾缺口。最后一类有一个共同特点：旧结果被过滤掉了，但新流程也被旧流程打断，最终不是串入错误数据，而是没人继续给当前界面供数。

## A. 账号与安全

### A.1 问题清单

#### A-01｜退出账号依赖"下一份访客档案能正常读入"，且准备阶段提前发布了当前属主

现象："我点了退出，但它报了个存储错误，屏幕上还是我的账号和复盘；这时不能把手机当作已退出交给别人。"

机制：AccountFeature.logout() 先调用 onPrepareAccount?(nil)，再清 Keychain、清用户状态及装入访客视图。prepare(nil) 会读取访客的偏好、自选、画线、复盘等，任一必需读取抛错，后面的 signOut()、user = nil 和界面卸载都不会执行。与此同时，AccountFiles.directory(user:) 在创建目录及后续准备成功前就写了全局 currentProfile；实际显示的个人 store 还归 A，派生行情缓存却可能已经认成访客或 B。证据：AccountFeature.swift:101–112、AppAccountBridge.swift:162–185、AccountFiles.swift:35–47、QuoteBook.swift:170–189。

最短触发：A 已登录；让下一访客目录中的必需档案不可读；点击退出。检查账号仍为 A、个人视图仍未卸载，而 AccountFiles.currentProfile 已改变。也可以在 B 的准备过程失败时检查全局 profile 与已激活 store 的不一致。

确信度：确认。这是可失败的退出流程与身份提交点不一致，不是已经证明的云端跨账号读取漏洞。错误会显示出来，不能描述成"UI 明说已退出却偷偷保留账号"。

建议：先完成本地安全退出——封住旧账号请求、卸下旧个人视图，再尝试载入访客档案；访客档案失败时显示可继续看行情的安全空壳，不覆盖损坏原件。把 currentProfile 发布移动到实际激活提交点，准备目录不应改变"当前是谁"。

#### A-02｜冷恢复后立即退出，服务器会话不会被吊销；有过期 access 时也可能只完成本地退出

现象："本机已经退出了，但设备列表里那条会话还活着；已经复制出去的那份绑定凭据仍有机会使用。"

机制：SavedAccount 不存 access；冷恢复后 AccountClient.access 为空。signOut() 只抓取内存里的 access?.accessToken，先删本地凭据，再仅在该值存在时启动一个不等待结果的 logout 请求。没有 access 就完全不发吊销；有 access 但它已过期时，发送的仍是该旧值，没有刷新或另一条会话级吊销路径。证据：AccountClient.swift:69–111、Models.swift:24–30、auth.rs:143–151。

最短触发：成功登录并保存 refresh；重启客户端，不发任何认证业务请求，直接退出；检查服务器 account_sessions.revoked_at 仍为空。第二种样本：让内存 access 过期后直接退出，观察 logout 的 401。

确信度：确认。不意味着正常使用同一部手机的 B 会自动拿到 A 的 token；正常本地 Keychain 删除仍发生。

建议：明确"本地退出已完成"和"服务器会话已吊销"是两件事。在线路径使用可认证的会话级吊销，或者先取得有效吊销凭据；离线路径不能因此阻塞退出。设计待补吊销时不要把已经退登的通用 refresh 继续留在活动凭据槽里。

#### A-03｜同一 request_id 的合法重试超过 60 秒，会被当成盗用并吊销整条会话

现象："刚才只是网络不好，过几分钟回来就再也同步不上，必须重新登录。"

机制：服务端已消费的 refresh 只有在 request_id 相同且 used_at 距当前少于 60 秒时才重放密封响应；相同 request_id 超过窗口也直接进入 revoked_at = now() 分支。客户端恰好会把重试 ID 和旧 refresh 持久保存，失败后不清，下一次仍用它重试。清理任务又会清除超过该窗口的重放响应。证据：auth.rs:118–138、AccountClient.swift:69–96、maintenance.rs:9–17。

最短触发：发送 R0 + id=X；服务器提交 R1 后丢弃响应；客户端保持离线 61 秒以上；再发同一个 R0 + X。结果为 401，并撤销整条 SID，包括已经签发的新 access/refresh。

确信度：确认。请求前落盘的顺序是正确的：vault.write(saved) 在 HTTP 之前。崩在那次落盘之前通常不会形成"服务器已消费"；崩在服务器提交之后、客户端保存新对之前才是该反例。

建议：将"已知同一绑定、同一 request_id 的恢复"与"不同请求重用旧 refresh"分支分开；按移动端可能中断多久设计可恢复窗口/结果保留，而不是以 60 秒后同样吊销收尾。不能通过清空用户本地档案来处理。

#### A-04｜登录和注册的 IP 额度是全员共享的，登录额度耗尽又被伪装成密码错误

现象："另一台设备一直在试，我输入正确密码也说用户名或密码不对。"

机制：注册和登录以 ConnectInfo(peer).ip() 生成 key，实际反代部署下是 Caddy 到 API 的连接地址。注册为 30 次/60 秒，登录为 60 次/60 秒；它们不是"仅失败才计数"。登录超过额度返回 unauthorized，UI 映射为密码错误。每用户名的第五次错误锁定是另一套 key，只锁该用户名。证据：auth.rs:71–115、Caddy.routes:25–30、AccountFeature.swift:64–92。

最短触发：经同一 Caddy 在一个窗口里完成 60 次进入登录限流器的请求，再让另一真实用户用正确密码登录。它同样被挡。

确信度：确认。题目"Caddy 没注入客户端 IP 头"不是准确根因：Caddy 默认会设置/追加 X-Forwarded-For，这里是后端没有使用可信反代提供的客户端地址。

建议：只对可信本地反代连接解析其提供的客户端地址，保留每用户名的锁定；对额度超限返回可区分的限流结果，而不是密码错误。不要直接信任任意外部传入的 XFF。

#### A-05｜已确定失效的服务器会话没有对应的"需要重新认证"状态

现象："账号页看着已经登录，却所有同步都失败；改密码还把会话失效说成我输错旧密码。"

机制：冷恢复只根据 SavedAccount 激活本地账户，这是离线能力所需；问题在后半段：refresh 收到终局 401 后只向上抛错，账号的 user 和档案保持激活，却没有独立的认证失效标记。改密和注销路径把任何 401 归成"密码不对"，包括请求压根没进入验密码处理函数的情况。证据：AccountFeature.swift:51–61、AccountFeature.swift:64–112、AccountClient.swift:38–52、AccountClient.swift:69–96。

最短触发：另一台设备吊销本 SID，或者超过 30 天不续期；冷启动恢复本机 SavedAccount；发同步、再尝试改密。验证本地账户仍显示已登录而云端不可用，并检查错误文案。

确信度：确认。restore() 不先调用 /me 本身不是 bug；也不能把所有网络失败都当终局 401。错误绑定、已吊销、到期都可进入该终局路径，但普通断网应保留"暂时未联通"。

建议：分离"已挂载本地个人档案"与"云端认证可用"。确定失效时显示重新认证入口，停止无意义的重复认证请求；保持现有本地档案、自选与画线可用，不强制退成访客、不清本地数据。

#### A-06｜刷新单飞只在单个 AccountClient 内成立，同一凭据槽的多个客户端可以互相吊销

机制：refreshFlight 和 generation 均为实例字段。两个客户端从同一 vault 各读到 R0、各生成不同 request_id 后，服务器将后到者按 refresh 重用处理。证据：AccountClient.swift:12–30、AccountClient.swift:69–99、auth.rs:118–138、KanpanApp.swift:11–31。

确信度：确认该输入条件的协议结果；疑似当前正常 UI 是否产生两个同时活跃的实例。

建议：同一活动凭据槽只保留一个认证会话所有者，所有功能客户端共享它。无需换 token 方案。

#### A-07｜Release 测试种子能覆盖真实账号的自选读取，隔离并非由一个统一开关保证

机制：SymbolPrefsStore.read() 在读任何 storage 之前先返回环境种子；它不区分传入的是内存仓还是账号目录的 PersonalFileStorage。MainScreen.wireAccount 仅在测试模式且没有 API 环境变量时跳过桥；桥的独立测试根又要求另一个 profile 是 UUID。证据：SymbolPrefs.swift:407–469、MainScreen.swift:1219–1254、AppAccountBridge.swift:40–60、AccountFeature.swift:24–49。

确信度：确认在能够控制进程环境的前提下存在该组合路径。不是可远程利用的登录绕过。优先级低于 A-03。

建议：Release 对测试模式入口整体关闭，或要求进入测试模式前一次性验证完整隔离上下文；不能让"测试种子生效"与"账号目录隔离生效"分别由不同变量决定。

#### A-08｜灾难恢复只保留数据库、丢失服务密钥时，账号不能按原密码恢复

机制：密码验证依赖 HMAC pepper；refresh 重放密文依赖加密 key。backup.sh 备份数据库，不包含这两项；install.py 在没有既存环境文件时生成新值。证据：crypto.rs:10–37、install.py:1–79、backup.sh:1–10。

建议：备份/恢复说明将数据库与原密钥定义为一组，分别安全存放；恢复旧账号库但缺少原密钥时显式中止，而不是静默生成替代密钥。

### A.2 令牌 / 会话的完整状态图

实际表名是 account_tokens，通过 kind 区分 access 和 refresh。每次鉴权同时检查 token 到期、session 到期/吊销和用户 disabled 状态；"token 行仍在"不等于"token 仍可用"。

|事件|access 的结果|refresh 的结果|session / 用户的结果|是否误踢、是否仍可用|
|--|--|--|--|--|
|正常刷新|签发新 access；未过期旧 access 可并存|旧 refresh 标 used，新 refresh 可用|SID 滑动延长 30 天|正常|
|60 秒内同 request_id 重放|返回原来那一个 access|返回原来那一个 refresh|SID 不建立第二条|网络重传正确幂等|
|60 秒后同 request_id 重放|家族 access 被 SID 吊销挡住|新旧 refresh 都失效|SID revoked|合法丢响应会误踢，A-03|
|旧 refresh、不同 request_id|家族 access 失效|家族 refresh 失效|SID revoked|复制同一 SavedAccount 的两个客户端也会触发|
|绑定 id/secret 不匹配|已有 access 的使用不靠 device 重新绑定|此次 refresh 拒绝|此分支不主动吊销 SID|客户端可卡在 A-05|
|改密码|当前 SID access 继续有效；其他 SID access 即使行未删也被拒|当前 SID 可续；其他 SID 不可续|撤销其他 SID|排除题目的残留 access 越权猜测|
|服务端 logout|该 SID 所有 access 拒绝|该 SID refresh 拒绝|SID revoked|已经通过鉴权的在途请求另论|
|客户端冷恢复后直接 signOut|本地没有 access；不发 logout|本地删除，服务器那份仍可能有效|服务器 SID 未必改变|本地退出不等于远端吊销，A-02|
|吊销某台"设备"|目标 SID access 拒绝|目标 SID refresh 拒绝|SQL 同时限定 SID 与 i.user|接口 id 实际是 session id|
|注销账号|Identity 的 disabled 检查拒绝|refresh 的 disabled 检查拒绝|用户 disabled|不依赖逐条删 token 才安全|
|30 天不续期|session 到期仍会挡住|拒绝，不自动续命|SID expired|需要重新登录，本地资料仍应可用|
|两设备各自正常登录并发刷新|各自 access|各自 refresh|各自 SID|不应互踢；排队不是重用|
|同 user、同 device.id 再登录|旧同 device SID access 被撤销|旧同 device SID refresh 被撤销|new_session 先撤销同设备旧 SID|当前协议明确行为|

设备身份的结论：AccountFeature.init 的新 device 是初值；restore 会拿 savedDevice() 覆盖它，refresh 请求始终使用 SavedAccount 内的 device。设备列表返回 SID，吊销通过 WHERE id = ? AND user_id = ? 限定本人，正常路径成立。

### A.5 Keychain、主机、输入与运维的其余裁决

- AfterFirstUnlockThisDeviceOnly 合适；未标 kSecAttrSynchronizable，不会 iCloud 同步。
- kanpan.scorebook 是遗留的独立 Keychain 服务，当前激活链是 AppAccountBridge 创建 ScorebookClient 委托给共享 AccountClient；未读到下一用户自动从该旧服务拿 A token 的调用链，排除"仅因为没清就必然串复盘"。旧项可以在确认不再依赖的迁移中清理。
- claimGuest 先持久登记归属并轮换 guest；B 不能把已登记给 A 的批次再认领一次。已有测试。
- APIHost 管行情 REST/WS；AccountClient 的 base 来自固定账号配置，refresh 不会发给新行情主机。
- AccountClient 不是域名白名单：构造器允许任意 https host。SavedAccount 不绑定 origin。当前 Release UI 没有重定向入口。
- path 守卫：普通 `..`、前导 `/`、字面 `://` 被拒；编码 `%2e%2e` 可通过字面检查但仍同源。
- sync operations：deny_unknown_fields、白名单等齐全。客户端按条数/依赖切批，没有按实际 JSON 字节预算切批；512 KiB 对"100 条合法操作"不是保证；服务端 413 发生在业务验证之前。应补按实际编码字节的分批。
- 没有超时层：应验证请求体读取截止、业务处理截止与数据库语句/锁等待截止三层。
- account_limits 有窗口重置和 maintenance 清理。refresh 没限流：已有有效绑定的失控客户端能反复刷新制造 token 行；适合一个低成本的会话级请求节奏上限。
- 注册返回 username_taken，能测名字是否占用，有限用户名产品的可见性，不高危。
- account_challenges 等旧邮箱表未启用 RLS；mail.rs main 在配置邮件能力时仍可能启动。应使用追加迁移处理废弃的表/列/worker。
- backup.sh umask 077、600、.part 后改名、30 天保留。需要补成套恢复的是原密钥与数据库，A-08。

## B. 并发与生命周期

### B.1 问题清单

#### B-01｜RoutedMarketFeed 在启动完成前公开新 feed，旧启动能覆盖更新的 selection

现象："正在启动或换线路时马上点另一个品种，页面停在加载/旧图；当前选择的行情事件都不再进来。"

机制：activate 只在 await oldFeed.stop() 后核验一次 request/route。随后把 created 提前赋给 feed，再 await 设置快照、创建 events，最后用最初保存的 request 调 created.start。这几个 await 之间，另一条 switchTo 可以看到这个尚未启动完成的 feed，并把新 selection B 交给它；旧 activate 恢复后又用 A 调 start，将内层选择改回 A。外层 selection 已是 B，forward 正确地丢弃 A，结果整条当前数据通道失去活性。RoutedMarketFeed.swift:128–185

```text
activate(A): feed = created
activate(A): await created.setSnapshotEnabled(...)   ← 允许其他调用进入
switchTo(B): outer.selection = B; await created.switchTo(..., B)
activate(A): 恢复，await created.start(当前 symbol/interval, selection: A)
forward: inner=A，但 outer=B → 全部拒绝
```

还有另一侧：旧 feed 的 stop 尚未返回时，shared feed 仍指向它，新 switch 可以被交给正在拆除的对象；旧 activate 因 selection 变化退出，未必有人负责完成新线路建成。

确信度：确认静态交错成立。巡检仅在 pendingHistoryError != nil 时重试，不能保证修复这种静默丢事件。RoutedMarketFeed.swift:316–334

建议：启动作为有代际的完整操作：先在局部建成，验证最新 request/route 后发布；或者每个 await 之后核验并明确让最新请求接管。

#### B-02｜回前台先取消首屏历史，再用"没有跨桶"判据决定不补取

现象："打开时还没加载好，切出去再回来，最新价在跳，但历史只剩一两根，自己不再加载。"

机制：enterForeground 不区分"已正常运行，只需追实时"与"首次历史尚未完成"。它先 loadTask?.cancel()，随后发现 pendingBars() <= 1 就返回。冷启动无缓存但 WS 已给一根当前桶时，这个条件完全可能成立。被取消的 fill 走取消分支，不报 historyError；路由巡检也只对明确 historyError 重试。MarketFeed.swift:276–313、MarketFeed.swift:660–778、RoutedMarketFeed.swift:316–334

最短触发：无缓存；把首屏小页和全页 REST 都挂起；放行一根当前桶 WS；在同一桶内短暂切出并返回；放开网络，确认原历史请求取消，而没有新的完整 fill。

确信度：确认该时序与数据形状。

建议：恢复策略至少区分首屏已完成、首屏仍在途、需要补缺；未完成首屏不要无条件取消，取消就必须有接替任务。

#### B-03｜WS 的 runGeneration 没有覆盖收帧、订阅完成及清理，旧操作可修改新连接状态

现象："快速断线重连或停止再启动后，连接看起来恢复了，某些订阅却没真正装上；偶尔旧帧跑进新流。"

机制分三处：
1. start() 替换 continuation/runTask、加 runGeneration，但不主动结束前一条流或取消被替换的 runTask。已进入 pump 的循环不检查 generation，且收帧/取时钟的 await 之后直接向当前字段 continuation yield。再次 start 而没有完整 stop 时，旧 pump 可以服务新流。
2. syncStreams 发送控制帧后才修改共享 sentStreams，没有检查完成的是不是当前 socket/run；旧任务的 defer 还会无条件 syncTask = nil 并调度下一轮，可能清掉新任务的句柄。
3. loop 的重连清理在 await socket?.cancel() 前检查 generation，之后却直接清 socket/sentStreams。

证据：WSClient.swift:80–158、WSClient.swift:171–238。

确信度：确认 API 交错边界；正常 UI 中出现频率未测。Feed 的 startWS 自身在 await ws.start 前后才发布 wsTask，且网络、前后台命令不共用就绪状态。

建议：run 使用自己的 continuation/socket，并将 generation 传入 pump、控制帧完成与 defer；旧任务只能清自己的句柄。start 明确是幂等还是替换，替换时同时收掉旧生产者。

#### B-04｜取消只检查在"提交停止命令之前"，晚到的生命周期命令仍可打断新状态

现象："刚回来已经恢复，紧接着又断一下，或回前台后多经历一次无缘由重连。"

机制：25 秒任务醒来检查 Task.isCancelled 后，才跨 actor 调用 suspendWS()；该方法入口没有复核取消或前后台 epoch，await ws.stop() 后又给当前 composer 记缺口、发 offline。enterForeground 的多个 await 之间没有统一的"现在仍希望前台运行"校验。networkGeneration 只约束 networkChanged 的那一条恢复。MarketFeed.swift:252–369、MarketModel.swift:222–241

确信度：确认缺少统一代际的控制路径；所述用户可见交错仍需原项目可控夹具复现。

建议：用一个明确的期望运行状态/生命周期 epoch 约束这类控制命令；suspendWS/startWS 在实际改状态的入口和 await 后复核。

#### B-05｜REST 赛马的失败路径检查取消，成功赢家路径却仍会污染线路冷却

机制：MarketRESTTransport.get 在 race 没有赢家时检查 cancellation，再记失败冷却；有赢家时直接 settle。race 得到赢家后还要等落败子任务结束；在该等待中父任务被取消，仍可能返回赢家，进而修改 preferred 与其他候选的 10 秒冷却。setPolicy 清理过冷却后，老请求也没有 policy epoch 防止重新写回。MarketSource.swift:44–90、MarketSource.swift:118–129、MarketSource.swift:188–224

确信度：确认交错窗口。低严重度。

建议：race 返回后、无论有没有赢家都立即检查取消和本次 policy/route 身份，再提交线路状态。

#### B-06｜两个 DisplayLink 的离屏清理不对称，弱 target 不会使链接自己消失

机制：主图在 didMoveToWindow(nil) 清主 link，正确；但 animation.didSet 可在无 window 时直接 resumeLink。LinkProxy.tick() 在 view 已释放时只是空操作，没有 invalidate。画线的第二条 link 不在 didMoveToWindow 的清理中，只在下一帧满足 claimed/touches/animation 全空时自灭。ChartView.swift:238–274、ChartView.swift:347–409、ChartView.swift:475–489、ChartView+Drawing.swift:47–69、ChartView+Drawing.swift:660–690

确信度：确认存在缺少显式清理的资源路径；真实旋转/来电稳定复现为疑似。

建议：离屏统一取消两条 link 并收掉交互态，resume 必须确认视图可呈现；弱代理在宿主消失时也要有链接自清理能力。

#### B-07｜根宿主和长期 Task 的所有权没有完整释放契约

机制：MarketModel 的 pump 强持有 self，模型又保存该 Task。AppLifecycle 按固定 ID 保存闭包、覆盖 hook 不等于停止旧模型的任务；Routed monitor 在进入 while 前绑定强 self。MarketModel.swift:198–220、RoutedMarketFeed.swift:291–303、MainScreen.swift:1134–1217、AppLifecycle.swift:25–70

确信度：疑似生产根销毁路径；强引用等待关系确认。

建议：明确谁拥有整套 feed 生命周期，并在实际宿主终止时执行 stop。

#### B-08｜报价合批缓冲没有与账号/线路切换一同重置

现象："刚切账号或线路，短暂出现上一轮攒着的报价，之后才被新值替换。"

机制：retargetProfile 清 raw、opens、receivedAt、everPublished，却不清 coalesced、steady 和其待刷任务；flushSteady 发布时也不重新按 owner/source 过滤。restartStream(clearing:) 的 cancelQuotes 会先冲掉 coalesced，再清 raw/onReset，延后 steady 仍可能发布旧一批。QuoteBook.swift:170–189、QuoteBook.swift:660–730、QuoteBook.swift:783–809

确信度：确认缓冲没有同代清理。

建议：合批数据携带 profile/source epoch，切换时明确丢弃旧缓冲或仅提交给原属主；flush 前再做代际过滤。

### B.2 三条 AsyncStream 的收尾与缓冲

"没有 onTermination，所以 for await 永远不退出"已排除（独立 Swift 6.2.1 检查：消费者等待时取消，循环退出）。真正缺的是消费者终止后由谁停止长期生产者。MarketModel.pump 强捕获 self 的释放要等异步闭包实际结束；显式 pump.cancel() 才是关键。

建议边界：需要上限时按事件语义合并可覆盖的行情，保留必须有序的控制/结构事件；不要统一改为 bufferingNewest(1)。

### B.6 unchecked / unsafe 逐处排查

已读取的 10 个 @unchecked Sendable（SnapshotGate、ArchiveWriter、URLSessionSocket、PathSnapshot、InMemoryPrefsStorage、PersonalFileStorage、DiagnosticsCenter、DiagnosticsStore、SeriesStore.PruneClock、NetworkFakes.Counter）均有锁或串行队列保障，排除。DiagnosticsCenter 的 lazy subscriber 和 add/remove 在锁外，生产单例一次 start 可排除常规竞争。

已读取的 7 个 nonisolated(unsafe)（SeriesStamp.counter、Paint 的四个 cache、drawingSessionKey、ChartView.swift:469 ctx）均有锁或为常量；ctx 依赖调用者当时已经在 MainActor，当前路径未见反例。

### B.7 存储型 Task：创建 → 取消 → 体内检查（摘要）

主要结论已并入 B-01～B-08。额外：
- MarketModel.statsTask 内部一次 meta 子 Task 没继承取消，有限但可能继续，低风险。
- QuoteBook.persistTask 体内没有取消检查，cancel 不能保证已开始写不完成；persistPending 单纯取消去抖时通常有替代写，不支持"最后值必然永远不写"。
- QuoteBook.idleTeardown 实际执行前再查 needsConnection，排除通常的迟到 teardown。
- BackgroundGrace.expiry deinit 只 cancel Task 不等于主动 end OS id，自定义实例销毁场景需测试。
- Orientation.rotate 的 600ms Task：较旧 Task 可能提前放开较新方向请求；最终都是 allButUpsideDown，低严重度；保存一个可取消复位任务/序号，只让最后一次复位。
- MarketModel.startStats 的一次 meta 子 Task 不随 statsTask 取消而自动消失。

### B.8 detached、优先级与缓存写入链

writeSnapshotNow 的"Now"是安排写，不是 await 全链完成。SeriesStore.warm 是 background，并非所有 detached 都是 utility。ArchiveWriter.drain 的同步等待可能把主线程挂在排队写盘上，但没有反向主线程依赖，不是静态可证明死锁。

### B.9 Observable、boot、账号交接与单例

- onChange 各链路均有同值 guard，未见闭环。
- boot 一开始 guard !didBoot，同步置 true，没有 await，双入口不等于双初始化。
- prepare 返回的激活闭包在 MainActor 上同步执行，没有 await；旧网络 push 返回后需过 epoch/runID 检查。发现的是 A-01 的闭包提交之前提前改变 currentProfile。
- MarketFeed 不直接持有 ChartViewport；不是裸数据竞争。
- K 线快照是按市场源/品种/周期的公共缓存，恢复登录后不必重下载。
- AppLifecycle/MemoryWarningRelay 单例观察者不注销合理；固定 ID hook 的覆盖意味着多根宿主会争用同一个键。

### B.10 测试缺口与夹具选择

先纠正夹具用法：StepPacer.sleep 立即推进自身时间并 yield，不是"等测试手动放行"的时钟；pendingBars() 直接读系统 Date，不受 pacer 控制。稳定重放交错应使用可阻塞的 Gate/持有 continuation 的 fake。NetworkFakes.Gate 目前是内部声明，跨测试模块使用时须通过正确 test-support 接口。
