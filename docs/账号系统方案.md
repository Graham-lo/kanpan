## 一、先把家底摆清楚

动手之前查了一遍现有的东西，有三件和之前的假设不一样：

1. **后端不是没有，是没部署。** `/Users/mdd/zhk/scorebook-backend` 是一套完整的 Rust 服务
   （axum 0.8 / sqlx / PostgreSQL 17 + pgvector，30 个 migration，schema 43），但 README 自己写着
   「**Mac 本机已部署**，入口 127.0.0.1:5178」「**多用户产品功能不做**」。它是给你一个人在 Mac 上用的工具，
   不是对公网提供服务的产品。
2. **它没有密码、没有邮箱、没有注册。** 认证只有一张 `api_keys(token_hash, owner_id, revoked_at)`，
   Bearer 一个手工发的 key。全库没有 argon2/bcrypt，没有任何发信代码。
   但**每张业务表都已经带 `owner_id` 和 `UNIQUE(owner_id, id)`**——按用户隔离的骨架是现成的，缺的是
   「一个人怎么拿到 owner_id 和令牌」。
3. **Codex 正在对接的复盘接口，后端里还不存在。** `ScorebookClient` 请求的是
   `v1/native-review/records | search | statistics | profile`，backend 里搜不到 native-review 任何痕迹。
   也就是说复盘的服务端这一半，本来就是要新写的。

再加上你说的：两台 VPS 现在只转发行情，没有后端。所以服务端是从零起步，没有历史包袱。

顺带确认了 Codex 这一轮写的东西（`KanpanReview/`、`Kanpan/Kanpan/ReviewIntegration/`）：
`ReviewStore` 按注入的 `directory` 落盘、`ReviewCredentials` 已经在用 Keychain 且是
`AfterFirstUnlockThisDeviceOnly`、同步队列带幂等 `op_id`、首次连接只认领本机匿名数据。
**这几个接缝的位置都是对的**，账号系统接进去不用返工，详见第七节。

## 二、架构：三个进程，各管各的

| 进程 | 在哪 | 管什么 | 认证 |
|---|---|---|---|
| `kanpan-gateway`（现有，Python） | 两台 VPS | 公开行情转发、WS 扇出 | **匿名，永远不带令牌** |
| `kanpan-api`（**新写，Rust**） | VPS | 账号、同步、复盘记录与判定 | Bearer，一套令牌 |
| `scorebook`（现有，Rust） | 你的 Mac | 截图检索、历史索引、vision、备份这些重算 | 不动 |

三条理由：

- **行情必须能在账号服务挂掉时照常看。** 冷启动进图不依赖登录，这条是硬的。所以行情连接不加鉴权、
  不带 user_id，网关一行都不改。
- **账号和复盘用同一个服务、同一套令牌、同一个库。** 拆成两个服务就是两套令牌、两次登录态、
  两处要同步的用户表，没有任何好处。复盘的服务端反正要新写，一起写。
- **不把 `scorebook` 整个搬上 VPS。** 它带着 pgvector、图像特征、vision 子进程、restic 备份，
  是单人 Mac 工具的形态，公网多用户服务不该长这样。但**判定逻辑不重写**：
  `scorebook-core` 是个干净的 crate（`domain/criteria.rs`、`statistics.rs`、`interval.rs`、`calendar.rs`，
  依赖只有 serde/chrono/uuid/bigdecimal），`kanpan-api` 直接把它当 path 依赖引进来复用。

`kanpan-api` 的技术选型跟着 `scorebook` 走，省得你维护两套习惯：Rust 2024 / axum / sqlx / PostgreSQL，
不上 pgvector（找相似那部分先不迁）。放在本仓库 `Backend/kanpan-api/`。

## 三、后端只做一件事：换台设备，还是原来那套图

你说后端是为了提升体验，那就把它的职责钉死成这一句：**用户在这台手机上把图调成什么样，
换一台还是什么样。** 它不是产品的地基，除了复盘判定，服务端不持有任何「权威」。

由此推出三条约束，后面所有设计都受它管：

- 不登录能用全部看图功能。登录只多了「跨设备」这件事。
- 同步失败、令牌过期、服务端下线，都不许打断用户，更不许拦住启动。后台重试就行，界面不用提。
- 不追求强一致。末次写入胜出加墓碑就够，不必为每个偏好字段在 SQL 里建模。

### 上云 · 图表与界面的那套设置

这是你点名的「K 线图表指标的大小布局」。照现在 `Prefs` 的字段逐项过了一遍：

| 组 | 具体字段 | 为什么值得上去 |
|---|---|---|
| 指标与副图布局 | `overlays` 主图叠加、`subs` 副图顺序、`subHeights` 三档高度、`subHeightOverrides` 拖分隔线拖出来的精确高度、`params` 每个指标的参数、`indicatorColors`、`hiddenOutputs`、`rsiUpper/rsiLower` | 调一套 MA/EMA/MACD 参数和副图高度是最费时间的事，也是换设备最烦的事 |
| 周期 | `quickIntervals` 常用周期行（最多 8 档，长按能增删） | 每个人常看的周期不一样，重排一遍很烦 |
| 外观 | `theme`、`ambientTheme`、`styleID` 蜡烛造型、`redUp` 涨跌配色、护眼/夜读档位与字号档位 | 配色和字号是调过一次就不想再调的东西 |
| 图表开关 | `priceMode` 价格轴、`candleKind` 蜡烛/平均K、`gridChoice`、`bodyChoice`、`lastLine`、`countdown`、`magnet`、`sinceChange`、`viewAnchor`、`priceBias`、`dataDisplay`、`crossPrice`、`compactValues`、`adaptiveIndicators`、`allowMainInversion/allowSubInversion`、`portraitHeight` 竖屏主图占比、`timeZone`、`changeBasis` | 十几个开关，逐个重调一遍相当于重新装一次 app |
| 画线偏好 | `DrawingPreferences`：`favorites` 常用工具、`magnet` 磁吸、`continuous` 连续画、`styles` 每种工具的默认颜色线宽虚实 | 已经是现成结构，顺手就带上去了 |
| 自选 | `SymbolPrefs`：`favorites`、`groups`、`groupForSymbol`、`pinned`、`selectedGroupID` | 换设备第一件事就是看自选 |
| 画线本身 | 按品种存，每品种上限 50 条 | 手画的，丢了不可再生。全部加起来也就几百 KB |

### 上云 · 复盘

| 数据 | 说明 |
|---|---|
| 正式记录（提交后的 `ReviewRecord`） | 含区间、规则、原话、把握、来源、提交时间 |
| 判定结果与历史版本 | **必须在服务端算**：客户端不能自己宣布自己判对了。行情订正要能产生新版本且留旧证据 |
| 反思正文与历次修订 | 长期资产，最不该丢 |
| 战绩统计口径 | 按冻结样本算，不是按客户端当前加载的那一页临时算 |
| 「找相似」里显式保存的案例 | 普通翻看不写，保存了才上去 |

### 上云 · 我补充的几样

前面都是「把本机的东西存一份」。下面这几样是**只有后端才做得到**的体验，客户端再怎么写也做不出来：

1. **到期与触价提醒（推送）。** 复盘记录到了期、目标价或失效价被触达，服务器算完直接推给你。
   app 没开着也能算——这是后端唯一能做而客户端做不到的事，也是复盘这个功能真正活起来的关键。
   顺带可以做普通的**价格提醒**（给某个品种设一条线，到了就推）。要接 APNs。
2. **误删找回。** 画线和自选的删除是墓碑不是真删，服务端保留 30 天。用户手滑删掉一整个品种的画线时，
   这一条能救命。界面上不用做成「回收站」，做成一句「恢复上一次删除」就够。
3. **一键导出。** 把自己的全部记录和设置打包下载。既是体验，也是上架时「用户能带走自己的数据」的合规项。
4. **登录设备列表。** 能看到哪几台设备登着、能把某一台踢下线。这属于账号最基本的安全体验。

### 不上云

| 数据 | 为什么 |
|---|---|
| K 线快照、exchangeInfo、持仓量归档（`Library/Caches/kanpan`） | 公开行情，不是私人数据。谁登录都拉到一样的东西，上传只是流量翻倍 |
| `interval` 当前周期、上次视野、十字线位置、滚动位置 | 换台设备接着看的应该是你的自选，不是你的滚动位置 |
| `recents` 最近打开 | 设备局部状态，同步过去反而乱 |
| `apiHost` / `streamHost` / `smartMarketRoute` | 每台设备的网络环境不一样。把一台设备上改过的域名同步到另一台，可能直接让那台连不上 |
| `launchSnapshot` 启动快照开关、`keepAwake` 不锁屏 | 跟本机缓存和本机电量有关，属于这台设备的事 |
| 复盘草稿、回放游标、待同步队列 | 过程状态。草稿一旦点了「记下」就成了记录，那时才上去 |

### 永远不存在

交易所账户、API 密钥、资金、助记词。看盘不索取，界面上没有地方填，库里没有这个字段。

### 所以服务端可以很小

上面全部加起来，一个重度用户大约 **1–3 MB**（画线和复盘正文占大头），增量同步每次几 KB。
不需要对象存储，Postgres 的 jsonb 直接装。同步侧的库表也简单：设置整份一个 jsonb 文档带字段级时间戳，
自选一张表，画线一张表（按 id + `updated_at` + `deleted_at`），复盘按现有的记录表走。
**不要为了「以后可能要」把每个偏好字段拆成列**——偏好字段每个版本都在变，拆了就等着写迁移。

## 四、端上：私人数据按账号分开存

一台设备上可以有多个「槽位」，同时只有一个是当前的：

```
Application Support/kanpan/
  current                     ← 当前槽位名
  accounts/
    local/                    ← 匿名槽位，装 app 就有
      prefs.json  draws.json  favorites.json  review/  outbox.json
    u-<user_id>/              ← 登录后的槽位
      同上
Library/Caches/kanpan/        ← 行情缓存，不分槽位、不上传、不备份
```

要点：

- 现在设置存在 `UserDefaults`（键 `kanpan.prefs.v<n>`）、画线存在 `kanpan/draws.json`、
  复盘存在 `kanpan-review/<sha256>/`——**三个位置各走各的**。统一收进槽位目录，首次启动做一次性迁移
  （先复制、校验、再删原件）。
- **切槽位后所有内存状态重建**：`PrefsStore`、`DrawStore`、自选、`ReviewFeature` 全部按新目录重新构造。
  上一个账号的 `@Observable` 对象一个都不许留着用，否则会串号。
- 退出登录切回 `local/`，**不删** `u-<user_id>/`。同账号下次登录不用重拉一遍。
- 令牌只进 Keychain（`AfterFirstUnlockThisDeviceOnly`，不进 iCloud 钥匙串、不进备份），
  access token 只活在内存。日志里出现令牌算事故。

## 五、自动合并：不给面板，所以规则必须先立对

按你说的，登录之后系统直接合，不展示合了什么，用户全程无感。代价是合并规则一点都不能含糊——
出错了用户不会来报 bug，只会发现画线少了然后卸载。三条底线：

**底线一：「本机没有」永远不等于「删除了」。**
删除必须是一条带时间戳的墓碑记录。新装的手机本机什么都没有，如果把「没有」当成「删了」，
一登录就把云端清空了。

**底线二：从没改过的字段不参与竞争。**
设置逐字段带 `updated_at`，用户没动过的字段没有时间戳，合并时直接让位给云端。
否则新设备的一套默认值会把你调了半天的配色刷掉。

**底线三：合并前服务端留快照。**
覆盖式写入之前存一份 30 天可回滚的快照。用户不需要知道它存在，但出事时能捞回来。

逐类规则：

| 数据 | 怎么合 |
|---|---|
| 自选 | 并集 + 墓碑。加入和移出各带时间戳，同一品种取时间新的那个动作 |
| 分组 / 置顶 / 排序 | 整段按 `updated_at` 取新的。顺序是一个整体，逐项合会排出谁也没要过的顺序 |
| 画线 | 逐条。每条带 `id`、`updated_at`、`deleted_at`，同 id 取新的。每品种 50 条上限在**合并之后**按时间裁 |
| 设置 | 逐字段，见底线二 |
| 复盘 | 只增事件流，服务端权威。客户端从不修改判定结果 |

**匿名数据只认领一次。** 本机 `local/` 槽位在第一次登录任意账号时，整体作为「新增」并入该账号，
之后打上 `claimed_by`。同一台设备换第二个账号登录，不会把上一个账号的东西合进去——
Codex 现在写的 `ReviewFeature.connect` 里已经是这个逻辑（`if connection == nil`），保持一致。

## 六、账号本身：最小可用集

### 界面（按你说的砍掉文字）

- **登录**：邮箱、密码、一个主按钮，下面一行「忘记密码」。没有副标题、没有安全说明、没有脚注。
  出错就在密码框下面一行红字，连错几次那行字变成倒计时。
- **注册**：邮箱、密码、一个主按钮。密码规则**不合格时才出现**一行提示，合格时什么都不显示。
- **找回密码**：一屏填邮箱 → 一屏填收到的 6 位码和新密码。两屏，没有第三屏。
- **账号页**：邮箱、同步状态一行、退出登录、注销账号。
- 登录不是门槛：不登录的人在设置里只看到一行「登录」，其余界面完全不受影响。

### 服务端要做对的

- 密码 **Argon2id + pepper**，pepper 放机器上的 secret 文件不进库。
- 令牌用**不透明随机串**，不用 JWT——因为「改密码要立刻踢掉所有设备」JWT 做不到即时吊销。
  access 15 分钟，refresh 90 天且一次性轮换；同一个 refresh 被用第二次即判定为泄露，整串会话作废。
  现有的 `api_keys` 表形态正好可以演进成会话表。
- **登录失败恒定回同一句话**，不区分「邮箱不存在」和「密码错」；邮箱不存在时也跑一次假哈希再返回，
  否则响应快慢就把「这个邮箱有没有注册」告诉对方了。按邮箱和 IP 双计数退避。
- **注册和找回密码恒定返回同一个 202**，不论邮箱是否已注册。已注册的人收到的信内容不同
  （「你已经有账号了，忘了密码点这里」），但接口看不出区别。
- 验证码 6 位、10 分钟、最多试 5 次、存哈希不存明文。
- 库里沿用现有的 `owner_id` 隔离习惯，并给同步相关的表加 **Row Level Security**：
  `user_id` 只从会话解析，接口永不接受 `user_id` 参数。这样哪天漏写一个 `WHERE user_id` 也不会漏数据。
- **不做端到端加密**，也不要在隐私政策里假装做了：复盘判定要在服务器上算，服务器必须看得见目标价和
  失效价。实际做的是磁盘加密、备份加密、日志不落业务正文、注销真删。

## 七、和 Codex 这一轮的接缝

不要让 Codex 现在改任何东西，复盘先按他手上的做完。账号落地时接这三处，改动都很小：

1. **`ReviewFeature(directory:)`** —— 现在传的是 `kanpan-review/`，内部再按
   `sha256(baseURL|account)` 分命名空间。账号落地后直接传槽位目录 `accounts/<slot>/review/`，
   那层 hash 命名空间删掉。注入点已经是对的，只换传进去的路径。
2. **`ReviewConnectionView`（手填服务地址 + 访问凭证）整屏删掉。** 地址由 app 内置，
   令牌从登录来。用户不该知道「服务地址」这种东西。
3. **`ReviewCredentials`（Keychain，service `kanpan.scorebook`）** 并进账号的 TokenBox，
   统一成一个 service 名，一个槽位一份。

另外提醒一句：`ScorebookClient` 请求的 `v1/native-review/*` 在后端**还不存在**，这套接口要在
`kanpan-api` 里实现。等于说复盘的服务端和账号的服务端是同一件工程，排期上要放在一起看。

## 八、要你拍板的四件事

1. **发信通道。** 找回密码必须能发邮件，这是唯一绕不开的外部依赖。自建 SMTP 到 Gmail/QQ 基本进垃圾箱，
   建议用 Resend 或 SES 这类服务商（免费额度够用），需要一个域名做发信域并配 SPF/DKIM。
   你有现成的域名吗，还是要我把这块也列进采购清单。
2. **数据库放哪台。** 两台 VPS 现在只跑行情转发。Postgres 是要和 `kanpan-api` 同机，
   还是单独开一台？同机最省事，但备份和扩容要提前想好。另外备份方案要定（现在 scorebook 用的是 restic）。
3. **要不要做推送。** 第三节里补的「到期与触价提醒」是后端唯一能做而客户端做不到的体验，
   但它要接 APNs、要申请推送证书、要服务器常驻盯价，工作量不小。可以放到阶段 8 单独做，
   也可以干脆先不做——你定。
4. **上架时机。** 只做邮箱密码就不触发 App Store 那条「接了第三方登录必须同时给 Sign in with Apple」；
   但只要有账号体系，就必须在 app 内提供注销入口。如果近期要上架，注销流程要一起做，不能留到下一版。

## 九、做的顺序

| 阶段 | 内容 | 做完的标志 |
|---|---|---|
| 1 | `kanpan-api` 骨架：Rust 服务、库表、RLS、部署到 VPS、健康检查 | 用 B 用户的连接查 A 用户的数据，查出 0 行 |
| 2 | 注册 / 登录 / 刷新 / 登出 + 限速 + 恒定响应 | 已注册与未注册邮箱的响应体和耗时分不出来 |
| 3 | 找回密码 / 改密码 / 踢设备 | 改密码后旧令牌立刻失效 |
| 4 | 端上槽位目录 + 三处数据迁移 + Keychain | 老版本升级上来，设置和画线一条不少 |
| 5 | 登录注册那几屏 UI | 逐屏对照，含离线态和错误态 |
| 6 | 同步引擎 + 自动合并 | 两台设备互改，结果符合第五节的表；断网改十处再联网，补传无重复 |
