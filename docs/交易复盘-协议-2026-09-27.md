## 0. 分工与边界

| 事 | 谁做 | 为什么 |
| --- | --- | --- |
| 拉成交、拉资金费、拼回合 | **手机** | Key 只存本机 Keychain（`deviceOnly`），从头到尾不离开手机；定稿时 VPS 在美国，币安对美区 IP 的账户端点回 **451**，服务端既不能也不需要碰用户账户接口（2026-10-02 服务端迁到新加坡后 451 这条理由不再成立，但「Key 不离开手机、服务端不碰账户接口」的设计不变） |
| 存回合、随账号同步、RLS | 服务端 | 走现有 `review_records` 存储，换手机后交易复盘记录随复盘同步回来（Key 要重贴） |
| 持仓期间最大浮盈 / 浮亏、盈亏比；平仓后 1h / 4h / 24h；自动截图的周期与时间窗 | 服务端 | 要 1m K 线，服务端已能取行情（`review_market.rs` 经 `binance_gate`） |
| 战绩（胜率、分组）、「上周」周报卡 | 客户端 | 全是算术，服务端不另存聚合 |

客户端上传给服务端的**只有回合本身**（成交明细是回合的一部分）。API Key、Secret、Key 尾号、水位
一律不上传。

## 1. 通用约定

- **数字一律是十进制字符串**（照币安的做法）：`"0.0012"`、`"-35.5"`、`"0"`。
  - 只有 `.` 一个小数点，可带前导 `-`；不用科学计数法、不带千分位、不带 `+`。
  - 客户端输出去掉尾随 0（`"1.50"` 写成 `"1.5"`，零写 `"0"`）；服务端解析时不要依赖这一点（按 decimal 解，比如 `rust_decimal`）。
  - 价格、数量、金额保留到 8 位小数；比例（`…Pct`、`changePct`）是**比值**不是百分数（`"0.0123"` = 1.23%），保留 6 位小数；盈亏比 4 位小数。
  - 舍入一律「四舍六入五成双」（banker's，Foundation `NSDecimalRound(.bankers)` 与 `rust_decimal` 的 `round_dp` 一致）。
- **时间一律是整数毫秒**（Unix epoch，UTC），JSON number。时长也是毫秒（`…Ms`）。
- **金额单位**：`realizedPnl` / `commission` / `funding` / `netPnl` / 浮盈浮亏 都以回合的 `quoteAsset`（保证金资产，U 本位合约通常是 `USDT`，也可能是 `USDC`）计。
- 字段名 camelCase。可空字段**一律写出来**、值为 `null`，不省略键（两端都好对账）。
- 未知字段：服务端对 `round` 里的未知键**宽容**（存进 jsonb 原样保留），只校验下面列为「必填」的键——
  这一点与复盘草稿的 `deny_unknown_fields` 不同，因为回合是从交易所数据机械推出来的，客户端升级
  加字段时不能让老服务端整条拒收（2026-09-19 客户端同步白名单比服务端多十九个字段、整条拒收把队列
  堵死，就是这个坑）。版本不认识（`version` > 服务端支持的）才拒收。
- **服务端输出同样去掉尾随 0、零写 `"0"`**（服务端落地补充）：结果里的数都按上面的位数舍入后再去尾随 0，
  所以 `"0.018250"` 实际写成 `"0.01825"`。两端比对数字时按 decimal 比，不按字符串比。

## 2. 回合（TradeRound）

一个「回合」= 某品种某持仓方向的仓位从 0 建起，到回到 0（或反手穿过 0）为止。

### 2.1 字段

| 字段 | 类型 | 可空 | 说明 |
| --- | --- | --- | --- |
| `version` | int | 否 | 结构版本，现在是 `1` |
| `id` | string (UUID) | 否 | 幂等 id，算法见 2.2 |
| `venue` | string | 否 | 与多交易所模块 `InstrumentID.venue` 一致，第一期 `"binance"` |
| `market` | string | 否 | `InstrumentID.market`，第一期 U 本位合约 `"usd_m"` |
| `symbol` | string | 否 | 交易所代号，如 `"BTCUSDT"`；品种键 = `venue/market/symbol` |
| `accountTag` | string | 否 | 账户标识，第一期固定 `"primary"`（理由见 2.2） |
| `positionSide` | string | 否 | `"BOTH"`（单向持仓）/ `"LONG"` / `"SHORT"`（双向持仓），照交易所原样 |
| `direction` | string | 否 | `"long"` / `"short"`：这一回合开出来的仓位方向 |
| `status` | string | 否 | `"open"`（持仓中）/ `"closed"` |
| `quoteAsset` | string | 否 | 保证金资产（成交明细的 `marginAsset`），如 `"USDT"` |
| `openedAt` | int ms | 否 | 首笔开仓成交时间 |
| `closedAt` | int ms | 是 | 仓位回到 0（或穿 0）那笔成交的时间；持仓中为 `null` |
| `holdingMs` | int ms | 是 | `closedAt − openedAt`；持仓中为 `null` |
| `openAvgPrice` | decimal | 否 | 所有「加仓方向」成交（开、加）的数量加权均价 |
| `closeAvgPrice` | decimal | 是 | 所有「减仓方向」成交（减、平）的数量加权均价；还没减过为 `null` |
| `openedQty` | decimal | 否 | 加仓方向成交数量合计（正数） |
| `closedQty` | decimal | 否 | 减仓方向成交数量合计（正数）；平仓后等于 `openedQty` |
| `maxQty` | decimal | 否 | 回合内持仓数量绝对值的最大值 |
| `peakNotional` | decimal | 否 | 回合内 `|持仓量| × 当时持仓均价` 的最大值（名义峰值，按成本价，不按市价） |
| `leverage` | int | 是 | 取自 `positionRisk` 的当前杠杆；推不出（该品种当前没有持仓记录、历史回合）留 `null` |
| `realizedPnl` | decimal | 否 | 各成交 `realizedPnl` 之和（交易所算的，已含开平价差，不含费用） |
| `commission` | decimal | 否 | 手续费合计，**正数表示付出**，已折成 `quoteAsset`（BNB 抵扣的折算见 2.4） |
| `commissionByAsset` | object<string, decimal> | 否 | 按币种的手续费原值，如 `{"BNB":"0.0021","USDT":"0.4"}` |
| `commissionUnpriced` | bool | 否 | 有非 `quoteAsset` 的手续费折不出价（`commission` 里没算它）时为 `true` |
| `funding` | decimal | 否 | 分到这一回合的资金费合计，**正数是收入、负数是支出**（照交易所 income 的正负） |
| `netPnl` | decimal | 否 | `realizedPnl − commission + funding` |
| `fills` | array<Fill> | 否 | 这一回合的成交，按 `(time, id)` 升序 |
| `updatedAt` | int ms | 否 | 折进这一回合的最后一条事件（成交或资金费）的时间；服务端用它判断新旧 |

**Fill**（回合里的一笔成交）：

| 字段 | 类型 | 可空 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 否 | 交易所成交 id（币安 `userTrades.id`，数字转字符串） |
| `orderId` | string | 否 | 订单 id（数字转字符串） |
| `time` | int ms | 否 | 成交时间 |
| `side` | string | 否 | `"BUY"` / `"SELL"` |
| `positionSide` | string | 否 | 同回合 |
| `price` | decimal | 否 | 成交价 |
| `qty` | decimal | 否 | **计入这一回合的**成交数量（正数）；反手拆开的那一笔，这里只是属于本回合的那一部分 |
| `quoteQty` | decimal | 否 | `price × qty`（按拆分后的数量） |
| `commission` | decimal | 否 | 计入本回合的手续费原值（拆分时按数量比例） |
| `commissionAsset` | string | 否 | 手续费币种，如 `"USDT"`、`"BNB"` |
| `realizedPnl` | decimal | 否 | 计入本回合的已实现盈亏（拆分时全部归平仓那一半，开仓那一半为 `"0"`） |
| `maker` | bool | 否 | 是否挂单成交 |
| `role` | string | 否 | `"open"` / `"add"` / `"reduce"` / `"close"`：复盘图上标开 / 加 / 减 / 平用 |
| `split` | bool | 否 | 这一笔是不是反手时被拆开的（同一个 `id` 会分别出现在前后两个回合里） |

### 2.2 幂等 id

```
material = "trade-round-v1\n" + venue + "\n" + market + "\n" + accountTag + "\n"
         + symbol + "\n" + positionSide + "\n" + firstFillID
digest   = SHA-256(UTF-8(material))
b        = digest[0..16]
b[6]     = (b[6] & 0x0F) | 0x80      // 版本位 8（RFC 9562 UUIDv8）
b[8]     = (b[8] & 0x3F) | 0x80      // 变体位 10
id       = 小写 8-4-4-4-12 形式
```

`firstFillID` = 这一回合第一笔成交的 `Fill.id`（反手时就是被拆开的那一笔的 id）。

测试向量（两端的单测都要钉住）：

| venue | market | accountTag | symbol | positionSide | firstFillID | id |
| --- | --- | --- | --- | --- | --- | --- |
| binance | usd_m | primary | BTCUSDT | BOTH | 5012345678 | `2a54e776-a993-8446-b97e-ed7561670918` |
| binance | usd_m | primary | ETHUSDT | SHORT | 987654321 | `7482f6ac-d858-8f56-9479-152b2fd978e9` |

为什么做成 UUID：`review_records.id` 是 `uuid` 列，交易复盘和观点复盘放同一张表。为什么是哈希而不是
随机：同一个回合在两台手机上、或者重装后重新回溯 90 天，拼出来必须是同一条记录，不能长出两份。

为什么 `accountTag` 固定 `"primary"`：只读的四个端点都不返回账户 UID；拿 Key 派生会在用户换手机、
重建 Key（币安 Secret 只显示一次，换手机通常就是新建一把）时换掉，历史回合全部重复一份。第一期一个
看盘账号只接一个币安账户，所以一个常量就够。以后要支持同一交易所多个账户时，新账户用别的标签，
`"primary"` 那一份不动。

### 2.3 拼回合规则（客户端做，服务端不重算，写在这里给服务端理解数据）

- 按 `(symbol, positionSide)` 各自累计净持仓；**有符号变化量：`BUY` = +qty，`SELL` = −qty**，
  单向（`BOTH`）与双向（`LONG` / `SHORT`）都这么算——双向的空头仓就是负数。
- 净持仓从 0 离开 = 回合开始；回到 0 = 回合结束；一笔成交越过 0 = 反手：这笔拆成两半，平掉旧仓那一半
  结束旧回合（带走这笔全部 `realizedPnl`，手续费按数量比例分），剩下那一半开新回合。
- 同一笔成交拉到两次只算一次：去重键 `(symbol, id, side)`（自成交时同一个 id 会有买、卖两条）。
- 同一毫秒的多笔成交按 `id` 升序处理。
- **回溯窗口之前就开着的仓**：第一次回溯时，用 `positionRisk` 里的当前持仓量减去窗口内成交的变化量，
  得到窗口起点的持仓；起点不为 0 时，窗口开头那些成交先用来把它消化到 0（跨过 0 的那一笔，剩下的
  部分照常开新回合），这段残缺回合**不产出**——它的开仓价不在窗口里，产出来就是错的。
- **资金费**：每一条 `FUNDING_FEE` 按时间 `t` 分给同品种在 `t` 时刻开着的回合；同时开着多个（双向持仓
  两边都有仓）时按名义额（`|持仓量| × 持仓均价`）比例分。只有一个回合开着时是精确的，两边都开着时
  是近似（交易所的资金费流水不分多空两边）。流水的 `time` 就是结算时刻，按这个时刻找当时开着的回合；
  那个回合可能在拉到这条流水之前就已经结束（下一次增量才拉到）——最近 3 天内结束的回合都留在
  拼回合状态里，照样归过去，并重新产出一版（`updatedAt` 变大，服务端换版）。
- 持仓中的回合照样产出（`status = "open"`），后续每次拉到新成交、新资金费就产出新的一版，直到平仓。

### 2.4 手续费折算

`commissionAsset == quoteAsset` 的直接相加。别的币种（BNB 抵扣）按**拉取时** `positionRisk` 里
`<币种><quoteAsset>` 那只合约的标记价折算（例如 `BNBUSDT` 的 `markPrice`）——这样不用多调一个端点。
这是近似：用的是拉取时的价，不是成交时的价；BNB 手续费本身很小，误差在分位以下。折不出价的
（当前没有这只合约的标记价）不计进 `commission`，`commissionUnpriced = true`，原值仍在
`commissionByAsset` 里。

## 3. 复盘记录（`kind = "trade"`）

### 3.1 存储

同一张 `review_records`，`record` jsonb 形如：

```json
{
  "kind": "trade",
  "id": "2a54e776-a993-8446-b97e-ed7561670918",
  "revision": 3,
  "submitted": 1790000000000,
  "updated": 1790000300000,
  "voided": false,
  "round": { "…": "TradeRound，见第 2 节" },
  "result": { "…": "TradeResult，见第 4 节；持仓中或还没算出来为 null" },
  "note": { "text": "当时怎么想", "updatedAt": 1790000400000 }
}
```

| 字段 | 说明 |
| --- | --- |
| `kind` | 固定 `"trade"`。老的观点复盘记录没有这个键，视为 `"view"` |
| `id` | 等于 `round.id` |
| `revision` | 服务端每次改动 +1（回合换版、结果回写、改备注） |
| `submitted` | 服务端第一次收到这个回合的时间 |
| `updated` | 最后一次改动时间 |
| `voided` | 预留，第一期恒为 `false` |
| `round` | 客户端上传的最新一版回合 |
| `result` | 服务端算的结果，或 `null` |
| `note` | 用户补的「当时怎么想」，或 `null`（这是用户唯一能填的东西） |

列：`symbol` 写 `round.symbol`；`timeframe` 写 `result.chart.interval`（未算出前写空串）；
`range_start` / `range_end` 写 `result.chart.start` / `end`（未算出前写 `round.openedAt` /
`round.closedAt ?? round.updatedAt`）——「与观点复盘对上号」（规格 3.5，同品种、时间区间重叠）
直接按这三列查。`episode_id` / `group_pending` 对交易复盘不用（`NULL` / `false`）。

`id` 在库里一律存规范的小写形式：客户端传大写的同一个 UUID，服务端认作同一条并改成小写存（服务端落地补充）。

### 3.2 端点

老客户端的 `ReviewRecord` 必须有 `draft`，解不开交易复盘。所以：

- `GET /v1/native-review/records`（现有列表）**默认排除** `kind = "trade"`；新增查询参数
  `kind=trade` 只列交易复盘（其余过滤参数对交易复盘只认 `after`、`symbol`）。
  `/v1/native-review/statistics` 也排除交易复盘（交易侧战绩客户端自己算）。
- `GET /v1/native-review/records/{id}` 对交易复盘照常返回（新客户端才会拿交易复盘的 id 来查）。
- **上传** `POST /v1/native-review/trades`，头 `Idempotency-Key: <uuid>`，体
  `{"rounds": [TradeRound, …]}`，一次最多 100 个（首次回溯 90 天可能有几百个，分批传）。
  逐个 upsert：
  - 服务端按 2.2 重算 id，对不上的整批拒收 `invalid_round_id`。
  - 库里没有：新建，`revision = 1`。
  - 库里有、`round` 完全相同：不动。
  - 库里有、新的 `round.updatedAt >= 旧的`，且内容不同：换成新版，`revision + 1`；`status` 从
    `open` 变 `closed`、或已平仓回合的成交 / 资金费变了，都清空 `result` 并重新排结果任务。
  - 新的 `round.updatedAt < 旧的`：丢掉（晚到的旧版本）。
  - 回应 `{"records": [record, …]}`，与请求同序。
- **备注** `POST /v1/native-review/trades/{id}/note`，头 `Idempotency-Key`，体
  `{"expectedRevision": 3, "text": "…"}`；`text` 最长 2000 字，空串表示清掉（`note = null`）。
  版本对不上回 `409 record_revision_changed`（与观点复盘的 reflection 同一套乐观锁）。

**服务端落地补充**（2026-09-27）：

- 列表 `?kind=trade` 按 `round.closedAt` 倒序、持仓中（`closedAt = null`）排最前，同值按 `id` 倒序；
  一页 50 条，回 `{"records": [...], "next": <游标或 null>}`，游标只能喂回同一种列表。`kind` 取其他值回
  `400 invalid_filter`。交易复盘也不进 `todo=true`（「待判定」）与 `decided=true`。
- 观点复盘的 `…/reflection`、`…/void`、`…/group` 对交易复盘回 `400 invalid_change`。
- 上传体上限 6 MiB（100 个回合连成交明细，默认的 512 KiB 装不下）；一个回合的 `fills` 最多 10 000 笔。
- 上传的错误码：
  - `400 invalid_round`：任何一个必填键缺失、类型或取值不对（十进制字符串、整数毫秒、枚举、
    `status` 与 `closedAt` / `holdingMs` / `closeAvgPrice` 的一致性、成交时间不降且落在
    `[openedAt, closedAt ?? updatedAt]` 内、成交的 `positionSide` 与回合一致、时刻不晚于服务器时间 5 分钟以上）。
  - `400 unsupported_round_version`：`version` 比服务端认得的新。
  - `400 invalid_round_id`：按 2.2 重算对不上。
  - `400 too_many_rounds`：一次超过 100 个。
  - `409 record_identity_conflict`：这个 id 在库里已经是一条观点复盘（理论上撞不上）。
  - 以上任何一个都是**整批拒收**，一个都不落库。幂等键的 `idempotency_key_required` / `409 idempotency_mismatch` 与观点复盘相同。
- 同一个幂等键重放回的是这些回合**现在**在库里的样子（不是第一次的原样回应）。
- 「清空 `result` 并重排」的判据落地为：`status`、`direction`、`positionSide`、`openedAt`、`closedAt`、
  `closeAvgPrice`、`netPnl`、`funding`、`fills` 任一变化（上面三条的超集——平仓均价与净盈亏是结果的输入）。
  已平仓回合又变回持仓中时同样清空、并收掉结果任务。只改了别的键（例如 `leverage`）不清结果。
- 备注回 `{"record": record}`；超过 2000 字回 `400 invalid_note`；不是交易复盘或不是自己的回 `404`。
- **客户端怎么知道结果回写了**：看 `record.revision` / `record.result`，重新拉 `?kind=trade` 列表或详情即可。
  结果不另走 `/v1/sync` 同步日志——复盘记录本来就不是同步对象，另写一份会多一个真相源、还得凭空起一个集合名。

## 4. 结果（TradeResult，服务端算、回写到 `record.result`）

只有 `round.status == "closed"` 才算；持仓中 `result = null`。

```json
{
  "version": 1,
  "computedAt": 1790003600000,
  "excursion": {
    "maxFavorable": "182.5",
    "maxFavorablePct": "0.01825",
    "maxFavorableAt": 1790000120000,
    "maxAdverse": "-64.2",
    "maxAdversePct": "-0.00642",
    "maxAdverseAt": 1790000060000,
    "rewardRisk": "1.8349"
  },
  "after": {
    "h1":  { "at": 1790003600000, "price": "64210.5", "changePct": "0.00412" },
    "h4":  null,
    "h24": null
  },
  "chart": { "interval": "5m", "start": 1789996400000, "end": 1790006000000 },
  "unavailable": {}
}
```

（示例里的比值照第 1 节去掉了尾随 0：`"0.01825"`、`"-0.00642"`、`"0.00412"`。）

**`unavailable`**（服务端落地补充）：拿不到数据的那几部分各记一个原因码，键是 `"excursion"` / `"h1"` / `"h4"` / `"h24"`，
对应的值一定是 `null`；没有拿不到的就是 `{}`（键总在）。原因码：

| 码 | 意思 | 之后 |
| --- | --- | --- |
| `klines_missing` | 交易所没有这一段 K 线（下架、太早），该收盘的 K 线过了 1 小时还不全 | 终态，不再重试 |
| `market_region_blocked` | 服务端所在节点被行情源拒绝（451 那一类） | 每天重试一次，取到了就补上、原因码消失 |

还没到点的格子是 `null` 但**不**出现在 `unavailable` 里——客户端据此区分「还没到」与「拿不到」。
行情源暂时不通（超时、限流）不写结果，60 秒后重试。第一次写结果要等浮盈浮亏算出来（平仓那一根 1m K 线收盘 30 秒后）；
之后每补上一格 `revision + 1`，三格都有了（或成了终态）结果任务就收掉。

### 4.1 持仓期间 `excursion`

- 取 `[floor(openedAt, 1m), closedAt]` 内的 1m K 线（即开盘时间从 `floor(openedAt, 1m)` 到 `floor(closedAt, 1m)` 的每一根，含平仓那一根）。
- 持仓超过 30 天（43 200 根 1m）时改用 1h K 线，式子不变（服务端落地补充：1m 要取几百页，一次任务的租约里取不完）。
- 对每一根 K 线 `[T, T+60000)`，持仓状态 = 应用完所有 `time < T+60000` 的成交之后的
  （有符号数量 `q`、持仓均价 `avg`）；若这根 K 线里仓位已经归零（平仓那一根），改用这根 K 线里最后
  一个非零状态。
  - 多头（`q > 0`）：`fav = (high − avg) × |q|`，`adv = (low − avg) × |q|`；
  - 空头（`q < 0`）：`fav = (avg − low) × |q|`，`adv = (avg − high) × |q|`。
- 同时把每笔成交当成一个点，用成交价按上式算一次（1m K 线拿不到成交前后的先后顺序，这一步保证至少
  成交那一刻的值是准的）。这个点用的是**这笔成交之前**的持仓（服务端落地补充：平仓那一笔就是「以平仓价平掉整仓」那一刻；
  首笔开仓之前没有持仓，不算点）。
- 极值相同时取更早的那一刻。
- `maxFavorable` = 全部 `fav` 的最大值与 0 取大（≥ 0）；`maxAdverse` = 全部 `adv` 的最小值与 0 取小（≤ 0）。
  `…At` = 取到极值的那根 K 线的 `T`（或那笔成交的 `time`）；极值是 0 时为 `null`。
- `maxFavorablePct` / `maxAdversePct` = 取到极值那一刻的价格相对当时 `avg` 的变化（按方向取符号，
  多头 `(high − avg) / avg`、空头 `(avg − low) / avg`，浮亏一侧同理为负）；极值是 0 时为 `"0"`。
- `rewardRisk` = `round.netPnl ÷ |maxAdverse|`（可正可负）；`maxAdverse == 0` 时为 `null`。
- 这是 1m 粒度的近似（同一根 K 线里的高低点和成交谁先谁后不知道），界面不写「精确」字样。
- 取不到 K 线（交易所没有这只、时间太早）时 `excursion = null`，不要拿 0 顶。

### 4.2 离开后 `after`

- `h1` / `h4` / `h24` 的目标时刻 = `closedAt + 1h / 4h / 24h`。
- `price` = 收盘时间 ≤ 目标时刻的**最后一根已收盘 1m K 线的收盘价**（即 openTime =
  `floor(目标, 1m) − 60000` 那一根）。
- `changePct` = `(price − round.closeAvgPrice) / round.closeAvgPrice`，比值，只看价格、不按方向翻号——
  界面只给数字和一句事实（「平仓后 4 小时再涨 2.1%」），不打分、不评价。
- 目标时刻还没到（或那根 K 线还没收）时该格为 `null`，到点再补、`revision + 1`（服务端在目标时刻后 30 秒去取，
  按到期时刻排进现有的 `review_jobs`，`kind = "trade_result"`）。
  `h24` 走现有到期机制补，**不进「待判定」角标**。
- `at` = 目标时刻。

### 4.3 自动截图 `chart`

周期按持仓时长挑（`ReviewChartInterval.forHolding`，客户端 `KanpanCore/Trades/ReviewChartInterval.swift`
是同一张表）：

| `holdingMs` | `interval` |
| --- | --- |
| ≤ 4 小时（14 400 000） | `"5m"` |
| ≤ 2 天（172 800 000） | `"1h"` |
| ≤ 14 天（1 209 600 000） | `"4h"` |
| 其余 | `"1d"` |

边界含等号。`interval` 取值与客户端 `Interval` 的 rawValue 一致。

时间窗：`pad = max(10 × 周期毫秒, holdingMs / 4)`；
`start = floor(openedAt − pad, 周期)`；`end = min(ceil(closedAt + pad, 周期), floor(computedAt, 周期))`。
开 / 加 / 减 / 平的标记由客户端按 `round.fills[].role` 画在复盘图上，**主图一个点都不碰**。
