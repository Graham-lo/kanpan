# 提醒触发记录（提醒日志）协议 · 2026-10-05

提醒「触发即删」：响完之后同步对象（`alerts` 集合）与服务端物化表 `alert_watches` 那一行都会消失，
用户回头想看「哪几条响过、响在多少」无处可查。kanpan-api 从这一版起给每次触发追加一行流水，
iOS 顶栏铃 →「提醒」表的「日志」页读它（客户端 `Kanpan/Kanpan/Alerts/AlertLog.swift`）。

服务端代码：`Backend/kanpan-api/src/alert_log.rs`，迁移 `migrations/0043_alert_log.sql`，
集成测试 `tests/alert_log.rs`。

## 1. 什么时候记一行

两条写入路，都在这个人的同步咨询锁里、都只认「非 fired → fired」那一次转变，谁先到谁写：

| 路 | 在哪儿 | 覆盖 |
|---|---|---|
| 服务端判响 | `alerts::record_fired`，和把状态改成 fired、写同步日志同一个事务 | 币安 / Coinbase / 美元指数三支的价格与画线提醒、条件提醒、复盘到点 |
| 客户端判响 | `alerts::materialize`（`POST /v1/sync/operations` 里），同一个事务 | 前台 `AlertEngine` 本机判到、随同步推上来的 `status: "fired"` |

- 同一次触发只留一行：唯一约束 `(user_id, alert_id, fired_at)` + `ON CONFLICT DO NOTHING`。客户端重推同一次、
  评估器后到（库里已经是 fired，`record_fired` 返回 false）都不会多一行。
- 提醒随后被删（触发即删），记录**不受影响**。
- 客户端补报的 `firedAt` 早于 30 天前的不记（记了下一轮清理也会删，多半是旧设备补报的陈年状态）。
- 已知限制：若客户端离线时把「改成 fired」与「删除」在发件箱里折成一条删除推上来，服务端看不到那次转变，
  不会记（服务端替它发 Webhook 也依赖这次转变，口径一致）。

## 2. 表 `alert_log`（迁移 0043）

| 列 | 类型 | 说明 |
|---|---|---|
| `user_id` | uuid，FK `account_users(id) ON DELETE CASCADE` | 注销账号连带删除 |
| `id` | uuid 主键 | 每行新生成 |
| `alert_id` | text | 同步对象 id，如 `binance/usd_m/BTCUSDT/9F1E…` |
| `kind` | text | 照抄 `alert_watches.kind`：`price` / `drawing` / `condition` / `reviewDue`（画线提醒在线上就叫 `drawing`） |
| `symbol` | text | 完整品种键 `venue/market/SYMBOL`：`binance/usd_m/BTCUSDT`、`coinbase/spot/ETH-USD`、`macro/index/DXY` |
| `title` | text | 用户（客户端）起的标题，即 `alert_watches.title`；空的话按推送兜底标题补（「BTC 触到你画的线」「SOL 到点了」…） |
| `condition` | text | 人读条件，和推送 / Webhook 文案同一套措辞（见下） |
| `fired_at` | bigint | 触发时刻，毫秒 |
| `fired_price` | double precision，可空 | 触发价；复盘到点没有价，为 null（不拿 0 冒充） |
| `created_at` | timestamptz | 写入时刻 |

索引 `(user_id, fired_at DESC)`；`ENABLE` + `FORCE ROW LEVEL SECURITY`，策略 `personal_owner`
（`user_id = current_setting('kanpan.user_id')`，USING 与 WITH CHECK 同一条），和 `alert_watches` 一样。

`condition` 的写法：

- 价格 / 画线：`{条件词} {目标价}`，条件词是「价格达到」（碰到）或「收盘穿过」，目标价按 Webhook 的金额格式
  （千分位、去尾零）：`价格达到 86,000`、`收盘穿过 3,000.5`；斜线取触发那一刻离触发价最近那条线上的价。
- 条件提醒：条件本体的那一句（`conditions::Rule::phrase`），如「资金费率高于 0.05%」；认不得的条件写「条件提醒」。
- 复盘到点：`复盘到点`。

## 3. 保留

30 天。`maintenance::cleanup`（worker 每小时一轮）逐人按批删 `fired_at` 早于 30 天前的行。

## 4. 接口

两条都要登录（`Authorization: Bearer <token>`），没登录 401。外层照全站惯例包 `{"data": …}`；
客户端两种形状都认。

### `GET /v1/alerts/log?symbol=&since=&limit=`

| 参数 | 说明 |
|---|---|
| `symbol` | 可选。完整键（`macro/index/DXY`）原样比；裸代号（`BTCUSDT`）按 `binance/usd_m` 补全。只收字母数字与 `/ - _ .`、≤ 80 字节，否则 400 `invalid_symbol` |
| `since` | 可选，毫秒；只回 `firedAt >= since` 的 |
| `limit` | 可选，缺省 200，夹到 1…500 |

按 `firedAt` 从新到旧（同一毫秒再按 `id`）。回：

```json
{"data":{"records":[
  {"id":"5d6c…","alertId":"binance/usd_m/BTCUSDT/9F1E","kind":"price","symbol":"binance/usd_m/BTCUSDT",
   "title":"BTC 价格达到 86,000","condition":"价格达到 86,000","firedAt":1791234567890,"firedPrice":86010.5}
]}}
```

字段名与大小写固定为这八个：`id`、`alertId`、`kind`、`symbol`、`title`、`condition`、`firedAt`、`firedPrice`。

### `DELETE /v1/alerts/log?symbol=`

清空这个人的记录；带 `symbol` 只清那一只（同上的补全规则）。成功 `204 No Content`，无响应体。
