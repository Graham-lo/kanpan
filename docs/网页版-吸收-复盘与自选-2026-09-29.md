# 网页版吸收 · 复盘与自选（2026-09-29）

这一轮五件事：找相似 1h / 4h 从服务端补根、复盘 KPI 四项、自选小部件、板块「跑赢大盘」空白、手机副图名额与网页对齐。

## 1. 找相似 1h / 4h：服务端补索引

### 根因

找相似的流程是：查询片段 → `candle-geometry-v2` 192 维描述子 → 在 `market_features` 里精确取最近的 300 个候选 → 逐个去币安取 K 线做 DTW 重排 → 分数 ≥ 门槛 → 同品种时间重叠去重。

候选只能从 `market_features` 里来，而这张表是 2026-09-23 用一次性脚本 `import_public_history` 灌的，此后没人维护：

| 周期 | 窗口数 | 品种 | 最后一个窗口（上海时间） | 窗口长度 | 步长 |
|---|---|---|---|---|---|
| 15m | 62,537 | 30 | 09-23 17:45 | 64 根 | 16 根 |
| 1h | 18,229 | 30 | 09-23 17:00 | 64 根 | 16 根 |
| 4h | 3,799 | 30 | 09-23 00:00 | 64 根 | 16 根 |
| 1d | 541 | 29 | 09-19 | 64 根 | 16 根 |

（另有 okx 1h 2,677 条，找相似按 `source=venue` 过滤，不参与币安检索。）

同样是一年历史、同样 16 根一个窗口，1h 的窗口数只有 15m 的四分之一，4h 只有十六分之一；而且只有 64 根一种长度，用户拿 32 根去找就只能跟 64 根的形状比。候选池太小、太稀，DTW 重排后几乎没有一段过 0.60——上线前最近的 1h 检索全部 0 条，4h 几乎全部 0 条。

### 离线实验（照线上算法在本机复刻，币安前 50 只，一年 K 线）

| 场景 | 现状（只有 64 根、步长 16、门槛 0.60） | 32/48/64 根、1h 步长 4 / 4h 步长 2、门槛 0.60 | 同左、门槛按周期分 |
|---|---|---|---|
| BTC 1h×32 最新 | 0 | 5 | 11 |
| BTC 4h×32 最新 | 0 | 1 | 2 |
| BTC 4h×32 历史随机 8 段平均 | 0–1 | 10.6 | 23.6 |
| ETH 4h×32 历史随机 8 段平均 | 0–1 | 13.4 | 31 |

分数档看过图（`docs/acceptance/网页版-2026-09-29/找相似-BTC4h32根-分数档.png`、`找相似-BTC1h64根-分数档.png`，第一格是查询）：1h 到 0.58、4h 到 0.56 时形状仍然一眼看得出是一类；再往下（0.52 左右）开始混进走势方向相反的段，所以门槛停在这里。

### 改了什么（`Backend/kanpan-api`）

- **新模块 `src/market_index.rs`**，worker 里常驻一个 `market-index` 循环（`src/main.rs`），滚动维护 `market_features`：
  - 品种：币安 U 本位 USDT 永续里正在交易的加密币（`underlyingType=COIN`），按 24h 成交额取前 40，每 6 小时重排一次。
  - 窗口：1h 取 32 / 48 / 64 根、步长 4；4h 取 32 / 48 / 64 根、步长 2；1d 取 32 / 64 根、步长 1；15m 32 / 64 根、步长 16（原来只有 64 根）。窗口按绝对根号对齐步长、遇到缺口就断开，所以哪天重跑切出来的窗口都一样、`ON CONFLICT DO NOTHING` 不会重复。
  - 深度：一年（与 15m 一致），每小时删掉 366 天以前的窗口。
  - 顺序：先补各品种最新一段（滚动），再从近到远回填。
- **币安权重**：这台 VPS 整个出口平时每分钟就用到 750 上下（订单流深度快照占大头，另有同 IP 的网关等服务）。索引守三道闸，**手机行情转发与有人在等的检索永远优先**：
  - 读共享账本 `provider_budgets`：本分钟已用 + 这一页 ≤ 上限（1200）的 50% 才出站；进程级 418 / 429 闸门关着时不出站。
  - 自己每分钟最多 120 权重（24 页）。
  - 找相似 worker 90 秒内认领过检索，索引整个让开。
  - 挡住了就睡到下一分钟开头（账本按自然分钟清零）接着做，不重数库。
- **门槛按周期分**（`search::min_score`）：15m 0.60、1h 0.58、4h / 1d 0.56。只在候选池天然更小的周期放宽。
- **写库每条 40 行**：表上有 HNSW 向量索引，200 行一条要 1.2–1.8 秒、次次触发 sqlx 慢语句告警刷日志。
- `import_public_history` 改用同一套切窗与写库函数，单测搬到 `market_index`。

- **第二次**（`61a386bc` + `9569b998`，22:31）：出站改成上面的三道闸，挡住就睡到下一分钟开头；写库每条 40 行。1h 与 1d 从这时起稳定增长。回滚备份在 VPS `/opt/kanpan-backups/market-index-20260929-222630/`，里面有二进制、源码和 `market_features` 转储。
- **第三次**（`ef2a98fb`，22:50）：第二次之后 1h 和 1d 在长，**4h 和 15m 却一行没长**。原因出在排活：「滚动」原来只认每只每个周期最新那一段。
  - 4h 一段约 155 天，而 09-29 08:00 刚跨进新的一段，这一段里只有 31 根，凑不出一个 32 根的整窗口，所以一件滚动的活也没有。
  - 最近的 4h 窗口全都起在上一段里，被当成回填；回填又是按周期排的，要等 1h 的全年回填做完才轮到。
  - 15m 同理：一段约 9.7 天，也在 09-29 08:00 刚跨段。
  - 改法是「滚动」按最近那个整窗口的起点所在段算，刚跨段时把上一段也算进滚动。回填改成按「离现在第几段」由近到远，同一深度里 1h、4h、1d、15m 轮着做。补了单测 `just_after_a_chunk_boundary_the_previous_chunk_rolls`。
  - 回滚备份在 `/opt/kanpan-backups/market-index-20260929-224451/`。

每次部署都是同一个流程：
1. 从 origin/main 打包 `Backend/kanpan-api`；
2. 备份；
3. 确认 VPS 上没有别的 cargo 在编译，再 `flock nice cargo build --release`；

## 2. 复盘 KPI（P2-8）

KPI 全部在前端算（`Web/src/review/model.ts` 的 `roundStats` / `sideStats`），服务端不动。只统计已平仓的回合，顺序按平仓时刻。

- **盈利因子** = 总盈利 ÷ |总亏损|。没有亏损的回合时写「—」，不写 ∞；下面的小字给出总盈利和总亏损。
- **最大回撤**：把每回合的净盈亏按平仓先后累加，得到一条已实现资金曲线（从 0 起）。取峰到谷跌得最多的那一段，同时给金额和「占峰值 x%」，再加上从哪天起跌。
  - 峰值 ≤ 0 时（一开始就在亏）没有可比的本钱，百分比不写。
  - 百分比可以超过 100%，意思是把之前赚的全吐回去还倒亏。
  - 没有回撤时写「0.00 · 没有回撤」。
- **最大单笔**：盈利最多的那一回合占净盈亏的比例。占比 ≥ 50%、净盈亏为正、而且至少有两个已平回合时，小字换成红色的「这段时间的盈利主要来自 1 笔」。
- **做多 / 做空**：分别给净盈亏、回合数和胜率。战绩表里也加了「按方向」一段。

单测在 `Web/tests/review-model.test.ts`（8 条），覆盖这些情况：没有亏损（包括没有回合）、峰值 ≤ 0、回撤超过 100%、只有一回合时不提示、净盈亏 ≤ 0 时没有占比、多空各自统计。回归脚本的 review 段用 5 个回合的样本逐格核对：净盈亏 +600、盈利因子 2.20、最大回撤 −400 且占峰值 44.4%、最大单笔 100% 并出提示、做多 +800、做空 −200；另有一组没有亏损的样本核对「—」与「没有回撤」。

## 4. 板块 DeSci「跑赢大盘」空着

**根因**：板块目录 `Web/src/data/sectors.json` 里 DeSci 只有 BIO 一个成员，有行情的成员数是 1。

网页版和手机端（`SectorBoardOrder` / `SectorSubtitle`）规则一致：不到三家的板块算「薄板块」，整组沉底，也不算广度（跑赢大盘的占比）。所以 DeSci 涨得再多也排在最后，而且广度那一格是空的。

排序和计数本身都对，问题出在呈现：空格子看起来像数据还没到。

**改法**：
- 薄板块的「跑赢大盘」写「—」，悬停说明「只有 N 只有行情，不到 3 只不算跑赢大盘，排在最后」。
- 判定统一走 `isThin`，不再在页面里写死 3。

单测：`Web/tests/sectors.test.ts` 里加了 DeSci 的例子。截图：`板块-不到三家写横杠.png`。

## 5. 手机副图：成交量不占名额（与网页对齐）

原来手机把成交量算进「最多三个」。读档时的 `prefix(3)` 会把网页推上来的「成交量 + 三个副图」里最后一个副图丢掉，两端开着的副图对不上。

现在两端口径一致：**成交量 + 最多三个别的副图**。
- 截断统一走 `Prefs.cappedSubs`：成交量留在原位，别的副图按顺序留前三个。读档（`PrefsCodec`）和编码前的 `IndicatorLayout.sanitized` 用的是同一把尺子。
- 开满后再开一个，只在非成交量的副图里换下最早的那个；开成交量不会挤掉别的副图。
- 服务端 `sync_validation` 的 subs 上限是副图词表长度（12），不用改。
- 指标面板标题写「副图 · 最多三个 · 成交量不占」。
- 只改了逻辑和单测；手机上成交量仍是单独一格副图（网页版叠在主图底部），画法没动。
