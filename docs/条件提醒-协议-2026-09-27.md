# 条件提醒 · 客户端与服务端协议（2026-09-27）

> 规格出处：`docs/方案-我的-自动复盘-周期分组指标-2026-09-27.md` 第 5 节（第四阶段）。
> 创建提醒页的「条件」从两种（价格达到 / 收盘穿过）扩成四种新条件：**费率、持仓量、均线、大单**；
> 第五种「品种状态」不建提醒，是设置 › 通知里一个开关。仓位类提醒（离强平 X%）不做。
>
> 这份文档是**两端对账的唯一口径**：客户端按它写 `alerts` 同步对象与设置字段，服务端
> `Backend/kanpan-api` 按它校验、物化、判定、推送、回写。任何一边改字段，同一次改动里先改这里。
>
> 仍然是那条老规矩：**提醒只响一次，响完就算完**（`kanpan-alerts-fire-once-no-repeat`），
> 没有「每次 / 重复」频率选项；触发后客户端照旧把它当已触发处理（页里不再列出）。

## 0. 分工与边界

| 事 | 谁做 | 为什么 |
| --- | --- | --- |
| 建 / 改 / 删条件提醒，写 `rule` | 客户端 | 走现有 `alerts` 同步集合，和价格提醒同一条路 |
| 判定四种条件 | **只有服务端** | 要预测费率、持仓量历史、整根 K 线、三家聚合的盘口——手机锁屏后都拿不到；客户端**不在本机判这四种**，也不自己把它们置 fired |
| 触发：置 fired + 写同步 op、推送、Webhook | 服务端 | 同一个事务置 fired 并写同步日志，然后才推送 / 发 Webhook（和价格提醒同一条路 `alerts::record_fired`） |
| 品种状态（上新 / 停牌 / 下架） | 服务端 | 读用户同步上来的自选与设置开关；每个变化每人只推一次 |

所以条件提醒**要登录才有**（它的判定在后端，属于 `kanpan-sync-is-not-a-login-gate` 里说的「权限验证」那一类）；
没登录时客户端不给这四种条件的入口。

## 1. 同步对象的形状

仍然是 `alerts` 集合、仍然是那一个对象 id 形态 `<market>/<symbol>/<alertID>`（`binance/usd_m/BTCUSDT/9F1E…`）。
新加 **一种 kind、一个键**：

| 键 | 类型 | 可空 | 说明 |
| --- | --- | --- | --- |
| `kind` | string | 否 | 新值 **`"condition"`**（原有 `drawing` / `price` / `reviewDue` 不变） |
| `rule` | object | 是 | **新键**。条件提醒必填，形状见第 2 节；别的 kind 不写或写 `null` |

其余键照旧，条件提醒上的取值约定如下（客户端永远写出可空键，值为 `null`）：

| 键 | 条件提醒上的值 |
| --- | --- |
| `symbol` / `market` | 品种；**`market` 只能是 `"binance/usd_m"`**（四种条件的数据都来自币安 U 本位；Coinbase 品种上不给条件入口，服务端拒收） |
| `condition` | 固定写 `"touch"`（不参与判定；见第 5 节为什么不把条件塞进这个键） |
| `lines` | 固定写 `[]` |
| `drawingID` / `dueAt` / `reviewID` | `null` |
| `armedAt` | 武装时刻（毫秒）。**只有武装之后的观测才算数**，各条件怎么算「之后」见第 2 节 |
| `once` | `true` |
| `status` | `"active"` / `"paused"` / `"fired"`；暂停的不判 |
| `title` | 客户端生成的中文短句，推送标题用它；空串时服务端按第 3 节的默认标题补 |
| `note` / `webhook` / `webhookText` | 与价格提醒相同（备注进推送正文与 Webhook；Webhook 只填地址，文案用默认） |
| `firedAt` / `firedPrice` | **服务端写**：触发时刻、触发时的价（各条件的「价」是什么见第 2 节） |

一条完整的费率提醒：

```json
{
  "kind": "condition", "symbol": "BTCUSDT", "market": "binance/usd_m",
  "rule": {"type": "funding", "side": "above", "rate": "0.0005"},
  "condition": "touch", "lines": [], "drawingID": null, "dueAt": null, "reviewID": null,
  "armedAt": 1790517600000, "created": 1790517600000, "once": true, "status": "active",
  "firedAt": null, "firedPrice": null,
  "title": "BTC 资金费率高于 0.05%", "note": null, "webhook": null, "webhookText": null
}
```

### 1.1 通用约定

- `rule` 里的**比例与金额一律是十进制字符串**（照 `docs/交易复盘-协议-2026-09-27.md` 第 1 节：只有 `.`、可带前导 `-`、
  不用科学计数法、不带千分位、不带 `+`）；服务端按 decimal 解（`rust_decimal`），不经过浮点比较阈值。
- **比例是比值不是百分数**：`"0.0005"` = 0.05%，`"0.05"` = 5%。
- 整数（`length`）是 JSON number。
- `rule` 序列化后 ≤ 1024 字节。
- `rule.type` 未知（将来的新条件）：服务端**收下、存着、不判**（打一行 warn），不整条拒收——客户端总是跑在已部署服务端的前面，
  整条拒收会把那台手机的同步队列堵死（2026-09-19 白名单的坑）。已知 `type` 的字段一律严格校验。
- 已知 `type` 的 `rule` 里多出来的未知键忽略（不拒收、不使用）。

## 2. 四种条件

### 2.1 费率 `funding`

```json
{"type": "funding", "side": "above", "rate": "0.0005"}
```

| 字段 | 类型 | 取值 |
| --- | --- | --- |
| `side` | string | `"above"`（高于或等于）/ `"below"`（低于或等于） |
| `rate` | 十进制字符串 | 资金费率阈值，比值；`|rate| ≤ 0.1`（10%），可为负（`"-0.0001"` = -0.01%） |

- **判定时刻**：每一次结算前 15 分钟判**一次**。服务端每分钟拉一次币安 `premiumIndex`（全市场一次请求），
  对每条费率提醒：`now ∈ [nextFundingTime − 15 min, nextFundingTime)` 且这一次结算还没判过 → 判。
  所以实际判的时刻在结算前 15 分钟到 14 分钟之间。每个品种按它自己的 `nextFundingTime`，1h / 4h / 8h 结算周期都对。
- **拿什么判**：`lastFundingRate`（币安在结算前给的就是本期**预测**费率），`above`：`预测 ≥ rate`；`below`：`预测 ≤ rate`。
- **武装**：判定时刻 ≥ `armedAt` 的那一次起算。在窗口里（结算前 15 分钟以内）新建的提醒，下一分钟就判这一次结算。
- **只对永续有意义**：没有资金费的品种（交割合约）`premiumIndex` 里没有下一次结算，永远不会响——客户端只在永续上给这个条件。
- `firedPrice` = 判定时的**标记价格**（`markPrice`）。
- 服务端重启时如果正好落在窗口里，这一次结算可能被再判一次（判定是无状态的「此刻预测费率过没过线」，结果不会变坏）。

### 2.2 持仓量 `openInterestChange`

```json
{"type": "openInterestChange", "threshold": "0.05"}
```

| 字段 | 类型 | 取值 |
| --- | --- | --- |
| `threshold` | 十进制字符串 | 1 小时持仓量变化幅度阈值，比值，**绝对值**（涨或跌超过都算）；`0.001 ≤ threshold ≤ 10` |

- **判定时刻**：每 5 分钟一次（每个 5 分钟整点后约 1 分钟，等币安把那个 5 分钟点发出来）。
- **拿什么判**：币安 `futures/data/openInterestHist?period=5m&limit=13`（每个品种一次请求）。取最新一个点 `L`，
  和恰好 1 小时之前的那个点 `P`（`P.timestamp = L.timestamp − 3 600 000`）比：
  `change = (L.sumOpenInterest − P.sumOpenInterest) / P.sumOpenInterest`，`|change| ≥ threshold` 就响。
  用的是**币数量**（`sumOpenInterest`），不是美元价值——美元价值里混着价格涨跌，不是「持仓量变化」。
  缺 `P`（刚上线的品种、币安那一段没数据）这一轮不判。
- **武装**：只看 `L.timestamp ≥ armedAt` 的点。这是一个「状态」条件：建提醒时如果过去 1 小时已经变了这么多，
  武装后第一个 5 分钟点就会响——客户端建提醒时可以把当前 1 小时变化显示出来，让用户自己心里有数。
- `firedPrice` = `L.sumOpenInterestValue / L.sumOpenInterest`（那个点上的价）。

### 2.3 均线 `maCross`

```json
{"type": "maCross", "interval": "4h", "length": 20, "side": "above"}
```

| 字段 | 类型 | 取值 |
| --- | --- | --- |
| `interval` | string | 客户端周期代号之一：`1m 3m 5m 15m 30m 1h 2h 4h 6h 12h 1d 1w 1M`（不含客户端自己拼出来的 `1y`，币安没有这个周期） |
| `length` | int | MA 的 N，`1 ≤ length ≤ 1000` |
| `side` | string | `"above"`：收盘站上（上穿）；`"below"`：收盘跌破（下穿） |

- **MA 的算法**：收盘价的简单移动平均，**含这一根**：`MA_k = (C_{k−N+1} + … + C_k) / N`，和客户端
  `KanpanCore/Sources/KanpanCore/Indicator/Math.swift` 的 `sma` 一个口径（浮点）。数据来自币安 U 本位公开 K 线
  `fapi/v1/klines`，和图上画的是同一份。
- **判定时刻**：每根 K 线**收盘**时判一次（收盘后几秒内）。同一品种同一周期的所有提醒（不分用户）合并成一次 K 线请求。
- **判法**（边沿触发，只认真的收盘价，盘中来回穿不算）：设刚收盘的一根为 `k`、前一根为 `k−1`：
  - `above`：`C_{k−1} < MA_{k−1}` 且 `C_k ≥ MA_k`；
  - `below`：`C_{k−1} > MA_{k−1}` 且 `C_k ≤ MA_k`。
  需要 `N + 1` 根已收盘的 K 线；不够（新上线品种）这一根不判。
- **武装**：只判收盘时刻（`k` 的开盘时间 + 周期）晚于 `armedAt` 的那一根。服务端停机期间收掉的 K 线不补判。
- `firedPrice` = `C_k`（那一根的收盘价）。

### 2.4 大单 `orderflowWall`

```json
{"type": "orderflowWall", "threshold": "5000000"}
```

| 字段 | 类型 | 取值 |
| --- | --- | --- |
| `threshold` | 十进制字符串 | 大单墙的名义美元门槛；`10000 ≤ threshold ≤ 10000000000` |

- **默认值（客户端给）**：这只品种此刻生效的主力订单流门槛（用户改过的用用户的，没改过用默认表；合约那一档），客户端写进
  `threshold`；服务端不再替它推导。
- **数据**：服务端常驻跟踪的主力订单流（`orderflow_history`，币安 / OKX / Coinbase 三家、现货与合约各产品聚合，逐单模型）。
  品种 → 订单流 base：去掉计价后缀，再去掉币安的倍数前缀（`1000PEPEUSDT` → `PEPE`）。有条件提醒的 base 服务端会保证在跟
  （按需层，和手机打开这只品种时一样）。
- **判定时刻**：跟踪器每 0.5 秒评估一次簿，评估完回调一次条件判定（实时，不等写库）。
- **判法**：一面**还挂着**的墙（任一家、任一产品、买或卖）当前名义美元 `≥ threshold` 就响，但只认**新的墙**：
  - 首次出现时刻（`firstSeen`）在 `armedAt` 之后的，算新的；
  - `armedAt` 之前就在、但武装后第一次看到时还没到门槛、后来长过门槛的，也算新的；
  - 武装后第一次看到时就已经 ≥ 门槛的老墙不算（不因为建了提醒就立刻响一面早就在那儿的墙）。
  服务端重启会重新取一次「第一次看到」的基线，停机期间出现又消失的墙不补。
- **门槛下限**：服务端只按默认门槛跟踪大单，低于跟踪门槛的挂单根本不会成为「大单」，所以 `threshold` 低于这只品种的
  服务端跟踪门槛时，实际效果等同于跟踪门槛。
- `firedPrice` = 那面墙的价位，按提醒品种的报价口径（`1000PEPEUSDT` 上乘回 1000，和图上一致）。

## 3. 触发之后

和价格提醒完全同一条路：

1. **同一个事务**里把物化表 `alert_watches` 置 `fired`，并以服务端身份往这个人的同步日志写一条 op
   `{status:"fired", firedAt, firedPrice}`（`alerts::record_fired`）。已经不是 `active`（暂停、已触发、删了）的一行都改不到，
   不推、不发——「只响一次」靠的是这条 `WHERE status='active'`，不是内存标记。
2. 事务提交之后：有 Webhook 地址就发 Webhook（第 4 节），有 APNs 密钥就推送（没有密钥时只记一行日志，状态照常同步）。

**推送**（`kind` = `"alert"`，点开 `hkline://symbol/<SYMBOL>`）：

| 条件 | 默认标题（`title` 为空时） | 正文 |
| --- | --- | --- |
| 费率 | `BTC 资金费率高于 0.05%` / `低于` | `预测费率 0.0612% · 14 分钟后结算` |
| 持仓量 | `BTC 1 小时持仓量变化超过 5%` | `1 小时持仓量 +6.21% · 现价 84,671` |
| 均线 | `BTC 4h 收盘站上 MA20` / `跌破` | `收盘 84,671 · MA20 84,210.5` |
| 大单 | `BTC 出现 5M 以上的大单墙` | `币安 U 本位 买墙 12.4M @ 84,000` |

- 品种名用短名（`BTCUSDT` → `BTC`，同 `watch_move::short`）；金额用 K / M / B 单位；费率、变化幅度写百分数；价格千分位。
- 有备注就接在正文后面：`… · 备注`。
- 产品名：`spot` 现货、`usdtPerp` U 本位、`coinPerp` 币本位、`delivery` 交割；侧：买墙 / 卖墙；交易所：币安 / OKX / Coinbase。

## 4. Webhook

仍然是 `POST` 一份 JSON（`User-Agent: Hkline-Alerts/1`，8 秒超时、网络错误或 5xx 重试一次、不跟跳转、不发内网地址），
**键和价格提醒相同**，条件提醒上的取值：

| 键 | 值 |
| --- | --- |
| `event` | `"alert"` |
| `alertId` / `symbol` / `market` / `name` / `title` / `once` / `price` / `firedAt` / `time` / `note` | 同价格提醒（`price` = `firedPrice`） |
| `condition` | `rule.type`：`"funding"` / `"openInterestChange"` / `"maCross"` / `"orderflowWall"` |
| `target` | `null`（条件提醒没有目标价） |
| `text` | 按模板渲染的一句话；默认模板 **`{品种} {条件}，{数值}`** → `BTC 资金费率高于 0.05%，预测费率 0.0612%` |

条件提醒多带三个键（价格提醒上没有）：

| 键 | 值 |
| --- | --- |
| `rule` | 提醒的 `rule` 原样 |
| `detail` | 和推送正文同一句（不含备注） |
| `value` | 触发时观测到的数（十进制字符串，比例是比值）：费率 `{"rate","markPrice","nextFundingTime"}`；持仓量 `{"change","from","to","at"}`（`from`/`to` 是币数量，`at` 是 `L` 的时刻）；均线 `{"close","ma","openTime","closeTime"}`；大单 `{"exchange","product","side","price","notional","firstSeen"}`（`side` 是 `"bid"` / `"ask"`） |

模板占位符在价格提醒那一套（`{品种} {代号} {价格} {目标价} {条件} {时间} {备注}`）之外多一个 **`{数值}`**
（= `detail`）；`{条件}` 在条件提醒上是第 3 节表里的默认标题去掉品种名那一段（`资金费率高于 0.05%`）。

## 5. 老客户端兼容

老客户端（不认识 `condition` 这个 kind、不认识 `rule`）拉到一条条件提醒时：

- 解码：`kind` 认不得 → 当成 `drawing`；`rule` 不在它的模型里，但它**只替自己认识的字段说话**
  （`SyncStore.capture` 的 `ownedKeys`），`rule` 原样留在对象上，不会被删。
- 它下次记账时会把 `kind` 重新编码成 `"drawing"` 发上来。这条 op 如果原样落库，条件提醒就变成一条没有线、没有 `drawingID`
  的画线提醒——既会被 `invalid_alert` 整条拒收（堵住那台手机的队列），又会丢掉条件。所以服务端在合并之后、校验之前做一次
  **规范化**：**body 里有 `rule` 对象，`kind` 一律改回 `"condition"`**。老客户端的那条 op 照常 200，结果不变。
  代价只是老客户端每次动提醒时可能多发一条无害的 op。
- `condition` 键不放条件对象、固定 `"touch"`，也是为了老客户端：它把认不得的 `condition` 解成 `touch` 再编码回去，
  如果条件放在这个键里，老客户端一碰就把它覆盖掉了。
- 老客户端本机不会判这条提醒（没有线），界面上可能把它当成一条画线提醒列出来；用户升级后恢复正常。

服务端总是先于客户端部署，老服务端不会收到这些对象。

## 6. 品种状态（设置开关，不是提醒）

### 6.1 设置字段

| 字段 | 集合 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| **`notifyListingChanges`** | `settings` | bool | `false`（缺省即关） | 设置 › 通知里的「品种上新与下架」开关，跟着账号同步 |

客户端把它加进 `PrefsFieldPlan.table`（同步字段）并 `make sync-contract` 重新生成
`Backend/kanpan-api/contract/settings-fields.json`。服务端的白名单与值规则先行上线（`sync::SETTINGS_FIELDS`
里有它，值规则 `bool`），契约对账测试把它列为「服务端先行、客户端还没生成进契约」的名字，客户端生成之后自动对齐。

### 6.2 事件

服务端每 10 分钟对一次品种表（币安 U 本位 `exchangeInfo`，与 Coinbase 现货 USD 对的产品表），和上一轮存下来的目录比：

| 事件 `event` | 什么时候 | 推给谁 |
| --- | --- | --- |
| `listed` | 目录里出现一个新的、在交易的品种 | 开了开关的**所有人** |
| `delistScheduled` | 币安永续被排上下架时间（`deliveryDate` 从远期占位值变成一个真实日期） | 开了开关、且**自选里有它**的人 |
| `halted` | 在交易 → 暂停交易（币安 `status` 不再是 `TRADING` 且不是结算 / 关闭；Coinbase `status` 不是 `online`，或 `is_disabled` / `trading_disabled` 为真） | 同上 |
| `resumed` | 暂停之后恢复交易 | 同上 |
| `delisted` | 已下架（币安 `SETTLING` / `CLOSE` 或从表里消失；Coinbase 从表里消失或 `delisted`） | 同上 |

- 第一次对表（空目录）只建基线，不发任何事件。某一轮表拉失败或明显残缺（品种数不到上一轮的一半）就跳过这一轮，
  不把「没拉到」当成「全下架了」。
- **每个变化每人只推一次**：每条事件有一个 id，推过的记在这个人名下（`listing_notices`，RLS），重复跑、重启都不会再推。
- 只推**刚发生的**：事件发生后 1 小时内推不出去（服务停着）的不再补推，开关打开之前发生的也不补推。
- 自选按 `venue` + `symbol` 匹配（老自选没有 `venue` 的按币安算）。

### 6.3 推送与拉取

## 7. 校验（服务端拒收什么）

整条 op 400 `invalid_operation` / `invalid_alert` 的情形（合并之后按对象校验）：

- `kind = "condition"` 但没有 `rule` 对象，或 `market` 不是 `binance/usd_m`；
- 已知 `type` 的字段缺失或越界：`side` 不在枚举里、`rate` / `threshold` 不是规范的十进制字符串或越界、
  `interval` 不在第 2.3 节那 13 个里、`length` 不是 1…1000 的整数；
- `rule` 不是对象也不是 `null`、超过 1024 字节。
